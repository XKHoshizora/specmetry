## 5．新增 BLOCKER：B-P5-1，线程一致不证明残留 errno 已建立

**位置**：规范 `:2858`（§21.9“残留的 errno”），关联 H4 `:2735`、错误后健康对照 `:2853`～`:2854`、通过时的证据声明 `:2929`；处理记录 `:8198`。

计划断言：错误调用和健康调用用 `runtime.LockOSThread` 放到同一个 OS 线程，因而健康调用时 errno“确实仍是前一次的错误码”；健康结果err=0才说明残留被屏蔽。

**这个推论缺少关键前提。** LockOSThread保证 goroutine 与线程绑定、其他 goroutine 不在该线程执行；它不是对线程局部 errno 值的锁，也不保存或验证该值。计划没有规定并观察错误调用与健康调用之间全部相关操作，也没有直接记录健康调用所见的底层 errno。仅凭先前一次外部返回的 ECHILD/EINVAL，不能证明后一次使用的底层读数仍是非零残留。

固定 Go 源码恰好清楚地区分这两层：

- [Go 1.27.1 的 syscall6](https://github.com/golang/go/blob/862c888e612ac346c7c4d99c9392bdfd265f33b0/src/syscall/syscall_darwin.go#L326) 在 `syscalln` 返回后调用 `errno(r1, err)`；后者仅当 `int32(r1)==-1` 时保留底层错误，其余返回0。
- [arm64 的调用桩](https://github.com/golang/go/blob/862c888e612ac346c7c4d99c9392bdfd265f33b0/src/runtime/sys_darwin_arm64.s#L560) 在调用后另外读 TLS errno。这是**过滤前的读数**，不等于公开包装返回的err。
- [LockOSThread 的固定源码说明](https://github.com/golang/go/blob/862c888e612ac346c7c4d99c9392bdfd265f33b0/src/runtime/proc.go#L5658) 只给出线程绑定，不给出 errno 保留契约。Libsyscall 的 [cerror_nocancel](https://github.com/apple-oss-distributions/xnu/blob/ac9718fb1af618d5ce8678d0dc6e8a58f252216f/libsyscall/custom/errno.c#L63) 证明错误出口会设置errno，不证明任意后续用户态步骤不再改变它。

**静态的证据反例**：错误调用外部返回ECHILD，随后仍在同一个OS线程；若健康调用前的准备/包装路径把底层errno变为0，则健康调用返回成功且err=0。现有计划列出的线程、错误返回及健康返回断言全部可以成立，却没有在健康调用上施加任何非零残留负载，不能区分“确实屏蔽了非零残留”和“底层本来就是0”。即使只是变成别的错误码，“仍是前一次错误码”的具体断言也不能由线程一致推出。

这是对计划证明力的反例，**不是**本轮已运行出某个TLS读数，也不是断言现有Go或libSystem实际错误、健康waitid必然清零errno。固定源码支持现有Go的过滤设计；本项反对的是计划在没有所需观察时宣称已经验证了它。Apple归档 [intro(2)](https://developer.apple.com/library/archive/documentation/System/Conceptual/ManPages_iPhoneOS/man2/intro.2.html) 也要求在失败语境解释errno；它不能替代这一具体Go/libSystem链路的取样。

**实际影响**：H4是新增入口采用前需要回答的假设。一个未建立残留负载的健康对照可能得到confirmed，却被报告为已经检验“残留屏蔽”；这会夸大 Q-4(a) 的前置证据。不是一般未知或生产尚未实现的问题。

**最小修正**（仍只修计划，不在本轮实施）：

1. 撤回“同OS线程使errno确实仍为前一次错误”的保证，保留线程一致是必要前提的表述。
2. 定义如何取得同一实际调用链中**过滤前**的返回值与errno，并与外部err分别记录；证明健康调用所对应的底层非零errno负载确实建立。可以选择受控的读取/接缝，但必须说明它检验哪一层，不能复制一个新包装自测后冒充真实E2的同一调用。
3. 若只安全取得“错误返回之后健康恢复”的证据，就准确限定H4的覆盖，把“已验证非零残留屏蔽”撤回，列明其固定源码依据及未动态覆盖部分；不能从当前计划自动宣布该差额获准接受。
4. 负载没有建立或必要观察失败时，不得将“残留屏蔽”子检查写为confirmed；后续成功不消除该错误。采用哪一种最小方案须在授权前计划中写定，无须为此增加cgo、任意用户进程操作或新的产品保证。

### 6.2 N-105-2：健康对照的读取次数与覆盖需精化

**位置**：`:2849`、`:2872`～`:2873`；直接依据为当前 `prototype/wp25/p3_darwin_test.go:813`～`:849`。

P5.w.exit7保留“两次读取相同”；它复用的P-3路径在 `waitid2` 确实调用两次。EINTR健康对照又要求“R/N/M与w.exit7相同”，同时只许调用一次。如果“相同”包含完整R读取序列和W5的重复检验，不能同时满足；若仅指第一次的值，则应明确这个较窄的覆盖。

**定稿方式**：最小建议为故障第一次命中后只调用1次、不得重试；健康分支仍读2次，说明第二次是协议重复观察，不是错误重试。另一种合法安排是把单次健康对照明确限定为单读恢复检查，不宣称其证明W5，由独立P5.w.exit7的双读承担W5。无需改变W5或增加生产行为。

本项作为**非阻塞的计划精化、授权前必须定稿**：正常双读场景已经明确保留，不据这句简写推定整个W5保护被撤销，也不因此重开Review104其他规格。不得在实施后才任意选一种口径以解释测试结果。

### 6.3 N-105-3：分类、注入与预算的可执行边界

§21.9明确继承§19.12的优先级，所以不把它最后一行“清理失败”读成低优先级豁免。T失效/清理未知仍先于预期拒绝和原生预测比较；同一个场景遇到额外工具错误时不能只找到because就通过。

授权前至少要把下列边界写成可执行断言，不能只列类别名称：

| 状态 | 必须保持的终判/记录 |
|---|---|
| 工具报告/解析/关闭/身份观察错误；必要元数据未知；清理失败或最终未知 | invalid/非零；列出全部原因，后续成功和补救成功不恢复 |
| 可靠确认Rosetta、架构不符或缺少所需工具 | unsupported，不计confirmed；“读不到元数据”归T，不能当已确认环境不具备 |
| 布局invalid/refuted，预算不足，场景未执行，或注入未命中 | 对依赖的目标不能confirmed；按既有T与E规则区分，并保留前提场景自己的最终理由 |
| ECHILD/EINVAL原生候选返回值/errno与预测不同 | 在工具前提有效时按本节专门规定为refuted；不要被“观察器错误”泛称全部吞成T。与无关工具读取失败叠加时仍invalid |
| EINTR计划改写 | 先保存真实调用。真实调用已发生计划外错误时须持续记T，不得被改写的EINTR覆盖；只保存一份原始值而无人消费不足以证明失败关闭 |
| 计划改写被预期规则拒绝 | 内层invalid/非零，门禁仅在命中、唯一理由、内外清理/最终状态均满足时通过；其他理由、未命中或漏检均失败 |
