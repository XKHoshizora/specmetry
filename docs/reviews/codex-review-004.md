## BLOCKER

### B1：已有数据目录权限不安全时，仍然继续创建和写入数据库

位置：[datadir.go:72](../../internal/datadir/datadir.go#L72)、[perm_windows.go:36](../../internal/datadir/perm_windows.go#L36)、[store.go:87](../../internal/store/sqlite/store.go#L87)。

`Ensure` 对已存在的目录直接返回；Windows 文件保护完全依赖继承的 DACL，数据库打开路径没有检查实际权限。

**独立复现：** 放宽已有目录权限，授予 Everyone 读取权限后，`Open` 仍然成功；新建的数据库、WAL、SHM 都继承了该权限。`doctor` 能发现问题，但不能阻止此前的数据暴露。Unix 的已有目录、已有数据库也存在跳过权限处理的分支，尚未实际运行验证。

**影响：** 自定义目录、恢复的数据目录或被放宽权限的目录可能泄露本地数据，不满足既定私有权限契约。

**建议：** 写入前验证已有目录及文件的权限、所有者；不符合时，在产生写入前返回环境错误。补充“已有不安全目录”和“已有不安全数据库”的反例，断言拒绝时没有新增或改写数据文件。

### B2：`doctor` 会隐式改写数据库，并非真正只读

位置：[inspect.go:37](../../internal/store/sqlite/inspect.go#L37)。

检查连接使用 `mode=rw` 和 `query_only=1`。后者限制 SQL 修改，不能保证数据库文件不被 checkpoint 改写；SQLite 官方也明确说明这一边界。[SQLite 文档](https://www.sqlite.org/pragma.html#pragma_query_only)。

**独立复现：** 子进程写入后直接退出，留下未合并的 WAL。调用 `Inspect` 后，主数据库哈希改变，原有 24,752 字节 WAL 被清除，SHM 也消失。

**影响：** 诊断命令改变了待诊断现场，违反明确的只读承诺。现有测试只检查正常关闭后的数据库，遗漏了崩溃遗留 WAL。

**建议：** 使用真正只读的检查路径；无法在不恢复、不创建辅助文件的条件下检查时，应报告限制。不要直接对活跃 WAL 数据库使用 `immutable=1` 来规避写入。新增崩溃 WAL 场景，检查主库、WAL、SHM 的内容及目录项全部不变。

### B3：版本保护既晚于写入，也无法保护已打开的旧连接

位置：[store.go:94](../../internal/store/sqlite/store.go#L94)、[store.go:217](../../internal/store/sqlite/store.go#L217)、[store.go:239](../../internal/store/sqlite/store.go#L239)。

确认了两个漏洞：

- **拒绝前已经写入。** 连接初始化先执行 `journal_mode(WAL)`，再检查版本。使用本实现生成的 `VACUUM INTO` 备份恢复较新数据库后，旧程序虽返回退出码 6，却已改变数据库哈希，将文件从普通日志模式切换为 WAL。**`MVP-STO-02` 的“不做任何写入”失败。**
- **已打开的旧程序继续写入。** 旧连接打开后，另一连接完成 schema 升级并设置 `min_binary_version=9.9.9`；旧连接随后调用 `WriteTx`，仍成功提交并分配 `seq`。

**影响：** 拒绝打开仍改变新版本数据库；并发进程升级后，旧程序可能按不兼容的结构写入。

**建议：** 在任何可变连接初始化之前进行只读版本检查；同时在每个写事务取得写锁后、调用写入回调之前重新验证兼容性。补充上述两个反例，断言拒绝时文件、事实和 `seq` 均不改变，写入回调没有执行。

### B4：只追加触发器可被 `INSERT OR REPLACE` 绕过

位置：[appendonly.go:20](../../internal/store/sqlite/appendonly.go#L20)、[store.go:214](../../internal/store/sqlite/store.go#L214)。

当前仅阻止 UPDATE、DELETE，没有启用递归触发器。

**独立复现：** 对带有 `AppendOnlyTriggers` 的事实表执行同主键的 `INSERT OR REPLACE`，原事实被成功覆盖，无需维护模式。SQLite 的 REPLACE 删除行为只有启用递归触发器才会触发删除触发器。[SQLite 文档](https://www.sqlite.org/lang_conflict.html)。

**影响：** 当前辅助函数不能兑现只追加约束，后续事实写入可能无意覆盖历史。

**建议：** 每个连接显式启用适当的触发器配置，并禁止事实写入使用 REPLACE。新增主键冲突和 UNIQUE 冲突反例，断言原记录保持不变。

## NON-BLOCKER

### N1：墓碑辅助实现存在崩溃恢复和外键删除顺序缺陷

位置：[tombstone.go:75](../../internal/store/sqlite/tombstone.go#L75)、[tombstone.go:61](../../internal/store/sqlite/tombstone.go#L61)。

两个问题均已通过合成表复现：

- 删除提交后、VACUUM 前中断，再次打开时因 `deleted == 0` 跳过整理，数据库文件仍含已删除数据的 canary。使用驱动默认配置也能复现。
- 表按名称排序删除，父表先于子表时发生外键错误，导致数据库打开失败。

**建议：** 区分“逻辑删除完成”和“文件清理完成”，支持恢复未完成的清理；明确外键安全的删除顺序或延迟约束策略。

M0 约定只提供墓碑挂载点，因此不据此要求提前实现 M2 的完整删除功能；但必须在 M2 删除验收前解决，M1 建表时应同时考虑外键关系。

### N2：非法墓碑测试存在假阳性

位置：[store_test.go:610](../../internal/store/sqlite/store_test.go#L610)。

测试先创建 schema v2，然后用仅支持 v1 的默认配置重新打开。实际错误来自版本保护，尚未执行非法墓碑校验。

**建议：** 使用相同迁移集合重新打开，验证错误明确来自非法 `project_id`，同时断言数据库不变。

### N3：`doctor` 忽略最低二进制版本

位置：[doctor.go:119](../../internal/cli/doctor.go#L119)。

`Inspect` 返回 `MinBinaryVersion`，但诊断只比较 schema 版本。schema 相同而最低程序版本过高时，会报告数据库正常，实际打开却被拒绝。

**建议：** 在只读诊断中复用兼容性判断，补充这一组合的测试。

### N4：公开文档包含本机用户名和绝对路径

例如：[codex-review-003.md:7](../../docs/reviews/codex-review-003.md#L7)。

这会公开本机用户名、目录结构，且链接在其他机器上不可用。未发现由这些路径直接暴露凭据或客户内容。

**建议：** 发布文档时采用仓库相对链接；已有外部审查原文的处理应遵守只读约定。
