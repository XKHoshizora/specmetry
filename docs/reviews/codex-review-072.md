## 四、BLOCKER：B3 的残余

### B3-R1：放弃复制 goroutine 后，没有保证当前错误呈现及后续调用的输出安全

**位置**：[§8.5 S6，第 431～450 行](../wp2.5-check-runner.md#L431)、[§9.1 管道路径，第 464～471 行](../wp2.5-check-runner.md#L464)、[D20，第 830 行](../wp2.5-check-runner.md#L830)。

草案已经承认关闭管道读端不能中断目的端 Write，但把后果停留在“它留到 Specmetry 进程结束；流程继续”，并断言二个有限预算没有无界等待。对于 `cli.Execute` 的进程内调用，返回并不等于宿主进程退出：旧 goroutine 可以一直存活、保留缓冲区和 Writer，之后再写出旧输出；重复调用还可以不断累积。若随后的错误/警告又写向该阻塞 Writer，控制流程仍可能卡住。此问题不能靠关闭上游读端解决。

**本轮有界机制反例（Windows/Go 1.27.1）**：

1. 启动仓库外合成子进程，将自建 `os.Pipe` 写端以 `*os.File` 交给它；父进程立即关自己的写端。子进程打印 `late-check-output`，以 3 退出。
2. `Cmd.Wait` 在约 13 ms 返回，证明新的 E-main 设计解决了原循环依赖。复制此时阻塞在一个线程安全的目的端 Writer 的第一次 Write。
3. 100 ms 后关闭读端，复制仍没有结束。按照 F2 的“流程继续”模拟返回后，另一调用向同一 Writer 写出完整 error.v1。
4. 解除旧 Write 的闸门，最终字节为 **完整 JSON，随后又出现旧检查输出**。不是一份完整机器文档。测试最后等待复制结束，没有遗留 goroutine/子进程。

另有健康 Writer 正对照：主进程以 0 退出、排空完成、输出完整。以上是对草案协议的机制复验，**不是运行尚不存在的 Check Runner/Execute 实现**。

[Go os/exec 文档](https://pkg.go.dev/os/exec#Cmd) 也明确，目的端阻塞 Write 不是 WaitDelay 能普遍中断的对象；换成自行复制不会为任意 io.Writer 增加取消能力。

**影响**：一次 F2 返回后，不能默认输出对象和进程内调用环境已经恢复可用；正常 JSON 后续调用可能被旧输出污染。草案对“有界失败/exit 6”的表述也缺少错误输出目标可用的前提。不能把“控制器停止等复制”说成“复制已停止、资源已回收或后续可安全复用”。

**最小修正**：

- 明确选择管道目的端的支持契约：例如要求可取消/可关闭并能确认 Write 结束的目的端；不满足时在启动前拒绝，或把尚无可用方案准确列为 T1/T6 未解决门槛。普通 io.Writer 不能自动得到这一保证。
- 如仍提议放弃复制，完整披露迟到写入、内存/句柄生存期、重复 Execute 和 Writer 复用限制，以及后续错误如何避免再次阻塞；任何公共使用保证的缩小都须在 D20 中明确，不能由审查代为批准。
- 区分“复制完成且成功”和“复制因读/写错误提前结束”：E-drain 要求 EOF 与全部写完，不能把任意 copy goroutine 返回都算 E-drain。提前转发错误也要有受控出口，不能映射成用户命令非零。
- 明确 F1、启动失败、取消等提前出口如何结束/保留自己的复制任务和句柄。可以保留未解决项，但应撤去目前尚不成立的完整闭环断言，不要求本准备 PR 实现生产代码。

### B3-R2：Linux 的新收养归属推理不成立，Unix 数字 PGID 保护也未覆盖首次终止

**位置**：[§8.2，第 365～370 行](../wp2.5-check-runner.md#L365)；[E-main/S3/S5，第 403、423～428 行](../wp2.5-check-runner.md#L403)。

**a. 基线之外的新收养者不一定来自检查树。**

第 366 行允许设置之前已有子进程，只记录并排除它们的 PID/启动时间；第 367 行随后推导“这段时间里新收养的子进程都来自检查”。既存子进程还可能在基线之后产生后代，这些后代不在基线中，但仍可能被 Specmetry 收养。

**本轮独立反例（WSL Ubuntu，普通 UID 1000）**：

1. 先启动一个等待输入闸门的正常辅助进程，记录它为基线；之后才设置审查夹具为 subreaper。
2. 放行该既存辅助进程，让它启动新的、独立会话的短时 sleep，然后退出。
3. sleep 的 PPid 变成审查夹具，且不在原基线中；整个实验 **没有启动任何检查**。
4. 通过事先绑定的 pidfd 终止并 wait 回收自己的 sleep，辅助进程也已回收。

输出确认 `adopted_by_reviewer=True, not_in_baseline=True, no_check_started=True`。因此问题不在“pidfd 能否绑定”：它会准确绑定这个**归属被错误推断**的进程。父进程与启动时间复核也不能证明来自检查。[Linux subreaper](https://man7.org/linux/man-pages/man2/PR_SET_CHILD_SUBREAPER.2const.html) 对祖先子树提供收养机制，不提供按业务用途区分后代的能力。

**最小修正**：最简单的保守方向是要求可排他控制的检查区间，基线非空/归属不明即不启动，且区间内不允许其他子进程来源；或者另行设计能保留既存根及其未来后代归属的机制。不能仅排除基线 PID 后把其余收养者都清扫。把具体未解决部分留作 T2 门槛是可以的，先删除错误推理。无需为本准备 PR 开发新服务或完整清扫器。

**b. “组内还有成员则 ID 不复用”没有覆盖组已经消失的分支。**

E-main 明确定义为 Cmd.Wait 返回，正常无后代命令的组长此时可能已被回收，组已消失；S3 却仍要求无论何种原因都 `kill(-pgid, SIGKILL)`。第 426 行的条件命题不能证明 S3 此时仍指向原组。

本轮仅用自己的 `/bin/true` 新会话正对照确认：Wait 后旧组已不存在；**没有进行信号误投或强制 PID 复用实验**。剩余风险是严格的机制推导：若调度暂停期间数字被复用于另一个同用户进程组，按数字发信号会指向新组。pidfd 绑定某个被收养进程，也不自动绑定后续 `kill(-pgid)` 的组对象。参见 [kill 的负数参数语义](https://man7.org/linux/man-pages/man2/kill.2.html)、[wait 的回收语义](https://man7.org/linux/man-pages/man2/waitpid.2.html)、[pidfd_open 的身份与回收前提](https://man7.org/linux/man-pages/man2/pidfd_open.2.html)。

**最小修正**：从第一次终止到最后一轮检查明确组身份/生存期的保护规则；不能先向一个可能失效的数字发终止信号，再检查归属。可研究保持可证明的组身份直到终止完成，或改用已绑定且已证明归属的进程对象；无法确认应进入受控失败。具体机制可以保持待原型验证，但不能继续用“仍有成员时不复用”覆盖已经为空的时间窗。

**影响及边界**：a 有实际有界复验，b 为明确的条件逻辑证明；没有声称已在生产 Runner 中误杀。两者涉及本工具清理其他正常进程的能力，**不在 WP2.3 方案 B 的临时命名空间排除范围内**，不能拿该批准作豁免。D7 的进程树覆盖范围也不是误杀无关进程的批准。

### B3-R3：推荐的取消与 F2 组合没有唯一的事实/退出结果

**位置**：[§6.2，第 242 行](../wp2.5-check-runner.md#L242)、[§8.5 F1/F2，第 440～450 行](../wp2.5-check-runner.md#L440)、[D8/D19/D20，第 824、829～830 行](../wp2.5-check-runner.md#L824)。

## 六、NON-BLOCKER 与开工/实现门槛的拆分

### N1：T1～T6 的“实现并测试”应区分隔离原型和生产验收
