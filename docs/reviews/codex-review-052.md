## 二、BLOCKER

### B1-R：严格 log 仍可能借 commit-graph 接受已经消失的排除对象

**位置：**[WP2.3 规范](../wp2.3-git-reader.md) 351～370、736 行；[MVP-EV-16](../acceptance-criteria.md) 184 行。

新方案正确去掉全局 `--ignore-missing`，每个 ref 单独读取，stdin 使用正向完整 ID 和 `^<SHA>`。在普通夹具中，不存在的正向 ID、排除 ID 都返回 128；固定正向提交在准备后删除时，带完整正文格式的 log 也返回 128。这些原始修订成立。

但规范进一步承诺“排除项在分类之后消失，严格 log 必然非零，整次不写入”。这不适用于已有 commit-graph 的仓库。

**独立反例：**Git for Windows `2.56.0.windows.2`，隔离仓库建立可读提交 `A → B → C`，写出 `commit-graph --reachable`，然后删除 A 的松散提交对象。之后：

| 操作 | 实际结果 |
|---|---|
| `cat-file --batch-check` 查询 A | exit 0，`A missing` |
| 裸 ID 的 `cat-file -e A` | exit 1 |
| 使用规范的完整 `%H / %ct / trailers / %B` 格式，stdin 为 `C` 和 `^A` 的严格 log | **exit 0，正常返回 C、B，stderr 为空** |
| 同一调用额外固定 `-c core.commitGraph=false` | **exit 128，bad object A** |

旧排除对象已消失，但遍历可以使用 commit-graph 中的关系，而不重新读取其提交对象。这个反例不依赖 `--ignore-missing`，也没有依赖损坏的输出或异常 stderr。

**影响：**按当前 §5.5 编排，成功的 log 会允许扫描进入游标发布事务，违反本轮明确要求的“排除项准备后消失必须失败、不推进游标”。本轮没有实现扫描器或实际推进数据库游标；这一后果由规范的读后发布规则直接得出。不能仅凭此例宣称已实际遗漏某条提交：本例证明的是缺失检查和失败／拒写保证没有成立。

**最小修正：**

- 为严格遍历规定不会用 commit-graph 掩盖必需排除对象缺失的机制。每次调用固定 `core.commitGraph=false` 是本轮对该反例有效的最小候选，不应依赖用户配置；仍需覆盖相关对象读取与错误边界。
- 增加“先存在并形成计划、写出 commit-graph、再删除排除对象”的反例，而不只测试一个从未存在的随机 SHA。
- 实现验收须断言所有提交／关联／seq／游标不变，并覆盖已经获得部分日志结果后失败的整次回滚。

Review 050 B1 的原始普通假成功路径已修正；**B1 所需的完整拒绝保证尚不能关闭。**

### B2-R：batch missing + 裸 ID exit 1 不能证明对象可靠不存在

**位置：**[WP2.3 规范](../wp2.3-git-reader.md) 327～337、362～371、403～410、541～552 行；§5.6 的退出码例外；[architecture §6.7](../architecture.md)。

不再使用 `^{commit}` 修复了原来的退出码错误。新组合也能区分作者测试的部分松散对象损坏。但它仍把“协议没找到对象”直接提升为“已可靠确认不是读取失败”，并不成立。

**独立反例：**隔离仓库中，旧提交 A 已正常打包；打包后另建一个无父提交的新根 C，C 的提交对象仍为松散对象。先验证 A、C 都可读，再只破坏装有 A 的 `.idx`，保留 `.pack`。结果：

| 操作 | 实际结果 |
|---|---|
| 破坏前，一次 batch 查询 A、C | 两条 `commit <size>`，exit 0 |
| 破坏后，一次 batch 查询 A、C | **`A missing`、`C commit <size>`，exit 0** |
| 破坏后，裸 ID `cat-file -e A` | **exit 1** |
| 从 C 执行完整格式的严格 log，不把“已缺失”的 A 放入排除集合 | **exit 0，正常返回 C** |

前三个故障调用的 stderr 中存在 pack 索引过小的错误，但新分类器明确只看 stdout 协议和退出码，不看它，因此恰好命中“可靠地不存在”。新根 C 不需要读取 A，最后一次严格 log 不会自动补上该缺失的错误判定。

这与 [Git 2.56 cat-file 的 `-e` 实现](https://github.com/git/git/blob/v2.56.0/builtin/cat-file.c)及 [ODB 存在性接口](https://github.com/git/git/blob/v2.56.0/odb.c)的边界相符：存在性结果不是向调用者提供完整 errno 分类的三态证明。不能从某几个损坏样例推导所有权限、包索引、I/O 状态都已区分。

**影响：**按规范会把读取故障当成正常的旧 tip 缺失／历史改写，允许正常发布游标和新关联，违反“旧 tip 不可读或无法确认则 exit 6、不写入”。本例没有证明数据丢失；它已证明核心错误边界违约。

**“只会多读”论证的限度：**省略一个排除项在集合上不会缩小可达范围，这部分成立；但这不证明对象确实不存在，也不满足遇到无法确认状态必须拒绝的契约。如果该旧 tip 不在新 T 的祖先中，后续读取 T 可以成功，正如本例。额外读取还可能带来首次入库机会，不能用已接受的正常重扫限制自动豁免读取故障。

**最小修正：**

- 撤回“这两个结果足以证明可靠缺失”的定义，补上对象存储／索引损坏和不可读时的保守分类；不能可靠确认的状态返回 exit 6。
- 对本例，至少不能把 Git 已报告索引异常的运行归为可靠缺失。可以考虑把异常诊断视为不确定而拒绝，且不回显原始 stderr；这与按本地化错误文字匹配不同。不过，这一措施本身尚不是所有无提示权限／I/O 错误都已区分的证明。
- 在冻结前说明可靠缺失的判据与适用条件；补真缺失、坏 `.idx`、坏包数据、不可读对象目录及并发变化的正反例。不能只把作者列为“未验证”的权限／I/O 留给测试，同时把完整三态保证写成已经成立。
- 保留真正缺失旧 tip 的重扫要求，不得以一个未经批准的“所有 missing 永久拒绝”悄悄替换它。

PD-26 阻断按需抓取，不提供存储完整性或缺失分类证明。本轮未动态模拟权限／I/O；**坏 `.idx` 的独立反例已足以使 B2 保持未关闭。**

### B3-R：私有 Git 目录尚不能保证正确的 clean 和原仓库不变

**位置：**[WP2.3 规范 §4.3](../wp2.3-git-reader.md) 197～242 行，特别是 199、206、213、216、232～239 行；[data-model §1](../data-model.md) 16 行；[MVP-EV-18](../acceptance-criteria.md) 186 行。

白名单配置、不让超级项目的 status 自动递归、对子模块分别执行受控读取，这些方向可以阻断此前直接继承 `filter.*` 的路径。但两个核心保证仍不成立。

#### B3-R1：取消过滤器可把 dirty 变成 clean

“只有 clean → dirty 的保守差异”不是 Git 过滤器的单调性质。

**独立双向夹具：**安全的合成 clean 过滤器只执行 `sed s/raw/canonical/g`，没有网络或仓库写入。工作区文件内容为 `raw`，属性指定该过滤器；改变 stat 以迫使重新比较。私有目录使用索引副本、alternates 和无过滤器的白名单配置。

| 建库及配置时序 | 定义中的正常 status | 私有目录方案 |
|---|---|---|
| 提交时未配置过滤器，索引保存 raw；提交后才配置转换器，工作区仍为 raw | **` M f`，dirty**：转换后为 canonical，与索引不同 | **空输出，clean**：未转换的 raw 与索引相同 |
| 提交前已配置转换器，索引保存 canonical；工作区为 raw | 空输出，clean | ` M f`，dirty |

两方向均 exit 0；两组的原索引与配置哈希均未变化。第一行就是新方案遗漏的反方向，且不需要恶意过滤器、进程失败或用户同时改文件。

**影响：**新读取会把按已冻结语义实际 dirty 的上下文记为 clean，进而可能错误地让后续执行符合代码上下文条件。本轮没有把它扩大成 WP2.1 推导算法缺陷，也没有声称已经产生 ready；问题在新增事实读取层。

**最小修正：**不能把原样内容相同当成已证明与 Git 过滤后的语义相同。对无法在不执行程序的前提下可靠比较的文件／仓库，必须采取有依据的 dirty／unknown／环境失败边界，或给出等价且不执行过滤器的比较方案；不能报告 false clean。新增上述双向反例，并同步 data-model、验收和 §63 的错误单调性表述。

若选择扩大保守拒绝或 dirty 的适用范围，用户可见的限制应另行明确确认，不能称作 D1 加一个子模块参数的自然同步，见 PRODUCT DECISION。

#### B3-R2：alternates 不提供只读保护，稀疏索引展开会修改原对象时间

**独立夹具的有效前提：**原仓库启用 cone-mode sparse index；`ls-files --sparse --stage` 明确包含 `040000 ... outside/`。私有目录复制该索引，白名单含原来的 sparse 配置，alternates 指向原对象目录。测试始终设置 `GIT_OPTIONAL_LOCKS=0`、禁用 Fetch 的受控变量等。

分开对每个命令记录原对象的哈希和修改时间：

| 私有目录的内容／操作 | 原对象变化 |
|---|---|
| 按草案清单未复制 `info/sparse-checkout`；执行私有 status | 3 个原树对象的 **mtime 改变，内容哈希相同** |
| 同一私有目录执行草案 `ls-files --stage -z` | 3 个原树对象的 **mtime 再次改变** |
| 补复制 `info/sparse-checkout`；执行私有 status | 该次未观察到原对象变化 |
| 补复制模式文件后，仍执行不带 `--sparse` 的 ls-files | 3 个原树对象的 **mtime 改变** |
| 同一对照改为 `ls-files --stage --sparse -z` | 保留稀疏目录条目，该次未观察到原对象 mtime 变化 |

Git 的 [稀疏索引展开代码](https://github.com/git/git/blob/v2.56.0/sparse-index.c)会重建 cache tree；私有主对象库经 alternates 引用的对象仍可能被 freshen。`GIT_OPTIONAL_LOCKS=0` 不是原对象目录的操作系统只读边界。这个问题也与既有 [architecture §6.1.2](../architecture.md) 已记录的“不带 --sparse 展开索引会改写对象时间”直接对应。

**影响：**“索引和配置是副本，因此不写用户仓库”的推论不成立。这里没有观察到源码内容改变，但已违反原对象文件不被改写的既有读取保证；它不是待产品批准后就自动无害的普通保守差异。

**最小修正：**明确阻止所有会借 alternates 写回／freshen 原对象的展开路径。正确复制 sparse 模式、保留稀疏列举是本轮有效的局部候选；仍需检查 status、子模块枚举及失败路径。也可在未证明安全的布局上先保守拒绝，或采用真实只读的对象访问机制；不应直接要求大范围重构。将对象内容与时间均不变加入 EV-18，不能只检查索引／配置。

**B3 尚未关闭。** 普通索引对照没有观察到原索引／配置变化，不足以覆盖上述稀疏路径。将稀疏索引写为“实现时再验证”不能消除已经可复现的当前方案缺陷。

## 四、NON-BLOCKER 与实现测试边界

### N1：标准 gitfile 子模块及 unborn HEAD 的构造步骤需细化

**位置：**WP2.3 规范 198、216～219、268～270 行。

本轮创建正常的本地子模块并执行 absorbgitdirs，不使用 clone 或远端。其 `.git` 为指向 `../.git/modules/sub` 的 gitfile：

- 在子模块目录正常 `rev-parse --verify HEAD`：exit 0；
- 按草案直接传 `--git-dir=<sub/.git>`，从超级项目执行：本机 Git 返回 exit 128；
- 传入解析后的实际 Git 目录：exit 0，与正常调用得到相同 HEAD。

因此不能把“`.git` 存在”与“`.git` 是可直接使用的目录”混同。应使用受控 Git 元数据解析实际 GitDir／CommonDir，不能靠字符串假设。对于尚无提交的私有仓库，不写 HEAD 也会使 status 报“not a git repository”；应明确合法 unborn HEAD 表示及其允许结果。

这些是可局部修正的读取步骤，当前失败会保守拒绝，没有由它们观察到错误放行，故不单列新的核心 BLOCKER。split index、worktreeConfig、多层子模块、路径编码等可以保留为明确的实现验收项；但已确认的 gitfile／unborn 构造问题应先修正文案，不能当成完全未知。

### N2：临时副本生命周期与错误标签还需明确

**位置：**WP2.3 规范 197～234、573～575 行。

私有权限、位置、复制范围、大小与取消行为可以在实现时确定，但规范应约束：成功／失败／取消均执行清理；清理失败如何报告、崩溃遗留如何识别、不能把副本纳入项目事实、日志或普通备份。临时索引和 Git 配置元数据不应成为任意源码／完整配置落盘的许可；继续遵守 architecture §10，不自行批准秘密值或 C0 内容保留。

另外，新增命令的全局参数含 `--git-dir=<路径>`；既有 `runWith`／`runObjectsTo` 等会用 `args[0]` 构造失败标签。实现新调用时应保持固定的子命令标签，不能把带路径的参数当作可回显的命令名。当前 PR 没有该实现，本轮不把一个尚未出现的参数接线错误当作已复现泄露。

### N3：D2 重用路径的验收措辞应保留祖先判断

§5.2 已正确按旧 tip 的存在性和祖先关系决定增量／改写。§5.1 也说明重用路径后旧 tip“通常”不是新 HEAD 的祖先。但 WT-06、L20 等简写为“沿用游标、按改写重扫”，容易被实现为无条件全量重扫。

最小同步：同一路径沿用身份后，仍按统一 §5.2 判断；非祖先或可靠缺失才走相应重扫，旧 tip 仍为祖先时正常增量。这不推翻 D2，也不需要新产品决定。

Review 050 N2 的空扫描游标事务／EV-15 前提及 N3 的 UTC 毫秒已合理落实，不再重开。
