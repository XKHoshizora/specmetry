## 三、BLOCKER

### B1：把 Clean 概括为“从不误报 clean”，遗漏方案 B 已批准的局部边界

**位置**：[草案 §2，第 57 行](../wp2.5-check-runner.md#L57)；关联 §7.1、§7.4。

依据表把 WP2.3 §4.3/§14.3 一起概括为“从不误报 clean”。但现行 [WP2.3 §14.3，第 1146 行](../wp2.3-git-reader.md#L1146) 及 [决定 §71](../review-resolution.md#71b1-方案-b-的批准与实施范围) 明确：不合作同用户进程干预 Git 私有临时命名空间（包括普通误操作）被排除，Clean 可读替代输入，不能排除 false-clean。

**逻辑证据与影响**：同一已批准边界在草案中被重新表述成无条件保证；仅写“按方案 B”不足以抵消紧邻的绝对断言。后续检查执行、合格证据及用户说明若按这个概括实施，会对 Clean 提供超出既有批准范围的保证。本项不重新开启 WP2.3，也不把该局部边界扩展为交付证据的一般豁免。

**最小修正**：将依据表改为“在既定适用前提下保守判定；仍受 §14.3/§71 的局部边界约束”，明确保留 false-clean 的限定条件。§7 的上下文与 qualifying 仍使用现有返回值和冻结公式，不声称新 Runner 消除了该窗口，也不新增风险接受。

### B2：D9 将批次汇总与逐条执行能否影响交付混为一谈

**位置**：[草案 §11.2，第 468 行](../wp2.5-check-runner.md#L468)，D9 第 607 行；与 §12 第 504～507 行冲突。

草案建议批次 `is_target_snapshot` 仅在每条执行都从 S 开始时为 true，随后说“只有这时，这些执行中的合格执行才能影响交付状态”。冻结的 [data-model §4.11.1](../data-model.md#4111-证据等级)、[§6.1](../data-model.md#61-符号) 却逐条选择满足快照、当前修订和配置的合格执行，没有批次全真条件。已验收的 `derive/criterion.go` 第 58～65 行也是逐条筛选，CheckRun 模型不依赖该批次输出字段。

**合法反例**：目标 S=A；AC-001-1 在 A 上开始和结束，干净、通过。两次检查之间用户切换到 B；AC-001-2 在 B 上开始和结束。按推荐汇总，批次标记为 false；第一条仍属于 AC-001-1 的 `runs(A)`，应参与 V，第二条不属于目标快照。这不要求第一条运行期间发生变化，也不涉及非法历史。

**影响**：按该句过滤会丢弃合法目标证据；若仅用于解释输出，也会向调用方错误宣称第一条没有交付效力。它不是普通展示文案选择。

**最小修正**：可以继续把“所有条目均在 S 上开始”作为待确认的批次汇总选项，但明确该字段不进入逐条 `runs(S)`、V 或交付推导。Schema 描述的既有歧义应一并澄清；增加混合 head_start 的语义用例。不改变已冻结的推导规则，无需新增推导字段或重做 WP2.1/WP2.2。

### B3：主进程结束、管道结束和后代结束尚未形成可执行的失败闭环

**位置**：[草案 §4.2 第 4～5 步，第 112～113 行](../wp2.5-check-runner.md#L112)、[§8.1～8.3，第 330～358 行](../wp2.5-check-runner.md#L330)、[§9.1，第 374～376 行](../wp2.5-check-runner.md#L374)。

草案已正确披露 setsid、SIGKILL、Job 外启动和 macOS 未验证，D7 也正确保持待决。但它进一步断言管道分支在主进程退出后清树，因而 `Wait` 不会被后台拖住；这还缺关键顺序和失败规则。

**本轮精确机制复验**：Go 1.27.1，WSL Ubuntu，`sh -c 'sleep 4 & printf ...'`，独立进程组，Stdout 接内存 Writer。300 ms 后主进程已经被回收（`/proc/<pid>` 已消失），`Cmd.Wait` 仍没有返回；定向终止该测试进程组后，Wait 才返回。测试全程有界，并回收了自己的测试进程。这证明“主进程已退出”与“Cmd.Wait 已返回”不是同一事件。

Go 明确规定，非 `*os.File` 输出会创建复制管道，Wait 还等待复制完成；即使设置 WaitDelay，底层 Writer 的阻塞 Write 也可能继续阻塞。见 [os/exec 的 Stdout、Wait、WaitDelay](https://pkg.go.dev/os/exec)。因此不能先以 Cmd.Wait 返回作为主进程退出信号，再执行清树；也不能把输出复制故障当作用户命令非零退出。

此外，现有 [cli/root.go 第 97～98 行](../../internal/cli/root.go#L97) 对正常 CLI 输出也包了 `termtext.Writer`。不显式取得预期的底层输出对象，所谓“非 OS 文件只在进程内测试中出现”并不成立；直接把 Cobra Writer 交给子进程既会走管道，也会转义本应原样转发的检查输出。

**另一个必须写清的失败分支**：kill/TerminateJobObject 调用成功、PID 列表暂时为空或主进程结束，均不能直接当作整个预期树已结束。Windows 终止请求与进程真正结束有区别；参见 [TerminateJobObject](https://learn.microsoft.com/en-us/windows/win32/api/jobapi2/nf-jobapi2-terminatejobobject)、[TerminateProcess 的异步语义](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-terminateprocess)。当前计时只到主进程退出，没有定义清扫、等待及管道收尾的期限，也没有定义无法确认结束时的返回和记录资格。

**影响**：实施者若按常见的 Cmd.Wait 顺序实现，会卡在清树前；若超时/取消后猜测结束再采集上下文，可能在仍有可修改 worktree 的后代时发布合格记录。这里尚无生产实现，裁定是准备机制说明不足，不是声称已存在上线漏洞。

**最小修正**：

1. 区分主进程退出通知、树的终止/回收证明、输出排空和最终 Wait；明确哪一步不依赖管道 EOF。取得检查输出的底层句柄只能用于检查转发，Specmetry 自身文本仍走安全 Writer，JSON stdout 仍隔离。
2. 给清扫/等待/排空定义有界策略与失败结果；不能确认预期后代已结束时，禁止直接走正常合格记录路径。说明已经执行、已经记录及尚未记录的区别，保留之前已提交的事实，不重跑检查。
3. Linux subreaper 的归属识别、PID 复用防护、重复收养/回收、与 `os/exec.Wait` 和自身 Git 消费者的协调仍是技术门槛。不得以一次 `/proc` 扫描或“开始后出现”作为完整归属证明。
4. D7 若要对某些后代不作结束保证，明确这如何限制观测证据和用户可见承诺，交负责人决定；不能一边承认脱离仍存活，一边无条件声称 §7.1 已等到全部后代结束。也可先准确记为尚未解决的开工门槛，不要求本准备 PR 完成全部平台机制。

### B4：EV-04 的方案 A 仍误承诺“出现命令不存在就不会 pass”

**位置**：[草案 §6.3 第 251 行](../wp2.5-check-runner.md#L251)、[§14 第 544 行](../wp2.5-check-runner.md#L544)。

草案已经正确删除了 127/1/9009 和 stderr 的反向根因推断，但改写草案又说“检查中的命令不存在 → 结果不是 pass，为 fail/nonzero_exit”。合法的 shell 命令串可以消化这个失败，最终退出 0。

**本轮独立复验**，均为合成命令，不执行项目检查：

| 平台/命令 | 实际解释器退出状态 |
|---|---|
| WSL `/bin/sh -c 'review071_no_such_tool'` | 127 |
| WSL `/bin/sh -c 'exit 127'` | 127 |
| WSL `/bin/sh -c 'review071_no_such_tool; :'` | **0**，虽有未找到消息 |
| WSL `/bin/sh -c 'false \| true'`（管道） | **0** |
| Windows `cmd /d /s /c "review071_no_such_tool & exit /b 0"` | **0**，虽有未找到消息 |

这些命令串均可以作为当前 checkSpec 的 command，不违反长度、类型或密钥规则。按草案 §6.2，它们在上下文正常时应当为 pass；按 §14 的新断言却必须 fail，内部矛盾仍在。这里的 exit_code 是解释器进程最终状态，不能概括成每个内层程序的退出码。

**最小修正**：方案 A 明确为“按解释器最终状态分类，不保证发现内层命令查找失败或被命令串掩盖的失败”。EV-04 的非零反例限定为最终确实非零的独立命令，并增加“缺失命令后成功/失败管道被最后一项覆盖”对照，准确展示能力边界。此取舍仍在 D5 下等待负责人批准；不要求实现 shell 解析器，也不以读取输出推断原因。它沿用 [Review 041 对方案 A 的要求](codex-review-041.md)：按最终状态精确分类，而非仅断言“不是 pass”。

## 四、NON-BLOCKER 与规范收口建议

### N1：解释器、启动文件与终端事实的措辞需要精确

- 第 153 行“`/bin/sh` 是 POSIX 规定的位置”不正确。POSIX 的 [sh Application Usage](https://pubs.opengroup.org/onlinepubs/9699919799/utilities/sh.html) 明确不能假定 `/bin/sh` 或 `/usr/bin/sh`。可以把 `/bin/sh` 规定为本产品 Linux/macOS 支持策略，不应归因于 POSIX。Windows/Linux 的本轮结果也不能证明 macOS 的实际二进制与行为。
- 第 193 行“不读启动文件；BASH_ENV、ENV 照常生效”需拆开。非交互 bash 会读取 BASH_ENV 指向的文件；以 sh 名称启动的非交互 bash 与交互 POSIX 模式的 ENV 行为不同。保留继承环境的边界，但不能承诺统一不读启动文件。参见 [GNU Bash Startup Files](https://www.gnu.org/software/bash/manual/html_node/Bash-Startup-Files)。
- `exec.LookPath` 对当前目录候选的 ErrDot 防护，不等于自定义查找器已经忽略所有相对 PATH 项；后者仍须显式实施并测试。解析实际路径后排除当前及本项目已登记 worktree 的方向合理。
- E8 关于 `/dev/tty` 一律 SIGTTIN 停止仍只是未验证概括；无控制终端、信号被忽略/阻塞或孤儿进程组等条件要分开。空设备 stdin 的决定本身合理，不需要为此接受新风险。

这些是可定向修正的文案和验证门槛，不是要求扩展 shell 支持范围。

### N2：“不读取任何环境变量的值”与继承、查找及 PATH 改写不一致

第 383 行应区分：读取环境以传递给子进程、查找解释器及构造 PATH；与采集到执行记录、错误、日志或输出。前者是正常实现需要，后者受禁止。W2 的 PATH 前置已如实列为待批准行为，不能借此记录原环境值。

同样，已经确认的检查配置按既有基准契约保存，与运行时不在 `check_runs`、日志、错误中捕获原始命令不是一回事。第 388～392 行总体方向正确。原样输出中出现 canary 是有意转发，不得误判为数据库/日志泄漏；数据库、WAL、备份及临时区仍须分别查验。

### N3：部分执行、错误详情和输出收尾还需精确化

- `error.v1.details` 只有 `pointer` 和必填 `problem`，最多 200 项；D10 可以用受控 problem 文本描述 AC/evidence_id，不能直接增加未定义字段，或给任意长度批次生成超过上限的详情。完整列表如需新结构再走契约评估；本轮不要求新增字段。
- 错误分类保留 internal/1 与 environment/6 的区别：单项校验失败是 1，不能被 D10 的统一 environment 文案覆盖。
- “先读取状态再决定重跑”须补充：没有执行记录不能证明从未执行；提交返回不确定时，没有观测到记录也不能证明未提交。不要给出安全自动重试的暗示。
- 单项提交前校验、整份结果校验/编码、已经部分提交后的内部错误、输出短写，是不同阶段。当前草案大体已区分，但实现测试须分别注入，文本和 JSON 均适用；不能将最终整份校验失败说成能够回滚之前所有执行。
- 第 4.1 节把 PD-26、Scratch 和目标读取放在执行前，方向正确；“不执行、不分配 seq”不能扩大成普通 Open/辅助文件零变化。首次 worktree 路径扫描应明确落在任何检查启动前，而不仅写事务内。

### N4：统计、实验和未完成内容的表述边界

作者 23 个字符串、6/7 个后代及 X1～X7 是作者证据，不是穷尽证明。本轮只复验其中选定机制。现有 CI 中三平台通过也不包含草案外实验，§15 是计划，不是已经通过的 Check Runner 测试。草案对此总体披露准确。
