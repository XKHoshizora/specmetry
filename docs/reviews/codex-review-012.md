## BLOCKER

### B1：继承的 Git 环境变量可以将构造操作重定向到其他仓库

**位置：** [git.go:47](../../internal/testutil/git.go#L47)、[fixture.go:84](../../internal/testutil/fixture.go#L84)。

`NewGitRepo` 继承整个 `os.Environ()`，随后只覆盖部分变量，没有清除 `GIT_DIR`、`GIT_WORK_TREE` 等 Git 定位变量。设置 `cmd.Dir` 不能覆盖这些变量的作用。

本轮只使用临时仓库，通过公开的 `BuildFixture` 路径复现：

1. 创建另一个临时仓库，记录其 HEAD 和配置。
2. 设置 `GIT_DIR`、`GIT_WORK_TREE` 指向该仓库。
3. 调用 `BuildFixture(t, "fx-docs-only")`。
4. **那个仓库的 HEAD 和配置均发生变化；预期夹具目录中反而没有 `.git`。**

**影响：** 测试进程继承这些变量时，构造器可能污染用户工作仓库。后续 SHA 断言即使失败，也不会撤销已经执行的提交和配置修改。这是实际写入隔离问题。

另一个独立探针确认：继承 `GIT_DEFAULT_HASH=sha256` 会生成 64 位提交 ID，说明固定 SHA 的环境隔离也不完整。

**最小修复建议：**

- 为夹具 Git 子进程过滤继承的 Git 专用环境变量，再加入明确受控的配置、身份和日期；固定对象格式。
- 在首次修改配置、提交之前，确认实际 Git 目录属于新建的临时仓库。
- 增加公开路径回归测试：预置指向另一个临时仓库的环境变量，验证其 HEAD、索引和配置保持不变。

隔离缺口位于复用的测试助手，新增 `BuildFixture` 路径直接受影响；不涉及重新审查 M0 存储层。

## 已验证的正确部分

### 三个夹具的当前内容

- **docs-only：** 没有业务代码；8 条需求，R8 无可判定验收描述，R3、R7 保留歧义；候选来源排除场景齐全。

- **incomplete：** 两段说明性 README，没有正式需求规格；代码具备增加、获取、列表、删除、搜索和标签六项功能。这些功能只能作为现状观察，不能据此声称存在客户要求。

三个夹具能够分别模拟只有需求文档、开发进行中、代码已有但需求未整理的首次接入情形。夹具本身未发现真实凭据、私人信息、本机路径或不必要的外部依赖；样例应用只使用 Go 标准库。

### 阶段和历史检查的独立验收价值

阶段测试有独立价值：[fixture_test.go:123](../../internal/testutil/fixture_test.go#L123) 比较实际文件推断结果与独立写定的阶段预期，不是单纯信任 Manifest 的 `stage`。

独立探针和变异测试验证了：

- 只改 Manifest 的阶段声明，不会改变文件推断结果。
- 在 docs-only 中添加代码，文件推断结果变为 `in_development`；随后将实质文档缩短到不足 512 字节，结果变为 `incomplete_docs`。
- 修改 brief 一个字符，会触发固定 SHA 校验失败。两个重复构造之间即使仍然一致，也不能绕过与固定 `expected_refs` 的比较。
- 提交时间与身份受控，正常全局配置中的签名、换行和忽略设置不会改变夹具结果。独立探针预置了这些全局配置，构造结果仍匹配固定 SHA，且原配置文件未被修改。

因此，阶段和历史检查并非整体自证循环；但其价值不能掩盖 N1 所列的 Proposal 语义断言缺口，也不能证明 B1 涉及的环境变量已被隔离。
