### B-140-1：正常 omitempty 输出与“缺失失败”规则冲突

**位置**：[方法稿 DS-2～DS-4](../wp2.5-c9-exception-identity-method.md)、I-2（137）、J-3（335）。

固定工具链的 `list/context.go:16` 把 `CgoEnabled` 定义为 `bool` 且带 `json:",omitempty"`。本计划所有分析条件都是 CGO_ENABLED=0，因此健康的第二种调用会省略这个键。DS-2 却将其与 ToolTags／ReleaseTags 合列，统一规定“缺失：J-3”，没有为 false 的正常省略写出分支。

同样，`load/pkg.go:82,85,98–101,127–134` 的 Standard、Incomplete、文件切片、Imports／ImportMap、Error／DepsErrors 等均为 omitempty。健康第三方包的 Standard=false、无 CgoFiles、无 Error／DepsErrors 时，相应键本来就可以不存在。ModulePublic 的 Main=false、Replace=nil、Error=nil 也正常省略。反过来，标准库的 Module=nil 以及主模块的 Version／Sum 缺省，不能套用第三方模块 I-2 的非空要求。

**不需要实验的事件序列**：按已允许的三种调用与 CGO=0 执行 → 第二种调用成功输出正常 context JSON，但没有 CgoEnabled 键 → 按 DS-2 的缺失栏进入 J-3／阶段 B 停止；若实施者自行按 Go 零值补 false，又会继续健康分析。两种读取方式都能从现文字读出，V-1 没有唯一的健康准入结果。这不是“工具尚未构建”的问题。

**最小修正**：按字段及包／模块分支列出“正常省略的语义零值”和“必须实际非空／存在的值”；先按固定 JSON API 的省略约定解码，再做必要字段、类型和语义核对。不得把任意缺失都放行：ImportPath、必要 Dir、第三方所需 Sum／GoModSum 等仍必须满足其语义前提；格式、错误类型、错误值与整体采集失败仍失败。补健康 CGO=false、非标准包、标准库、主模块，以及必要字段缺失的文档对照，DS／J／V 同步。无需增加调用。

### B-140-2：条件差异读取未闭合；逐文件哈希不证明时点目录一致

**位置**：[方法稿 I-4～I-6](../wp2.5-c9-exception-identity-method.md)、149～152、DS-8（175）、80；交叉 [实施计划条件差异检查](../wp2.5-implementation-plan.md)。

本稿 I-5 绑定预筛、parser 和条目约束提取使用的 B，方向正确。但 I-6 写“被读取的文件集合等于该包的 GoFiles”，DS-8 也只到 GoFiles。既有条件差异检查却必须枚举、判断其他非测试 `.go` 文件，并读取匹配文件的导入，分别核对默认标签、CGO=0／1 等生产变体。

固定 `go/build` 的 `MatchFile` 会经 Context.OpenFile 读取内容；未设置时回退 os.Open（build.go:210–216,1402–1410,1477–1497）。本稿没有规定这些读取使用 I-5 的验证字节或受绑定的目录／文件集合，也未明确把它们纳入 I 链。一个实际接点是 linux/amd64 的 libc 包：`libc_unix.go` 的文件名不先按 GOOS 排除，但其 build 行排除 linux/amd64，条件判断需要读取它，它又不在该配置的 GoFiles 中。若按原检查读取，就超出 I-6 的集合；若不读，又删掉了已审的条件差异检查。

**影响**：不能由“所有最终 GoFiles 的 parser 输入都通过哈希”推出“影响文件选择和生产变体覆盖的全部输入都已绑定”。一个条件判断读取了临时不同的文件头／导入，而后恢复原字节的序列，不会被只核对 GoFiles 的 parser 哈希必然发现。这里指出的是规格缺少接点，不声称已在本仓库运行出了某个实际扫描假通过。

另有可直接反驳的强声明：149～152 把 I-4 说成“快照时目录一致”，并声称快照读取过程中修改必使 h1 不等。设目录中 f、g 原字节为 f0、g0；I-4 读 f 时只有 f 是原值，读 g 时只有 g 是原值，得到的哈希仍可恰好是原模块 h1，过程中不必存在目录整体等于原内容的时点。更简单地，未编入文件在它被 I-4 读完后改动，I-5 不读它，改动也不必使本次计算失败。均不涉及 SHA-256 碰撞。Lstat 之后才替换路径的类型竞争，也不能单靠先前一次 Lstat 排除。

**最小修正**：

- 分开“模块哈希输入集合”“条件分类／导入读取集合”“最终预筛／类型分析集合”。保留 GoFiles 的完整 parser 覆盖，同时把影响条件差异与闭包判断的第三方／x/sys 输入纳入受核对的来源；不得通过删除既有检查满足 I-6。
- 明确 MatchFile／导入读取消费哪份已验证的 B／目录名字记录，可通过受控读取接口实现这一约束；不要求现在实现它。
- 把哈希结论收窄为本次所读文件名字与字节的内容关联、以及实际消费字节的相等，不宣称原子目录快照或任何期间改动必然被检出。若另要求更强文件系统保证，须另提方法，不能从 Hash1 推出。

该修正不要求本轮发明新实验、取消逐文件绑定或增加未经批准的支持／风险保证。

### 5.3 表示、批准及五种状态

10a 用途进入 h_list，10b 处理记录节号留在批准登记，能避免“摘要内包含批准自身依据”的循环。先有实际发现，再生成完整清单、独立审查、负责人明确 h_list、登记及每次当前身份核对，五状态分层可保留。撤销登记不删除历史处理记录，也不等于回写过去的事实。

机器核对恰好一次摘要和有效节号，只证明受控登记中有这项关联。由人核查该节决定、文件提交和摘要，是治理前提；不要求本轮凭空引入签名。但登记的编码、行尾、节号形式、重复／撤销规则应随最终表示定稿，不能借其受控性质豁免解析或真实读取错误。
