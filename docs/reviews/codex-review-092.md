## 3．B1：租约等待的原阻塞可关闭

[§19.4:1589～1628](../wp2.5-check-runner.md#L1589)、[§8.3:490](../wp2.5-check-runner.md#L490)、[§19.2:1528](../wp2.5-check-runner.md#L1528) 与 [MVP-EV-23](../acceptance-criteria.md#L191) 现在分别表达三种生命周期：

| 角色／情况 | 修订后的契约与裁定 |
|---|---|
| 共享持有者 | 持至自己的子进程回收；没有统一期限。gitx 使用调用方 context；doctor／macOS ACL 子进程没有可取消 context。不从检查阶段预算推导它们及时释放 |
| 排他持有者 | S0～S5；主进程及终止／确认有阶段预算，同步步骤和系统调用没有硬期限。F1 的释放与资源保留按 G3，不能推广为全部持有者实际执行时间有硬上界 |
| 等待者 | 可取消，没有固定总上界；排队不计入任何执行阶段预算或 duration_ms |
| 排队取消 | 闸门锁下删除自己的等待资格，排他等待计数减一并唤醒受写者优先影响的共享请求；不等他人的子进程，不释放他人的租约 |
| 取消与可取得同时发生 | 先在锁下检查 context；已取消则不取得。若取得先线性化，则由自己在 S0 前处理取消并释放自己的租约，不同时走“退出排队”和“释放持有租约”两条责任 |

按原反例推演：共享 doctor 子进程长期不结束，排他请求可以长期等待；收到取消后只退出自己的队列，原共享持有者继续持有。已取消的排他请求不再阻挡共享请求；其他仍有效的排他持有者／等待者可以继续阻挡，这不是该取消请求遗留的阻塞。不存在“等待超时后强行释放活跃子进程租约”的新机制。

“生产 CLI 预计不排队”提供的是进程内拓扑解释：自己的 Git 已先回收，其他 CLI 是另一个进程。它没有删除进程内 Execute／gitx 并发契约，也没有把同步 Git、ACL、系统调用时间计入已证明的有限等待。文中的“立即返回”应按取消被调度、取得闸门短临界区后的协议动作理解，不是操作系统实时保证。

C-9 补入 Cmd.Wait 和按类型识别调用目标，方向正确。go/types 本身不完成任意函数变量的流向分析；获准实施后仍需具体解析规则、不能解析时的拒绝策略及导入者测试，不能因这句话就宣称生产静态覆盖已实现。持有者启动失败、取消、正常 Wait、资源移交的释放责任也要在生产测试逐项验证。本轮不要求为此新增原型或修改既有 Git／doctor／ACL 实现。

**裁定：Review 091 B1 关闭，限于撤回错误上界并给出自洽的等待／取消规格；不是闸门生产实现验收。**

## 4．BLOCKER：B2 的剩余知识状态与字段冲突

### B2-R1．未挂起／已恢复不等于已经执行用户代码

**位置：** [§19.7:1701～1704](../wp2.5-check-runner.md#L1701)、[1726～1727 行](../wp2.5-check-runner.md#L1726)、[1762 行](../wp2.5-check-runner.md#L1762)，连带 [P-4:1952](../wp2.5-check-runner.md#L1952) 与 [§110:6604、6625](../review-resolution.md#L6604)。

返回 0 的“证明什么”列正确写“调用之前线程没有挂起”，但随后写成“**已运行**……在本进程恢复之前就已运行”；“不证明什么”只保留开始时刻未知。返回 1 也写成“自调用返回起运行”，对应表直接列 U 已运行。

[Microsoft ResumeThread 契约](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-resumethread)给出的是挂起计数与恢复状态；[CREATE_SUSPENDED](https://learn.microsoft.com/en-us/windows/win32/procthread/process-creation-flags)和[线程挂起说明](https://learn.microsoft.com/en-us/windows/win32/procthread/suspending-thread-execution)也不提供用户指令实际获得 CPU 或其开始时刻的证明。解除挂起与实际调度是不同事件。

**合法静态事件序列：** 按 P-4 自己计划的前置操作，夹具先把挂起计数从 1 减为 0；主线程尚未获得执行机会，Runner 再调用 ResumeThread 得到 0，随后请求终止。返回 0 成立，用户检查代码却可以尚未执行。无须假设 API 返回错误，也无须用一次没有标记文件的实验来证明它。若线程获得了执行机会，则也可能已经运行；正确知识状态是“已经不处于该挂起状态，用户代码**可能**执行过，开始时刻未知”。

这不是要求抵御任意恶意外部程序：本轮准备稿明确为这一异常分支制定正常处理规则，P-4 还准备主动构造它。即使把干预列为不受控前提，也不能在观察到异常后声称得到了 API 没有提供的执行证据。该错误反复进入 U 维度、处理记录与原型预期，不能仅靠 Q-2 待决定掩盖。

**最小修正：** 返回 0 改为“未挂起／可被调度，可能已执行”；返回 1 改为“本次解除最后一层挂起，按协议视为已启动”，明确这不是实际执行指令的认证。正常 t_start 可以继续约定为调用成功返回时刻，但不能称为精确物理起点；异常分支继续使用定义区间。同步 U／T 表、当次说明、§110 的作者推演与 P-4 预期，不修改历史审查原文。无需产品新字段或新实验才能纠正这一事实。

### B2-R2．异常 A6 与通用 D19 对同一行给出不同字段

**位置：** [§6.2 第 0a 条:298](../wp2.5-check-runner.md#L298)、[§8.6 规则 1:667](../wp2.5-check-runner.md#L667)、[§10.1:981～985](../wp2.5-check-runner.md#L981)，对照 [§19.7:1731](../wp2.5-check-runner.md#L1731) 和 [§19.10:1851～1853](../wp2.5-check-runner.md#L1851)。

通用规则：取得正常退出信息时保留主进程退出码，并按 t_main−t_start 记时；未取得才为 NULL 和 t_S3−t_start。新“Windows 恢复结果异常，终止未确认（A6）”却无条件要求 NULL 和 t_S3−t_start。§19.10 又要求按 §6.2 优先级命中，没有说明何者覆盖。

**合法组合：** 返回 0 后立即进入 S3；主进程在终止调用前自行正常退出 7，Runner 可靠取得该退出信息，但 Job 后代的结束查询失败，整个保证范围未确认，进入 F1／A6。主进程退出已知与整棵 Job 未确认可以同时成立。通用 D19 要求 exit_code=7，新异常行要求 NULL；若使用通用时间行，又会把异常返回时刻之后的区间称成实际运行时间。新表不能既使用异常的“未知开始”前提，又无说明地套用普通运行时长。

**最小修正：** 为异常 A6 明确字段优先级：是否可靠取得退出信息仍要保留，已知的退出码不要被“异常”标签静默抹掉；由于开始时刻未知，相关时间只按明确的定义区间展示，不称运行时间。将 §6.2、规则 1、§10.1、§19.2／§19.7／真值表及必要 data-model／EV 映射同步。若另要规定主动丢弃已知退出信息，应明确提出其语义依据和代价，不能让互相冲突的行自行选择。A12 的 Q-2 决定不能解决已经写定的 A6 矛盾。

以上都是固定文档和官方 API 的静态反例，**本轮没有运行新的 Windows 调度实验，也没有宣称已经动态复现原生 ResumeThread 故障。**
