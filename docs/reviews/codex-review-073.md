## 三、B3-R1：支持契约已有收口，异常出口仍未闭合

### 已成立的修订

[§8.5 第 438～441 行](../wp2.5-check-runner.md#L438) 正确区分：主进程退出但未回收、树结束、复制任务返回，以及 EOF 且全部字节写入目的端。复制提前因读错、写错或停止读取而返回不再被算成完整排空。

[§9.1 第 550～574 行](../wp2.5-check-runner.md#L550) 将检查转发的候选目的端限制为：

1. `*os.File` 直接继承，没有 Specmetry 复制任务；
2. Specmetry 自己定义、识别、控制的内存目的端；
3. 其他 Writer 在启动检查前拒绝，候选错误为 internal/1。

这没有继续假设普通 io.Writer 可以被中断。内部内存类型可以设计成没有用户回调/外部 I/O 的受控实现；它仍须明确并发写、容量/错误及别名支持，不能把类型名称当作证明。D20 正确保留了进程内调用支持限制的待确认状态。

子进程拿到原始文件句柄或自建管道写端，Specmetry 自己的文本仍安全转义；JSON 的正常分流未回退。已有 [Go os/exec 契约](https://pkg.go.dev/os/exec#Cmd) 区分文件直连与复制，并不赋予任意目的端 Write 可取消性；自行复制也没有改变这一点。

### BLOCKER B3-R1-S：用尽排空预算后的 join 与 internal/1 出口互相冲突

**准确位置**：[§8.5 S6，第 472～477 行](../wp2.5-check-runner.md#L472)、[时限第 501～505 行](../wp2.5-check-runner.md#L501)、[§9.1 第 568 行](../wp2.5-check-runner.md#L568)；关联 [§8.6 第 519 行](../wp2.5-check-runner.md#L519)、D20、T1/T6。

**源码级/流程级反例，不依赖生产 Runner**：

1. S5 确认后开始计 T_drain。复制任务尚未返回，到达 S6 的排空期限。
2. 按第 473 行，现在才关闭读端；复制的 Read 被唤醒，但复制任务还需要被调度、返回并通知等待方。
3. 第 476 行只允许使用 T_drain 的“剩余部分”。此时剩余预算为零。即使目的端 Write 从不阻塞，也不能据此证明复制已经返回。
4. 文档把未确认 E-copy-end 判为目的端违约、internal/1，并说明之后仍可能写出；紧接着第 477 行又规定，只有确认 E-copy-end 才能写记录、写最后文档、返回。第 505/568 行进一步无条件断言受支持目的端总能在时限内确认复制结束、重复调用不累积。

这不是要求 Go 提供实时调度保证，而是当前协议没有为“到期后停止读取并确认任务结束”分配一致的阶段/预算，且没有给失败分支一致的结果。若第 503 行被解释成停止读取时重新计完整 T_drain，又与“覆盖 S6 的全部等待”及 §8.3 的单份预算说明不一致，必须明说，不能两种解释混用。

[Go File.Close 文档](https://pkg.go.dev/os#File.Close) 对支持 deadline 的文件说明了取消待决 I/O；这不等于调用 Close 时复制 goroutine 已经返回。**Write 不阻塞，不等于复制任务已经结束**。本轮没有把一次立即返回的 X11 正例推广为所有调度均成立。

**影响**：

- 若等到确认才返回，当前“剩余预算”不能解释如何完成该等待；若到期直接 internal/1 返回，又违反“只有确认后才返回”的保证。
- internal/1 本身不会撤销已经进入复制任务的输出权限。未确认的任务仍可能影响该目的端及后续复用它的调用；不能未经说明继续走普通最终输出路径。
- 默认 JSON 使用不同 stdout/stderr 时，不应把 stderr 的迟到输出直接说成 stdout 污染；问题在于异常出口没有规定哪些输出对象已经安全、是否还能写最终文档、是否可以复用，以及并发/别名调用的处理。
- 仅把这一分支挂到 T1，不能同时保留“受支持类型所有路径已回收”的无条件保证。

**最小修正方向**：

1. 将正常排空与停止读取后的复制确认分成有明确预算的阶段；可在总预算内预留 abort/join 时间，或明确额外预算并同步最长时间公式。具体参数是工程细化，不必新增产品审批。
2. 为 E-copy-end 未确认单列出口，写明是否允许尝试记录、哪些对象还能接收最终错误、是否允许返回/后续调用；不要让普通 Execute 错误输出自动掩盖该状态。
3. 具体机制若仍未解决，可以准确列为冻结前 T1/T6，撤去第 505/568 行的完整保证；准备 PR 不需要提前提交实现。
4. 对支持的内存目的端明确同步、独占/别名规则及最终文档与复制共享时的屏障；JSON 模式的检查目的端不能在不说明的情况下等同于 JSON stdout。调用者主动 `2>&1` 的既有例外继续保留，不扩大成自动免责。
5. S1、F1、取消的提前出口也使用同一复制确认协议；不能在这些分支重新采用“放弃复制即可返回”。

**裁定：B3-R1 部分修复，尚不能关闭。** 这是一处规范收尾矛盾，不是宣称当前未实现 Runner 已发生输出泄漏。

## 四、B3-R2：原错误论证已撤回，候选机制可作为准备依据

### 1. Linux 归属与身份已分开

[§8.2 第 385～404 行](../wp2.5-check-runner.md#L385) 明确承认 Review 072 的基线反例：既存子进程之后创建的后代，不能只因出现在基线外就归入检查树。新候选要求：

- 设置 subreaper 时没有任何子进程，**僵尸也算**；
- 整段检查区间没有其他子进程来源；
- 排他条件无法确认时不启动，或者进入受控失败；
- pidfd 只绑定身份，不承担归属证明；
- 归属/身份没有确立的进程不得被终止或回收。

在这些前提真正成立时，候选归属推理成立；之前设置 subreaper 前已经脱离祖先链的进程不因这个设置被重新收养。[Linux subreaper 文档](https://man7.org/linux/man-pages/man2/PR_SET_CHILD_SUBREAPER.2const.html) 的最近祖先收养语义支持这一划分，并不按业务用途认定进程。

第 392 行的“测试基座串行化”本身不是生产强制机制，但 [T2 第 942 行](../wp2.5-check-runner.md#L942) 已明确要求覆盖 gitx、并发 Execute 的进程级强制设计与原型，现状为“尚无方案原型”。因此本轮没有把测试约定冒充已经可依赖的互斥。

### 2. 保留组长修正了原先的回收顺序

[第 380～384 行](../wp2.5-check-runner.md#L380)、[E-main/S3/S5 第 438、461～470 行](../wp2.5-check-runner.md#L438) 改为：

1. 有界观察退出，Unix 用 WNOWAIT 留下可等待的组长；
2. 首次及后续组信号发出时，组长尚未回收；
3. 确认树结束后才由 Cmd.Wait 回收；
4. 回收之后不再使用旧数字 PGID 发信号；不能保持身份则 F1，不先盲目发信号再检查。

[waitid 的 WNOWAIT](https://man7.org/linux/man-pages/man2/waitid.2.html) 保留可等待状态；[pidfd_open 的文档](https://man7.org/linux/man-pages/man2/pidfd_open.2.html) 也明确未回收子进程 PID 保留的前提，包括没有其他回收者、没有 SIGCHLD 的自动回收设置。冻结时应把这些前提纳入互斥/信号策略，而不是外推为任意宿主程序均成立。主进程只由一次 Cmd.Wait 回收、清扫排除主进程、其他 Git 在区间之外运行的方向与此相容。

这足以撤销 Review 072 中“组已经消失后仍按旧 PGID 发信号”的原论证。没有要求强制 PID 复用，没有声称本轮已观察到生产误杀。

### 3. 剩余生命周期不算已解决或已获豁免

F1 明确保留可能仍存活的进程，不读结束上下文、不继续后续检查，不把终止请求或空列表当作完成证明；Windows 仍须持有正确的 Job/进程句柄并查询实际状态。[QueryInformationJobObject](https://learn.microsoft.com/en-us/windows/win32/api/jobapi2/nf-jobapi2-queryinformationjobobject) 提供相应状态查询，但正常正例不能证明全部失败分支。

**仍须冻结前补齐的内容见 NON-BLOCKER N1**：Unix 组长/被收养者、pidfd、Go Cmd 资源、subreaper 属性及进程级锁在 F1 返回后的归属。文档没有把这些写成已经完成的生产机制，T1/T2/T3/T4 继续未通过；以接缝模拟 F1 的测试不等于验证真实无法退出的进程。

macOS 的有界观察、WNOWAIT、组成员确认均如实未验证；Linux 的 X12/X14 不替它作证。D7 未批准，不能将未来选定的有限管理范围直接等同于原承诺的所有后代。

**裁定：B3-R2 在准备文档层面关闭。** 这只确认原错误归属与组身份论证已经修正；不冻结机制、不认可实现完成、不接受新的进程树风险。

### BLOCKER B3-R3-S：持久化失败不能重置收尾事实，也不能一概断言没有记录

**准确位置**：[§8.6 第 536～542 行](../wp2.5-check-runner.md#L536)，关联 [§11.4 第 720 行](../wp2.5-check-runner.md#L720)、[D19 第 966 行](../wp2.5-check-runner.md#L966) 和 §86。

**可达的候选流程反例**：

1. 用户代码已经启动。到达 F1，树没有确认结束，仍可能有进程；禁止读取结束上下文。
2. 若负责人选择当前推荐 D19(a)，尝试写入一条明确不合格的记录。
3. 此时数据库写入或执行项校验失败。这是本版自己要求覆盖的组合，第 542 行还明确把第 5～7 行引到第 13 行。
4. 第 13/14 行却固定给出“可能仍有进程：否”“读取结束上下文：是”。这些不是持久化失败能改变的事实，与第 5 行和 F1 的强制边界相反。

不能把后一个错误当作覆盖前一个状态的整行替换。即使第 14 行的 internal/1 最终优先，也必须保留“树未确认、可能残留、不读取结束上下文、已停止后续项”的状态。第 13 行的 environment/6 同样不能洗掉它们。这是当前推荐组合内部的技术矛盾，不需要负责人另选产品行为才能修正。

另一个内部矛盾是“记录是否存在”：第 516 行和 §4.3 正确说提交结果不确定时不能从未观察到记录推出未提交；第 13 行、第 542 行、D19 和 §11.4 又把笼统的数据库失败一概写成“没有记录”。

- BEGIN/写入前拒绝、提交前确定回滚：可以断言本次没有提交。
- 提交结果已知成功：记录保留。
- **COMMIT 结果不确定**：只能报告本次记录状态不确定，保留可能已经提交的事实，不建议自动重跑。

必要调用链核查：当前 [sqlite.withTx 第 406～415 行](../../internal/store/sqlite/store.go#L406) 将 `tx.Commit()` 的结果向上传递，没有给 Runner 提供“任意数据库错误均发生在提交前并确定回滚”的保证。本报告没有声称复现 SQLite 磁盘故障，也不要求修改该存储实现；这里是新规范必须分开的失败阶段。

**影响**：照表实现可能丢失残留进程警告、误入结束上下文/普通清理路径，或者向调用者错误保证本次没有记录。只给最后一个错误排退出码不能修复这些状态丢失；也不能因保留一条通用“不要重试”说明就允许具体事实相反。

**最小修正方向**：

1. 将第 13/14 行写成对前面状态的叠加：进程状态、E-tree、是否已读上下文、复制状态和支持对象均继承，不能统一写死为“否/是”。
2. 分开确定回滚、已提交和提交结果不确定，统一 §4.2、§8.6、§11.4、D19/§86 的说法；不增加 SQLite 重试或改变既有错误映射。
3. internal/1、environment/6 只决定最终错误优先级；先前的 F1、取消、F2 和输出通道可用性继续保留。
4. 明确 no-process 分支衔接：`input_missing` 不启动进程，应跳过进程/输出资源步骤并将“没有本次消费者”作为结束上下文的依据；spawn_error 同理。§4.2 当前直接转结束上下文，而该步骤又要求 §8.5 确认，应补这一明确例外，不要求新增复杂机制或第 18 行。

## 六、NON-BLOCKER 与冻结前必须补齐的说明

### N1：真实 F1 的宿主生存期仍需在 T1/T2 定稿

[第 495 行](../wp2.5-check-runner.md#L495) 已披露主进程可能不退出、不调用会阻塞的 Cmd.Wait，并等 Specmetry 进程结束后的系统处理。这是残余资源的披露，不能读作“全部进程已经清理”。但还缺下列具体规则：

- 主进程已经退出但尚未回收、或者仍存活时，Cmd/进程句柄、pidfd、已收养僵尸由谁继续拥有；
- 只在 S5 成功时清除 subreaper 的当前顺序，F1 后属性与进程级互斥是否继续保留，宿主存活时是否禁止后续调用；
- 管道复制确认与这些进程资源是不同的生命周期；关闭一个对象不证明其他对象已经结束；
- 父进程退出后系统收养/后续回收，不保证尚存活的检查立即被终止；不能把调用 Execute 返回等同于宿主退出。
