## 二、BLOCKER

### B5-R：合法事实域不能把所有重复 seq 都排除

**准确位置**：[m2-readiness.md 第 810 行](../m2-readiness.md#L810)把“seq 全局唯一、严格递增”列为合法历史的不变量；[第 821～823 行](../m2-readiness.md#L821)把“重复的 seq”列为畸形，并排除在 ready 双向等价对照之外。

这里必须区分“计数器分配的序号”与“持有这个序号的事实记录”。全库统一分配和递增，不意味着不同事实行的 seq 必须两两不同。现有冻结模型允许一次逻辑写入的多条记录共用 seq。

**源码级反例：正常审核接受条目并附带 Scope。**

1. [公开 review 路径](../../internal/cli/review.go#L120)只调用一次 `sqlite.NextSeq`，取得 `plan.Seq = n`。
2. [baseline.Apply](../../internal/baseline/apply.go#L148)用 `n` 写入 `baseline_versions`。
3. [变更记录](../../internal/baseline/apply.go#L272)也用同一个 `n` 写入一条或多条 `baseline_changes`，并用 `change_index` 保留版本内顺序。
4. [review.ConfirmScope](../../internal/review/scope.go#L82)把同一个 `plan.Seq` 交给 `scope.Write`；[scope_confirmations 插入](../../internal/scope/confirm.go#L184)仍使用 `n`。

这些都是合法的不同事实记录，事务原子提交；不是重复分配、损坏或非法并发。这与 [data-model §1](../data-model.md#L11)的写事务内分配和 [§5.5](../data-model.md#L483)的一次审核应用模型一致。

因此，按第 3 版当前文字，正常审核产生的 Baseline＋Changes＋Scope 历史就会被归为“生产写入无法产生”的畸形组合，退出双向对照。即使不附带 Scope，Baseline Version 和其 Changes 已足以构成反例。

**实际影响**：生成器或转换器若照该定义实施，会缩窄合法输入域，漏掉常见的真实生产历史；若进一步用 seq 作为每条记录的唯一键，还可能丢记录。后者是错误实现该定义的风险，本轮没有发现或声称已存在这种 M2 实现。

若原意只是“序号的分配值唯一”，也应明确这一限定，并删除“任意重复 seq 都是畸形”的表述。当前两个句子结合起来，不能支持该限定理解。

**最小修正**：

- 改为“seq 在全库写入顺序中统一分配、分配值单调递增；按既有模型，同一次逻辑写入的多条事实可以共享 seq”。不要把 seq 当作所有事实行的唯一标识。
- 畸形例子只保留确实违反既有分配／时序约束的情形，不把正常的共享 seq 判为异常；无需发明新的行间排序规则。
- 将“正常审核的 Version、Changes、Scope 共用 seq”明确列为合法历史正例。以后冻结 F4／F5 时，要求生成器和两套转换器保留这类记录；`as_of_seq = n` 时不能只保留其中一条，版本内部仍按已定义的 `change_index` 处理。
- 同步任何把“重复 seq”作为畸形前提的定义、摘要或处理说明，保留审查原文。

**这是报告中的事实域定义错误，不是要求现在新增 M2 测试或重审 M1。** 修改范围可以很小，也不需要产品负责人重新决定已冻结的共享 seq 行为。

## 三、B3-R：准备报告层面可以关闭

### 1. E4 的范围与普通 Open 结果

[E4](../m2-readiness.md#L435)现在已独立于 recover 的 E1～E3、E5：

- 等数据目录、锁、版本、墓碑校验、墓碑执行与整理、迁移前备份及迁移全部成功后，才作为最后一步、在释放打开锁之前清理。
- 前面任一步拒绝或失败，都不执行遗留清理，不再将“版本兼容”等同于“打开成功”。
- 清理失败不把成功 Open 改成失败；遗留保留，日志只记录错误码和遗留 ULID，doctor 只报告，下一次 Open 再试。

- 普通 Open 的既有拒绝保证和 doctor 只读保证保留；E4 的备选“不采用”也保留。

这里的“拒绝／失败路径不清理”指 **Open 自身**。Open 成功、清理执行后，上层命令仍可能因自己的业务校验失败；不能进一步宣传为“所有非零退出的命令都没有清理副作用”。第 3 版按 Open 分界并披露全部调用者，已足以支持这一解释，后续规范同步应保持该边界。

### 3. “整理未完成”的含义

[第 355、410 行](../m2-readiness.md#L355)把日志恢复、版本／结构检查、墓碑逻辑删除提交与连接正常关闭，作为“数据库恢复已完成”的判定；checkpoint／VACUUM 未完成则保留 `.compaction-pending`、报告整理未完成并返回草案退出码 6。

这种分层可以成立，但它只确认原库的可用／逻辑恢复结果，**不证明空闲页、WAL 或临时副本中的已删除数据已经清除**。本版的非成功结果、残留表和整理标记保留了这一区分，没有把可用性当成全部隐私义务完成。

后续实现仍须满足 [architecture §11.4](../architecture.md#L1113) 和已有 N1 门槛：读 checkpoint 的结果；整理真正完成后才能移除标记；下一次打开继续完成。单纯删除行或 SQLite 连接关闭，不是整理完成的证据。STO-11 的无 canary 保证对应清理完成的结果，不能套用于 STO-13b 明确报告的整理／清理未完成路径。

这不是认定 N1 已修复，也不是批准新的退出码；而是确认准备报告已经将逻辑恢复与未完成义务准确拆开。恢复中哪个阶段发生失败，仍以表中的完成判定为准。
