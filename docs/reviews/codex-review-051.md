## 二、BLOCKER

### B1：工具故障和未形成工作量仍可能被报告为正常 PASS

**位置：**[m14_diag_test.go](../../internal/store/sqlite/m14_diag_test.go) 56～66、237～253、319～328、355～401 行；[运行说明](../m14-diagnostics.md) 131 行。

`m14Spawn` 将启动／退出异常及 JSON 解码失败转成 `Stage="helper crashed"`，没有把它们作为工具错误上报。只读探测的写入进程分支和真实 Open 的汇总分支都只增加失败计数。若故障发生在提交之前，`committed=0`，空数据库恰好通过 `m14Check`，最终整个诊断仍 PASS。`resolve`、`migrations` 等尚未进入被诊断 Open 的失败，也没有独立的无效工具判定。

探测进程的阶段异常会调用 `t.Errorf`，但写入辅助进程没有相同保护；探测中的非 SQLite `other` 错误也只被计数。这与说明中“辅助进程崩溃属于会使测试失败的工具错误”不一致。

此外，参数允许零秒、零探测进程、零写入进程、零轮数或零 Open 辅助进程。没有实际负载时仍打印正常结果和 PASS。`helper_opens=rounds*procs` 只是计划调用数，工具故障时不是实际进入 Open 的次数。

**独立校准：**Windows/amd64、Go 1.27.1、SQLite 3.53.4、modernc.org/sqlite v1.60.1；没有真实项目数据或网络。

| 条件 | 实际结果 |
|---|---|
| 未修改诊断代码；秒数、写入／探测进程、轮数及 Open 辅助进程均为 0 | 两个探测变体均 `probes=0`、`writer_commits=0`；Open 结果 `helper_opens=0`、平台字段为空；整体 PASS／exit 0 |
| 隔离副本中仅让 `m14OpenHelper` 在调用 Open 前退出 42；每变体 1 秒、2 个写入进程、1 个探测进程；Open 路径 1 轮、2 个辅助进程 | 并发变体 `writer_commits=0`、两个 `helper crashed`；Open 路径 `failed_helpers=2`，仍报告 `helper_opens=2`；两个测试均 PASS／exit 0 |
| 同一隔离配置，仅将故障改为输出 `not-json` 并正常退出 | 损坏 JSON 被记为两个 `helper crashed`；没有任何辅助 Open 或提交；两个测试仍 PASS／exit 0 |

故障校准中的探测进程保持原实现，分别实际完成了 235、202 次并发变体探测。因此这不是整个测试未启动，也不是用一个无关断言失败代替目标问题。

**影响：**损坏的诊断环境可以产生绿色作业；所谓“并发提交”可能没有提交，所谓 Open 样本可能根本未进入 Open。后续据此计算未复现率、比较控制组或验证插桩，会得到不成立的证据。这不等于现有诊断 CI 已发生这些工具故障。

**最小修正：**

1. 将启动失败、异常退出、损坏／不完整结果、初始化失败等与被诊断的 SQLite 错误分开；前者使测试失败，并保留具体失败记录。
2. 校验辅助结果的阶段和必要计数。预期的 SQLite Open／写入错误可以继续只记录，不应为了测试绿色而要求它们全部成功。
3. 对诊断所需参数规定正的下限，或显式标记为未执行／无效；“during commits”必须证明有实际提交，探测组必须有实际探测，不能把零工作量当作有效通过。必要时记录启动／运行区间，避免只凭总数声称持续并发。
4. 分开计划启动数、实际启动数和实际进入 Open 的次数。某一轮所有真实 Open 都以已识别的 SQLite 错误返回，可以是有效诊断结果；所有辅助进程在进入 Open 前失败则不是。
5. 为上述崩溃、损坏 JSON、初始化故障和零工作量增加小型校准回归；无需反复施压复现 M-14。

本项修正不涉及生产重试、错误分类改变或 M-14 关闭。

## 三、NON-BLOCKER

### N1：seq“从 1 连续”的检查缺少下界

**位置：**[m14_diag_test.go](../../internal/store/sqlite/m14_diag_test.go) 256～275 行。

当前验证行数、不同 seq 数、最大 seq、计数器，却未验证最小 seq 或正值。隔离合成表写入 seq `[0,2]`、计数器 2、报告提交数 2 后，`m14Check` 返回空问题列表，虽然缺少 seq 1。`integrity_check` 也不会替代这一业务断言。

这不是已经发现生产 NextSeq 生成了 0；正常写入调用链从 1 开始递增。它是诊断自检对其声称不变量的覆盖缺口。最小修正为非空时增加 `min(seq)=1`，结合现有唯一性和最大值断言；空表单独验证计数器为 0。

### N2：时间参数限制循环量，尚未形成完整的辅助进程超时／回收保证

**位置：**[m14_diag_test.go](../../internal/store/sqlite/m14_diag_test.go) 172、182～183、209、237～253 行；既有 [HelperCommand](../../internal/testutil/testutil.go) 44～48 行。

辅助程序使用 `context.Background()`，父进程执行 `cmd.Output()` 并等待所有 goroutine，没有本轮诊断专用的取消、杀进程和 Wait 收尾。秒数检查只发生在循环之间，不能中断正在进行的 Open 或 SQL 调用。工作流有 25 分钟测试超时和 30 分钟作业超时，但 Go 测试超时本身不证明本地子进程已被回收。

本轮小规模运行均正常结束，未观察到遗留测试进程，也没有证明存在生产死锁。建议在进一步插桩前，为辅助进程增加有界上下文和取消后的 Kill／Wait，给每轮收尾留出余量；不需要修改生产 Open 或通用测试基座。报告应将循环秒数与整体硬超时分开。

### N3：阶段分类和调用次数需要更准确的标签

**位置：**[m14_diag_test.go](../../internal/store/sqlite/m14_diag_test.go) 114～125、209～225、400 行。

- 原始完整错误含 `cannot read the database version: cannot read the database:`，可沿现有代码定位到只读探测返回路径。但只有外层 `cannot read the database version` 不足以判断阶段。当前兜底将它标成“read-write version read”；只读探测的 stat／文件头读取失败也可能经过该兜底，实际尚未建立读写连接。不能用这一字符串规则排他定位所有未来错误。最小改法是不能唯一定位时标记阶段未知，后续用插桩取得确切证据。
- `probes` 是首轮探测次数，立即重试另计；macOS 的 466,837 次首轮探测，加 12 次重试，才是 466,849 次实际辅助读取调用。保留原统计即可，但应明确字段含义。
- 本次正常 CI 没有工具崩溃或初始化故障，600 个辅助结果均为 done 或 write 失败，支持其确实进入 Open；不能据此让 `rounds*procs` 在任意运行中都叫实际 Open 次数，见 B1。

这些精度问题不推翻已记录的 264／1288 和 SQLITE_BUSY 计数。

### N4：保证措辞应明确业务写入、辅助文件与实际覆盖范围

**位置：**[运行说明](../m14-diagnostics.md) 42～57 行及 PR 描述中的 “before anything is written”。

在已定位的只读探测失败返回路径，确实尚未执行读写连接、墓碑应用、迁移或用户写事务；可据此说“本次 Open 未执行这些 SQL／业务写入”。但此前已执行 [store.go](../../internal/store/sqlite/store.go) 99 行的目录准备和 105 行的打开锁流程，协调文件可能首次创建；既有 MVP-STO-02／07 还规定了严格受限的 WAL／SHM 辅助文件例外。因此不能扩写成数据目录绝对零变化。

建议补上上述限定，并将运行后的检查表述为“所测数据库的结构检查、合成 facts 数量和 seq 检查通过”。真实 Open 在这些诊断运行中没有出现打开失败，不能将其写成已经动态验证过该失败分支。检查也不核对每条 payload 的身份与内容，不能推广成任意状态下不丢数据或绝不会损坏数据库的证明。

文档已正确排除崩溃、断电、其他程序及一般性“无害”结论；保留这些限制，不新增豁免。

## 四、隔离、默认行为与工作流结论

1. `SPECMETRY_M14` 必须精确为 `1` 才开启；本轮独立执行默认测试，两项均 SKIP。常规三平台 CI 日志也均明确列出 SKIP，不是诊断压力测试通过。
2. TestMain 只登记两个新的测试辅助入口；未启用时不会启动它们，没有新增生产行为。
3. 参数的负数／非整数会失败，过大值会截到上限，`M14_FACTS=0` 在 Open 轮次测试中被提升为 1；其他零工作量问题见 B1。
4. 工作流限定诊断分支及相关路径的 push，并支持 workflow_dispatch；文档变化不触发 push 诊断。权限仅 `contents: read`，没有 PR 写入、部署或生产数据访问步骤。手动触发的可用性需要默认分支已有工作流。
5. 实际 Actions 的 bash 使用 `-e -o pipefail`，所以 `tee` 不会掩盖 go test 的非零退出。Results 的兜底只负责展示，不会把前一个已失败步骤变成功；当前绿色误判来自测试自身 B1，而非该管道。
