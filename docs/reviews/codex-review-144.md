## 3. 唯一阻塞：B-143-2-R

### 3.1 位置与冲突

位置：[限定取证计划](../wp2.5-c9-limited-evidence-plan.md) §6.4 第 471、480～485 行，§7.1 第 514～522 行；直接依据为 [实施计划](../wp2.5-implementation-plan.md) §12.14 第 13 条，第 1717～1730 行。

第二稿已经给**写者**规定“每次建立、写入、关闭之前重新读时钟，已到 D 不开始”。但是新增收尾顺序仍有两处未兑现同一个规则：

1. 第 481 行只检查 **m.Run 刚返回时**是否已经到 D。随后第 482 行允许父端等待非收尾记录／W，再无条件取快照、发收尾信号、登记并启动诊断；没有规定等待返回之后的重新准入。第 483 行的诊断等待写者终态之后，又直接进入一串新的标准错误写入，未列出对应的截止复核。第 471 行的主语只是写者，不能直接充当这两个新接点的守卫。
2. 第 517 行把保持暂定结论 3／4 的条件写成“**当且仅当父端最后一次消费已发布的状态时**”写者和诊断都已成功。该条件检查的是读取快照时的完成知识，未检查完成／发布是否在 D 之前。第 485、517 行又要求晚到成功不恢复结论；第 521 行将非零收尾解释为未在 D 前完成。两套规则不能由“最后看起来成功”同时兑现。

这里不是要求调度器在 D 精确唤醒，也不是要求系统调用硬实时返回；恰恰因为不具备这样的保证，等待返回后已知过期的决策、以及晚到成功是否有资格进入最终有效结论，必须写清。

### 3.2 可达事件序列一：等待返回后启动新诊断

设 W=110 s、D=120 s（只是同一绝对期限的相对表示）：

1. m.Run 在 109 s 返回，故第 481 行的检查允许继续。
2. 父端按第 482 行等待记录终态或 W。W 到达，但父端直到 121 s 才恢复执行；不需要外部调用持锁，也不假定任何异常的时钟倒退。
3. 按该步骤的文字，父端现在仍取快照、发收尾信号并登记／启动诊断。诊断又按第 483 行开始输出。
4. 此时应走已到 D 的失败／未完成／持有出口，不能凭 109 s 时通过过检查就启动 121 s 的新诊断。

父端自身没有同步打印这一点已经修好，但不能因此省去其对新任务的准入。应在这次等待返回之后重新检查当前时刻，并明确直接进入同一到期出口。

### 3.3 可达事件序列二：最后的成功状态晚于 D

1. 非收尾的 R／F／O 已终态，暂定结论为 4；写者与诊断正常开始收尾。
2. 写者最后一次 manifest Close 在 D 之前获准开始，却在 D 之后才返回 nil 并发布。单次 Close 没有硬实时上界，计划也没有要求这样的上界。
3. 诊断从等待写者状态的步骤恢复，按第 483 行写哈希与终结行并发布“完成”。父端也可能尚未获得调度。
4. 父端恢复后按第 484 行读取一次状态：全部成功已经发布。**第 517 行明写的充要条件满足**，会保持结论 4／退出 0；但第 485 行及既有 §12.14 要求这次晚到完成不能使运行成为有效完整证据。

更小的边界也要覆盖：终结行的实际写入已在 D 前返回，但“完成”直到 D 后才发布；仅凭看到完整日志，不能替代计划要求父端可消费的及时完成知识。

这里的错误不是“正常调度下一定假通过”，而是正文的一条明确终判规则允许接受另一条规则禁止的结果。当前没有实现，不能假定实现者会自动补上缺失的完成时点或到期锁存规则来消除冲突。

### 3.4 影响与最小修订方向

**影响：**B-143-2 尚不能整体关闭；新增记录链可能在已知过期后继续启动诊断工作，或把截止后才取得的完整状态算成有效结论 3／4。LE-10 若被选择，这会进一步对应退出 0，因此不是仅影响诊断文字的精化。

最小修订，不扩大预算、不重设 pidfd 协议：

- 在 m.Run 后的等待、诊断等待写者、每次诊断外部写入返回后的**后续新动作决策点**，明确重新核对原 D；到期不登记新诊断、不开始下一次写入，只保留已启动任务和已发布结果。
- 写定什么叫“D 前已经完成并可供消费”。可采用带截止资格的持续结果或等价的到期锁存方案，但须使第 517 行与这一定义一致；不是在审查中替作者选具体实现。
- 明确父端最后消费的是已经确定的截止资格，而不是把读取快照时的当前成功状态追认成 D 前成功。到期与完成竞争的两种顺序都须唯一；晚到成功不能消除已经成立的未完成。
- 保留原有及时成功路径：若必要结果已在 D 前按规则完成／发布，只因父端之后才恢复，不应无依据地改写成失败。它与“D 后才发布成功”需要可区分的证据。
- 用文档固定推演覆盖上述两例，以及及时完成、写入失败、原暂定结论 1／2、日志写完但完成未及时发布。现在只须修订规则及独立预期，不要求运行实验。

上述属于同一条新增收尾链的残余，按一项计。既有驱动／pidfd 的已关闭问题不因此重开。

### 4.2 R／F／O 的责任与判定

修订已消除 Review 143 的两种相反结果：负向对照在 F 内预期出现 J 错误，不会单凭该错误使 R 失效；但也不会因找到了这个理由而吞掉额外真实错误。

- R 保留真实采集、身份／读取、A/B、S/K 与 LC-1 的结果。LC-1 的真实 h1 不符是 R 的 J-4／未完成，不是用“对照通过”覆盖真实身份不符。
- F 每个变体有自己的登记、任务和结果，使用同一套相关检查。外层逐项比较站点、类型、来源、次数、完整成立／失败／未评估集合、进入记录和控制协议终态；不能只数错误条数或匹配错误文字。
- O 持有准备／清理与记录链的责任。F 的预期拒绝不豁免 O 的删除失败、关闭失败或未知，也不豁免 R 的真实失败。

- §5.5 第 388 行要求被测任务和资源在 W 前终态；第 394 行“完整预期逐项相同”必须包含这一条件。截止后才收齐结果不能按最后快照倒填及时命中，实施审查须核对这一接线。

## 5. B-143-2 已成立的部分及剩余证据边界

除 §3 的残余，§6.4～§6.5 已比第一稿具体且可追责：

| 出口／接点 | 静态评价 |
|---|---|
| 目录、记录文件、manifest | 唯一写者先登记；父端不直接执行文件操作；建立、写入、Close 都锁外执行并发布真实结果 |
| 第 k 个文件建立失败 | 已打开的前 k−1 个对象仍归写者，各一次关闭；到 D 的守卫优先，不因失败出口重取预算 |
| 写入失败 | 不继续写记录，不建立 manifest；保留未写入项，对已打开对象按既有截止收尾 |
| Close 失败 | nil 才确认释放；错误持续，释放未知，不重复 Close；不能仅因任务返回或测试进程退出写成已释放 |
| manifest | 只有记录文件写入及关闭全部成功才开始；自身 Write/Close 也须成功，不能只靠存在或哈希相符判健康 |
| 诊断失败／挂起 | 父端只消费状态；失败或未完成不能保持 3／4；剩余任务及对象仍有持有者，不同步补打印 |
| 写者等待收尾 | m.Run 返回后父端发信号；诊断等待写者，写者不等待诊断，因此未发现这条顺序本身形成循环 |
| 原暂定结论 1／2 | 锁定不改善，也不重新细分；其后发布的成功／补救不能恢复有效证据 |
| 日志完整但状态未发布 | 单有字节不等于任务完成。第 517 行要求已发布；其截止资格仍须按 B-143-2-R 修订 |

“全部非收尾记录终态”只有在实际协议的每项必要结果都已消费时，才能支持之后只剩写者／诊断。`Done` 或外层测试返回不是这种终态的替代品。第二稿已引用完整协议而非仅引用测试结果，固定实现审查仍须逐项验证。

**记录范围必须按 §6.4 第 485 行理解。** 快照之后的晚到结果保存在持续持有者中，不保证进入 artifact；某些失败运行可能只留下部分记录。这不会使该运行变有效，但也不能称其 artifact 保存了所有最终错误。§7.1 第 525 行“任一结论都保留全部记录”宜精化为已取得的持有记录与实际完成保存的记录分层，避免向交接者许诺全部晚到结果均已落盘。该处作为非阻塞的可追溯性精化处理。

在实现格式中须分清有限的记录前缀、收尾摘要与写者／诊断自身的状态：发布字节计数、哈希和完成状态，不应不断生成要求同一写者再写一次的“我写入了记录”记录。当前“发布状态”和“追加记录”是不同操作，未发现正文必然要求无限自我追加；§8.1 可以固定它们的序号和封口边界。不能在实现中把这项区分留给日志格式猜测。

manifest 证明的是列出的保存字节；终结行证明的是诊断已输出的声明。它们**不能单独证明真实 Close 成功**。需要固定实现中“全部真实结果成功才建立 manifest／发布成功”的实际接线，以及正确的最终退出；本轮只是审查这一条件关系，不把候选文字当成已经运行的证据。

LE-6 的“不含 Sync”是明确提案，不因这一点要求新增 Sync。Write 成功的含义仅限正常操作系统语义下字节已交付；不能扩大成 runner 崩溃持久性、上传成功或完整 artifact 保证。§6.5 另核对 manifest、字节数、哈希、终结行及身份，缺失即降级，方向成立。
