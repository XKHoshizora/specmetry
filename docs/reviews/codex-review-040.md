## 二、BLOCKER

这里的 BLOCKER 指准备报告的技术依据或开工结论必须修正；不是把尚未实现的 M2 草案当作已经上线的代码漏洞。

### B1：Q1 的结果映射不满足现有 EV-04，127 也不能反向证明命令不存在

**位置**：[m2-readiness §5.1，第 190～194 行](../m2-readiness.md#L190)；[MVP-EV-04](../acceptance-criteria.md#L171)。

现有验收要求“检查命令不存在 → `error / not_found`”。草案却规定 cmd／PowerShell 无法区分时一律记为 `fail / nonzero_exit`，并把该选择归为“实施细节”。这实际改变了结果和失败类型，不能在不修改契约、未经负责人批准的情况下实施。

另一个方向同样不成立：`sh -c 'exit 127'` 是明确主动退出，不能仅凭 127 就判为没有找到命令。POSIX 分别规定了命令查找失败的 127 和 `exit n` 的指定退出状态；相同数字没有携带产生原因。[Shell Command Language](https://pubs.opengroup.org/onlinepubs/9799919799/utilities/V3_chap02.html)、[exit](https://pubs.opengroup.org/onlinepubs/009695399/utilities/exit.html)。

**独立复验**：Windows 临时目录中，cmd 执行主动 `exit /b 1` 和一个不存在的随机命令，均返回 1。这证明数字本身不能提供草案所需的可靠区分。sh 复验因 MSYS 启动失败未执行，不能声称已在本机复现其 127 对照。

**影响**：缺失命令被错误记作普通检查失败，或正常存在的检查被错误标成 `not_found`；结果、错误类别和验收证据不一致。

**最小修正**：把“解释器可用性”“启动失败”“shell 脚本执行结果”分开。删除“127 足以证明不存在”的结论。对 EV-04 的适用命令形式、各 shell 能提供的可信诊断及无法判定时的处理，提出明确方案：要么能满足原契约，要么将受限保证／结果分类变更列为新的产品取舍，并同步验收。无需在本 PR 实现通用 shell 解析器。

### B2：Q3 在复核之后没有持续排除外部活动，不能保证不兼容数据库在原库修改前被拒绝

**位置**：[恢复第 10～12 步](../m2-readiness.md#L316)、[外部并发说明](../m2-readiness.md#L380)；[PD-23 与实施计划 §8.1](../implementation-plan.md#L323)。

第 10 步之后还要对副本执行 `VACUUM INTO`、发布备份和轮换，之后才进入第 12 步。这个窗口包含可能耗时很长的完整备份，不能当作可以忽略的瞬间。

**源码级反例**：第 10 步比较通过后，外部 SQLite 程序修改 schema／`min_binary_version` 或日志状态；第 11 步生成的仍是旧副本备份；第 12 步对已经变化的原库建立读写连接。SQLite 可能先回放热日志、改变日志状态，或由连接配置切换 journal mode，再执行应用层版本检查。检查最终拒绝，并不能撤销这些先发生的文件副作用。

现有 [store.go](../../internal/store/sqlite/store.go#L111) 特意先执行只读版本检查，再建立读写连接；[DSN](../../internal/store/sqlite/store.go#L346) 包含 `journal_mode(WAL)`。普通打开的这一顺序不是恢复流程可以省略的保证。SQLite 对热日志的恢复发生在读取数据库内容之前，参见 [SQLite locking §4.1](https://www.sqlite.org/lockingv3.html#dealing_with_hot_journals)。

`.migrate.lock` 只协调 Specmetry；一次锁探测不能阻止之后的新活动，也不能普遍证明所有 SQLite 连接均已关闭。复制前后文件指纹相同，只证明两次观测值一致，不等于整个复制期间持续静止或已经取得 SQLite 一致性快照。副本的 `integrity_check` 也不能反向证明原库与副本在随后打开时仍是同一版本。SQLite 对原始文件复制的安全前提是复制期间没有事务活动，并正确保留相关日志，见 [SQLite backup/corruption guidance](https://www.sqlite.org/howtocorrupt.html#_backup_or_restore_while_a_transaction_is_active)。

**影响**：草案可能在最终报告“不兼容”之前修改原库文件；所保留的备份还可能早于外部已提交内容。这超出既有 STO-02 的两项有限例外，不能凭“SQLite 自己做的”或“已记录窗口”自动接受。

**最小修正**：报告中明确保留一个尚未解决的安全前提：如何从一致性复制／兼容性检查一直保护到 SQLite 原库连接接管。需要可验证的跨平台协调设计，或者单独提出离线操作前提及相关保证变更，由负责人决定；提示关闭其他程序本身不是排他机制。不能笼统断言原始锁方案都不可能：POSIX 描述符关闭和 Windows 句柄冲突说明方案必须审慎设计，不构成所有协调方案均不可行的证明。本准备 PR 不必实现新锁或重构存储层，但必须删除已经满足严格保证的暗示，并为 WP2.10 保留明确门槛。

### B3：Q3 的清理、备份和失败阶段与“拒绝后不变”互相矛盾

**位置**：[恢复第 3～4 步](../m2-readiness.md#L299)、[第 11～13 步](../m2-readiness.md#L317)、[拒绝契约与 STO-10～13](../m2-readiness.md#L350)。

有三个直接的流程反例：

1. 开始时已有 `recover-<ID>/` 遗留目录，第 3 步先删除；第 4 步判断不适用并声称“什么都不改”。结束目录项已经不同，违反 STO-10 的同样表述。
2. 第 11 步已发布备份并按保留三份进行轮换，第 12 步随后因版本或一致性失败。此时不能同时保证“拒绝不生成备份、目录项不变”。轮换甚至可能已经删除原有备份。
3. 原库读写打开后失败或进程被终止，不应只描述为“原库未变或已经恢复”。它可能仍需要下一次 SQLite 恢复；必须保留日志并报告恢复未完成／状态未确认。

临时副本经过墓碑处理后再生成保留备份，是合理方向；但含原始数据的中间副本、清理失败、崩溃遗留及备份轮换都属于生命周期契约。不能仅以“不承诺物理擦除”替代逻辑删除和失败报告要求。

**最小修正**：建立阶段化结果表，至少分为“未打开原库的拒绝”“已生成备份但未打开原库”“原库已打开后的失败”“崩溃遗留的后续处理”。区分本次新建临时文件与原来就存在的遗留项；明确何时允许清理和轮换、清理失败如何报告。需调整保证的部分单列待批准例外，不能借恢复命令放宽普通 Open 或 doctor。保留备份仍应经过墓碑与整理；临时路径需使用既有私有文件／目录机制、确认删除成功，并在 purge 和崩溃恢复验收中覆盖。

## 三、NON-BLOCKER 与实施前补充

### N1：Q1 的解释器选择和参数实验不足以支撑通用结论

[第 179～188 行](../m2-readiness.md#L179) 的方向有价值，但需补充以下细节，最晚在 WP2.5 开工前冻结和验证：

- “绝对路径”不等于“不来自 worktree”。例如 PATH 含某个 worktree 的绝对 `bin` 目录，在 Git 安装不提供 sh 而走回退时，仍可能选中其中的解释器；符号链接／目录联接还可能隐藏真实位置。需要明确规范化、实际目标身份及工作区排除策略。`git --exec-path` 必须沿用受控 Git 环境，不能重新继承 `GIT_EXEC_PATH` 等注入变量。
- sh、bash、cmd、pwsh、Windows PowerShell 应分别定义适配器及测试。少量字符串实验、特别是 Windows PowerShell 只测一个字符串，不能推广成全部目标解释器的正确性证明。Go 文档也明确 Windows 命令行由目标程序自行解析，cmd 是不同于常规规则的例子：[os/exec](https://pkg.go.dev/os/exec#Command)。
- “统一 sh”统一的是默认解释器种类和语言约定，不是三个平台拥有同一二进制或相同执行环境。用户继承的 BASH_ENV 等启动行为也需要如实说明。
- 使用 GetSystemDirectory、禁用 cmd AutoRun、PowerShell NoProfile 是合理方向。Git 的存在不能证明每一种 Windows Git 安装都附带报告所需的 sh；CI 必须明确准备和验证所需解释器。
- Unix 进程组、Windows Job Object 是候选机制，不是已完成的整棵进程树证明。Windows 需避免“启动后、加入 Job 前”子进程已经逃逸的窗口，并验证 Git Bash 后代；取消、超时、输出管道与等待回收均需测试。主动脱组等不受该机制覆盖的边界不能自动写成已接受保证。

这些不是当前生产实现的新漏洞，也不要求准备 PR 立即完成全部平台实验。

### N2：Q2 需要明确“对象缺失”的层次，不能只根据 ls-tree 成功判定

**独立 Windows 最小复验**：在无远端、所有传输禁用的临时 SHA-1 仓库中，建立引用不存在 Blob 的有效 tree／commit。`ls-tree <commit> -- missing.txt` 返回 0，并列出 `100644 blob 111…111`；`cat-file -e` 同一 OID 返回 1。

所以 [第 244～262 行](../m2-readiness.md#L244) 需要区分：

1. 提交／祖先树无法读取；
2. 提交树中没有该路径；
3. 路径条目存在，但叶 Blob 不在本地；
4. gitlink 指向的子模块提交本来不存于上级仓库对象库。

应明确只保证读取路径元数据，还是也要求相关叶对象可读取。若后者是目标，需增加受 PD-26 门禁保护的相应检查，且不能把正常 gitlink 按上级库缺对象误拒。若只读取元数据，应收窄“对象缺失一律退出 6”的文字。

mode／type／OID／路径的结构化记录有充分理由；本轮还独立验证了同一 Blob 可同时对应 `100644` 与 `120000` 条目。需要同步 data-model §4.11、§4.13、§6.2／§6.3 和比较规则，不仅修改存储说明。末尾斜杠、分隔符与路径规范化还应与 M1 已保存配置、check_config_hash 保持一致，不隐式改变旧配置。生产输入读取仍须固定到 head_start，不运行 LFS、子模块或其他过滤器。
