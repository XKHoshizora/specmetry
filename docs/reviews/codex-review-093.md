## 3．B2-R1：可关闭的知识状态修订

核对[§19.7矩阵](../wp2.5-check-runner.md#L1719)、[U维度](../wp2.5-check-runner.md#L656)、S1／F1、A6／A12、§11.4、P-4和§111：

| 情形 | 修订与裁定 |
|---|---|
| 返回0 | 仅证明此前未挂起／可被调度；用户代码可能执行过，实际开始时刻未知。即使立刻终止且用户指令从未获得CPU，也不违反这项说明 |
| 返回1 | 解除了最后一层挂起，按协议视为已启动；不证明指令执行恰好从返回时开始 |
| Unix Start成功 | 同样只是协议启动和计时边界，不认证实际指令执行或其精确起点 |
| 返回-1、>1、多线程快照 | 保守记为可能执行过；不拿失败、当前仍挂起或线程数量证明从未执行 |
| 退出状态／树结束 | 主进程状态与Job／进程组是否结束分开；取得主进程状态不证明后代全部结束，恢复异常也不反推出开始时刻 |
| U与输出 | U中的“已运行”已明确定义为按协议启动；恢复异常写“可能已执行”，写入失败也不升级成确定执行或降成未执行 |
| P-4 | 预先恢复／额外挂起要求夹具命中记录；当前挂起计数不再用作历史执行证明，没有标记文件也不证明未运行 |

这些表述与[Microsoft ResumeThread文档](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-resumethread)提供的挂起计数／恢复状态相称。记录一个协议起点是合理的工程定义，不等于恢复了原先“返回0证明已经执行”的错误事实。

[1719行](../wp2.5-check-runner.md#L1719)现在把无其他恢复者写成推出“确定未运行”的工程前提，明确不是D7豁免、不是新增保证例外；有异常证据时仍保守报告、终止、确认、移交。**N-092-1可关闭**，本轮没有批准抗干预保证调整。

矩阵中退出状态列新采用的S3前／后分法，其**信息保留及因果推论**仍有§4的问题；不因此否定已修正的API执行知识，也不把B2-R1的关闭扩展为整项B2关闭。

## 4．BLOCKER：B2-R2的残余

### 4.1 观察在S3之后，不是丢弃可靠退出码的既有依据

**位置：** [§6.2:309](../wp2.5-check-runner.md#L309)、[§10.1:989～1005](../wp2.5-check-runner.md#L989)、[§19.7:1774](../wp2.5-check-runner.md#L1774)、[真值表:1894～1898](../wp2.5-check-runner.md#L1894)、§111事件推演，以及P-4和Q-2对该规则的引用。

本轮将“主进程正常退出”重新定义为**进入S3之前可靠取得**的自行退出；S3之后才取得则把exit_code置NULL，理由是可能由Specmetry的终止造成。它没有仅解决异常A6的无条件NULL，而是为正常启动、异常启动乃至其他context_changed行增加了一个观察时点的保留门槛。

必须分别保留五种事件：

1. 进程实际退出；
2. 父端观察到退出通知／句柄已发出信号；
3. 父端可靠读到退出状态；
4. Runner决定进入S3；
5. Runner实际发出终止请求及其结果。

固定文档[1545～1546行](../wp2.5-check-runner.md#L1545)自己已说明：t_main是可靠取得信息的父端事件；t_S3在任何身份核对或终止调用之前，甚至可能根本没有发出终止。因此，t_main大于t_S3不意味着实际退出晚于S3，更不证明终止的因果。

以下均为合法静态事件序列，不是新机制实验。以恢复异常进入A6为例，实际开始时刻始终未知、时间使用t_S3−t_anom，假设退出码可靠读到7，Job后代仍未确认结束：

| 事件序列 | 当前固定稿的结果 | 问题 |
|---|---|---|
| 主进程在S3前已自行退出；父端在S3后才读取到7 | NULL | 读取晚没有使已经存在、后来可靠取得的状态变成未知；正是Review092要求保留的那类信息 |
| 进入S3；尚在身份核对／终止准备中，主进程自行退出；先取得7，再发终止请求 | NULL | 本次退出发生在实际终止请求之前，不能把它按已可能由该请求造成来抹掉 |
| 进入S3；终止请求失败；随后主进程自行退出，可靠取得7 | NULL | 请求失败不等于导致退出；保留数值与不知道退出因果是两件事 |
| 主进程状态已知为7，Job查询失败或后代未结束 | 仍须A6，context_changed、不合格；数值却受S3前后限制 | 已知主进程信息不能由整树未知自动作废；也不能由保存7反推整树已结束或开始时刻已知 |

即使一般情况下确实无法区分自行退出与终止造成的退出，结论也应是**因果未知**，不是**数值未知**。[GetExitCodeProcess官方契约](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-getexitcodeprocess)给出进程终态数值；其来源可以是应用、终止调用或异常，不附带这里需要的因果证明。[进程终止说明](https://learn.microsoft.com/en-us/windows/win32/procthread/terminating-a-process)也将实际终止／对象发出信号和随后查询分开。需先确认进程已结束，不能把STILL_ACTIVE单独当作终态；本报告也没有把数字本身当作执行成功证明。

原固定base及上轮活跃§6.2、§10.1，在D19/context_changed下要求保留可靠取得的正常退出码，并未设置“S3之后读取一律丢弃”的门槛；Review092的最小修正也明确要求不要静默抹掉已知退出信息。原[§6.1:292](../wp2.5-check-runner.md#L292)还承认Windows被他人终止的任意码与应用退出不可区分，照实际码处理。现有语义从来不是“只有证明某个数值出自用户自己的退出，才知道这个数值”。

**裁定：这是主动不保存一部分已知信息的新记录政策，不是因果可以由观察顺序推出的技术澄清。** 它不改变qualifying公式，但会改变事实／回执中的数值和诊断能力，故也不能因为不加字段就视为没有契约变化。§10.1标题将整套规则标为“D19，产品已决定”，§111称异常不抹掉可靠状态，而实际只保留其一个子集，依据不足。

**最小修正方向：** 撤回这个额外的S3读取时点门槛。分别处理“是否可靠取得及其值”“启动类别决定的时间区间”“result/failure_kind的优先级”；保留既有Unix信号NULL、未取得NULL及命中timeout时的显式规则，不从数值推断退出原因。若负责人确实希望只保留某一截点之前的数值，须另列其准确范围、信息损失和展示影响，作为**待决定的新选择**；不能借Q-2只涉及A12的决定覆盖已写定的A6或全部正常启动路径。负责人可以拒绝该扩展，采用原信息保留规则，不必为了修正文再新增产品选择。

### 4.2 S3与“第一次终止请求”尚未同步，验收仍有两个口径

**位置：** [data-model §4.11:379](../data-model.md#L379)、[EV-28:196](../acceptance-criteria.md#L196)，对照[§10.1:990、1001～1002](../wp2.5-check-runner.md#L990)、[§19.2:1546](../wp2.5-check-runner.md#L1546)。

- 规范按**进入S3**分割退出状态，异常duration=t_S3−t_anom。
- data-model却按**终止请求之前／之后可靠取得**分割退出状态；异常duration写“到第一次终止请求”。
- EV-28新增异常条款写的是**主进程在进入S3之前自行退出**，不是退出状态在S3之前被可靠读取；正常D19段落又保留“第一次终止请求”的时长描述。

例如：t_anom=10，t_S3=11，可靠读到退出7的时刻为12，实际终止请求到14才发生（单位只用于说明事件顺序）。规范要求exit_code=NULL、duration=1；data-model的字面规则要求保留7、duration=4。若身份检查失败、根本未发终止请求，后者的区间终点甚至不存在。另一个例子：实际退出在10.5，读取在12，EV-28的“在S3前自行退出”要求保留，规范却丢弃。

不能靠“§10.1是唯一定义”的标题，同时保留规范来源data-model与正式验收中的不同事件。应把每个引用统一成**明确的父端协议事件**；若沿用已澄清的t_S3，写“进入终止阶段／决定终止”，不要继续写成必然实际发生的首次请求。若选择实际请求事件，必须处理请求尚未发出、永不发出和失败的分支，并重新说明预算／时间含义。本轮不替负责人改变时间保证，也不要求为了时间戳向未知对象发信号。

另有非阻塞的精化：990行的`t_main ≤ t_S3`应是既定事件顺序的示意，不宜仅靠两个时钟读数的大小识别先后；有限分辨率下两个不同事件可能得到相同读数。需要保留哪一个状态，应由实际读取／阶段转换的顺序判定，不能把数值相等扩大成已经证明发生在转换前。

### 4.3 正常路径的影响应单独说明

正常Start／返回1仍使用t_start到t_main，已知协议边界与实际执行起点的区别只是正确收窄证据。恢复异常改用t_anom且不倒推实际起点，也有合理且清楚的方向。started_at按相应事件采样挂钟、finished_at在写事务之前采样，不参与seq或推导，没有发现必须另行增加字段的问题；无进程时duration=0继续保留。

**但新的退出码截点已扩展到正常路径**，不能因主要修复对象叫Windows异常就忽略它。逐项裁定：

- **超时**：命中timeout且整树已确认时，§6.2第4条明确NULL；F1优先命中D19则按D19，不应把两种记录混为一类。若timer已先触发，但进入S3前状态读取又完成，通用字段表的“正常启动、S3前取得就保存”与timeout显式NULL还需写出分类优先级；不要让一张脱离result的字段表隐含覆盖§6.2。
- **普通取消**：树已确认、写事务前取消仍不记录；不能为取消凭空产生一行。取消与F1叠加时按D19，已知信息也不能仅因取消或S3标签丢失。
- **D11**：先可靠取得主进程退出、再进入S3清理后代的通常路径，当前仍保留数值；这一正确对照不能证明其他晚读取路径没有信息损失。
- **D19**：整树未确认与主进程状态已知可以同时成立，退出码、duration、树状态和qualifying必须各自裁定。保存可靠数值不等于认定它是用户命令自身造成，也不使不合格行变合格。

**总裁定：B2-R2未关闭。** 上述是同一字段修订的具体残余，不是要求重审Runner全部机制。无需新原型即可用事件序列和条文修正验证。
