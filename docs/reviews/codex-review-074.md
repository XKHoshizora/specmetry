## 三、B3-R1-S：独立预算与封闭入口的审查

### 1. 原预算矛盾已经消除

[§8.3 第 433～439 行](../wp2.5-check-runner.md#L433)、[§8.5 S6 第 487～503 行](../wp2.5-check-runner.md#L487) 和 [时限第 548～556 行](../wp2.5-check-runner.md#L548) 同步为：

1. 正常排空 D 阶段，最多 T_drain；
2. 到期则停止读取；F1、S1 终止未确认跳过 D 阶段，直接停止读取；
3. 自停止读取起，使用**独立**的 T_join 等待复制返回；
4. 在进入后续处理之前封闭本次全部复制入口。

最长时间公式增加 T_join，不再要求在已经用尽的 T_drain 中等待复制任务返回。复制提前出错已经是 O2，仍走封闭入口这一收尾接点；不需要为了等待不存在的正常 EOF 再走完整 D 阶段。

S1 没有创建进程的情况没有消费者，关闭自持写端并处理空输出；S1 管理失败但终止已确认，输出按 O1/O2；未确认时明确进入停止读取/J 阶段。F1、取消的管道路径均使用同一协议，不重新采用“遗弃普通 Writer 即完成收尾”。实现阶段仍须测试这些接点的资源关闭与预算起点。

这些是协议规定的有限等待预算，**不是操作系统硬实时调度保证**。封闭还要取得锁，锁内追加必须有限、无外部 I/O/用户回调；不能将 X15 的立即完成外推为任意调度下的绝对时限。最终向真实 stdout/stderr 写文档的阻塞另有明确披露，不属于检查收尾预算。

### 2. O1、O2、O3 不再互相冒充

| 结果 | 能证明的状态 | 不能据此声称 |
|---|---|---|
| O1 | 复制返回、EOF 且全部字节写完；唯一的 E-drain | 整个进程树由输出完成单独证明结束 |
| O2 | 复制已经返回，转发不完整 | 输出已经完整排空 |
| O3 | 未确认复制返回，但本次复制入口已封闭 | 任务已经结束、读端和入口引用已经释放 |

[第 512～515 行](../wp2.5-check-runner.md#L512) 明确保留 O3 残留任务。第 3 版“未确认结束即 internal/1”却又“只有确认才返回”的冲突已经撤回；O3 候选按 F2 处理，报告不完整与未确认结束，产品选择仍归 D20。

O3 的正确解释是：任务继续持有其读端/入口引用；若继续产生写入，旧入口拒绝它，复制可以因写错结束；若永远阻塞在 Read，**封闭入口不会让这个 Read 自动返回，也不会让该对象自动释放**。文档的“直到读端对象被释放”不是一个已完成的释放机制，不能依赖普通 GC 消除仍被任务持有的引用。其资源处置及是否允许同进程继续调用，仍明确留在 T1/T6 冻结前规格中。

这不是已接受的泄漏风险，也不是已经证明可无条件重复使用宿主。它足以支持准备文档准确披露未完成项，不足以支持生产实现验收。

### 3. 封闭点的静态论证成立，但依赖具体同步规则

[§9.1 第 674～686 行](../wp2.5-check-runner.md#L674) 的候选契约为每次执行/每个流分配独立复制入口，所有者入口单独持有权限，全部写入及封闭由目的端同一同步规则串行化。

要兑现这条契约，复制入口的 **closed 检查、数据追加、seal** 必须处于同一临界区，不能在锁外先读取 closed、之后仅给 append 加锁。按该规则：

- 已进入临界区的追加，在 seal 能完成前就已完成，归属于封闭点之前；
- 正在等待锁的旧写入，取得锁时检查已封闭，不能追加；
- seal 返回后发生的旧入口写入全部失败；
- 后续调用新建入口，不能把旧入口重新打开；
- 所有者可在 seal 后写最后文档，复制任务无权借所有者入口继续写入。

这与 [Go Mutex 的同步关系](https://pkg.go.dev/sync#Mutex) 相容。本轮只确认该协议可实现，不把尚不存在的 Go 类型当成已检查的代码。普通 Writer 仍按候选契约启动前拒绝，不能把以上证明推广到任意 io.Writer。

### 4. 别名、容量与最终文档的保证范围

两个流共享同一受控对象时，同一锁允许各次追加串行化，但两路检查输出仍可交错。两个调用共用对象时，各自入口独立，整体文档之间也可出现其他调用的输出。内部并发检查还受 Linux 排他区间约束；这里不是授予并发调用新能力。

**一次文档整体加锁仅保证字节不被复制写入插入，不保证 Write 一定成功。** 复制达到容量上限是 O2；所有者文档写入失败或短写，必须进入 §8.6 C2/§11.4，保留事实、exit 6，不能追加第二份文档。容量预留、所有者容量规则及内存错误策略应在 T6 定稿，不需要审查代选。

同一底层对象已经收到检查输出时，即使文档随后整体写入，**整个别名流也未必是一份 JSON**。第 701 行保留调用者合流的既有例外；只能在 stdout/stderr 未被合流的前提下要求机器 stdout 恰好一份文档。默认 JSON 转发使用 stderr，不能把 stderr 的迟到输出直接说成 stdout 污染。

正文关于“最后文档完整”的概括应按“所有者写入成功时，文档字节完整且不被复制输出插入”理解；失败路径已经另行定义。建议使概括措辞更明确，见 NON-BLOCKER N2。

### 5. 继承路径与提前出口

真实文件继承路径没有复制任务，不使用封闭入口证明其进程已经结束。F1 下残留进程仍可能写文本 stdout/stderr；JSON 正常分流时只得到 stderr。既有合流例外、D7 未批准及树未确认的事实均保留，不能因内存目的端的新机制而扩大进程树或 JSON 豁免。

**裁定：B3-R1-S 在准备文档层面关闭。** 封闭不等于回收的差别已经写清；独立原型只支持必要的线性化机制，不替代 T1/T6 或未来生产测试。

### 2. 现有接口足以支持保守分类

独立读取 [DB.WriteTx 第 382～388 行](../../internal/store/sqlite/store.go#L382) 和 [withTx 第 406～415 行](../../internal/store/sqlite/store.go#L406)：

- BeginTx 成功后才进入外层事务函数；
- checkWritable 在调用 Runner 的函数体之前执行；
- 函数体返回错误时走 Rollback，不进入 Commit；
- 函数体成功返回后才调用 tx.Commit，并直接返回其错误。

因此，**按每次写入独立初始化的函数体成功标记**，可以保守分类，不需要修改存储接口：

| 路径 | 本次函数体成功标记 | WriteTx 最终结果 | 合理分类 |
|---|---|---|---|
| BeginTx/写锁取得前拒绝 | false，函数体未调用 | error | 本次未提交 |
| checkWritable 拒绝 | false，Runner 函数体未调用 | error | 本次未提交 |
| Runner 写入/执行项校验失败 | false，函数体未成功返回 | error | 提交前失败，未提交；校验错误为 internal/1 |
| 函数体成功，Commit 返回错误 | true | error | **结果不确定**，不能从函数体成功推提交成功 |
| 函数体和 Commit 均成功 | true | nil | 已提交 |

这里的 true 只应在函数体全部写入、构造、校验均完成后紧邻 `return nil` 设置；它记录的是本次事务阶段，不是上一次执行的状态。未来实现需覆盖“上一项成功、下一项在函数体之前失败”，防止标记跨次复用。当前没有 Runner 代码，本轮确认的是规范可由现有接口兑现，不能宣称该标记的生产接线已经测试通过。

把函数体成功后的所有错误保守归为不确定，不需要猜测每个 SQLite 错误是否实际回滚；某些错误后来可证明未提交，并不使这个保守分类错误。没有观察到 Commit 结果时也不发布成功。已有 [database/sql 事务接口](https://pkg.go.dev/database/sql#Tx.Commit) 没有给 Runner 提供“函数体成功就已提交”的保证。

本轮不要求修改 WriteTx/withTx，不增加重试，不改变 M-15 或既有 SQLite 错误映射。无本次 COMMIT 的受控函数体失败与提交阶段不确定已分开，不把存储层原契约扩张成文件系统零变化。

## 八、独立验证、作者证据与未验证边界

### 1. 本轮实际独立运行

除固定对象/文档/必要源码核查外，在仓库外 review074 专用目录建立了一个 **PowerShell 7.6.7 / .NET C# 的最小门禁模型**。它不是 Specmetry 生产实现，也没有执行任何用户项目检查：

- 每个复制入口的 closed 检查与追加、seal 共用同一锁；所有者入口分开；
- 使用闸门模拟已进入写入、排队写入、J 阶段后仍待写入的任务，最后主动放行并 join；
- 所有任务使用 1～2 秒等待/回收上限；复核运行另有独立 **20 秒进程硬时限**，超限才终止自己的测试进程树；实际未触发；
- 首次执行退出 0；带硬时限的复核也退出 0，辅助进程已结束、stderr 为空，模型全部 Task 已 join，无遗留实验进程；无失败或失效夹具。

| 模型用例 | 结果/实际证明范围 |
|---|---|
| O3 点仍未结束，封闭后才放行旧写入 | 旧写入被拒绝；最后文档后没有旧追加；不证明永久阻塞 Read 已结束 |
| 写入已在临界区内 | seal 等它完成；其字节在封闭/所有者文档之前，不穿过封闭点 |
| 写入已排队等待锁 | seal 后取得锁时拒绝，不能凭排队前状态追加 |
| stdout/stderr 别名 | 文档字节未被插入，但含前置检查输出的整个流不能作为一份 JSON 解码；未夸大保证 |
| 复制达到容量上限 | 写入报告失败；封闭不改变已有字节 |
| 同一容量策略下 owner 文档也无法容纳 | owner 写入失败；加锁不等于成功，这需要 C2 处理，不表示现实 Runner 已有此实现 |
| 后续调用建立新入口 | 新入口可用，旧入口一直拒绝，不会因复用被重新启用 |
