### B-126-1：任意 Wait 错误返回都释放，不能保证子进程已回收

**位置**：§12.4，936～941 行；§12.6，1015～1019 行；对照 §12.12，1175 行；冻结规范 §19.4，1717、1730、1742 行；处理记录 §161，10268 行。

1015 行明确把成功、`*exec.ExitError` 和“其他错误”一律作为可释放出口；1175 行却要求释放时 `cmd.ProcessState != nil`。这两者并不等价。

固定 Go 1.27.3 中，`Cmd.Wait` 先取得 `state, err := c.Process.Wait()`，随后原样保存 `ProcessState = state`。Linux 的 `pidfdWait` 在真实 `waitid` 返回错误时直接返回 `nil, error`，尚未执行成功回收之后的状态更新。普通 Unix 等待链同样存在返回 `nil, error` 的分支。参见固定源码 [Cmd.Wait](https://github.com/golang/go/blob/2aae1000ea1d4b28923b96db28acf4e3b99d6aff/src/os/exec/exec.go#L936)、[pidfdWait](https://github.com/golang/go/blob/2aae1000ea1d4b28923b96db28acf4e3b99d6aff/src/os/pidfd_linux.go#L103)、[pidWait](https://github.com/golang/go/blob/2aae1000ea1d4b28923b96db28acf4e3b99d6aff/src/os/exec_unix.go#L36)。

**允许的事件序列**：Start 成功、共享租约持有→必要等待系统调用失败，未取得退出状态→`Cmd.Wait` 返回错误且 `ProcessState == nil`→按 1015 行释放→排他等待者取得租约。例如 Cmd 的输入输出直接使用文件、没有尚待完成的复制任务时，不存在复制循环替这个错误出口继续阻塞的前提。此时只是等待返回，未证明本次消费者结束／回收。这不是声称本轮观察到了某个原生 errno；它是源码明确保留、设计又明确包含的错误出口。后续基线检查不能代替共享租约契约，也不能将“未知”变为“已排净”。

**最小修订**：按可靠回收知识区分等待错误。已取得有效 `ProcessState` 的非零退出、复制或上下文错误可以保留原映射并按原规则释放；没有回收确认时不得只因 Wait 返回释放，须明确持有 Cmd、租约和错误的责任对象及返回路径。`started` panic 的 Wait 也适用同一规则。不要顺带增加重试、固定超时、终止策略或 C-4/D21 禁用条件。正反例须分别覆盖“已回收但返回错误”和“等待出错、回收未知”，不能只测取消的健康路径。

### B-126-3：os.Interrupt／os.Kill 是可变变量，不能直接当作已知信号常量

**位置**：§12.9，1072 行；§12.7，1045 行；§12.8，1052 行；§12.12，1195 行。

Go 将这两个导出对象声明为 `var ... Signal`，初始值分别为 SIGINT、SIGKILL，没有不可修改的类型或运行时约束；`NotifyContext` 则把实际参数交给 `Notify`。参见固定 [os 信号变量](https://github.com/golang/go/blob/2aae1000ea1d4b28923b96db28acf4e3b99d6aff/src/os/exec_posix.go#L21)、[NotifyContext](https://github.com/golang/go/blob/2aae1000ea1d4b28923b96db28acf4e3b99d6aff/src/os/signal/signal.go#L293)。

**静态反例**：一个 Unix 生产包的初始化代码执行 `os.Interrupt = syscall.SIGCHLD`，随后现有 `signal.NotifyContext(ctx, os.Interrupt)`。前者不是禁用对象的调用／取值，不触发现有对象规则；后者被 1072 行的变量例外接受，实际却登记 SIGCHLD。当前仓库未发现这种赋值；问题是拟议规则无法兑现“运行时由别处改变会被 C-9 禁止”的声明。

**最小修订**：变量例外必须以覆盖作用范围内的修改／地址逃逸检查和不变性依据为条件，或采用不依赖可变变量的已知信号调用方案。新约束及是否改变既有 main 接线须显式登记，不把它当成已冻结的要求。本轮不要求修改 main，也不要求对任意不可信机器码证明不变性。保留当前健康 SIGINT 对照，另固定“先修改、后调用”的拒绝对照。

### B-126-4：全源码导入器不能把 unsafe 当作普通源码包装载

**位置**：§12.10，1123～1129 行。

当前规则为“全部从源码做类型检查”，导入器只返回本次已经检查的包，却没有 `unsafe` 的特殊出口。固定 Go 自己的源码导入器在 `unsafe` 上明确返回 `types.Unsafe`；`unsafe/unsafe.go` 的 `ArbitraryType` 等声明只是文档占位，不能以普通源码检查所得包替代内建 unsafe 的类型、转换及常量语义。参见 [srcimporter 的特殊处理](https://github.com/golang/go/blob/2aae1000ea1d4b28923b96db28acf4e3b99d6aff/src/go/internal/srcimporter/srcimporter.go#L76)、[unsafe 源码说明](https://github.com/golang/go/blob/2aae1000ea1d4b28923b96db28acf4e3b99d6aff/src/unsafe/unsafe.go#L13)。

按现稿无例外地装载，会在需要真正 `unsafe.Pointer`／`unsafe.Sizeof` 语义的依赖声明或初始化表达式上失败，而不是得到可靠的完整类型信息。`IgnoreFuncBodies` 不跳过包级初始化、常量和类型声明，不能解决这一点。该闭包已经使用 unsafe，不是仅针对未来代码提出要求。

**最小修订**：明确 `unsafe → types.Unsafe`，不对文档占位包作普通装载；固定每配置的包身份／ImportMap、依赖缓存和导入完成规则。标准库没有普通模块元数据时的语言版本来源也要写明，不能对 `Module == nil` 直接取值。用包含 unsafe 常量、指针转换、包级初始化的固定对照验证装载。这里要求补齐既有方案的必要特殊规则，不要求新增依赖、预先编写分析器或改用另一种工具。

### B-126-5：Windows 同源对象表有直接漏口

**位置**：§12.9，1066、1092 行；§12.11，1155～1156 行（X1／X2）。

固定 Go 1.27.3 不仅有 `syscall.CreateProcess`，还有导出的 `syscall.CreateProcessAsUser`；X1 只列前者及 x/sys 的两个对象。标准库还提供 `syscall.(*Proc).Call` 和 `syscall.(*LazyProc).Call`：前者直接调用 `SyscallN`，后者委托前者；X2 只增加 x/sys/windows 的同名方法。参见 [syscall.CreateProcessAsUser](https://github.com/golang/go/blob/2aae1000ea1d4b28923b96db28acf4e3b99d6aff/src/syscall/zsyscall_windows.go#L226)、[syscall.Proc.Call](https://github.com/golang/go/blob/2aae1000ea1d4b28923b96db28acf4e3b99d6aff/src/syscall/dll_windows.go#L255)、[syscall.LazyProc.Call](https://github.com/golang/go/blob/2aae1000ea1d4b28923b96db28acf4e3b99d6aff/src/syscall/dll_windows.go#L374)。

**静态反例**：闸门之外的生产包直接调用 `syscall.CreateProcessAsUser`，或取得 `syscall.NewLazyDLL(...).NewProc("CreateProcessW")` 后调用其 `Call`。`go/types` 解析出的对象都不在现稿表中；它们的内部标准库调用又不扫描。即使 X1/X2 按当前推荐获批，仍能漏掉这些已知入口。对 `syscall.SyscallN` 的禁令并不会跨过标准库方法包装自动命中调用者。

**最小修订**：对照固定源码补齐同源对象及其平台，将它们纳入 X1/X2 的待决范围、白名单和固定反例，而不是只在字面名单外继续扩充实施豁免。精确限制用途，不将整个 syscall 或 windows 包列为允许。这是已知同源能力的完整性问题，不是要求 C-9 证明不存在任何未来启动方法。

## 5. C-9 方法及未列入 X1～X4 的限制

### 5.1 对象、间接引用和词法预筛

`types.Info.Uses`、方法对象的 Origin、类型别名 Unalias 的方向可以采纳；需要结合选择器信息、实例化签名和表达式类型落实。方法值、方法表达式、点导入、别名和函数值最初取值的位置，确实能按对象识别，不能只按 `Run` 等文本报违规。

第三方词法预筛的可靠性只限于：**源码显式引用表内对象时，其标识符会出现在相应 Go 词法 token 中**。它不证明存在任意接口派发、反射或函数指针时最终目标一定被静态解析。必须处理 dot import、import alias、嵌入提升和泛型方法的身份；不能用原始字符串搜索代替 token 和类型信息。

特别是第三方 `func f(c *exec.Cmd) error { var w interface{ Wait() error } = c; return w.Wait() }` 中，Uses 的 Wait 是接口方法对象，不是 `(*exec.Cmd).Wait`，而仓库专用 X3 不适用于该依赖。现稿的第三方保证应准确写为既定对象引用扫描，不能宣称已经覆盖该动态派发。若要把这种已知、可构造的能力流也列为必拒绝，须补充解析／敏感转换规则或精确的待决边界，不可默默记成已接受的 L。无需因此对全部第三方套用所有泛型／any 禁令或证明任意恶意程序行为。

### 5.2 装载与失败出口

除 B-126-4 外，须在实施前固定以下装载细节：ImportMap 的导入方作用域、每配置包身份与缓存、标准库／特殊包的元数据缺项、模块 go 版本与工具链默认版本、架构 Sizes、初始化表达式始终检查。`IgnoreFuncBodies` 只是跳过函数体，不是“这个包没有行为”。

go list 的 Error／DepsErrors／Incomplete、非零退出、输出解析失败、对象缺失、源码错误全部失败关闭的方向正确；对象自检应只要求该平台确有定义的对象，且未扫描的生产变体不能靠“缺少对象也失败”来补覆盖。前端变体、特殊包和 ImportMap 的固定正反例应先写预期，再实施。这里没有取得六配置完整类型检查的动态证据；gopls 等工具的先例也不能替代该证明。

### 5.3 精确白名单与额外工程约束

两类白名单分开、按平台／对象／用途核对、陈旧项失败、未来 E2 的精确动态导入／linkname／四行跳板／唯一调用者，原则可采纳，须保留标准库与 x/sys 的第二类例外。不能用一个包名放行所有能力。第三批不存在 e2waitid 不算缺失；第五批加入时须独立核对实际产物和调用点。

以下不是冻结条文逐字规定的规则，应补入 §12.11 的提案和验收影响，不能因称为“失败关闭”自行生效：

- 只允许静态非 SIGCHLD 参数、禁用未知变量／展开／函数值的信号政策，以及 B-126-3 所需的可变信号对象约束。
