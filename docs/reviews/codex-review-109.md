### 3.2 发信号与唯一回收的条件证明

在以下前提下，新的身份保护方向成立：

1. 对直接启动的内层，只有该 Wait 任务回收；其他代码没有 Wait／Process.Wait、wait(-1) 或忽略 SIGCHLD 导致自动回收的旁路。
2. 可靠观察明确核对它仍是本进程的未回收僵尸；不把 procInfo 的未知、外来对象或缺失当作该证据。
3. 同一把锁串行化“检查尚未开始回收并实际发送信号”和“标记开始回收”；标记后永久禁止再向该内层发信号。

则信号发生在回收开始之前，PID 仍由该直接子进程占有；标记之后不再发送，排除了本计划受控拓扑中的回收后 PID 动作。该证明不需要预先成功取得启动时间，但依赖上述独占回收前提，不推广到任意宿主。

普查、补救、保险清理及最终收尾必须同样排除这一个受专用规则管理的进程实例；不能绕过标记改用普查 PID 发信号。第三稿已写出这一点。身份与归属的其余规则保持，不新增未知对象动作的豁免。

不过，**PID 动作顺序正确并不证明父端的等待有界**；锁的持有边界需要另行闭合。

## 4．BLOCKER B1-R-S：共用锁的范围与截止查询尚未闭合

**位置**：`docs/wp2.5-prototype.md:4420`～`4422`、`:4435`、`:4477`～`4479`；处理记录 `docs/review-resolution.md:8628`～`8648`。

当前写法是“Wait 任务看到僵尸之后，在锁内标记‘开始回收’，再调用 Cmd.Wait”，信号方“在同一把锁内检查这个标记，只在标记之前发送”。没有明定：

- 标记之后是否必须先解锁，再调用 Cmd.Wait；
- procInfo、Close、实际信号操作及完成等待分别由哪个任务执行，哪些操作不得持有这把控制锁；
- 门禁取得请求结果、until 的错误快照和最终收尾查询，是否可能先阻塞等待一把被未完成任务持有的锁。

§16.8 的“until 到期即返回”是所需接口性质，不能自行证明取得共享锁也受该截止约束。所引用的现有 `stopTask.until`（`dest_test.go:338`～`350`）在完成／计时选择之后还要调用 result 取得错误锁；它成立的必要条件，是那把错误锁只保护短的状态访问，不跨 Close。新的回收／信号锁不能在套用这个模式时跨过可能挂起的操作。

### 4.1 当前文字未排除的事件序列

1. 唯一 Wait 任务可靠看到僵尸，取得共用锁，置“开始回收”。
2. 按“标记后再调用 Wait”的直接实现顺序，仍持锁调用 Cmd.Wait；这一次调用尚未返回。
3. 门禁在 k、补救阶段或最终收尾准备按同一锁检查标记；它首先等待锁，尚未进入带截止的完成信号选择。
4. w、d_g 或 D+30 已到，但控制流还在 Lock，不能执行“停止等待并移交”。如果 until 的结果读取复用同一锁，也有相同问题。

这是被第三稿文字允许、却违反其截止出口要求的一条实现路径。**本轮没有证明作者已经这样实现，也没有声称实际发生死锁或误杀。** 看到僵尸意味着预期 Wait 可以立即回收，不意味着允许把 Cmd.Wait 放在截止调用者必须取得的锁内；本轮也不要求任何单次系统调用具备硬实时保证。问题在于将可能未返回操作的持锁等待传播到了父端的用户态截止路径。

### 4.2 最小修正与边界

只需在定稿协议中明确：

- 控制锁的精确保护范围；**发布“开始回收”之后先解锁，再调用唯一一次 Cmd.Wait**。procInfo、Close、任务等待等不得处在该临界区。
- 信号检查与实际动作仍须对回收标记保持串行，不可简单解锁后裸发 PID 信号；同时写清父端发起／查询请求时怎样避免无期限等待控制锁。若由独立请求任务承担锁或系统调用，任务及错误也要登记和移交，不能留作无主调用。
- until／快照／最终收尾读取的锁不得跨外部阻塞操作；到截止直接保留 pending／unknown／T，任务与资源由同一持有者继续拥有。需要说明的是锁与调用顺序，无需现在选择某一种代码写法或实现新机制。
- 校正正常与迟到回收时间线中的解锁点；预算、角色 C、次数、exact 和动作归属规则不变。

这些约束能够同时保留 PID 安全与父端截止出口，不需要新的产品选择、扩大预算或建立生产后台系统。明确后才足以关闭 B1-R；不能只以“共用锁”或“调用 until”代替这项顺序说明。

## 5．输出、提前出口与所有权：修订大体成立

| 路径／资源 | 核查结论与条件 |
|---|---|
| Start 之前失败、Start 返回错误 | 管道由创建者持有，关闭错误持续记 T；没有成功返回的子进程不能捏造退出状态 |
| Start 成功后 | Cmd 的所有权从成功起建立；关闭父端写端、登记任务再读身份，不再进入旧 launchInner 的同步 Wait 出口 |
| 父端写端 Close 失败 | 必须保持 T，不能把“尝试关闭／不移交任务”解释为已验证释放；失败结果随该门禁记录保留 |
| 身份读取失败 | T 持续保存；只对仍未回收的直接子进程走专用请求规则；不靠不可信 PID 补救 |
| Wait 与 ProcessState | 完成信号在结果发布之后；只有 Wait 已完成且取得有效状态时读取 ExitCode。Wait 返回错误不自动证明成功回收，错误与状态未知须分别保存 |
| 复制与缓冲区 | EOF、停止读端、复制结束分别记录；只在复制已结束时解析稳定缓冲区。w 后仍 pending 就不能读取，不以部分数据猜结论 |
| 输出不完整 | 即使安全解析出布局或目标的最终行，也持续为 T，不能因找到预期理由而放行 |
| 复制／停止任务晚到 | 原门禁不再重新解析并恢复通过；字节数、结果、错误随任务保留，由最终持有者读取 |
| 移交后的活对象 | 清单、任务、Cmd、读端及缓冲区始终有持有者；移交不是释放，进程结束不是全部句柄已释放 |
| 最终截止仍 unknown | 保留 T／unknown，不再无期限等；测试进程退出或系统收养不是独立确认清理，不能回填成 clean |

上述是对计划的条件化认可，不宣称已有新门禁或任务实现。尤其不能为了修 B1-R-S 而提早读 ProcessState、共享缓冲区或丢弃晚到错误。
