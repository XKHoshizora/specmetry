## BLOCKER

### 旧版 Git 的只读保证尚未闭合

位置：[objectsReadable](../../internal/gitx/gitx.go#L450)、[CountLines](../../internal/gitx/gitx.go#L257)；同类结构也存在于 `CommitOf`、`TreeFiles`。

必须区分三层证据：

- **静态可确认：**配置检测与对象读取由不同 Git 进程完成，中间没有固定配置视图或能约束外部修改者的机制。
- **既有已验证事实：**Review 021 已证明，Git 2.32 在部分克隆缺失对象时，可能在传输失败前修改 `.git/config`。
- **尚未独立验证：**目标提交中，在上述精确窗口改变配置后是否实际触发同样写入，以及其完整跨平台表现。

风险需要同时具备：Git 不支持禁用 Lazy Fetch、对象缺失、其他进程在检测与读取之间启用 promisor。

| 保证 | 当前判断 |
|---|---|
| 阻止出站传输 | 静态实现与既有测试支持空协议列表有效。 |
| 阻止传输外部程序执行 | helper、upload-pack、ssh 的阻断有既有证据支持；旧 Git 仍可能启动自身的内部 Fetch。 |
| 阻止仓库配置写入 | **不能由当前实现保证；精确窗口的动态结果仍未验证。** |

[architecture.md:255](../architecture.md#L255) 要求读取不修改配置，而 [264 行](../architecture.md#L264) 又排除了这一并发窗口。文档记载风险不能自行替代对保证边界的正式批准。

因此，这里是**尚未解决的验收保证缺口**，不能作为已接受风险关闭。没有证据表明本次出现新的提交、Ref、Index 或业务数据损坏。

**最小修复方向：**局限在旧版 Git 的对象读取边界，使读取进程与可变的源仓库配置隔离，例如使用私有、固定配置的最小 Git 元数据视图访问原对象库。该方向仍需设计和验证，本轮不声称已经证明可行。增加一次前后检查不能撤销写入，Specmetry 内部锁也不能约束外部 Git；不建议擅自提高最低 Git 版本。
