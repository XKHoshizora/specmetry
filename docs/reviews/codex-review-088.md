## 5．调用链与诊断结论的证明范围

### 5.1 原测试与助手

[source_test.go](../../internal/cli/source_test.go) :135–154、537–546：空回答不是 noPrompt；它建立一个匹配 `press Enter to cancel:` 的步骤，发送 `\r`，Before 为 nil，期限为 60 s。第一调用已经 Fatal，第二次正确文本确认没有执行。

[pty.go](../../internal/testutil/pty.go) :60–100：每次读取先追加到 bytes.Buffer，再从 from 索引搜索完整 Expect。匹配后执行 Before，调用 p.Write，**同时忽略 n 与 err，随后 next++**。因此源码能证明“该分支不验证输入写入结果”，不能证明原作业实际返回了错误/短写。

超时分支先对自己创建的 cmd.Process 尝试 Kill，再 Close PTY，然后取得缓冲并 Fatal；这些返回值没有形成原作业的阶段日志。正常分支 Wait 之后最多等待 500 ms 读取，再 Close，之后另等 readDone 最多 2 s。文档的“读取 500 ms”应理解为最多等待，非每次固定读满。

[confirm.go](../../internal/cli/confirm.go) 与 [channel.Guard](../../internal/channel/channel.go) :110–145：文本模式显示提示；Guard 完整写出提示后 ReadString('\n')，空行不等于确认文本，返回取消。人类通道是启发式拦截，不是身份认证；本 PR 没有改变这些行为。

已读取本机缓存中 **go-pty v0.2.3** 的 Windows 源码：conPty.Read/Write 分别委托 outPipe.Read/inPipe.Write；Close 调用 ClosePseudoConsole 并关闭管道；Cmd.wait 调用 os.Process.Wait，之后向容量为 1 的 done 通道发送。对本次单 Wait、无 CommandContext 的用法，该发送不是额外的无接收者阻塞点；这不是整个 Wait/ConPTY 收尾不会阻塞的保证。

本机 Go 1.27.1 的 os.File.Write 源码明确在 n != len(b) 时返回非 nil 错误。因此 X4b 的“0 字节、nil 错误”是观测包装层的受控故障，不是已证明原生 os.File.Write 会如此返回。即使真实短写通常伴随错误，当前助手也忽略两者，盲点仍成立。
