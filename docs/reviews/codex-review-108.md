### 3.2 两条时间线与启动边界的独立复算

时间线一取 S=0、T=600，则 D=180、最终收尾截止 210。静态入口 0.5 秒，加 42 次布局／原生各 0.5 秒，结束于 21.5 秒；最后一次约在 21 秒准入，距 D 159 秒，成立。

门禁 s=22，则 **d_g=82、d_i=52**。布局在 22.5 开始，剩余 29.5 秒≥12；d=34.5、obsEnd=28.5。23 秒开始目标，剩余 29 秒≥12；d=35、obsEnd=29。目标及内层收尾在 23.4 前结束，随后外层核验，于 23.7 完成；对照于 23.8～25.3 完成，算术没有冲突。布局、目标、内层最终收尾、输出与退出确有合法可执行路径。这些耗时是示例，不是 E2 性能证据。

更精确的启动边界为：设 δ 是门禁开始到布局开始的时间，b 为布局耗时，h 为布局结束到目标准入之间的开销：

- 布局准入：`δ≤18`。
- 目标准入：`δ+b+h≤18`。
- 布局用满 12 秒时：`δ+h≤6`。

因此文中 δ=6、布局用满 12 秒的边界例子，需要 h=0 的理想事件时间线；真实实现若有间隔开销，应按实际当前时刻重新准入，不能把 δ≤6 当作充分的运行保证。此处不影响合法路径存在，按非阻塞精化登记，见 N-108-2。时间线一的 0.4 秒指内层进程进入、0.5 秒才是布局开始，套入上述 δ 时应取后者。

时间线二的 **57 秒发结束请求、62 秒返回、再得到 20 秒外层预算**，只在 57 秒已经观察到内层退出、I/O 等待额外用满 5 秒的前提下成立。此时 62～67 普查、67～77 补救、77～82 保险清理的分配正确；保险只能得到 5 秒，未知和迟到补救不能恢复原门禁。它不是请求 SIGKILL 后所有情形的最坏上界。

## 4．BLOCKER B1-R：WaitDelay 不能界定请求终止后等待 Cmd.Wait 的时间

**位置**：`docs/wp2.5-prototype.md:4363`～`4367`、`:4392`～`4398`、`:4433`～`4434`，以及 `:4492` 的内层结束方式；同步摘要 `docs/review-resolution.md:8548`。

第二稿声称：父端到 d_i+5 结束内层，WaitDelay 5 秒，因此 runInner 不晚于约 d_i+10=d_g−20 返回。这里把**请求结束**、**可靠观察退出**和**等待返回**合并成一个事件。

### 4.1 固定源码依据

本轮新读取固定 Go 1.27.3 提交 `2aae1000ea1d4b28923b96db28acf4e3b99d6aff` 的官方源码：

- [`os/exec/exec.go:289`～`305`](https://github.com/golang/go/blob/2aae1000ea1d4b28923b96db28acf4e3b99d6aff/src/os/exec/exec.go#L289)：WaitDelay 的计时起点是关联 Context 完成，或 Wait 观察到子进程退出，两者取早。直接调用 Kill 不是这里的计时起点。
- [`Cmd.Wait:936`～`970`](https://github.com/golang/go/blob/2aae1000ea1d4b28923b96db28acf4e3b99d6aff/src/os/exec/exec.go#L936)：先执行 `c.Process.Wait()`，之后才进入复制任务的 awaitGoroutines。
- [`awaitGoroutines:981`～`1016`](https://github.com/golang/go/blob/2aae1000ea1d4b28923b96db28acf4e3b99d6aff/src/os/exec/exec.go#L981)：没有 Context 提供的 timer 时，到这一阶段才新建 WaitDelay timer；到期关闭管道后还要接收复制任务结果。

现有 `gate_test.go:542` 使用普通 `exec.Command`；`:556`～`558` 在超时后 `Kill()`，接着无截止地 `<-done`。新计划只规定带截止变体与 WaitDelay，没有定义 Kill 后仍不能确认退出／Wait 返回的分支，也没有证明由 WaitDelay 取得所声称的上界。即使改成 CommandContext，也不能把取消请求当作 Process.Wait 已经完成的证明。

另一个直接接点是 `witness_unix_test.go:94`～`103` 的 launchInner：创建成功、身份观察失败时，当前分支 Kill 后同步 Wait，再返回错误。如果新变体仍复用该分支，同样不能从表中父端等待的截止推出它有界返回。指出该新路径需接线，不要求顺带修改角色 C 的旧预算。

### 4.2 合法事件序列及影响

使用文中相同的 d_i=52、d_g=82：

1. 内层没有按期返回；57 秒父端发出 SIGKILL 请求。
2. 在 62 秒，父端仍未得到可靠退出／Process.Wait 返回。请求返回并不构成退出确认；固定实现允许 Wait 仍停在 Process.Wait，I/O 的 WaitDelay 尚未开始。
3. 若照旧 `<-done` 等待，外层不能在计划的 62 秒进入普查；也没有明定到 d_g 后如何停止等待并移交 Cmd、唯一 Wait 任务及输出复制资源。D+30 的最终收尾不能因声明存在，就从这个等待中获得控制权。

此处不声称本轮复现了不可中断进程，也不要求强制制造它；这是 API 契约允许的未确认分支。问题也不是操作系统没有硬实时保证这一通常限制，而是**计划用 WaitDelay 给另一项等待推导了上界，并没有该分支的用户态截止出口**。

时间线二可以作为“退出已经得到确认”的条件例子；不能继续作为无条件最坏情形。直接将请求时间打印为“内层已被结束”，还会丢失真实知识状态。

### 4.3 最小修正

仅需先补文档协议，不要求现在实现或实验：

1. 分开结束请求、请求错误、可靠退出、Cmd.Wait 完成、管道关闭、复制任务结束；写清每次等待消费哪一个既有绝对截止。
2. 明确到截止仍未确认时的失败返回和移交：Cmd／Process、唯一 Wait 任务、输出端及复制任务、缓冲区／解析责任、晚到错误各有所有者；不得再无期限接收 done 或在 Wait 未完成时读取假定已稳定的 ProcessState／bytes.Buffer。
3. 覆盖 launchInner 创建后身份观察失败等提前出口；保持只操作本轮自有对象的规则，不借未知 PID 扩大动作授权。
4. 对仍挂起的任务／进程保留 unknown／T，并在最终收尾的既有截止内处理；不能把移交写成释放，也不能由补救成功恢复门禁。若无法确认，按既有停止条件报告负责人。
5. 重写返回上界与时间线二的适用前提；不扩 60 秒门禁、D、套件／作业预算，不取消布局、计数或 exact。

这项残余属于本次 B1 收尾设计的直接影响，阻塞当前“计划已足以授权执行”的结论；不是把生产阶段工作提前列成本 PR 门槛。

## 5．N1：互斥分类与调用次数——正文收口

位置：`docs/wp2.5-prototype.md:4241`～`4301`。X1～X5 以 `r=int32(r1)` 是否为 0／−1、err 是否为 0 分区，互斥且覆盖全部组合。五种形式与三种调用预期的分类已写定：

| 真实形式 | 健康调用 | 构造 ECHILD／EINVAL | 注入前真实调用 |
|---|---|---|---|
| X1：0／0 | 比较 R，正确则一致，错误则原生反证 | 应失败而成功，原生反证 | 允许注入；换上的 EINTR 只证明消费者拒绝 |
| X2：−1／非零 | 原生反证；错误后恢复失败也同样记录 | errno 符合则一致，不符合则原生反证 | 不注入，持续记 T，门禁不能通过 |
| X3：−1／0；X4：0／非零；X5：其他返回值 | 协议失效 T | 协议失效 T | 协议失效 T，不改写 |

协议失效明确指候选调用／报告契约失效，不冒称都是无关环境故障；原始 r、err、缓冲区及原因保留。真实非成功元组在接缝站点持续记 T，之后成功不能覆盖。无接缝的合法 X2 原生反证与消费者的正确拒绝分开，角色 C 仍按旧规则，不将原生反证吞为通用工具错误。

次数也有可独立实现的依据：实际由 waitidCall 递增；规则次数由固定状态机决定——正常双读第一步 X1 才读第二次，否则停止；错误恢复先执行错误调用再按同一双读规则；计划次数是预先固定的 0／1／2／3。不能用实际日志有几条就把“规则次数”设为几次。

例如健康第一次得到 X2：实际 1、规则 1、计划 2，原生 refuted，不附加 calls T；若第一步 X1 却漏掉第二次，则实际 1、规则 2，T；如果额外调用第三次，实际 3、规则 2，仍 T。T 与原生反证叠加时 invalid 并保留全部原因。正文没有发现由预期理由豁免额外错误的放宽。

**N-108-1（NON-BLOCKER，摘要同步）**：`docs/review-resolution.md:8561` 将“计划次数与规则次数：两者不符时记 T”写错；正文 `:4287`～`4289` 是“实际与规则不符才记 T，实际等于规则但不等于计划时保留调用本身的偏差”。上面的健康 X2 事件正好区分二者。最小修正是更正 §133 此摘要，不能把正文已保留的原生反证变成 T。处理摘要不能另加规范，因此此项不阻塞正文 N1 在计划层面的关闭。
