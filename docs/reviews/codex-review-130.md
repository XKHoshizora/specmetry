## 3. 共享 pidfd：独立状态推演

位置：生产计划 **1655～1688**；链接计划 **252～285**。两份文本一致本身不构成证明；本节分别核对其状态不变量、实际接点与七种交错。

### 3.1 状态不变量与接点

本轮的关键修复成立：

1. **请求登记即取得使用责任。** 只有在状态锁内重新核对请求窗口、fd 为 Open、请求为 None，才能将请求置 Reserved 并保存 fd。goroutine 尚未运行不再等于“没有占用”。没有通过无锁旧快照获得权限。
2. **Wait 发布与封闭准入只有一个顺序。** 启动任务在唯一 Wait 返回之后，同一次锁下发布本次结果并将 Open 置 Closing。后续请求不能在 Wait 发布与封闭之间插入。链接的 WaitUnknown 也按这一顺序封闭，并不保留未来请求承诺。
3. **Reserved 和 Running 都阻止真实 Close。** 唯一关闭者是启动任务；只有 Closing 且请求为 None、Done 或 Abandoned，才可以在锁外 Close 一次。Closing 先封闭后续借用，所以从决定关闭到实际 Close 之间没有新借用者。
4. **到期放弃有责任归还。** 请求任务开始时再次核对自己的窗口；过期发布 Abandoned、归还使用责任并通知关闭者，不发系统调用。已经 Running 的请求则持有 fd 直到原始返回保存为 Done；不能因父端过期而提前 Close。
5. **外部操作与等待不占状态锁。** Open、SendSignal、Close、等待变化均在锁外；状态锁只发布字段、结果和变化通知。父端可以取得短快照并按截止返回，不等待发送或关闭完成。
6. **完成知识与释放知识分开。** Closed 表示唯一 Close 已返回；只有真实结果 nil 才确认释放。错误持续记失败、释放未知、不重试。请求挂起、关闭挂起或晚到错误都由原记录持有，不能恢复成功。

实际启动链先 Start 成功、后 PidfdOpen、后唯一 Wait，保留“没有自动回收和其他回收者”的前提；因此取得时是尚未由本次 Wait 回收的直接子进程。Open 失败／尚未发布不授予动作权限，也不回退到整数 PID。Open 仍未返回时父端到期，记录继续持有启动任务、Cmd 和未知责任；没有从未发布状态伪造 fd。这里认可的是有前提的协议，不是任意宿主的完整 PID 保证。

链接状态表新增的 Started/WaitPending 不允许提前清扫。WaitUnknown 排除工具 PID、不接手其回收；记录继续持有 Cmd、错误及 fd 状态，封闭后没有使用责任即可 Close，有合法预留则等其结束／放弃。Reaped 仍要求本次 Wait 的 ProcessState 非 nil；不会把 Wait 返回、请求成功或 ESRCH 升格为回收证据。F-8 的未知工具不接手政策及其代价仍须负责人决定。

### 3.2 七种交错的独立期望

下面的期望来自使用责任和封闭不变量，不是把两份表相同当作证明：

| 交错 | 独立推演与应有判定 |
|---|---|
| 1. 父端判断超时，尚未预留；Wait 先发布并封闭 | 锁下预留失败；SendSignal **0 次**，唯一 Close **1 次**；终止未准入持续记失败，不能用之后已结束恢复原调用成功 |
| 2. Reserved 后、任务运行前，Wait 封闭 | Reserved 仍阻止 Close；请求在窗口内可用仍打开的 fd **发送 1 次**，保存返回并归还后 Close **1 次**；过期则发送 **0 次**、发布 Abandoned 后 Close **1 次** |
| 3. SendSignal 已开始但一直未返回 | Running 保持使用责任，Close **0 次**；父端仍到自己的截止，记录未知／失败并持续持有；不能释放 fd 给其他对象复用 |
| 4. Wait 在任何请求之前完成 | 同锁封闭；Close **1 次**；后续所有预留均拒绝，发送 **0 次** |
| 5. Open 失败／未发布 | 不预留、发送 **0 次**；已失败没有 fd 可关闭。未发布而后在窗口内、封闭前成功发布，可进行一次合法预留；否则未知／失败，持有未完成任务 |
| 6. Reserved 后运行时已过期 | 发布 Abandoned、归还责任，发送 **0 次**。**已封闭**时唤醒唯一关闭者 Close **1 次**；Wait 仍进行中则按规则 2/4 暂不关闭，直到其封闭。放弃本身不等于回收 |
| 7. Closing 之后拿旧 Open 快照申请 | 必须再次锁下裁定并拒绝；发送 **0 次**，不会取得旧 fd；关闭者原有唯一 Close 不增加 |

这些仍是待实现的固定对照，不是本轮动态执行次数。两协议请求窗口分别为 `[W,D)` 与 `[W,K)`，没有相互借用期限，也没有借后续成功、额外回收或终判遗漏来消除 Abandoned／NotAdmitted／Unknown。

### 3.3 两处非阻塞措辞精化

**N-130-1（旧 fd 的含义）：** 生产计划 **1671**、链接计划 **268** 的“Closing 或 Closed 后不能使用旧 fd”应明确为“不能凭无有效预留的旧快照新登记／使用；合法 Reserved/Running 所持 fd 在归还前仍可按规则使用；真实 Close 后绝不使用”。规则 3/5、交错 2 以及链接 Reaped 行已经给出了这一合法使用顺序，故本轮没有据此认定尚有实际 use-after-close 或另立一项阻塞；但不宜让一句概括被读成禁止所有 Closing 期间的合法预留使用。

**N-130-2（放弃后的关闭前提）：** 两份交错表第 6 行的“随后关闭一次”宜补“Wait 已发布并封闭时”。Wait 未返回时，仅放弃不能满足规则 4 的 Closing 前提。精确状态规则已有这一限制，不因此重开共享状态机；后续固定用例不要仅因请求放弃就预期 Close。

## 4. B-127-1：修订成立部分与截止残余

### 4.1 H 的三平台构造与半构造责任

生产计划 **1526～1547** 撤回 Windows 不支持的 ExtraFiles，改为三个标准句柄，方案在计划层面可实施：

- H 的 Stdout 为目标写端的 `*os.File`，只持有而不写。固定 Go 源码 `writerDescriptor:601～603` 直接使用调用方文件，不将其变成 Cmd 自有的父端关闭责任。H 启动时取得的子端副本随 H 自己结束释放；目标父副本仍由原启动任务唯一关闭。
- H 的 Stderr 使用独立就绪管道；Stdin 使用独立释放管道。Windows 标准句柄启动路径能够传递这些标准端点，不需要 ExtraFiles，也未借此增添生产继承白名单或 Job。
- 两条目标管道建立并移交读取任务后、原启动任务关闭目标父写端之前，启动 H 并取得有界就绪反馈；未启动或未就绪就记未命中／失败，不能把目标输出未闭合误算作已构造。
- H 就绪后，伪工具退出、目标父副本关闭，而 H 仍持有子端副本，使目标读取不能到 EOF；必须**先保存被测拒绝**，再由独立释放者关闭 H 的输入释放端，使 H 结束，由唯一 Wait 取得结果。之后 EOF、回收和真实关闭成功不能恢复原调用成功。

表 **1534～1541** 对目标父写端、H 子端副本、就绪两端和释放两端分别指定关闭者。就绪 reader 拥有读端；H Start 返回后测试关闭相关父端子用副本；独立释放者与 Cleanup 共用一次关闭责任。H 的 Wait 是独立任务，父端只读已发布状态，超期不再同步等待。H Start 失败、就绪失败、Wait 未确认及关闭失败有失败／持续持有出口；未确认时不拿 PID 再动作。接缝追加错误不能代替真实关闭结果。

该构造只验证“输出未闭合时工具控制正确拒绝及持有责任”，**不证明真实孤儿领养、任意后代清理或 Job 最后句柄语义**。本轮没有运行 Windows／Linux／macOS H 夹具。

生产计划 **1622～1629** 的半构造也已闭合：两个 Pipe 都建立后才移交两个 reader；第二个 Pipe 失败时，原启动任务关闭第一对端点，无 reader、无 Start。移交后启动方不重复关闭 reader；Start 失败后关闭两个父写端，reader 经 EOF／错误关闭自身端。真实 Close 返回、注入错误、任务完成与释放知识各自保存。

健康 EOF、读错误、超量、真实关闭失败、到期未完成等均不能仅因 Wait 成功而通过。相关通用 fd 修订可采纳，没有将注入 nil 后追加 E 说成自然关闭故障或泄漏证据。

### 4.2 B-130-1：c9lint 的包终判仍依赖截止后的输出

**级别：BLOCKER，B-127-1 的一个截止残余；不重复计算已修好的共享 pidfd 问题。**

**位置：** `docs/wp2.5-implementation-plan.md:1699`～`1701`，与同文件 **1589～1592** 的整包 120 秒唯一截止，以及 **1642** 的父端查询／截止出口相冲突。

第 13 条要求 TestMain 在 D 前等待记录；到 D 还有未决项时，TestMain“**打印每条记录的未决项并以非零状态退出**”。它没有把打印放入已登记的受控任务，也没有规定输出未完成时允许不再等待、直接非零退出。因此按当前正文顺序实现，仍允许下面的事件序列：

1. 读取、请求或 Close 任务未返回，TestMain 按既定 D 停止等待并取得快照；此时实验／包失败已经确定。
2. 父端为满足第 13 条，开始打印未决项。
3. 输出接收端停止消费或管道产生背压，真实写入／输出锁未返回，父端不能到达随后的非零退出。既定 D 不约束这次新 I/O；默认 600 秒包期限也已被正文明确排除为该预算。

这不是“调度无法硬实时”的一般性限制，而是**已知到期后新增的同步外部依赖**。固定 Go 的 `internal/poll/fd_unix.go:365～400` 在 File 写入路径持有 writeLock，并在 EAGAIN 时调用 `waitWrite`；没有从计划的 D 自动取得写入期限。普通日志调用本身不会继承该单调截止。反例是静态、允许的事件顺序，本轮没有运行阻塞输出实验，也不声称 CI 已发生此事。

链接计划已在 **320** 明确修掉 F 时补写 stderr 的同类依赖；不能据此推定 c9lint 的 D 出口也自动获得修正。第 6 条的父端只查询协议使状态快照可达，但不能约束快照之后第 13 条要求的打印。

**最小修正方向：** 在设计正文固定 D 的唯一出口：到 D 只消费已发布状态并确定非零退出，不因打印、刷新、关闭、查询或等待重新阻塞。需要的诊断在 D 前由已登记任务保存／输出，父端只等原有截止；到 D 尚未完整输出就保留缺失／未完成与失败，允许不再写入。日志任务、对象及晚到错误仍有持续持有者。普通及时完成路径可保存诊断，但不能让“完整打印”成为失败退出的必要前置。

不要求扩时、不要求新资源，不要求把每个同步读取改成异步，也不要求现在实现分析器。下一份计划宜固定一个“结果已失败、输出任务不返回，到 D 仍能选择非零退出”的独立预期；动态验证留在另行授权后的既有工具控制范围。

## 5. B-127-2：链接驱动与报告出口

本轮受审残余在计划层面可关闭，依据不只是共享状态机的文本相同：

- **接手顺序明确：** StartPending、Started/WaitPending 都不清扫；StartFailed(C) 先发布才接手，不谎称内部子进程已回收；WaitUnknown 排除工具 PID，不按 P_ALL 回收它；Reaped 则必须是本次 Wait 的可靠状态。旧请求只能通过持有使用责任的 pidfd 动作，不能回到整数 PID；驱动对其他对象仍需独立证明是自己的子进程。
- **清扫的证据不被扩大：** ECHILD 只在固定的子进程集合、subreaper、__WALL、没有自动回收／其他回收者等前提下证明该驱动无子进程；有排除 PID 则不能得空集合。观察错误、发现孤儿及未知回收持续为 T；补救后空集合不会消除被测机制失败。没有从“工具 Wait 返回”推出全部子树、文件或报告已释放。
- **半构造文件有关闭者：** 链接计划 **292～293**、**327～333** 将尚未到 Start 时已打开的输出文件交给启动任务唯一关闭。真实 Close 错误／未完成进入 T／释放未知；稳定读取、ELF/DWARF 解析器、pidfd、报告文件各有关闭责任；不能以空子树代替文件关闭或完整采集。
- **W/K/F 不重新取预算：** 工作与稳定读取／解析到 W；终止预留及运行窗口到 K；清扫和关闭确认到 F。等待／同步读取返回后，新动作重新检查当前活动截止；F 后不再新建观察、信号或回收。外部调用不占状态锁，父端到截止只消费副本。

报告 **315～321** 现有规则唯一且可实施：

| 事件 | 应有结论／动作 |
|---|---|
| 清扫确认，且当前 `now < F−20s` | 可以先登记再启动报告任务，仍只等到原 F |
| 清扫未确认、确认晚到，或 `now ≥ F−20s` | 不启动；缺证／T；等号也拒绝，不新取 20 秒 |
| 已启动报告的 Write、Sync 或 Close 出错 | 保存真实错误；缺证／T，成功读数及补救不能覆盖 |
| 到 F 报告还未完成 | 缺证／T；任务、文件、结果持续持有；父端不重新同步写 stderr／查询／关闭或等待 |
| 所有工作、采集、清扫、关闭和报告在各自期限完成且无 T | 可以形成完整有效报告；不能从单独报告完成推出整次方法验证成功 |
| F 后报告或清扫成功 | 只保存晚到结果，不恢复原结论 |
