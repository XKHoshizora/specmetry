## 3. B-126-1-R：主要知识修订成立，分类优先级仍须修订

### 3.1 可以采纳的部分

位置：实施计划 **1093～1115、1125～1133、1392～1433 行**。

- 不再由 `Process == nil` 推出“内部没有创建”；A 之外的启动错误归 C，保留租约、Cmd、原始错误和未知责任，PID 不可得时记 0，零动作。
- B 要求本次启动成功，并在本次唯一 Wait 返回之后取得非 nil ProcessState。已回收但有 ExitError、复制错误或上下文错误，与回收未知分开，方向正确。
- 绝对路径启动失败保守保留的代价已披露：随后排他请求可能一直等，可取消；不是新增超时、重试或宿主禁用。
- 一个租约只登记一份责任，双 panic 保留 Value／WaitPanic 两个原值；started panic 后的唯一 Wait、独立释放者、启动握手与测试父端截止均已写出。它们仍只是计划，未取得本轮动态证据。

这些与固定 [Cmd.Start 的早期检查](https://github.com/golang/go/blob/2aae1000ea1d4b28923b96db28acf4e3b99d6aff/src/os/exec/exec.go#L652)、[Cmd.Wait](https://github.com/golang/go/blob/2aae1000ea1d4b28923b96db28acf4e3b99d6aff/src/os/exec/exec.go#L936) 的知识边界相符。保留仍不等于确认释放，也不能从错误包装推定 PID。

### 3.2 阻塞残余：A①／A③与 pre-started 的 C 同时成立

位置：实施计划 **982～991、1097～1103、1123～1126、1421～1423 行**。

允许的事件序列：

1. 测试在闸门外成功 Start helper；它仍活着，Cmd.Process 非 nil，回收未确认。现稿明确把这样的输入纳入测试和 C 类。
2. 调用 `procgate.Output`，而 Cmd.Stdout 已经设置（这也是一个正常的 Cmd 构造）。
3. A③“调用前 Stdout 非 nil”要求释放；C“调用前 Process 已非 nil”和出口表要求保留，且闸门不再调用 Start。

两者没有写优先级。另一个同类序列是：已启动 Cmd 交入、取得租约后闸门 ctx 已取消。A①要求释放、称“没有启动进程”；C 要求保留已有对象的未知责任。只能证明**本次闸门未调用 Start**，不能据此证明所交 Cmd 没有正在运行的进程。

1103 行的“返回后 Process 非 nil就是等待阶段”也不适用于这个 Output 前置出口：固定 [Cmd.Output:1028～1031](https://github.com/golang/go/blob/2aae1000ea1d4b28923b96db28acf4e3b99d6aff/src/os/exec/exec.go#L1028) 在任何 Run／Wait 之前就返回；Process 可以来自先前启动，甚至 ProcessState 来自先前 Wait。不能用这两字段替代本次路径证据。

**影响**：A/B/C 并不互斥，接口、表格、阶段和 E-5 得不到唯一的租约责任；按 A 优先实现会与现稿 pre-started 必须保留的规则冲突。这是设计反例，不是声称当前三个生产接线已经传入这种 Cmd。

**最小修订**：写成有顺序的决策树，例如取得租约之后先识别并保存 pre-started 的 C，再处理确实未启动输入的取消／Output／Start 前置出口；B 只消费本次已执行的 Wait。同步接口、1103 行、出口表、E-5 和回归。至少增加“pre-started＋Stdout 已设”“pre-started＋取得后取消”的固定预期，健康 A/B 对照保留。可以选择另一套明确政策，但不能同时保留当前相反的答案。

## 4. B-127-1：父端出口已改好，关闭、夹具和 Linux 前提仍有残余

### 4.1 成立的主体

位置：实施计划 **1516～1579 行**。

120 秒是每作业整个 c9lint 包的共享预算；D 固定，W=D−10s，两个配置、夹具、工具及收尾不各取一份预算。编译测试二进制不在 TestMain 预算内，记录清楚。没有按“每步耗满上限”的加法判定它必然不可达。

先登记后运行、一个启动／Wait 任务、自建管道、稳定副本、外部调用不持 regMu、父端按 changed／W／D 查询，已经撤回 CommandContext／WaitDelay 的不成立上界和组信号动作。分析 goroutine 在 W 被放弃，不被写成已停止；不调用结束后的 t，失败持续保存，OOM 不保证完整报告，均可保留。

Windows Process 句柄指向同一进程对象；Linux pidfd 路径同样有身份锚点。Darwin 明确不在到期时调用 Kill，保留未知及可能继续运行的限制，与固定 [wait_unimp.go](https://github.com/golang/go/blob/2aae1000ea1d4b28923b96db28acf4e3b99d6aff/src/os/wait_unimp.go#L5) 的已知竞态相符。允许这种限定前提及失败出口仍需负责人确认；“持有到测试进程结束”不等于清理已核实。

### 4.2 残余一：EOF 没有关闭读端，成功条件没有消费完整关闭结果

位置：实施计划 **1538～1557、1566～1569 行**。

当前记录列出了 Start／Wait／读取／请求，却没有读写端的唯一关闭责任和关闭结果状态。读取任务只写成“读到 EOF 或错误”；后文明确登记表继续持有读端，没有规定 EOF、读取错误、超量、Start 失败和到期各由谁实际 Close、何时登记／消费。EOF 不会自动关闭一个 os.File。

按现有步骤直接实现，健康工具退出 0，两个任务 EOF，1557 行及 TestMain 的“已回收、两个输出 EOF”都满足，而父端读描述符仍没有任何执行关闭的步骤。另一种路径是写端真实 Close 返回错误，但随后能够观察到 EOF；成功条件没有要求该关闭结果已经保存和拒绝，泛称“任何失败”不能替代实际调用点的消费协议。

此外，Start 失败仍顺着步骤调用 Cmd.Wait，而固定 Go 对 nil Process 只返回“not started”，不能回收未交付的内部对象。应明确这是无回收能力的错误出口，不能在状态发布时误作已回收。超量输出之后继续排空、停止读还是启动关闭任务，也需要选定，不能让读取任务的退出成为无主 FD。

**最小修订**：每个读／写端一份唯一关闭责任，逐出口写定关闭启动、真实结果、完成知识与晚到结果；关闭不在 regMu 内，父端保留截止出口。判定消费真实 Close 错误，pending／释放未知不被 EOF 或工具退出覆盖；不得重复 Close。可复用本项目已有的持有思想，不要求实现通用 Runner。为正常 EOF、Start 失败、读取／超量和真实关闭成功后追加错误分别固定对照。

### 4.3 残余二：“输出不关闭”夹具没有后代自己的释放／回收者

位置：实施计划 **1469～1474 行**。

1472 行为直接伪工具写了标准输入释放；1473 行另让伪工具留下持有 stdout 的子进程，只要求测试因无 EOF 失败并记“后代未知”。没有定义该对象的启动反馈、持有者、解除闸门、唯一回收者和有界最终核验。直接伪工具已经退出时，关闭它的 stdin 不能保证这个后代结束。

这是计划主动创建的受控夹具，不能用 E-10 的“普通 go 调用没有后代”前提覆盖它，也不能只验证拒绝便结束测试、留下无持有的对象。需要独立的可释放协议，先保存无 EOF／T 的被测结果，再释放自有后代并核验；失败后也保持所有权。补救成功不恢复被测路径。Darwin 不能为补救这个用例重新引入现稿已经撤回的回收后 PID 动作。

### 4.4 残余三：Linux 非 pidfd 分支的防护有 ready 前提

位置：实施计划 **1560～1564 行**，链接计划 **238、256 行**的同源引用。

现稿说“不用 pidfd 时，pidWait 先等到可回收，再标记完成”，遗漏了源码条件：固定 [exec_unix.go:44～69](https://github.com/golang/go/blob/2aae1000ea1d4b28923b96db28acf4e3b99d6aff/src/os/exec_unix.go#L44) 只有 `ready == true` 才在 Wait4 前置 done／串行；[wait_waitid.go:21～36](https://github.com/golang/go/blob/2aae1000ea1d4b28923b96db28acf4e3b99d6aff/src/os/wait_waitid.go#L21) 对 ENOSYS 返回 `false, nil`。之后仍走 Wait4，再置 done。

所以合法源码序列是：未使用 pidfd、waitid 得 ENOSYS、Wait4 已回收而 done 尚未发布，此时到期请求取得 Process 并 Kill。没有前置完成标记，不能据这段源码排除旧 PID 被复用后动作。**这是固定源码反例；没有声称本机或当前 CI 已原生复现该故障。**

最小范围是补上可核验的运行前提／拒绝出口，或在不能成立时不采用这个动作；不能把全部 Linux fallback 都写成已经串行。链接驱动已有 waitid 的环境前置，能排除“waitid 整体不存在”的一部分环境，但仍应准确写出其依赖的等待方式和过滤条件，不能无条件写“Linux 上经 pidfd”。不要求现在新增平台探测实验，也不以任意未来内核行为要求无限证明。

### 6.1 本轮可以采纳的 Linux 推演

位置：链接计划 **205～240、247～260 行**。

撤回会话／进程组的错误等同是正确的。限定 Linux 的 child subreaper 可以承接孤儿；不因 setpgid／setsid 就离开这条父子责任链。直接工具唯一 Cmd.Wait、孤儿按指定 PID 回收、P_ALL 仅 WNOWAIT，能避免无差别 wait 抢走直接工具。工具之外出现孤儿即 T，补救成功不恢复结论，这个分层可采纳。

在驱动只启动受控直接工具、没有其他回收者、SIGCHLD／SA_NOCLDWAIT 及 PID 命名空间前提成立、工具可靠回收之后，未回收的子进程或僵尸会锚定 PID。清扫者串行观察、按它自己的直接子进程动作与回收，和读取任意见证 PID 后发信号不同。可以据此设计安全的有限驱动，不要求通用沙箱。

独立读取 [PR_SET_CHILD_SUBREAPER 手册](https://man7.org/linux/man-pages/man2/PR_SET_CHILD_SUBREAPER.2const.html) 和 [wait 手册](https://man7.org/linux/man-pages/man2/waitpid.2.html)。另用 Linux **v6.17 → `e5f0a698b34ed76002dc5cff3804a61c80233a7a`** 的固定源码交叉核对：

- [exit.c:636～730](https://github.com/torvalds/linux/blob/e5f0a698b34ed76002dc5cff3804a61c80233a7a/kernel/exit.c#L636) 处理最近存活 subreaper 和 reparent；被重新领养的 leader 的退出信号设为 SIGCHLD。
- [fork.c:2324～2334](https://github.com/torvalds/linux/blob/e5f0a698b34ed76002dc5cff3804a61c80233a7a/kernel/fork.c#L2324) 中 CLONE_PARENT 沿用父关系和退出信号，不能把它泛称为任意逃出本子树的路径。
- [exit.c:1125～1148](https://github.com/torvalds/linux/blob/e5f0a698b34ed76002dc5cff3804a61c80233a7a/kernel/exit.c#L1125) 的 wait 仍有 eligible-child 条件。因此 ECHILD 必须连同“仅这些子进程、正常退出信号／无自动回收／无额外回收者”等前提使用，不是脱离前提的整机空集合证明。

这些是静态参考，不是未来 runner 真实内核取证，也不是完成了一次驱动验证。没有因为 clone 的一般差异就虚构本计划已有一个确定的逃逸反例。前置失败不执行、未知不动作、实际环境留待取证的分层继续保留。

### 6.2 阻塞残余：Start 失败的清扫入口与回收门槛相反

位置：链接计划 **238～247、257～259 行**。

240、247 行要求“工具的回收发布之后才清扫”；246 行又要求 C 类 Start 错误“清扫照样运行”。允许的序列是：fork／exec 后启动失败，内部回收无法确认，没有交付 Process。此时 Cmd.Wait 只能返回 not started，不能发布可靠回收；也没有可供“从不对工具 PID 动作”使用的工具 PID。

若严格用回收门槛，246 行的清扫永远不能开始，可能遗留的内部直接子进程得不到它承诺的补救；若把 Wait 返回／not started 当作回收发布，又违背 §12.6 与 259 行的知识要求。另有 Start 成功、Wait 返回但 ProcessState 为 nil 的分支，必须与已确认回收分开，不能沿同一个“Wait 返回”标签接手。

**最小修订**：为 StartFailed(C)、WaitReturnedButUnknown、Reaped 分别写清清扫是否准入、已知 PID 的排除集合、唯一回收责任的移交握手和持续 T。可以为“Start 已返回错误且没有标准库等待任务再消费内部子进程”的情况单列驱动接手条件；不能把它称为已确认工具回收。对不能接手的分支维持未知及持有者。现有“所有失败都 T”不消除相反的动作规则。

### 6.3 阻塞残余：同步观察跨过截止后的新动作没有守卫

位置：链接计划 **247～260、269～275 行**。

允许的序列：清扫在 F 前开始读取 `/proc/*/stat`，该次读取在 F 之后返回；按 250 行，随后对读到的 PID 发 SIGKILL，并继续下一轮 wait／回收。当前只写“循环直到截止”“不滚动”，没有规定这个同步读取之后、每个新请求／指定 PID 回收任务启动之前重新检查剩余时间。类似情况出现在：等待工具结果后才启动清扫、输出文件读取之后再开始后续确认／关闭。

这不是要求单次系统调用能被硬实时取消。问题是**已经返回控制权、此时可以知道过期，却仍依据读取前的时间开始新的动作**。父端 F 的 select 可以先得到出口，但不能替任务内部的后续动作决策加守卫；也不能把“父端不同步 Wait／Kill／清扫”扩成文件读取和关闭自动有界。

**最小修订**：固定每个准入与动作的截止，所有等待／同步读取返回后，在新任务或新 PID 动作的决策点重新读时钟；到期走统一的未知／T／持有出口，不重取时间。已登记、已经启动的等待或关闭任务可以保存晚到结果，但不借“旧任务”绕过新动作守卫。说明 ELF／DWARF 与输出读取、文件关闭、报告保存的父端截止出口，外部调用不持状态锁。报告不能完整写出时仍失败并标明缺证，不承诺 F 时磁盘写入一定成功。

文件的打开、父副本关闭、最终读取／关闭结果也须有唯一责任和持续错误消费。§7 已要求写入或关闭错误为 T；§8 的执行流程须兑现，不能仅凭 ECHILD 和字节数相等代替关闭成功／完整采集。子树为空是对进程的知识，不是对 FD、输出收集或解析器的证明。

**裁定：B-127-2 未整体关闭。** 本轮采纳的是受限 subreaper 思路和它的前提，不是判定该方法不可行；未满足的 S 审计和资源授权另列，不拿它们替代上述具体设计残余。
