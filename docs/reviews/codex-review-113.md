## 3．B-P112-1：计划层面关闭

**主要位置**：`docs/wp2.5-prototype.md:4943`～`:5016`，R-B1-1／2／4 为 `:5025`～`:5071`。

### 3.1 状态与移交已形成唯一规则

第二稿明确保存真实 Close 结果、报告结果、注入标记与完成标志。只有“任务完成且真实结果为 nil”才能确认释放；不存在任务、pending、真实错误都属于释放未确认。门禁消费报告结果，资源移交消费真实释放知识，两者不互相代替。

新谓词在保险清理之后用新快照计算，除了原有 Wait／复制／请求条件，还接收任何读端释放未确认项。因此原反例有唯一结果：

| 允许的顺序 | 新谓词与最终处理 |
|---|---|
| 真实 Close 已完成但有错误 | 必然移交；同一任务的错误进入 unknown／final_T，不再 Close |
| 判定时 pending，移交前带真实错误完成 | 新快照仍为释放未确认，必然移交 |
| pending 到最终截止 | 保留任务与资源责任，unknown／final_T |
| 门禁已因 pending 失败，随后真实关闭成功 | 可以解除读端责任；原门禁 T 不恢复 |
| 真实关闭成功后，R-B1-2 注入报告错误 | 门禁拒绝；释放已确认只来自真实 nil，不凭注入豁免任何真实错误 |

最终收尾读取同一个持续结果，真实错误不会因 done=true 而掉出消费者。`:4993` 的“不再调用 Close”与“不存在任务时先调用 closeRead 建立任务”的兜底结合解释即可：已存在的任务不能重建或重试；缺失任务本身按释放未确认移交。

### 3.2 真实接线与模型的证据定位准确

- R-B1-1 在两个现有真实门禁增加必要条件，明确为复制的 until(w) **返回之后**启动关闭，可能早于 w；没有“到 w 才开始却要求 w 前完成”的冲突。
- R-B1-2 真实 Close 先执行，仅在 nil 后注入；真实错误保留且使组合不成立。唯一问题、命中、目标、calls、退出状态、保险与 Final 分别核对，不放宽原门禁。
- R-B1-4 用进入信号证明命中，用可释放闸门制造 pending，以截止核对完成，并调用真实门禁／移交／最终消费将使用的同一组函数。错误 E 对照覆盖“pending 后带错完成”；nil 对照同时要求旧 did-not-return 问题保留。

这足以关闭**计划缺陷**，不等于真实调用者已经兑现接线。实施复审仍须检查三个调用者确实调用这些函数、任务字段在完成信号前发布、错误不遗漏，以及共享消费没有被绕过。不能把模型通过预先写成原生关闭故障已验证。

本轮独立重新读取固定 Go **`2aae1000ea1d4b28923b96db28acf4e3b99d6aff`** 的 Mach-O 生成，以及固定 dyld **`fd8d0c4d52320ebf64db34f3cb280310d905c5ae`** 的范围、状态与展开规则。只核对本次采用的受限格式，不推定运行器 dyld 就是这一公开构建。

| 输入／前提 | 规定结果 |

| 偏移=vmsize−8，节在段尾结束 | 最后一个完整指针可成立 |
| 偏移=vmsize−7 … vmsize−1 | 完整范围不足，T(parser) |

| 最后位置越界或 count 乘加溢出 | 展开前拒绝，T(parser) |
| DONE 后非零、缺少 DONE、非空 weak／lazy | 按本受限格式失败关闭 |

## 5．B-P112-3：主要修订成立，残余 B-P112-3-R 仍阻塞

### 5.1 已经补齐的部分

**位置**：`docs/wp2.5-prototype.md:5178`～`:5261`。

第二稿固定两侧各一进程、各一次、不复用；T_r、25 s 准入、c_k=10 s、q_k=12 s、w_k=20 s、d_k=25 s 都按同一 s_k 计算，不滚动重取预算。充足套件余量下，两侧各占 25 s 具有总计 50 s 的可执行时间线；慢启动或剩余不足应失败关闭，不要求所有机器都能完成。

正常路径的证明也增强了：被测链先返回，才启动唯一 Wait；它运行期间不回收子进程，避免其 PID 动作与回收并发。要求 Wait 确认信号 9、持有者自己的终止请求为零、接缝恰好命中一次，能够排除持有者补救终止被算成被测链成功。helper 自己到期不再被算作清理。

但是下面三段仍未形成闭合的、可按本项截止返回的执行协议。

### 5.2 残余一：持有者终止请求仍可能把未返回操作带回父端

**位置**：`:5211`～`:5219`、出口表 `:5230`～`:5234`、收尾步骤 `:5237`～`:5243`，以及 `:5583`～`:5585` 的“按截止查询／不同步无限等待”。

计划要求持有者先发终止请求，再启动 Wait，但没有像已审 R0～R5 那样把这个请求放入“先登记、可查询的唯一任务”，也没有定义请求本身未返回时的状态和持有者。

**允许的事件顺序**：

1. 身份读取失败，或者被测链已返回但目标仍活着；父端进入自己的终止分支。
2. 在 s_k+13 s 发出 SIGKILL；该调用尚未返回。
3. 由于必须先发请求再启动 Wait，父端停在请求上，根本到不了 until(w_k) 或 until(d_k)。截止只在后续查询里生效，不能中断这个父端同步等待。

这不是声称本轮或原 CI 观测到 Kill 挂起；本轮不运行这项测试。它指出的是**计划没有隔离未返回调用**，却宣称收尾只按截止查询。把信号调用移入任意 goroutine 后立即启动 Wait 也不够：子进程可能先被回收，晚到的 PID 动作又违反本计划的“不回收期间才动作”前提。

**最小修订**：为持有者请求写定先登记、至多一个 pending、完成与错误持续保存、父端按既定截止查询的协议。可以采用已审请求／回收串行规则；也可以让 Wait 只在被测链和持有者请求均已返回后启动。请求未返回时父端不得同步等它，不得为了收尾另发第二次请求，也不得放行可能与晚到信号冲突的回收；持有任务与 Cmd 的责任按截止转入明确的未确认状态。

这是防止外部调用的等待传播到父端，不是要求单次系统调用具备硬实时保证，也不是新增生产机制要求。

### 5.3 残余二：t.Cleanup 的实际时机不能由“每侧一个”推出

**位置**：`:5180`、`:5204`、`:5235`～`:5241`，以及“每侧 d_k、两侧≤50 s”的声明。

当前只命名了一个顶层 TestP5CleanupReal，依次执行两侧；没有写定每侧使用自己的非并行 t.Run，或在离开本侧之前显式、且幂等地完成收尾。若两侧向同一个顶层 t 注册 Cleanup，则第一侧结束并不会触发它。

固定 Go 1.27.3 的规则是：Cleanup 在该 test／subtest 及其子测试完成后执行，并按后登记先执行；不是侧函数返回就自动调用。[testing.go:1438～1467](https://github.com/golang/go/blob/2aae1000ea1d4b28923b96db28acf4e3b99d6aff/src/testing/testing.go#L1438)、[runCleanup](https://github.com/golang/go/blob/2aae1000ea1d4b28923b96db28acf4e3b99d6aff/src/testing/testing.go#L1782)

**当前文字允许的时间线**（普通失败可用 Errorf 记录，不必 FailNow）：

- 第一侧 s_1=0，被测链到 q_1=12 s 未返回，记失败，然后开始第二侧；第一侧 Cleanup 尚未运行。
- 第二侧在 s_2=12 s 合法准入，持续到 w_2=32 s，才记录 Wait 未完成并结束顶层测试。
- 第二侧 Cleanup 先运行；第一侧 Cleanup 到来时 d_1=25 s 已过去。即使第一侧链已在 15 s 返回，计划也没有要求在其尚有清理余量时接手。

这条路径不会按规则恢复 PASS，但与“本侧收尾以自己的 d_k 为最后截止、两侧依次完成”的保证不一致。迟到的 Cleanup 还按第 2 步启动新请求／Wait，未写定截止已过时的准入和出口。

**最小修订**：明确每侧使用非并行 t.Run，并把 Cleanup 注册到该侧的 t；或写定本侧退出前的单次收尾，t.Cleanup 仅作幂等兜底。确保先收第一侧，再准入第二侧；若任何收尾第一次被调用时截止已过，只发布 T／unknown 与责任移交，不重新获得等待预算。FailNow 应只结束本侧并执行其收尾，不靠顶层测试最后返回才接手。

修订后可按原数字推演：第一侧最多到 25 s，第二侧从 25 s 开始、最多到 50 s；没有必要增加原预算。

### 5.4 残余三：到期以后不能只记录“责任未解除”而没有持有者

**位置**：`:5238`、`:5240`、`:5244`～`:5247`、`:5584`。

计划要求到 d_k 链仍未返回时不发信号、不启动 Wait，这能保留 PID 安全前提；Wait pending 也不在父端无限等待。但目前只写了局部持有者及其 Cleanup，没有说明 Cleanup 返回后谁继续持有 Cmd、尚未启动的回收责任、链／请求／Wait 的持续状态与晚到错误。

尤其是“链到 d_k 仍未返回，稍后才返回”这条路径：不能因为曾打印 unknown，就认为其真实结果已被持有和消费。Go 执行完 Cleanup 后会从回调表移除它；不能把注册过 Cleanup 当成直到测试进程结束的资源登记证明。[固定 Go 回调消费](https://github.com/golang/go/blob/2aae1000ea1d4b28923b96db28acf4e3b99d6aff/src/testing/testing.go#L1810)

**最小修订**：明确根测试进程内的持有登记或现有可用的移交结构，保留本侧标识、Cmd、任务、完成／错误结果和“未回收”的责任，直到测试进程结束；不要只保留一条文字。晚到结果只入持续状态，不从工作任务调用已经结束的 t，也不恢复该项或总汇总通过。不要求到期后继续等待、自动重试、借用 D 或宣称资源最终释放；未确认与系统收养仍分别记录。

以上是 **B-P112-3 的一个残余块**：请求任务、每侧收尾时机和到期后的持有责任必须共同写定，不能分别靠“按截止”“Cleanup”“责任保留”三个标签替代协议。其余 B2 的持续错误与消费设计沿用 Review 112 的认可。
