## 二、BLOCKER

### B2-R2：只检查 idx → pack，遗漏 pack → idx，仍会把索引故障当作可靠缺失

**位置：**[wp2.3-git-reader.md §5.2](https://github.com/XKHoshizora/specmetry/blob/5d707eb28e95631cf97808a3287d81375fd0e60f/docs/wp2.3-git-reader.md#L394) 第 400～412、423～427 行；data-model §4.12；MVP-EV-16。

新方案对截断／静默损坏的 idx、不可读目录和缺少 pack 增加了有效防线，比上版明显改进。但存储检查只要求“每个 idx 校验正确，且有对应 pack”。**一个可读 pack 失去其 idx 时，这个要求在空 idx 集合上成立**，并不会证明原对象已被回收。

**独立反例：**Windows、Git 2.56.0.windows.2，全新临时 SHA-1 仓库。提交正常打包后，旧提交可读；只把对应 idx 暂移开，不修改 pack：

| 步骤 | 结果 |
|---|---|
| 完整包索引存在时 batch 查询旧提交 | commit／exit 0 |
| idx 移开后 batch 查询 | missing／exit 0，stderr 为空 |
| idx 移开后裸 cat-file -e | exit 1，stderr 为空 |
| 存储布局 | 1 个可读 pack、0 个 idx；目录可列出，无 alternates |
| 恢复同一个 idx 后重新查询 | 又返回 commit／exit 0 |

现有第 2、3 项对所有 idx 的检查没有对象可查；也没有相反方向的完整配对要求。因此按当前规范仍会把这一可定位的存储故障判为可靠不存在，而不是无法确认。恢复索引即能读出同一 pack 中的对象，证明它不是已回收的对象数据。

**影响：**旧 tip 被误判为正常缺失，扫描可按历史改写扩大范围并发布游标，而不是遵守故障时 exit 6、不写入的保证。这里没有 WP2.3 实现，也没有实际推进 Specmetry 游标；后果由规定的分类与发布步骤直接推出。集合扩大不证明分类正确，亦不能用已批准的正常重扫生命周期豁免故障分类。

**最小修正：**完整检查对象存储中 pack 与 idx 的配对，现存 pack 没有可用 idx 时保守返回无法确认；保留真正对象回收后的正常缺失路径。将 idx 消失／不可访问的正反例加入 K 系列和 EV-16，并覆盖原对象库与 alternates。无需将所有 missing 都永久拒绝，也无需在本 PR 实现扫描器。

文档第 427 行把“可靠不存在”解释为若干观测一致，不能解决这个具体可识别的漏检；它与“不是所有网络文件系统或不可检测 I/O 的证明”不同。

### B3-R2：稀疏索引检查晚于 status，返回不可判定不能撤销已经发生的写入

**位置：**[规范 §4.3](https://github.com/XKHoshizora/specmetry/blob/5d707eb28e95631cf97808a3287d81375fd0e60f/docs/wp2.3-git-reader.md#L196) 第 212～238 行，特别是第 2 步先 status、第 4 步才识别稀疏目录；同类门禁须适用于第 3 步递归子模块。

当前步骤顺序仍是：

1. 建立带 alternates 的私有 Git 目录和索引副本；
2. 执行私有 status；
3. 处理子模块；
4. 根据 ls-files --sparse --stage 的 040000 条目认定不可判定。

报告自己已经正确说明：status 即使复制 sparse-checkout，也可能展开稀疏索引，借 alternates 更新原树对象 mtime。**把结果标为不可判定只是结果门禁，不是副作用发生前的执行门禁。**

**独立复验：**新隔离仓库启用 cone sparse index，明确观察到：

```text
100644 ... included/f
040000 ... outside/
```

在 outside/ 下建立未跟踪文件；私有目录复制原 index 及 info/sparse-checkout，使用白名单配置与 alternates，并设置 GIT_OPTIONAL_LOCKS=0、禁用隐式 Fetch 等受控环境。按第 2 步执行私有 status：

- exit 0，报告未跟踪文件；
- Git 提示稀疏索引正在展开；
- **三个原树对象的 mtime 改变，内容 SHA-256 不变。**

这与目标文档的 S8 机制一致，不依赖缺少 sparse-checkout 副本。最初夹具辅助文件的 Windows CRLF 导致 alternates 解析失败，未作为反例；修正为 Git 需要的 LF 后取得上述有效结果。

**影响：**即使第 4 步最终正确返回 unknown／dirty／exit 6，原仓库已经被触碰，仍违反 data-model §1 与 EV-18 的内容及 mtime 不变保证。P2 选择何种输出或支持范围，都不能追认这一写入。

**最小修正：**在任何可能展开索引的 status、diff-files 或递归读取之前，先以经过验证的非展开列举检查稀疏布局，按负责人最终选择的安全范围提前退出。超级项目和每个子模块均须遵循同一执行顺序；所需选项能力也在用户仓库调用前判定。验收不仅断言最终值，还须断言被门禁的布局未运行危险命令、原对象内容和 mtime 完全不变。无需重构整个 Git Reader。

**B3-R2 仍未关闭。** 已认可的安全列举、复制模式文件与保守拒绝方向可以保留，修正执行顺序即可。

## 四、PRODUCT DECISION：浅克隆加深必须明确生命周期

**位置：**§5.2 第 433～440 行的 last_tip=T／祖先增量规则；§8 P3 第 838 行；游标与发布规则 §5.5。

P3 正确保持待决定，不因它尚未获批而机械列为代码缺陷。但推荐选项 (a) 只有“在声明的浅边界停止”，不足以决定之后加深／取消浅边界如何扫描。

**独立无网络状态模拟：**

- 真实临时提交历史 A → B → C；先令 B 为浅边界且暂移走 A 的提交对象。
- 第一次从 C 扫描，成功得到 C、B，游标按规范记 C。
- 恢复 A，移除浅边界，模拟加深／unshallow 后可访问历史增加；HEAD 仍为 C。
- 此时完整 log 得 C、B、A，但规范 last_tip=T 的路径直接无工作；等价 C..C 的增量为空。A 从未被读到。
- 后续正常新增后代时，仅扫描 C 之后的范围，也不会自然回访 A。

这不是网络 fetch 实验，也没有运行生产扫描器；它验证加深前后的合法 Git 可达状态及现有规划规则的逻辑结果。

**必须补齐的最小决定／设计：**

- 若 P3(a) 意味着每次扫描覆盖当前本地可访问历史，须定义浅边界变化的识别、计划一致性和相应重扫；新出现提交仍以首次发现 seq 入库，已入库关联不补写。
- 若选择加深后仍永不回访旧边界之外的历史，须明确这是额外发现限制，由负责人决定，不能自动归入 §62 对“已扫描但未关联提交”的既有接受风险：A 在本例从未被扫描。
- P3(b)/(c) 也须说明仓库从“不允许扫描”变为完整仓库时如何恢复。选定后同步 WT-06、扫描示例与测试。

本轮不替负责人选择方案，不擅自提高 Git 最低版本。只批准静态 P3(a) 的一句描述，还不足以冻结完整扫描生命周期。
