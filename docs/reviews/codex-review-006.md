## BLOCKER

### R1 / B3：拒绝不兼容数据库时仍可能新建锁文件

**位置**：[store.go:105](../../internal/store/sqlite/store.go#L105)、[store.go:114](../../internal/store/sqlite/store.go#L114)、[lock.go:24](../../internal/store/sqlite/lock.go#L24)。

`Open` 在只读版本检查之前调用 `acquireOpenLock`；后者用带 `O_CREATE` 的 `CreatePrivateFile` 打开 `.migrate.lock`。已有数据库所在目录没有这个文件时，即使最终因版本不兼容拒绝，锁文件也已经创建并保留。

**独立反例：Windows、Linux 均复现。**

1. 用真实迁移流程生成 schema v2 的 `VACUUM INTO` 一致性备份。
2. 将备份复制为一个新、权限合格数据目录里的 `specmetry.db`；该目录没有 WAL、SHM 或锁文件。这是恢复备份的初始状态，测试没有在打开期间删除或替换任何文件。
3. 通过公开 `Store.Open` 路径，以只支持 schema v1 的迁移集合打开。
4. 正确返回退出码 6，提示数据库使用 schema v2。
5. 对比目录快照：数据库内容不变，但新增 `.migrate.lock`，目录修改时间也改变。

现有 [恢复新版备份测试](../../internal/store/sqlite/compat_test.go#L47) 在一个已经执行过 `Open` 的目录里恢复；锁文件预先存在，因此没有覆盖这一状态。

**影响**：违反 [MVP-STO-02](../acceptance-criteria.md#L264) 中“数据库、WAL、SHM 和目录项都不变”的要求。没有发现版本保护被绕过或数据库内容损坏；阻塞原因是明确的 M0 拒绝路径验收未满足。

**建议**：补齐“无锁文件的既有数据库”的无副作用拒绝路径。例如，在需要创建锁文件之前先做一次只读拒绝检查，通过后取得锁，并在锁内再次完成正式预检、连接建立和迁移。必须保留锁内复核，避免重新引入原有升级竞态。另一种可行处理是对不能无副作用取得协调锁的状态直接拒绝。不能在存在等待者时简单删除锁文件，否则可能形成不同锁文件身份上的两把锁。

**关闭条件**：新增通过公开 `Open` 调用的上述反例，断言拒绝后目录项与全部数据库文件不变；同时保留并发升级测试通过。

### R2 / B2：文件状态预检与只读连接之间仍可发生隐式辅助文件创建

**位置**：[readonly.go:89](../../internal/store/sqlite/readonly.go#L89)、[readonly.go:111](../../internal/store/sqlite/readonly.go#L111)、[readonly.go:119](../../internal/store/sqlite/readonly.go#L119)、[readonly.go:124](../../internal/store/sqlite/readonly.go#L124)、[readonly.go:138](../../internal/store/sqlite/readonly.go#L138)。

读取器先观察 WAL、SHM 存在，再建立 SQLite 只读连接。两步之间，另一个普通 SQLite 进程可以关闭数据库并删除辅助文件。随后诊断连接会自行创建辅助文件；读后检测能够报告 Unknown，却不能撤销这些写入。

SQLite 的 `mode=ro` 并不保证不创建 WAL 辅助文件；其官方文档明确允许在目录可写时创建辅助文件后打开只读 WAL 数据库。[SQLite 只读 WAL 规则](https://www.sqlite.org/wal.html#read_only_databases)。

**独立反例：Windows、Linux 均复现。**

1. Specmetry 正常打开并关闭数据库，留下持久 WAL 和 SHM。
2. 通过公开 `Inspect` 调用开始诊断；只在仓库外副本中，在文件状态判定之后、`queryReadOnly` 之前加入调度暂停点。
3. 一个真实独立子进程用普通 SQLite 连接读取并关闭数据库，确认 WAL、SHM 均被删除。
4. 在该子进程完成后记录目录快照，再让诊断继续。
5. Windows 上诊断连接新建空 WAL 和 SHM；Linux 上新建空 WAL。
6. 返回值正确带有 `Limitation`，版本为未知；从“外部关闭完成后”的快照到诊断结束的快照，能明确归因于诊断自身的新增文件仍存在。

测试分别记录了外部进程删除文件后的状态和诊断后的状态，没有把外部进程造成的删除误算成诊断自身的写入。

**影响**：违反 [MVP-STO-07](../acceptance-criteria.md#L270) 和 [architecture §11.5](../architecture.md#115-只读检查) 的零写入承诺。此次没有读到未提交数据，没有误报兼容或健康，也没有修改主数据库内容；问题是诊断自身产生了文件副作用。

[review-resolution.md:585](../review-resolution.md#L585) 已披露此边界，但现有验收和 PD-23 仍要求普通 `Open` 与 `doctor` 保持严格。披露实现限制本身没有将它变成已批准的验收例外。反例使用正常 SQLite 关闭流程，正是 PD-23 已描述的辅助文件状态转换。

**建议**：保留 SQLite 原生锁和事务隔离。诊断应只在能够实际阻止新建或写入辅助文件的读取通路上调用 SQLite；无法建立这种保证时直接报告 Unknown。若实现使用受限的原生 VFS 或操作系统访问边界，应禁止创建和写入，同时继续使用 SQLite 的原生锁，不能重新采用 `immutable=1`、`nolock=1` 或自行解析 WAL。读后的存在情况、大小检测可以用于诊断，但不能作为“没有写入”的证明。

如果产品选择明确排除外部 SQLite 关闭与诊断并发的情形，需要确认并同步修改保证边界及验收；按当前严格契约，本项尚不能关闭。

**关闭条件**：保留上述跨进程调度反例，断言诊断返回 Unknown，且外部关闭完成之后诊断没有新增、改写或删除任何文件。

### N3：并发升级测试可增加明确的启动握手

**位置**：[openrace_test.go:69](../../internal/store/sqlite/openrace_test.go#L69)、[openrace_test.go:81](../../internal/store/sqlite/openrace_test.go#L81)。

## 最终回答

1. **B1、B2、B3 是否分别关闭？** B1 可以关闭；B2、B3 的原有核心漏洞已修复，但严格文件不变验收仍分别被 R2、R1 阻断，尚不能整体关闭。
2. **是否发现新的实际正确性、安全或数据损坏问题？** 发现两项已复现的文件副作用契约缺陷；未复现新的跨用户数据泄露、未提交数据读取、事实覆盖、seq 错误或数据库内容损坏。R2 返回 Unknown，未将其误报为健康。
3. **是否可以保留现有实现，不再全面底层重构？** 可以保留原生 SQLite、祖先路径限制、操作系统打开锁和写事务复核的整体实现。修复上述写入边界，不需要恢复 WAL 解析器或重做存储架构；当前提交尚不能原样验收。
4. **是否具备进入 GitHub CI 验证的条件？** 可以启动 CI，与修复并行；CI 验证本身不等于接受 M0。独立失败反例应纳入修复后的回归，MVP-PLT-01 仍未通过。
5. **M0 代码审查结论：NO-GO。** 依据当前严格验收，必须关闭 R1、R2。恢复命令尚未实现、N1 延期及非必要的架构偏好均未被用作本轮阻塞理由。
