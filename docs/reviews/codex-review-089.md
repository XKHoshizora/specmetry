## 1．结论

**技术 NO-GO；当前不建议合并。** 原因是三处可以通过条文和合法事件序列确定的矛盾：

1. **B1：O3 的宿主拒绝被任务登记清空解除**，超出了负责人已批准的 C-4。

## 3．BLOCKER

### B1．C-4 的宿主拒绝不应因登记清空而解除

**性质：产品决定落实错误。**

依据是 [review-resolution §106](../review-resolution.md) 的 D20/C-4：O3 后当前宿主拒绝新的检查调用，MVP 不承诺长驻宿主恢复；同样的要求已写入 [architecture.md:707](../architecture.md#L707)、[MVP-EV-29:197](../acceptance-criteria.md#L197) 及草案 §17.1/§17.4。

但草案 [§8.6 规则 6:671](../wp2.5-check-runner.md#L671) 只在登记非空时拒绝；H 维度只有空/非空（619 行）；[E3:728](../wp2.5-check-runner.md#L728) 更明确规定“登记清空，新的调用照常”。§4.1 第 2 步、§7.5 也沿用这一条件。

**确定反例（静态事件序列，不是新增实验）：**

1. 第一次调用以 O3 返回，复制/停止任务进入登记。
2. 任务稍后结束，资源可以安全释放，登记清空。
3. 同一宿主再次调用检查：E3 允许打开数据库、读取 Git、执行检查；已批准的 C-4 和 EV-29 要求拒绝。

单次 CLI 入口不能消除内部调用与并发准入契约；“不承诺恢复”也不能同时被写成“清空就正常调用”。

**最小修正：** 将资源登记与宿主拒绝状态分开。可以回收已结束任务、清空资源登记，但 O3 已触发的宿主拒绝状态仍保留到该宿主结束。同步规则 6、E 表、§4.1、§7.5、G1。原子准入、已准入并发调用与退出时的资源所有权继续作为 G1 的冻结前规格。若希望增加恢复能力，需另外提出契约变更，不能算作现有决定的实现细化。

### B2．S6 的 J 起点仍在可能阻塞的停止操作之后

**性质：技术设计与证据同步错误。**

草案 [§17.4 C-2:1295](../wp2.5-check-runner.md#L1295) 已列明“停止读取在阶段 J 内由停止任务完成”，C-3 列出挂起停止的归属；但 [§8.5 S6:532](../wp2.5-check-runner.md#L532) 仍先规定关闭读端、Read 返回错误，之后在 535 行才从“停止读取”开始 J。§8.3 的预算说明也仍是“停止读取之后等复制返回”。S6 的 O3 行仅检查复制是否返回，没有同步描述停止任务仍 pending、带错完成及移交。

这不是尚无生产代码的泛泛疑问。已有 [Review 082 §3](codex-review-082.md)、[Review 083 §3](codex-review-083.md) 的受控 Windows 反例和修复结论明确区分了这一顺序：持有读取引用时同步 Close 可阻塞；正确机制先建立唯一 J 截止，再异步启动停止。当前未变的 [runS6On:426](../../prototype/wp25/dest_test.go#L426) 也采用先建截止、再 startStop，停止与复制共用截止，并移交任务而非丢弃晚到结果。

**静态反例：** 按 S6 第 2、3 步实现，Close 在持有读取引用的路径中等待，J 尚未开始；于是 `timeout_sec + T_kill + T_drain + T_join` 并未覆盖这次等待，也无法按协议到达封闭入口/移交。不能用 C-2 一行“候选”或 G1 的生命周期待办，把正文的先后关系视为已经自洽。

**最小修正：** 正文先建立所有流共用的 J 起点和截止，再将可能阻塞的句柄准备、停止/取消/关闭放入停止任务；J 内同时观察停止与复制，随后封闭；pending 或失败结果必须有持续保存结果的所有者与移交路径。同步 §8.3、S6、O3、提前出口、C-2/C-3 的落点及 G1/G2。Windows 重复取消可以继续明确为有前提的候选；不要求本 PR 实现它，也不要求重跑原型。

### B3．D19 的“未观察到退出”不能证明运行时长下界

**性质：时间字段的技术定义不成立。**

[§10.1:921](../wp2.5-check-runner.md#L921) 将“没有观察到 E-main”括注为“主进程在 T_kill 内仍未退出”，并规定从开始到第一次终止请求的时间是实际运行时间的下界。同步的 [data-model §4.11:379](../data-model.md#L379) 也声称是下界。

但本版 [§8.2:442](../wp2.5-check-runner.md#L442)、[C-19:1312](../wp2.5-check-runner.md#L1312) 将运行中的观察失败归入 F1/D19。F1 不只包含一个被可靠观察为仍存活的主进程。

**合法静态反例：** 主进程在 t0 启动，t1 自行退出；退出/状态观察失败，没有得到 E-main；t2 才发出第一次终止请求，并且此后无法可靠确认。t0 < t1 < t2。该路径属于 F1/D19，却按当前条文写入 t2−t0，并称它为真实运行时间 t1−t0 的下界；实际它更大。这里没有要求制造 PID 复用或新的硬件故障。

`finished_at = 放弃等待、尝试记录的时刻` 是清楚、可实现的展示语义；问题是 duration 的证据解释。仅声明“不参与推导”不能使错误的下界断言成立。

**最小修正：** 区分已观察退出、可靠观察仍运行、退出时刻未知。只在有相应证据时称实际值/下界；未知路径可保留同一数字字段，但必须写定保守取值及其展示含义，不能再将首次终止请求时刻无条件当作运行下界。同步 §8.3、§10.1、data-model、EV-28、E9/G12。无需为修正知识状态自动增加新字段或新产品决定；若选择增加字段/改变对外语义，再单列所需批准。

## 4．NON-BLOCKER 与冻结前澄清

以下问题没有单独作为本轮 NO-GO 的依据；不能据此把未完成的冻结前规格宣称为已满足。

### N1．无进程的结束上下文失败应在状态表中显式保留

[§4.2:139–143](../wp2.5-check-runner.md#L139) 规定 input_missing/spawn_error 没有本次消费者、仍直接读取结束上下文；读取失败按 D6。§6.2 也将 D6 置于 input_missing/spawn_error 之前。可是在 [A8:684](../wp2.5-check-runner.md#L684) 与 §7.5 的 D6 行中，U 一律是“已运行”，T 一律是“已确认结束”。

这遗漏了“不启动进程 + 结束上下文失败”，以及它之后的写入失败/提交不确定组合。最小澄清是在 D6 行允许 U 未运行、T 没有本次进程，并保持 duration=0；D6 的不合格记录、停止6和 P 叠加不变。不能在输出中声称用户代码已运行或曾确认一棵实际不存在的树。已有 §4.2 和 §6.2 足以确定修正方向，不需负责人重新选择 D6。

### N2．C-5 与容量上限的正文落点不同

[C-5:1298](../wp2.5-check-runner.md#L1298) 建议容量耗尽后继续读取并丢弃；[§9.1:833](../wp2.5-check-runner.md#L833) 却规定写错误使复制结束。前者可让高输出命令继续运行，后者可能阻塞写者或触发断管，两者不是同一个机制。

C-5 仍是待审查采纳建议，不是已批准的正文行为。冻结前须选定并统一“转发不完整”的记忆、是否继续读、D/J 和停止时机；不得将“只针对受控目的端”当作两种机制已经等价。D20 的结果/qualifying 不自动改变这一点保持不变。

### N3．D7 下的 E-tree 不必带来 EOF

[S6:531](../wp2.5-check-runner.md#L531) 的“写端已没有持有者、读端会 EOF”及 [§9.1:825](../wp2.5-check-runner.md#L825) 的概括须限于保证范围。获批 D7 允许范围外进程继续持有继承写端；确认 E-tree 不证明这些写端全部消失。D 到期后进入 J/O2/O3 的协议仍可处理它，故不因此重开 D7；只需删除无条件 EOF/全部进程不再输出的推论。

### N4．G13 的 L 类不能免掉通常可执行的取消测试

G13 将真实控制台取消与不可中断睡眠、强制 PID 复用等一起列作 L。冻结前可以如实保留难以构造的极端机制证据限制，但 [EV-23](../acceptance-criteria.md#L191)、§15 与 G15 明确要求生产层的 SIGINT/SIGTERM/控制台事件、取消与事务组合。应将通常可执行的取消接线测试归 P，L 只指明确未覆盖的特殊宿主/环境，不能读成取消整体不需要验收。

### N5．Windows 安装布局与工程细化的批准边界

G8 对无法可靠定位 Git for Windows 来源的候选保守判不可用，符合 D1/D2。对同一已批准来源增加便携版、shim 的可靠定位，不一定自动构成新产品决定；是否改变来源种类、支持平台或已批准查找政策才是判断点。建议把“支持这些布局须负责人另行决定”收窄为实际改变支持范围时需要决定，普通路径识别设计由技术审查确认。

## 5．§8.6 组合、持久化与输出

除上述明确问题外，新的分维度结构基本正确，且没有以退出码替代检查结果或 qualifying：

| 组合 | 静态核查结果 |
|---|---|
| 取消，T 已结束，写事务前 | 当前项不记录；后项停止；已有事实保留；environment/6，不误用 human_required/3 |

| 已提交 + 写出失败/短写 | environment/6；可能已有部分 stdout，不追加第二份 JSON；可用 stderr 尽力提示，不盲目重试 |

独立读取了 [store.go:382](../../internal/store/sqlite/store.go#L382)、[withTx:406](../../internal/store/sqlite/store.go#L406)：WriteTx 在回调前 checkWritable；withTx 的函数体失败走 Rollback，函数体成功之后才调用 Commit。每次事务单独初始化“函数体成功”标志，可用于区分上述阶段；**函数体成功不证明 Commit 成功**。本轮未修改存储层、错误映射或重试。

error.v1 的既有结构能承载受控 message/details；D10 不需要输出命令、工具输出或新增未定义字段。有限字段无法保证故障 stdout 必然完整，这一点在草案中已保留。正常 Open 或方案 B 的既有辅助文件/生命周期没有被提升为文件系统零变化保证。
