## 二、BLOCKER

### B1：--ignore-missing 不只忽略排除项，正向 tip 缺失会被当作成功空扫描

**位置：**[WP2.3 规范](../wp2.3-git-reader.md) 229、236、246～247 行；与 318～323 行的游标写入组合后产生问题。

草案把 --ignore-missing 描述为仅用于已经回收的负向旧 tip，并断言只会扩大范围、不会漏读。但该选项是整个 revision 解析的设置，并不只作用于 --not 后的排除项。

**独立复验：**Git for Windows 2.56.0.windows.2，隔离仓库已有一个有效提交；另使用一个确认不存在的 40 位对象 ID 作为正向 tip，从 stdin 输入正向 tip、--not 和有效排除 tip：

| 命令路径 | 结果 |
|---|---|
| log --ignore-missing --stdin --format=%H | exit 0，零条提交 |
| 相同输入，不带 --ignore-missing | exit 128 |

这与 [Git 2.32.0 revision.c](https://github.com/git/git/blob/v2.32.0/revision.c#L2070-L2085) 一致：名称解析或对象读取失败时，ignore_missing 可以把失败转换为成功，不检查该参数是否是负向排除项。[官方选项说明](https://github.com/git/git/blob/v2.32.0/Documentation/rev-list-options.txt#L205-L207) 同样没有“只忽略负向项”的限制。

**合法触发历史与影响：**扫描固定了新 ref 的 tip T，之后该对象在实际 log 读取前消失或无法读取。按草案命令可能得到 exit 0、没有候选，再按 §5.5 将 last_tip 写成 T。下一次仍见 T 时会认为不需要读取，遗漏被固化为成功游标。这违反“必需对象读取失败则 exit 6、不写入、不推进游标”。

本轮没有动态制造 GC 竞态，也没有实现扫描器；已复验 Git 的实际命令语义，并给出按草案流程必然存在的错误路径。较早验证一次 T 不能消除验证与 log 之间的窗口。

**最小修正：**

1. 实际遍历必须严格读取全部正向 tip，不能用全局 ignore-missing 掩盖其失败。
2. 将可省略的负向旧 tip 与必需正向 tip 分开处理：只省略能够可靠确认已不存在的负向项；无法区分缺失与读取错误时返回环境错误。
3. 最终 log 使用严格参数；负向对象在准备后又消失，也应使本次失败、不推进游标。
4. 加入“正向对象缺失／读取失败”和“负向旧 tip 已不存在”的独立反例。不能只覆盖作者 L8 的负向缺失成功对照。

### B2：旧 tip 缺失的退出码判断不成立，无法执行规定的改写后全量重扫

**位置：**WP2.3 规范 228、232 行及 IsAncestor 的 missing 返回值设计。

草案规定：is-ancestor 返回 128，随后 cat-file -e <old>^{commit} 返回 1，就视为旧 tip 不存在。实际对缺失对象加上 ^{commit}，Git 会在解析／剥离阶段失败，通常返回 128，不会到达普通存在性检查的返回 1 路径。

**独立复验结果：**

| 命令 | 结果 |
|---|---|
| merge-base --is-ancestor <不存在的完整ID> <有效提交> | 128 |
| cat-file -e <不存在的完整ID>^{commit} | 128 |
| cat-file -e <不存在的完整ID> | 1 |

[Git 2.32.0 cat-file.c](https://github.com/git/git/blob/v2.32.0/builtin/cat-file.c#L81-L112) 也明确分开了对象表达式解析失败与 -e 的存在性结果。

**影响：**游标中的旧 tip 在历史改写后被回收，属于草案明确承诺处理的状态，却无法命中“旧 tip 已不存在”的分支。它会被当成环境错误，反复拒绝扫描，而不是严格读取新 T 的全部历史。

**最小修正：**重新规定“存在、可靠确认不存在、无法可靠读取”三态探测，不把带剥离表达式的 exit 1 当成缺失证据。普通完整 ID 的 -e 可帮助拆开解析步骤，但单独某个非零码仍不能穷尽证明没有权限、损坏或 I/O 问题；不确定时 fail-closed。补旧 tip 缺失、旧 tip 存在但不可读、新正向 tip 不可读三类测试，并与 B1 的严格遍历规则同步。

这是技术判别错误，不需要负责人批准“缺失对象一律视为正常”之类的新豁免。

### B3：Clean 的 status 命令会执行 clean／process filter，受控环境和 Lazy Fetch 门禁不足以保证只读

**位置：**WP2.3 规范 §4.3，175 行；§6 的 Clean 与 runObjects 调用约定。对照 [gitx 的读取边界](../../internal/gitx/gitx.go) 及 [architecture §6.1.2](../architecture.md)。

新增方案直接运行 status，只覆盖了 FSMonitor、Lazy Fetch、可选锁等机制，没有阻断仓库属性与配置选择的 filter.<name>.clean／process。Git 为判断仅 stat 变化的文件是否真的修改，可能转换工作区内容并调用这些程序。

**独立最小反例：**

1. 临时仓库跟踪文件 f，.gitattributes 中声明 f 的 filter 驱动；建库时没有配置过滤程序。
2. 提交后，把该驱动的 clean 设为一个不存在的合成程序名，required=true。
3. 只改变 f 的修改时间，不改变内容。
4. 在与草案相同的受控环境、core.fsmonitor=、GIT_OPTIONAL_LOCKS=0、空协议允许列表下执行草案 status 命令。

实际 exit 128，诊断表明 Git 尝试启动该外部过滤器：

```text
cannot spawn specmetry-review050-nonexistent-executable
cannot fork to run external filter
clean filter 'review050' failed
```

去掉该过滤器配置后，相同文件状态下命令 exit 0、输出为空。

本轮故意使用不存在的程序，没有实际执行过滤器、写标记程序或发起网络请求。程序调用路径另外由 [Git 2.32.0 read-cache.c](https://github.com/git/git/blob/v2.32.0/read-cache.c#L218-L229)、[object-file.c](https://github.com/git/git/blob/v2.32.0/object-file.c#L2237-L2254)、[convert.c](https://github.com/git/git/blob/v2.32.0/convert.c#L981-L1004) 及当前版本源码交叉确认。若配置的是实际存在的程序，这条路径会执行它；Lazy Fetch 探测不能限制它的文件或网络副作用。

**影响：**按草案实现的普通状态读取，就可能执行仓库配置的程序，先产生副作用再报告读取失败。它不等于用户明确触发的 Check Runner。作者 S5 的普通索引修改时间不变，不能证明这条执行边界成立。

**最小修正：**冻结前为 Clean 写出并验证不会启动过滤器的实际策略：使用不会触发此转换路径的读取机制，或对实际 Git 进程强制隔离过滤器执行；不能只在较早步骤检查一次配置。无法保证时应保守拒绝读取并说明环境限制，不能报告 clean。补 clean／process 驱动的隔离正反例，验证没有程序执行或仓库副作用。若选择限制这类仓库的支持范围，应明确披露兼容性影响，不自行降低既有只读／无出站网络保证。

这不是要求本 PR 提交 Git Reader 实现；要求修正尚不能满足安全承诺的读取方案。D1 的子模块参数即使获批，也不能单独解决该问题。

## 三、NON-BLOCKER：需要补齐的兼容性、措辞与单位

### N1：Git 2.32 的命令支持不能从 Windows 2.56 推广

[Git v2.32.0 builtin/worktree.c](https://github.com/git/git/blob/v2.32.0/builtin/worktree.c#L674-L689) 的 list 参数表确实没有 -z。草案 208 行命令不能在这个版本直接使用。此外，[v2.32.0 revision.c](https://github.com/git/git/blob/v2.32.0/revision.c#L2107-L2132) 的 --stdin 模式拒绝 --not 这样的选项行；草案 247 行把 --not 放进 stdin 同样有版本问题。负向完整 ID 可以考虑用 ^<SHA> 行表达，但仍需实际兼容测试。

关键区别：

- 最低 Git 2.32 是配置隔离下限，不是“每项对象读取都能成功”的保证。
- 已批准 PD-26 另要求实际对象读取能力。既有真实 2.32.0 记录为不具备能力，应在对象命令前 exit 6；本轮不推翻此边界，也不擅自提高最低版本。
- 若先经 PD-26 拒绝，不能再把 -z 的失败宣传成已验证支持；若元数据入口单独调用 worktree list，必须定义能力探测、兼容读取或明确拒绝。
- 不可简单退回“按行切分路径”：该旧版本的 porcelain 路径直接输出，路径中的换行会造成歧义。应有可靠解析边界，不能靠猜测。
- 2.43.0 的官方源码支持上述 worktree -z，并已有较新的 stdin 选项处理；这是静态核查，不是本轮真实运行 2.43 的实验。

建议补命令／选项／能力的兼容矩阵与测试计划，明确旧版本的安全拒绝路径。不存在“所有 2.32 必须完成对象读取”的既有保证，因此不只凭不支持 -z 自动另列一个 BLOCKER；但该部分尚不能宣称全版本验证或无条件冻结。

trailer 的 key 大小写、valueonly、separator=%x2C，以及 ls-tree 的 -z、--full-tree、全局 --literal-pathspecs，在 v2.32.0 的[官方 pretty-format 文档](https://github.com/git/git/blob/v2.32.0/Documentation/pretty-formats.txt#L281-L303)、[ls-tree 参数表](https://github.com/git/git/blob/v2.32.0/builtin/ls-tree.c#L134-L145)和 git.c 中已有依据。没有发现这些格式本身需要提高版本。

### N2：无业务候选仍需游标事务；补足验收前置条件

294 行“没有任何像编号的词时，不必进入写入事务”与 §5.5 的空扫描更新游标容易冲突。应改为“不产生提交／关联候选”，游标仍按整次扫描的事务规则更新。否则会不断重读历史，scanned_at／节流也不能按约定工作。

L1／MVP-EV-15 的“编号尚不存在”测试需明确：项目已有其他需求或 AC，使 D5 不会直接跳过整个扫描。否则“没有扫描”和“扫描了但未入库”不能证明同一生命周期结论。

### N3：提交时间的存储单位与通用模型不一致

草案 433 行规定 committed_at 保存秒，而 data-model §1 的通用持久化时间是 UTC Unix 毫秒。Git API 的 %ct／Commit.Time 使用秒可以保留，但入库时应转换为毫秒，或显式同步一个经确认的字段例外。建议使用毫秒以保持既有约定，无需为普通转换增加产品审批。

## 四、决定与规范的一致性

§62 已批准的三项决定在 data-model、architecture 和主草案中得到正确表达：

- 固定匹配 trailer 与正文，不新增 commit_ref_mode 开关；
- 编号按现有 Requirement／AC 格式、整词匹配，项目内查找，退役条目仍可关联；
- trailer 优先，同提交同实体只留一条；
- 已入库 SHA 的关联首次固定，不补写，不在旧 seq 上追加未来事实；
- 未入库提交以后首次满足条件时使用那次发现 seq；
- 没有新入库提交时不分配业务 seq，但可以更新游标。

因此 commits.seq ≤ as_of_seq 加所属关联的历史读取前提可以成立。前提是实现只走同事务首次发布路径，未来也不能给旧 SHA 补链接。关联只提供参考进度，没有改成完成或验收证据；只关联 Requirement 的提交也没有被擅自改为直接贡献 AC 进度。WP2.1／WP2.2 的已验收算法和 ready 条件没有变化。

ASCII 字母／数字／下划线／连字符最长词、大小写与编号长度、trailer 与完整消息去重等细化自洽。跨项目同名编号的不可区分性已有披露，不新增项目限定 trailer 功能。

## 五、TD-23 的逐路径机制与可冻结部分

逐路径 ls-tree、literal pathspec、查找规范化与保留原 path 的区分总体可保留：

- 每次只查一个规范化路径，避免前缀路径相互改变输出；
- 目录查询不带末尾斜杠；
- 只有一条且路径完全匹配才接受；
- 仓库根用 ^{tree}，约定 040000／tree 是元数据细化 D3，不改变原保存路径或 check_config_hash；
- 缺少声明路径与读取必需对象失败分开；
- 查询叶条目的元数据不要求读取其 blob／目录树，不把 gitlink 指向的提交当作上级仓库必需对象；
- 所有对象读取继续经过 PD-26，不要求运行 LFS、子模块检出或过滤器。

本轮 Windows 2.56 独立夹具得到：普通文件 100644/blob、目录 040000/tree、深层文件精确路径均正确；不存在路径及大小写不匹配返回 0 且为空；根树解析成功；必需提交缺失返回 128。未动态重做作者全部 T1～T23，尤其没有删除叶对象、打包对象或运行真实部分克隆。

这些基础机制具备冻结方向，不必等实现代码完成才认可设计。但不能把本轮有限验证扩大到 Linux／macOS、2.32 实际运行或所有 L1～L4 状态；应在实现验收中完成计划中的平台与对象边界测试。TreeEntry 与 Clean 是两种不同调用链，前者不触发过滤器不能证明后者安全。

## 七、并发、三张表与历史发布

§5.5 的整体边界可保留：读事务取 C；Git 读取不占数据库事务；BEGIN IMMEDIATE 后重新比较 C、去掉已入库 SHA、按当前项目解析编号，最后统一提交。

- 有新增提交时只分配一次 seq，同批 commits 多行共享；commit_links 与游标同事务写入。
- 无新增提交、首次无匹配、只有重复 SHA 时不分配 seq；首次 scanned_seq 为 NULL，已有游标保留上次有入库扫描的 scanned_seq。
- 多 ref 共用 SHA 在同一候选集合去重，数据库 UNIQUE(project_id,sha) 作第二道防线。
- 删除 ref 的游标保留不会改写已发现事实；其排除项读取仍受 B1／B2 约束。
- 每个 tip 固定为完整 ID 后读取，比后续反复解析 ref 更可靠。但“开始时一次取得”是固定读取结果，不是数据库、所有 ref 和所有 worktree 的全局原子快照。
- 失败不得发布部分结果。B1 修正后才能保证“读取失败不推进游标”；单有 SQL 回滚不能补救 Git 把失败报告为成功。

迁移设计的项目列、提交复合外键、唯一性、非唯一共享 seq、受控可变游标和只追加表方向正确。建议：

1. 对 commit_links 增加同项目、对应 target_type 的 BEFORE INSERT 检查；应用仍按 project_id 查询。触发器或应用的分层属于工程选择，不要求负责人决定。
2. 只追加保护覆盖 UPDATE／DELETE／REPLACE，并延续每连接 recursive_triggers。
3. “关联只在提交首次入库事务内发布”是必需不变量。现有只追加约束本身不能禁止未来 INSERT 新关联，必须由唯一扫描写入入口、旧 SHA 直接跳过和相应回归测试保证。
4. 不建议为了这个不变量新增复杂的事务令牌模型；也不要使用“parent.seq 等于当前计数器”就声称已证明同事务，计数器在事务之间可能不变。
5. 迁移测试覆盖跨项目 target、类型不匹配、重复关联、维护／purge 外键，以及后续扫描不补写旧 SHA。

这些属于实现前可明确的技术约束，不需要改变已批准的发现 seq 或推导规则。

## 九、M-14 的独立边界

M-14 不在 PR #24 的修复范围。本轮没有运行数据库诊断、读取本地新增诊断测试或要求在此 PR 修复它。

对固定目标的 [store.go](../../internal/store/sqlite/store.go) 静态核查，相同“cannot read the database version”包装分别出现在：

- 124 行：原生只读兼容性预检失败；
- 167 行：已建立读写连接后的再次 readMeta 失败；
- 394 行：WriteTx 内 checkWritable 的 readMeta 失败。

因此不能仅凭这段错误文字排他定位到只读预检。辅助只读探测能重现相似错误，不等于已验证真实 Open 完整路径，也不等于证明 macOS 同根因。

能够区分的保证：

- 失败的该次写事务不会继续执行其业务回调；Open 在对应失败点不会继续执行后续初始化／迁移工作。
- 这不等于整个辅助进程此前没有成功事务，也不等于其他进程没有提交；不能据此声称全局 seq／数据库在一段时间内完全不变。
- 预检之前允许首次创建私有空 .migrate.lock；已批准的特定外部关闭竞态还允许原生只读连接创建必要的空辅助文件。错误发生在后续读写阶段时，更不能仅凭包装文字套用“从未打开读写连接”。
- “本次业务调用未提交”与“所有数据库／WAL／SHM 字节绝对不变”是两种不同结论；本轮未验证后者，也不新增豁免。
- §61 与 M-14 活跃记录保持根因待调查、重跑不关闭、不是接受风险的措辞，正确。此次 CI 成功不关闭 M-14。
