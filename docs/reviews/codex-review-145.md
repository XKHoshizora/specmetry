## 4. 发布资格及新动作准入的可采部分

### 4.1 新动作与消费分开看

第 487、489、513～515 行已覆盖此前遗漏的三个新动作接点：

- 父端等待快照点返回后，重新核对原 D，不能用 m.Run 返回时的旧检查代替。
- 诊断等待写者终态后，在开始输出之前再核对；已有 Done 不是输出许可。
- 每次诊断写入返回后，发布真实结果，并对下一次输出重新核对；已经开始的一次 I/O 不被强行中断，但不会因此获得无限后续写入。

第 513 行在外层锁下复核、取得外层快照、算暂定结论、发信号并登记诊断，锁外启动任务；诊断第一次外部写入又有自己的复核。这不是要求检查、启动 goroutine 与下一条指令硬实时原子。已知到期后不得作新决策，与检查后短暂调度延迟不能被消除，是两回事。

第 513 行在复核之前允许读取 R／F 的内存快照，并不授予诊断启动权限；情形 1 的“不取快照”宜理解为不再生成外层／暂定结论快照，而不是禁止消费已有内存状态。此处是范围措辞，未发现它另外引入外部 I/O 或权限旁路。

半构造、写入错误和关闭错误的收尾仍受原 D 约束；失败出口没有重新获得一段关闭预算。未完成句柄和已启动外部操作由登记表／原任务持有，不在 D 出口同步打印、刷新、关闭或等待。

### 4.2 “同一次锁下”与逻辑判定点

第 494 行给出了可实现的资格规则：发布者在外层登记表锁内读取时钟与锁存，确定资格，并连同结果保存；资格不再修改。它保证别的参与者不会插入一个相反的锁存／发布决定，并不保证线程在这段短临界区内绝不被暂停。

本报告按该**锁内读时钟并确定资格的逻辑判定点**评价，不要求实际字段赋值、解锁或其他 goroutine 观察到结果与它具有硬实时原子性：

| 事件 | 按当前资格规则的解释 |
|---|---|
| 发布者先取得锁，但到实际读时钟时已经等于或超过 D | 晚到。先取得锁本身不够 |
| 外部调用早于 D 开始，但返回后到发布判定点已经超过 D | 晚到，即使返回 nil |
| 输出字节早于 D 写完，但未进入发布判定点，直到 D 后才进入 | 晚到；日志存在不能代替资格 |
| 在锁内判定点读到早于 D、锁存未置，随后在同一临界区内保存该决定 | 按该逻辑点确定及时；不另要求字段实际可见时的墙上时间也早于 D |
| 先有到期锁存，后有成功发布 | 晚到，不能清锁存或恢复结论 |
| 判定点恰好等于 D | 不满足“早于 D”，为晚到 |

**措辞精化建议（非阻塞）：**第 496 行和修订对照的“只由锁的先后决定”应读作“锁串行化下的时钟／锁存判定”，不能缩减成“先抢到锁即及时”；可直接把上述逻辑判定点写明，避免把第 495 行“发布”误读成必须证明物理可见时刻。当前第 494 行已有时钟与锁存两个条件，所以不据此另列阻塞，也不要求一套新的时间协议。

### 4.3 必要结果与终态的关联

第 563～567 行已经要求每一项必要结果和最终终态都成功、及时，而不是只看一个 Done：记录写入、每个记录文件真实 Close、manifest 建立／写入／Close、写者终态；诊断的全部写入和含终结行的完成终态。

按当前顺序，写者先完成所列操作才发布成功；诊断等待写者终态再继续。任一早先结果晚到会置不可清锁存，因此随后成功终态不可能重新获得及时资格。任一真实错误持续保存，写者失败或诊断写入失败也不会被后来的 nil 覆盖。写者失败后诊断最多取得“完成，没有终结行”，不能满足最终 3／4 的要求。

所以父端使用汇总终态判断，在**固定实现确实消费全部必要结果**的前提下有条件证明；并非要求把所有 I/O 重做一遍。实际实现必须核对这个汇总关系，不能只给最后一个 Close 或最后一行 Write 打及时标签。
