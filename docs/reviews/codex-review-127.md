### 3.1 B-126-1：主体成立，残余 B-126-1-R 未关闭

**成立部分**：实施计划 1066～1120 行已区分非零退出、复制／上下文错误与没有 ProcessState 的未知；保留记录由唯一闸门强持有 Cmd、租约、PID、原错误和 panic 信息。保留共享仍占计数，保留排他仍占 holder；后续成功不会解除。`UnreapedError` 包装原错误，既有调用方映射不新增禁用条件。Windows 的“回收”明确限于确认结束并取得状态，没有把它写成 Unix 僵尸语义。

固定 Go 1.27.3 的 Windows `Process.wait` 在 WaitForSingleObject 成功之后，还可能在 GetExitCodeProcess 或 GetProcessTimes 失败而返回 nil 状态。因此 ProcessState 非 nil 是充分的成功判据；nil 则可能已经结束，也可能未知，按未知保留是保守而非假报活着。参见 [Windows wait](https://github.com/golang/go/blob/2aae1000ea1d4b28923b96db28acf4e3b99d6aff/src/os/exec_windows.go#L18)。Unix／Linux 的 Wait 错误也没有被合法 NULL 或后续读数豁免。

**B-126-1-R：Process 为 nil 只证明没有交付 Process，不能一概证明从未创建内部子进程。**

位置：实施计划 **1070、1078、1099、1335 行**；冻结 §19.4:1717、1730、1742，处理记录 §161:10268。

1070 行声称 Unix exec 失败的子进程“已由 syscall.forkExec 自己回收”，1078 行据此将 Process=nil 一律作为“没有创建子进程”并释放。固定源码实际是：fork 成功后读取错误管道；失败分支调用 Wait4，**只重试 EINTR，退出该循环后不检查其他等待错误**，随后返回启动错误和 PID 0。高层因此可以得到 nil Process，而内部子进程已经存在过，回收未获确认。参见 [forkExec:207～244](https://github.com/golang/go/blob/2aae1000ea1d4b28923b96db28acf4e3b99d6aff/src/syscall/exec_unix.go#L207)。

允许的序列：已 fork→子进程 exec 失败→父端取得启动错误→内部 Wait4 被运行环境拒绝／返回非 EINTR 的错误→forkExec 仍返回原启动错误与 PID 0→Cmd.Process 为 nil→按现稿释放共享租约。此时可能遗留未回收子进程；不能因为 Start 返回了错误就认定排净。这是静态错误出口推演，不声称本轮运行过 seccomp 或观察到该原生故障，也不要求 Go 的每个内部操作具备硬实时保证。

**最小修订**：把“没有交付 Process”“确定在创建之前失败”“内部创建／清理知识未知”分开。对不能从现有 API 可靠区分的启动错误，选择保守保留租约／Cmd／错误／未知责任，或把要依赖的标准库清理前提明确提出审查和负责人确认；不能继续引用 Wait4 的存在就声称它成功。不要求重写 Go 的启动器、重试 Wait、补发信号或提前实现第四批。E-5、接口注释、出口表和回归预期须同步。

**panic／夹具限定**：自锁 holder 身份与同锁同步、gitx waited 的出口修订成立。独立关闭写端和唯一 Wait 的设计解决了 started panic 等待自身 defer 的问题。但在实施前还须明确：若 started 的 panic 与随后 Wait 的 panic 叠加，两项原始信息都保留、一个租约只追加一份责任记录；不能由第二个 panic 覆盖第一个。Cleanup 读取 Cmd.Process／发 Kill 须有已启动的同步证据；Wait 替身的唯一真实 Wait 必须在独立任务中有父端截止出口，不是把同步 Wait 旁边写上“有截止”。这些不代表实际夹具已经验证。

## 4. 新阻塞 B-127-1：C-9 工具取消与回收之间缺少安全控制协议

位置：实施计划 **1465～1469 行**；冻结 §19.4 的归属／回收前提及 §163 第 6 项的截止、未知收尾要求。

### 4.1 向 -PID 发组信号可能发生在直接子进程已被回收之后

计划给工具新进程组，并把 Cmd.Cancel 改为向整组 SIGKILL，却只规定唯一 Wait，没有规定“回收标记与组信号动作”串行。

固定 Go [watchCtx:807～830](https://github.com/golang/go/blob/2aae1000ea1d4b28923b96db28acf4e3b99d6aff/src/os/exec/exec.go#L807) 的取消调用可以与 Process.Wait 竞争；[Cmd.Wait:944～952](https://github.com/golang/go/blob/2aae1000ea1d4b28923b96db28acf4e3b99d6aff/src/os/exec/exec.go#L944) 在回收后才与 watchCtx 交换结果。自定义 `kill(-pid, SIGKILL)` 不使用 Process 自己的身份／信号锁。

允许的序列：工具已正常退出并被 Wait 回收→Wait 尚未接收 watchCtx 结果→W 到达，watchCtx 选择取消分支→原 PID／PGID 数值可能已复用→自定义组 kill 对这个旧数值动作。唯一 Wait、Start 时 Setpgid 和取消上下文都不能排除此序列。此处报告的是静态可达的竞态，不是本轮构造了 PID 复用。

**最小修订**：明确回收与动作的串行协议／身份依据，或在证明工具不产生后代的限定下保留身份安全的直接 Process 取消并单独处理未知后代。不得仅把 Process.Pid 当作永久组操作授权；不得通过给同用户进程扩大动作范围补救。

### 4.2 WaitDelay 不是工具全部等待和清理的总期限

计划只给同步分析线程写了 W 的父端选择出口，工具路径则依赖 CommandContext、Cancel、WaitDelay。固定 Cmd.Wait 首先调用 Process.Wait；WaitDelay 既不使取消动作必然完成，也不把“已请求终止”变成可靠结束／回收。单次系统调用没有硬实时保证，恰恰意味着父端不能把它直接放在必须按 D 收口的同步控制路径上。

须固定：先登记工具及等待／取消／输出任务，父端只按 W/D 查询；请求失败、等待未完成和晚到错误由谁持有；D 后不重新取预算；完成之前不读 ProcessState 或仍被写入的输出；未确认一律持续失败。不要只在工具返回之后检查耗时。

1469 行“预期没有后代，未验证”是诚实的证据限制，但还不是判定协议：若后代关掉继承的输出并继续运行，不一定出现 ErrWaitDelay，不能由没有该错误推出后代不存在。要么以固定源码／受控前提证明这两个具体工具不会产生有关后代，要么定义可靠观察和责任清单；观察失败、未知或清理未确认必须使整包失败。

这些修订可以限于测试工具的持有／控制，不要求本批先完成生产 Runner，也不要求加时或增加作业。

### 5.2 B-127-2：setsid／timeout 不能兑现现稿的会话和后代收尾

位置：链接计划 **184～199 行，尤其 195～197 行**。

1. **会话不是信号目标**。setsid 创建会话和初始进程组，但一个会话可以包含多个进程组；普通 kill 的负 PID 选择进程组，不是整个会话。现稿“截止时向会话发信号”没有可直接实施的操作。GNU timeout 的默认机制向监控子进程和它自己的进程组发送信号，并非枚举／终止整个会话。
2. **包装顺序和直接子进程身份未固定**。util-linux setsid 在调用者已经是组长时会 fork；未使用 wait 模式的父进程可先返回成功。驱动若等待的是这一层，不能把其返回值／PID当作实际 timeout 或构建进程的完成和 SID。必须固定命令嵌套、选项、启动握手和真实 PID/SID/PGID。
3. **正常提前退出也可能遗留后代**。timeout 监控的是直接命令；命令退出会结束这次监控。后代可以另建组；若另建会话，原 SID 的最终空集合也不能证明它已结束。当前“所有后代都在这个会话中”没有给出固定工具的约束依据，也没有脱离该集合时的责任跟踪。
4. **期限与关闭不闭合**。`--kill-after=10s` 是初次信号之后的追加时间；kill 请求／退出码 137 不是全部对象结束证明。35 分钟 D、3 分钟清理余量和这一追加 10 秒的具体消费尚未写成同一时间线。setsid／timeout／命令各由谁唯一 Wait、输出由谁关闭、观察失败后谁继续持有，也未定义。

依据不是一般性猜测：独立读取 util-linux v2.41.3（提交 `5305e6c70b274f679329b79c0e1ef5a07e9dc1a6`）的 [setsid.c:98～123](https://github.com/util-linux/util-linux/blob/5305e6c70b274f679329b79c0e1ef5a07e9dc1a6/sys-utils/setsid.c#L98)，以及 GNU coreutils v9.8（提交 `76e161dc2d70f2d3e0b908e756d62be91bb72c41`）的 [timeout 信号范围](https://github.com/coreutils/coreutils/blob/76e161dc2d70f2d3e0b908e756d62be91bb72c41/src/timeout.c#L196)、[等待直接子进程](https://github.com/coreutils/coreutils/blob/76e161dc2d70f2d3e0b908e756d62be91bb72c41/src/timeout.c#L580)。这些是固定版本方法参考，不是未来 ubuntu-latest 上实际工具版本的取证。[kill(2)](https://man7.org/linux/man-pages/man2/kill.2.html) 和 [setsid(2)](https://man7.org/linux/man-pages/man2/setsid.2.html) 的范围与之相符。

**最小修订**：固定真实命令拓扑、工具版本和身份反馈、每个直接子进程的唯一等待者；证明受控工具不能脱离所观察集合，或给出持续的后代归属和责任协议；动作前核验身份，不向未知对象补发信号。正常返回、提前失败和超时都先保存被测事实，再做补救；结束未知持续记 T，补救不恢复结论。把父端截止出口、未返回任务／对象的持有、输出稳定读取和最终清理截止写清。可以限制为本次固定 Linux 工具链，不要求实现任意宿主的通用 Runner。

197 行没有把 runner 最后清理算作证据，这点正确，但不能据此跳过验证工具自身的安全责任。即使对未确认情况保守失败，也仍需要一个能据此执行的持有和收尾方案。
