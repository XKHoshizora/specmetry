## 3. B-127-1：普通 FD 修订成立，但仍有两个具体阻塞

### 3.1 普通描述符与持续结果的改进

位置：实施计划 **1585～1612、1624～1637、1503～1511 行**。

正常 EOF、读取错误、超量、Start 失败和到期不再只看 EOF：写端由启动任务关闭，移交后的读端由各自读取任务停止读取后关闭；外部调用不持 regMu；关闭结果与读取结果分开。Start 失败明确不调用没有回收能力的 Cmd.Wait。超量固定为停止读取并关闭，后续 EPIPE／SIGPIPE 不抵消先前工具失败。

成功必须在 W 前取得本次回收、四端真实 Close 为 nil、完整 EOF、无读取／超量／注入错误，并消费 pidfd 的关闭。TestMain 拒绝关闭未完成、请求未返回、C 类、关闭／请求及晚到错误。真实 Close 与之后追加的注入结果分存，不能由后续成功恢复。只关闭一次、真实错误不重试、到期不另加关闭者，这些主体修订可采纳。

这也使三个知识可以分开：Close 已经返回；真实返回 nil 从而确认释放；工具报告因为注入 E 或真实错误而失败。记录中的“已关闭”须作为完成态理解，不能把带真实错误的完成解释成释放已核实。pending 仍由原任务持有，测试进程退出不补成清理证据。

**半构造交接仍需精化**：1593 行说读端建立后交给读取任务，1604 行说建立第二个管道失败时关闭已建立的端。需要固定移交点，避免第一读端已经交给读取任务、第二个 Pipe 失败后启动任务又关闭同一端。最小办法是两管道都建立后才移交；此前所有端由启动任务关闭。若选择逐端移交，则失败出口只能关闭尚未移交的端，已移交端仍由读取任务关闭。加一个明确状态和固定故障预期即可，不需要新的机制类型。链接计划 257／283 行的输出文件半构造失败也应写出“未到 Start 的已打开文件由启动任务关闭”。这是完整实现前必须固定的责任接点，不另扩大成全项目资源改造。

### 3.2 BLOCKER：pidfd 关闭没有封闭尚待登记的请求

位置：实施计划 **1594、1607、1614～1618、1624 行**；同源问题在链接计划 **246～250、286 行**。

新取得方式本身有依据：在本次成功 Start 之后、唯一 Wait 之前取得自有 pidfd；没有自动回收或其他回收者时，即使子进程已退出，未回收状态仍锚定其身份。失败或未发布时不使用 PID fallback，保留错误／未知。这个方向解决了上轮的 Linux 非 pidfd／ready 前提问题。

但是关闭条件只是“Wait 返回，且请求任务（**若已开始**）已发布结果”。没有写定阻止**下一次请求登记**的状态，也没有规定请求登记和关闭资格必须在同一锁下取得唯一顺序。

可达的交错：

1. W 到达，父端观察工具尚未发布回收并准备发请求；pidfd 的整数为 f。此时请求还未登记或尚未开始。
2. 启动任务的 Wait 返回。它看到没有已开始的请求，符合表中关闭条件，在锁外关闭 f。
3. 父端随后登记／启动请求，仍在 `[W,D)`（驱动中为 `[W,K)`），时间守卫通过，使用旧 f 调用 PidfdSendSignal。
4. f 已无效则请求错误；如果已被另一个任务复用为另一个 pidfd，就会指向另一对象。原 pidfd 不会因 PID 回收改变身份，**并不等于已经 Close 的整数编号不会被重新分配**。

仅让查询在 regMu 内、外部操作在锁外，不足以排除这一序列；即使每个单字段访问都无数据竞争，也缺少动作的借用／关闭准入。请求“已开始但未返回”的情况有保护，不能据此覆盖“尚待登记／已预留但尚未启动”。

本轮独立解析 x/sys **v0.49.0 → `b6b8557e8e2974925aec7a136ba0e323eedc5f43`**，读取 [PidfdOpen／PidfdSendSignal:2123～2149](https://github.com/golang/sys/blob/b6b8557e8e2974925aec7a136ba0e323eedc5f43/unix/zsyscall_linux.go#L2123)：接口直接消费整数 fd，不替调用者维持这个借用关系。[pidfd_send_signal 手册](https://man7.org/linux/man-pages/man2/pidfd_send_signal.2.html) 的稳定引用保证以 fd 仍指向原 pidfd 为前提。

**最小修订**：请求准入与关闭资格使用同一个状态锁作原子裁定。登记／预留请求时就占有 pidfd 的使用责任，不等 goroutine 开始才算；关闭者先在锁下封闭后续准入并置 closing，再等所有已预留／运行请求结束或明确放弃，之后才在锁外 Close 一次。未启动请求因截止放弃也必须发布终态、归还责任。关闭后不能再从旧快照启动请求。不能把 PidfdSendSignal 或 Close 放在状态锁内。

至少固定这些交错的独立预期：父端已作到期判断但尚未登记；已预留尚未运行；请求阻塞未返回；Wait 先完成；PidfdOpen 失败／尚未发布；请求因到期未启动。旧错误不清除、到期父端仍能返回，未完成的 fd 有持续持有者。本轮仅提出计划修订，没有实现或运行这些对照。

**这是一个共享阻塞，影响 B-127-1 与 B-127-2，不按两项不同缺陷重复计数。**

### 3.3 BLOCKER：受控持有者的 ExtraFiles 在 Windows 不可执行

位置：实施计划 **1512～1518 行**。

把未知工具后代改为测试直接拥有的 H 是有效收窄：有启动反馈、独立 stdin 释放、唯一 Wait、先保存拒绝再补救、失败后继续保留责任，不再冒充孤儿领养证据。但当前要求把目标写端经 ExtraFiles 交给 H，没有 Windows 的替代分支。

固定 Go [Cmd.ExtraFiles:238～243](https://github.com/golang/go/blob/2aae1000ea1d4b28923b96db28acf4e3b99d6aff/src/os/exec/exec.go#L238) 明确不支持 Windows；[syscall.StartProcess:319～323](https://github.com/golang/go/blob/2aae1000ea1d4b28923b96db28acf4e3b99d6aff/src/syscall/exec_windows.go#L319) 对超过三个标准句柄的 Files 返回 EWINDOWS。H 不会到达就绪反馈，不能命中声称的“工具已退出而目标输出尚无 EOF”。当前常规 CI 尚无这个新测试，绿色不构成反证。

**影响**：这是计划中一个确定不能按现稿执行的 Windows 对照，不是自然关闭故障，也不是生产 Windows 能力被否定。不能把 H 启动失败或未命中当作验证了目标拒绝。

**最小修订**：固定可移植构造，例如让 H 的标准输出持有目标写端而不写它，标准错误作有界就绪通道、标准输入作释放通道；或者写定经审查的 Windows 句柄传递分支。明确目标写端父副本仍只由原启动任务关闭，H 得到的子端副本随自身结束处理。保留失败 Cleanup、唯一 Wait、持续持有和补救不恢复判定。无需为此扩大生产继承白名单或增加 Job／原生故障实验。

## 5. B-127-2：异常接手与主要守卫成立，整体仍未关闭

### 5.1 四状态的主体已形成可执行的知识区分

位置：链接计划 **225～265 行**。

| 状态 | 本轮静态裁定 |
|---|---|
| Start 进行中 | 不准入清扫；没有交付 PID 时零动作；父端截止、Cmd 与任务持有和晚到结果分开。Start 成功而 Wait 尚在进行时，同样不能借用任一最终移交状态提前清扫，应在实现的状态机中显式表示这一中间态 |
| StartFailed(C) | Start 已返回且不再调用 Cmd.Wait，内部同步 Wait4 也已返回，不会再与清扫者竞争；锁下发布是接手条件。空排除集合指“没有已知工具 PID”，不是认为工具已确认结束。发现的对象仍须经驱动父子关系验证，不能凭未交付 PID 动作 |
| WaitReturnedUnknown | 原 Wait 已结束；排除已知工具 PID，只处理独立证明属于驱动的其他子进程。工具不接手、不再 Wait，保留未知，不因 ECHILD 或补救把工具恢复为已确认 |
| Reaped | 本次 Wait 取得非 nil ProcessState 后才进入；清扫不抢原 Wait。旧 pidfd 若仍被合法持有，指向原对象；同号 PID 只能在再次证明属于驱动子进程的集合内按孤儿处理，不能用数值本身扩大归属 |

固定 Go [forkExec:234～244](https://github.com/golang/go/blob/2aae1000ea1d4b28923b96db28acf4e3b99d6aff/src/syscall/exec_unix.go#L234) 支持 StartFailed 接手时“内部等待已经返回”，并不支持“该等待必然回收成功”。本稿将二者分开，修复了上轮相反的清扫入口。

四个最终／起始分支与清扫循环的条件对应：排除 PID 不被 P_ALL 回收；返回排除 PID 或没有可回收结果时，另扫描 PPID 为驱动且不在排除集合的对象。WNOWAIT 观察不消费；指定 PID 回收才消费。WaitUnknown 中排除集合非空时不宣布整树结束，后续成功不清除已有工具失败。F-8 因而是明确保守政策，仍待负责人决定；没有把它变成可以安全重跑或已释放。

__WALL 同时用于观察与指定 PID 回收，覆盖不同退出信号资格；subreaper、无自动回收／其他回收者及 PID 可见性前提仍必需。[wait 手册](https://man7.org/linux/man-pages/man2/waitpid.2.html) 对 waitid 使用这些 Linux 标志的版本说明与本稿相符。不存在靠加一个标志就认证任意宿主拓扑的推论。

StartFailed／Reaped 的受限推演沿用 Review 128 以固定 Linux v6.17 的核对范围；本轮没有把它当作真实 runner 已取证。进程组／会话不再作为归属或全部结束的替代证明。

### 5.2 共用 pidfd 问题仍阻止整体关闭

位置：链接计划 **246～250、286 行**。

286 行与 c9lint 相同，只等待“若已开始”的请求。第 3.2 节的请求登记／关闭交错在驱动的 `[W,K)` 内同样可达，状态表声称“旧请求只经 pidfd，因此不竞争”的依据不充分：关闭后的整数可能已经不再指向原 pidfd。

WaitUnknown 行还说 pidfd 随记录持有到退出，而 286 行按任何 Wait 返回就允许关闭；必须明确它是保留对象记录还是保留打开的 fd，以及新的请求是否仍可准入。不能同时要求未来仍可用 pidfd 请求，又允许在无当前请求时先关闭。

因此，原 StartFailed／WaitUnknown／Reaped 的知识修订和唯一回收主体可以采纳，**B-127-2 整体仍受共享 pidfd 阻塞影响，尚不能关闭。** 同一份请求预留／封闭／关闭协议必须落实到两个调用者，而不是只在实施计划中修一处。

### 5.3 截止与文件责任的改进及剩余精化

位置：链接计划 **267～308 行**。

新的守卫已经覆盖上轮主要反例：清扫在 F 前读、F 后返回，不再向读到的 PID 新发信号；工具结果在 W 后返回，不再开始稳定读取。父端不同步等待 Wait、终止、清扫、读、解析或关闭，外部调用不持状态锁。W／K／F 同一起点，已开始的任务保存晚到结果不等于可以开始新动作。没有要求单次系统调用硬实时取消。

输出文件、稳定读取、ELF／DWARF、pidfd、报告各有关闭者，关闭错误是 T，不被进程子树空替代；错误与关闭未完成有持有者。主方向成立。实现前须固定第 3.1 节所述输出文件半构造出口，以及关闭任务完成但真实错误时的释放未知，不能用“最多关闭一次”替代首次关闭责任。

**报告截止还有一个父端出口须明确修订**：274 行规定 F 时失败退出并向 stderr 写一行，但没有规定这次补写是否仍由父端同步完成。允许的环境序列是 stderr 的管道尚未可写；普通 File.Write 可等待可写，而不是只“返回一个写入错误”。若在 F 的失败分支同步补写，父端会在已经到期之后重新等待 I/O。

依据固定 Go [os.File.Write:211](https://github.com/golang/go/blob/2aae1000ea1d4b28923b96db28acf4e3b99d6aff/src/os/file.go#L211) 和 [internal/poll.FD.Write:365～396](https://github.com/golang/go/blob/2aae1000ea1d4b28923b96db28acf4e3b99d6aff/src/internal/poll/fd_unix.go#L365)。这不是要求磁盘或单次系统调用有硬实时保证，恰是应让父端不依赖该外部调用。

最小修订是：通知写入若要尝试，也应在截止前登记并由任务执行，F 只取已发布快照并非零退出；或者允许 F 分支不补写该行。不能在 F 新启动一个无截止补写并以“可能失败”宣称已保有出口。它和报告正文的 Write／Sync／Close 一样，结果缺失就是缺证／T，不增加预算。

应把报告的分支补成唯一规则：

- 清扫确认且 `now < F−20s`：可开始报告任务，父端最多等到 F；
- 清扫晚到、未确认，或到达／越过最晚报告准入：不取得新的 20 秒，记录 T／缺证；
- 报告任务已启动但到 F 未完成，或任一 Write／Sync／Close 失败：T／缺证／非零，已登记资源与晚到结果仍有持有者；
- 到 F 不再依赖新的同步写入或查询才能退出。

303 行“F 时写出报告并退出”应同步为“F 时判定报告完成与否并退出”，避免与 274 行的提前启动规则混用。报告不完整的历史知识继续保存，不能为补齐报告而自动重跑或扩预算。此报告出口与共享 pidfd 的修订是本链接计划成为实施依据前的具体条件；不因尚未取证就否定 subreaper 方法本身。

### 5.4 时间算术不另增问题

W=t0+31m、K=t0+32m、F=t0+33m；最晚报告开始为 t0+32m40s。工作、终止、清扫／关闭和报告保存的预算分开，不能在阶段转换重取。12／12／5／3 分钟是准入最低剩余量，不是各步必耗时间，未出现由这组数字本身导致的恒定不可达。
