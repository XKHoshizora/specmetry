## 3．BLOCKER

### B1：运行时核对不能保证拒绝所有包装语义差异

**位置**：`docs/wp2.5-check-runner.md:2696`（§21.5 E2 行），关联`:2704`、`:2713`；对照§19.5 W1～W5及“运行时核对”的能力限定（约`:1855`～`:1902`）。

新增 E2 行断言：libSystem 包装与陷入的语义不同，就会由 W1～W5 得到观察失败并进入 F1。这不是这些规则可以提供的保证。

**静态反例**：本次直接子进程实际以7退出；设某个未经验证的入口/ABI错误在每次读取中稳定返回下列结构：`si_signo=20`、`si_pid=本次子进程`、`si_code=CLD_EXITED`、`si_status=0`，其余必需结构条件成立。

- W1 的身份字段和 code 集合成立；
- W2 按无符号读取；W3a 最高字节为0；
- W3b 得到0；W4不适用于正常退出；
- 两次相同的错误读取仍满足W5。

所以该错误可以通过所列核对，而不是必然F1。生产正常流程同次执行只选K或W一路（C1正文已明确），没有一份独立的真实退出码供这些字段自证。这里**不是**声称现有 libSystem 实际把7变0，也不是发现当前已关闭的原型又发生了该故障；它反证的是新增的普遍保证。

还有良性差异：若原始263被包装规范化为7，重复读取相同，W1～W5也可全部通过；按Q-3(a)最终退出值仍为7。语义或原始值不同既不必然有害，也不必然可检测。不能靠“两个入口最终进入同一内核”跳过对包装/ABI的验证。

**实际影响**：这是选择尚无构建/运行证据的入口时的兼容性论据。将不能检测的差异说成会安全失败，会错误降低所选入口的证据门槛；也直接抵触§19.5“核对只能排除所列字段不符”的正确限定。

**最小修正**：

1. 撤回必然F1的推论，改为“所列字段违规、读取错误或不一致会拒绝；稳定且落在合法值域内的错误不能仅由这些核对排除”。
2. 分开构建、加载/符号、调用ABI、返回值/errno、结构与语义风险。Go收紧linkname可能在构建暴露，不等于所有风险都只在构建暴露。
3. 将尚未验证的同义性明确留作P-5假设与所选证据路径，不要求本轮实现能检测任意未来语义变化的生产防线。

作者已经写了符号缺失可在运行系统上导致启动失败，因此不能把全文概括成“作者声称所有风险只在构建时”。本项针对的是仍然无条件存在的“语义差异→W1～W5→F1”，不是对“主要风险”四字作无依据的扩大解读。

### B2：E2 的无证据状态不能在所有 Q-4 路径下一律为 L

**位置**：§21.2 的分类定义及G5行（`:2567`、`:2575`）；§21.4“差额都是L”与第6项（`:2665`、`:2672`）；Q-4(a)（`:2733`）、§21.7第3步（`:2748`）。

**最小修正**：将差额6单独条件化，同步G5表、支持差额、Q-4及冻结顺序：

| C-15 | 可采纳§19.3 | P-1只是局部证据；F1资源持有与宿主禁用分开，不新增后台Wait或未知对象清理 |
| C-16 | 可采纳规格及已测分支 | Windows返回值知识矩阵保持，未测原生失败点留P/L，不称用户代码确定执行 |
| C-17 | 可采纳 | 请求终止不等于已结束，查询/等待失败不能当空集合 |
| C-18 | 可按所测适配器范围采纳 | 参数往返只是所测版本与字符串集合，不外推全部shell/发行版 |
| C-19 | 可在原进程观察范围采纳 | 启动前拒绝、启动后观察失败不可撤销；不能把摘要扩成“所有I/O错误都F1”，结束上下文D6和输出D20仍用各自规则 |
| C-20 | 可按Linux排他区间采纳 | 拒绝路径登记、收养和清扫依赖该区间；不推广其他宿主/平台 |

**C-9补充的静态评价**（§19.4，约`:1715`起；§21.3 `:2617`）：

- 新raw syscall/linkname/dynamic-import规则明确限定**仓库自有生产包**，对E1/E2都必要；本轮静态搜索当前 `internal/` 没有这些用法，不会要求修改无关已验收实现。
- 原“启动/回收只能经闸门”的白名单与新“macOS waitid原始入口/指令”的白名单是不同能力清单。不能把“只含waitid包”套到所有旧启动/等待规则，也不能将仓库自有代码的新禁令不加区分套到Go标准库或x/sys生成文件，否则它们本身就会触发规则。
- 需按go/types解析调用能力；显式覆盖`.s`/指令清单及别名等的具体lint实现属于P。白名单应指明允许的目标/用途及平台，不成为整包任意启动、回收的豁免。
- **无cgo与动态导入不同**：没有 `import "C"`、不依赖目标C工具链的Go代码仍可使用Go动态导入指令。Go编译器与x/sys现有用法提供静态先例；这不等于本候选E2已构建成功。规则应按实际cgo使用判断，不能仅因字符串含`cgo`就否定已允许的动态导入。

以上是实施范围/可执行性限定，不是要求本PR现在写lint、生产入口或新原型。

## 6．macOS 静态依据、支持声明与入口论证

### 6.1 固定来源与复算范围

独立解引用官方标签，并核对distribution的 `xnu` 子模块确实指向相同提交：

| 版本 | distribution-macOS 提交 | XNU提交 |
|---|---|---|
| 13.0 | `28fcecaa9a9991cefdca1b9e74bc18c40aebc750` | `5c2921b07a2480ab43ec66f5b9e41cb872bc554f` |
| 13.5 | `1103a82bbc0ce0def4c198db70251c29c27b2040` | `1b191cb58250d0705d8a51287127505aa4bc0789` |
| 14.6 | `19f03746a6c6bc6fe315423d41fb53e040b8f368` | `d8b80295118ef25ac3a784134bcf95cd8e88109f` |

读取三版本的 `kern_exit.c`、`kern_event.c`、`wait.h`、`proc_internal.h`、`syscalls.master`，及补充的 `cdefs.h`。所列关键文件SHA-256与§128一致；例如三份wait.h同为 `3a5896c72f9b60736234a05016da01cbc9bd62ddf9f4d00bf9a39f988c57c228`，13.0/13.5/14.6的kern_exit分别为文档所列 `294ba223…`、`16e9f12b…`、`637b66ba…`。

这些固定源码支持：173号waitid；`u_int p_xstat`与独立最高字节；exit移位；先发kqueue低16位事件、再在所列非shadow/父关系前提下转移最高字节；wait4低16位；waitid合并低24位与最高字节并清零；NOTE_EXITSTATUS按请求置位。`cdefs.h` 也保持未预定义时 `KERNEL → __DARWIN_UNIX03=0`，没有再误套用户态宏。以13.0为例，父端条件与转移见固定 [kern_exit.c:2484](https://github.com/apple-oss-distributions/xnu/blob/5c2921b07a2480ab43ec66f5b9e41cb872bc554f/bsd/kern/kern_exit.c#L2484)，另外两版本的对应语义一致。

这只是**固定公开源码的局部推演**。没有由此验证三个旧版本的实际内核构建参数、全部结构布局、部署的libSystem或所有执行路径。当前实际runner仍为Review 103所核的macOS26.6.x两架构，SDK26.5的用户态布局不是内核宏分支的证据。

macOS13+来自NFR-05/MVP的支持承诺；本地及官方固定Go1.27.1源码确有链接器 `macOS={13,0,0}`，但最低加载版本不等于每一个接口/布局都在所有13+系统动态验证。保留Intel与未测版本支持、不自动缩小，是正确口径；不能把“未测”一律当支持不成立，也不能说已测两个组合代表全部支持。

### 6.2 SIGSYS 与 libSystem：有依据的部分

[Apple QA1118](https://developer.apple.com/library/archive/qa/qa1118/_index.html) 是2011年归档说明：它不保证内核系统调用ABI，并以动态系统库为兼容性边界。它不是说当前Go程序是完全静态链接，也不是对单次waitid必然失败的证明。[Go1.12 Darwin说明](https://go.dev/doc/go1.12#darwin) 明确说明包装改经libSystem以改善前向兼容；Go1.27.1仍保留原始陷入入口，两件事不矛盾。

本轮还读取固定XNU26.5（`ac9718fb1af618d5ce8678d0dc6e8a58f252216f`）的：

- [`subr_xxx.c:181`](https://github.com/apple-oss-distributions/xnu/blob/ac9718fb1af618d5ce8678d0dc6e8a58f252216f/bsd/kern/subr_xxx.c#L181)：nosys在send_sigsys为真时发SIGSYS，并返回ENOSYS。
- [`signalvar.h:180`](https://github.com/apple-oss-distributions/xnu/blob/ac9718fb1af618d5ce8678d0dc6e8a58f252216f/bsd/sys/signalvar.h#L180)：DEVELOPMENT/DEBUG用`!no_sigsys`，其他分支直接为1。因而作者“未核对默认”的缺口可以补充这项静态事实；不能据此断言未知未来内核或某次实际运行必经nosys。
- Go1.27.1 darwin信号表的SIGSYS确为 `_SigThrow`。当前默认运行时存在不可当普通errno处理的终止路径；本轮没有触发该信号，也不要求通过新实验验证。

### 6.3 Go、libSystem 与 E2：静态可行，不是验证完成

`go1.27.1` 标签独立解析为 **`862c888e612ac346c7c4d99c9392bdfd265f33b0`**。官方固定源码与本机同版本的四个关键文件（macho、signal_darwin、syscall_darwin、noder）哈希与§128一致。`syscall.syscall6` 的容忍说明、带库名的动态导入允许分支均可确认，见 [syscall_darwin.go:396](https://github.com/golang/go/blob/862c888e612ac346c7c4d99c9392bdfd265f33b0/src/syscall/syscall_darwin.go#L396)、[noder.go:315](https://github.com/golang/go/blob/862c888e612ac346c7c4d99c9392bdfd265f33b0/src/cmd/compile/internal/noder/noder.go#L315)。这是实现先例，不是对外稳定API承诺。

x/sys v0.49.0与Go的kevent/sysctl/kill/wait4包装确经libSystem跳板；E1在所述macOS观察路径中是绕过这一包装的一处例外。无cgo的动态调用在技术上有根据，但具体E2包、汇编ABI、符号、地址取得及错误返回未验证。

本轮进一步读取了同一XNU提交内的Libsyscall生成路径，而不是假定另有同名仓库：

- [`create-syscalls.pl`](https://github.com/apple-oss-distributions/xnu/blob/ac9718fb1af618d5ce8678d0dc6e8a58f252216f/libsyscall/xcodescripts/create-syscalls.pl#L130) 把waitid列为cancelable，生成调用桩；
- [`custom/SYS.h`](https://github.com/apple-oss-distributions/xnu/blob/ac9718fb1af618d5ce8678d0dc6e8a58f252216f/libsyscall/custom/SYS.h) 将失败转到cerror；[`errno.c:75`](https://github.com/apple-oss-distributions/xnu/blob/ac9718fb1af618d5ce8678d0dc6e8a58f252216f/libsyscall/custom/errno.c#L75) 包含取消检查，再由nocancel路径设置errno、返回−1。

这组生成源码没有显示对正常siginfo做低8位改写，但它不是部署库的逐字节验证；错误/取消路径也说明E2不是“只换调用号、不存在新的运行路径”。本轮未把pthread取消判断提升为已复现的Go故障。

**可确认**：采用系统库边界比直接绑定内核ABI有更合适的兼容性依据；E2可作为优先验证候选。**仍是假设**：本候选的汇编/动态导入实际可构建，目标系统符号可加载，参数/返回/errno与预期相同，P1～P4及结构解释适用于目标组合。B1的通用F1推论不由这些静态先例支持。

E6的否决方向成立：固定 [`kern_sysctl.c:1190`](https://github.com/apple-oss-distributions/xnu/blob/ac9718fb1af618d5ce8678d0dc6e8a58f252216f/bsd/kern/kern_sysctl.c#L1190) 用 `MIN(p_xstat, USHRT_MAX)`，不是保留低16位。exit(256)的0x10000会饱和为0xffff，不能从中还原EV-32所需的正常退出0；K2会拒绝该组合，而非得到正确退出状态。无需运行新原型就能指出信息不足。

## 8．P-5：最小计划是否足够、授权前需补什么

**现有范围可覆盖部分健康构建/结构/数值，但不能单靠重跑 `w.*`、`c.*`、`k.esrch` 证明errno/EINTR处理。当前不是已固定的可执行计划，P-5未获授权，不可直接开工。**

这些健康场景大多只得到API成功。即使全部通过，错误返回值/线程局部errno传递可能根本没走到；把EINTR后续处理留成一条未命中的分支不能算验证。本项是**运行前计划门槛**，不是要求当前文档PR先提交实现。

最小预登记内容建议如下：

| 要回答的假设 | 计划中至少固定的检验 |
|---|---|
| 无cgo构建/链接 | 固定Go版本、两个原生架构、`CGO_ENABLED=0`、实际符号/跳板及链接方式；记录构建/加载是否成功。不能用编译器接受指令代替候选实际构建 |
| ABI/参数/缓冲区生命周期 | 明确Go声明、C ABI整型宽度、汇编入口/地址、调用寄存器和指针存活依据；复用已核对布局探针与受控子进程。静态核对与运行证据分开，不以unsafe地址存在证明正确 |
| 正常R/N/M | 保留计划中7、256、263、−1及其他边界/信号、重复读取、同一未回收对象K/W对照；独立N依据Q-3与固定预测表，不与M共用同一错误实现；原始值在改写前保存/标明既有N2限制 |
| 返回值与errno | 预先固定至少一种安全、确定的真实错误（例如本进程非子对象查询的ECHILD、非法选项的EINVAL，具体预期先对固定源码/接口确认）；错误后再健康成功，核对返回值与errno都正确且不沿用残留errno，不读取错误后的无效siginfo |
| EINTR | 固定哪一层注入、命中证据、恢复对照、重试策略与共享绝对截止；若不构造原生EINTR，明确它是接缝证据。不能用errno正常返回一次就证明EINTR分支；不要求为此无界发信号或操作未知进程 |
| 静态入口覆盖 | 两架构所有P-5 waitid调用都经指定E2，不能漏掉旧观察器/ESRCH回退；明确test-only白名单与生产C-9的关系；不顺带修改生产或根依赖 |
| 唯一分类与门禁 | 把未执行、无命中、工具观察/关闭错误、候选原生预测不符、计划故障拒绝/漏检、补救失败逐项分开。目标环境中的候选构建不可行不能confirmed；故意坏夹具/语法错误不是有效机制反证。编译失败也不能计作变异有效检出 |
| 次数与期限 | 场景ID、重复次数、单步/场景/总预算、go test截止准入与清理余量必须先写定；两个架构同一固定代码点。当前P-3仍有工具步骤和内层门禁，不能把P-5时间另加在套件总期限之外 |
| 归属/收尾与证据 | 复用已审工具/子进程登记、身份和独立归属；先保存被测状态再补救，未知零动作，补救成功不恢复结论。每个Cmd、文件、观察器和后代有所有者；未打印结果/内层失效仍保留最终信息与正式非零 |
| 元数据/支持范围 | 固定实际OS/内核、Go、SDK、原生架构/Rosetta和入口；环境未知不装作健康。保留旧P-3和旧失败，不将新E2成功补写为旧运行原因已知或全部macOS13+验证 |

不要求扩大成生产事务、CLI、全套Runner或任意ABI证明。真实原生错误、接缝注入、静态依据、构建检查及纯模型必须分别计证据；如果某项安全检验无法构造，计划先说明它限制了哪个假设，再由负责人决定是否授权这个明确范围。
