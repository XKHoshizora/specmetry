每项都给出：当前约束、推荐方案与备选、影响、建议的验收标准。实测、推断与未验证的区分见第 9 节；正文中的"（实测）"指第 9 节记录的实验结果，并注明是作者还是审查方的观察。

### 5.1 M2-Q1：TD-06 Windows 上执行检查的 shell（草案）

**当前约束**（既有批准决定与已有契约）：

- `checkSpec.shell` 的取值为 `sh`、`bash`、`cmd`、`pwsh`、`powershell`，可以省略（common.v1）。
- `check_config_hash` 包含 `shell`（省略时为 null），`shell` 是强制 `material` 的字段（data-model §4.4、§7.2）。
- 检查继承用户的环境，注入 `SPECMETRY_CHECK=1`；超时终止整个进程树（Unix 进程组，Windows Job Object）；输出只转发、不保存（architecture §6.4，FR-EV-01、02）。
- **MVP-EV-04："检查命令不存在 → `error` / `not_found`"。**
- 在推导中，`fail` 与 `error` 都是失败（data-model §6.1 中 `V` 的定义），所以结果分类只影响记录的 `result`、`failure_kind` 与给人的说明，不影响交付状态。
- TD-06 现在的建议默认是"优先 `sh`（Git for Windows），找不到时用 `cmd /C`；AC 可以指定 `shell`"，尚未确认。

**实测要点**（作者，Windows 11，Git for Windows 2.56；其他平台未验证）：

- 在普通的 PowerShell 会话中，`sh` 不在 PATH 上；`bash` 解析到 `%LOCALAPPDATA%\Microsoft\WindowsApps\bash.exe`，即 WSL 的启动器。Git for Windows 的 `sh.exe` 位于 `<Git>\usr\bin\` 和 `<Git>\bin\`，`git --exec-path` 给出 `<Git>/ucrt64/libexec/git-core`。
- 用 Go 默认的参数转义启动 Git for Windows 的 `sh`：不含空格的参数会被它的 MSYS 运行时展开通配符和花括号，引号也会被改写。自行构造命令行、每个参数都按 MSVCRT 规则加引号，11 个测试字符串全部原样到达。
- `cmd`：Go 默认的转义会改坏引号；用 `cmd.exe /d /s /c "<命令>"` 原样构造则正常。多行命令只执行第一行，不报错。
- `pwsh` 7.6 与 Windows PowerShell：`-NoLogo -NoProfile -NonInteractive -Command <命令>` 正常；`-EncodedCommand` 在输出被重定向时会把 CLIXML 记录混进转发的输出。Windows PowerShell 只测了一个字符串，不能推广为它的参数处理在所有输入上都正确。
- **退出码不能区分"命令不存在"与"主动以同一数值退出"**（作者第 2 轮实测，第 9 节）：`sh` 都是 127，`cmd` 都是 1，`pwsh` 与 Windows PowerShell 都是 1。审查方在 Windows 上独立复验了 `cmd` 的两种情况都是 1（审查 040 没有说明是否为另一台物理机器）；它的 `sh` 对照在 MSYS 启动时失败（`0xC0000022`），没有执行到命令，所以 `sh` 的结果只有作者这一个环境的观察。

**推荐方案**：

1. **默认（新增产品取舍）**：省略 `shell` 时，**所有平台都用 `sh`**，不回退到 `cmd`。
   - 统一的是**解释器的种类与语言约定**（POSIX shell），不是同一个二进制或相同的执行环境：Linux 上的 `/bin/sh` 可能是 dash，macOS 与 Git for Windows 上是 bash 的 POSIX 模式，行为细节不同。
   - 理由：同一个已确认的检查配置（同一个 `check_config_hash`）不应在有、没有 Git Bash 的机器上执行语法完全不同的程序。
   - Windows 上 Specmetry 需要 git，但 git 的存在不能证明每一种 Windows git 安装都附带 `sh`（例如精简安装）；找不到时按第 4 条处理。
2. **字段映射**（实施细节）：

   | `shell` | Linux / macOS | Windows |
   |---|---|---|
   | 省略、`sh` | `/bin/sh -c <命令>` | Git for Windows 的 `sh.exe -c <命令>` |
   | `bash` | PATH 上的 `bash -c <命令>` | Git for Windows 的 `bash.exe -c <命令>` |
   | `cmd` | 不可用 | `<系统目录>\cmd.exe /d /s /c "<命令>"` |
   | `pwsh` | PATH 上的 `pwsh -NoLogo -NoProfile -NonInteractive -Command <命令>` | 同左（`pwsh.exe`） |
   | `powershell` | 不可用 | `<系统目录>\WindowsPowerShell\v1.0\powershell.exe`，参数同上 |

   - `/d` 关闭 cmd 的 AutoRun，`-NoProfile` 不加载 PowerShell 配置文件：它们不属于经人确认的检查配置。
   - `sh`、`bash` 以非交互方式运行，不读启动文件；继承的 `BASH_ENV`、`ENV` 照常生效，属于"继承用户环境"的边界，文档如实说明。
   - 每种 shell 各有自己的适配器与测试，不以一种 shell 的实验推论其他 shell。Go 的文档也说明 Windows 的命令行由目标程序自行解析，`cmd` 与常规规则不同。
3. **解释器的查找**（实施细节）：
   - 只使用绝对路径，忽略 PATH 中的相对路径项。
   - 候选路径先规范化（解析符号链接与联接，Windows 上统一短文件名与大小写），再判断实际位置：位于本项目任何已登记的 worktree 之内的，一律不用。仅仅是"绝对路径"不够：PATH 可能含有某个 worktree 中 `bin` 目录的绝对路径。
   - Windows 上的 `sh`、`bash`：先取 `internal/gitx` 所用的 git 所在的 Git for Windows 安装中的 `usr\bin\`（由 `git --exec-path` 推出安装根，这条 git 命令同样在 `gitx` 的受控环境中运行，不继承 `GIT_EXEC_PATH` 等变量）；其次是 PATH 上的绝对路径项，但排除 Windows 目录之下和 `WindowsApps` 中的启动器（WSL）。
   - 系统目录由 Windows API（`GetSystemDirectory`）取得，不使用 `ComSpec`、`SystemRoot` 等环境变量指定解释器的位置。
4. **结果的层次与处理**（按审查 040 B1 重写；不用任何普通退出码反向证明"命令不存在"，也不依赖 stderr 文本）：

   | 层次 | 例子 | Specmetry 能得到的证据 | 推荐的处理 |
   |---|---|---|---|
   | ① 解释器不可用 | 找不到解释器；平台上不存在的取值（Unix 上的 `cmd`、`powershell`） | 预检时查找失败，进程没有创建 | 执行前对所有要执行的 AC 预检；任何一个不可用，整批不执行、不写记录，退出码 6，`error.details` 给出 `shell_unavailable` 和 AC 编号，不回显路径（**新增产品取舍**） |
   | ② 进程无法创建 | 工作目录不存在或不是目录；预检之后解释器被删除；操作系统拒绝创建进程 | 操作系统在创建进程时返回的错误，进程没有开始 | `error` / `spawn_error`，记录操作系统错误的类别（不回显路径） |
   | ③ 解释器已运行，命令不存在 | `no-such-tool --check` | 只有解释器的退出码和 stderr。退出码与主动退出无法区分（实测）；stderr 文本随语言与版本变化（实测为本地化的中文），并且属于不保存的检查输出 | **不能可靠识别**。按方案 A：`fail` / `nonzero_exit`，记录实际退出码，说明 Specmetry 不判断失败的原因 |
   | ④ 命令主动以非零状态退出 | 测试失败；`exit 1` | 退出码非零 | `fail` / `nonzero_exit`，记录实际退出码 |
   | ⑤ 解释器启动之后自身失败 | 审查 040 环境中 MSYS 初始化失败（`0xC0000022`）；崩溃 | 只有退出码，一般无法与 ④ 区分 | `fail` / `nonzero_exit`；可选的缓解：预检时对每种解释器运行一次空命令（例如 `sh -c :`），失败则按 ① 处理。这只能减少、不能排除这类误记（未验证） |
   | ⑥ 超时 | 长时间运行 | Specmetry 自己的计时 | `error` / `timeout`，终止整个进程树（不变） |

   `context_changed`、`input_missing` 的处理不变。
5. **EV-04 是否满足**：**不满足，是未解决的契约问题。**
   - 检查命令都经由 shell 执行，"命令不存在"只出现在第 ③ 层，而第 ③ 层没有可靠证据。
   - 草案能可靠识别的"不存在"只有第 ① 层（解释器本身），而草案又把第 ① 层定为退出码 6、不写记录。所以按草案，经 shell 执行的检查不会产生 `not_found`。
   - 选项（契约调整，草案，需负责人决定）：
     - **A（推荐）**：改写 EV-04 与 `not_found` 的含义：经 shell 执行的检查不报告 `not_found`；检查中的命令不存在时，结果为 `fail` / `nonzero_exit`，记录实际退出码，人类可读输出说明 Specmetry 不判断失败的原因。`not_found` 保留给将来可能由 Specmetry 直接启动程序的执行方式。需要修改 EV-04、data-model §4.11 中 `failure_kind` 的说明，以及 `check-run.v1`、`status.v1` 的描述。交付状态不受影响。
     - A'：A 的变体：第 ① 层改为记录 `error` / `not_found`，不再是退出码 6。代价是把环境问题写成检查结果：一次解释器缺失就会让已验收的 AC 变为 `failing`（`regressed`）。
     - B：在能可靠识别的 shell 上保留 `not_found`，例如 bash 的 `command_not_found_handle`、PowerShell 的 `CommandNotFoundAction`，由 Specmetry 注入前置代码并通过单独的通道报告。未验证；dash（常见的 Linux `/bin/sh`）与 `cmd` 没有已知的等价机制；注入代码改变了经人确认的检查的执行环境。EV-04 仍只对部分 shell 成立，验收同样要改写。
     - C：增加一种不经 shell 的执行形式（例如 `argv` 数组），由 Specmetry 直接启动程序，操作系统能可靠报告程序不存在，EV-04 对这种形式成立。需要修改 `checkSpec`、审核、人工编辑与 Skill 指南，是较大的契约变化。
     - 不采用：按退出码 127 或 9009 推断（POSIX 中 127 是查找失败的状态，但 `exit 127` 同样产生 127；实测歧义）；按 stderr 文本推断（未经证明可靠）。
6. **命令行与参数**（实施细节）：
   - Linux / macOS：直接以 argv 传入（`[sh, -c, 命令]`），没有转义问题（推断，未在这两个平台上实验）。
   - Windows：一律自行构造完整的命令行（`SysProcAttr.CmdLine`），不使用 Go 的默认转义：`sh`、`bash`、`pwsh`、`powershell` 的每个参数按 MSVCRT 规则总是加引号；`cmd` 用 `/d /s /c "<命令>"`。不使用 `-EncodedCommand`。
   - **`cmd` 与多行命令（新增产品取舍）**：`shell = cmd` 时命令不能含 CR 或 LF。推荐在提交、审核和人工编辑时拒绝（扩展 V-P04，退出码 2）；已经保存的此类检查，`check run` 在执行前拒绝（退出码 2），不写记录。批准之前，不改变已保存配置的含义。
7. **进程树**（实施细节，WP2.5 开工前冻结并验证）：Unix 进程组与 Windows Job Object 是候选机制，不是已完成的证明。
   - Windows 上先以挂起状态创建进程、加入 Job 再恢复，避免"启动之后、加入 Job 之前"子进程已经逃逸。
   - 需要验证 Git Bash 启动的全部后代，以及取消、超时、输出管道与等待回收。
   - 主动脱离进程组或 Job 的进程（例如 `setsid`、允许 breakaway 的进程）不在这一机制的覆盖范围内，作为边界写明，不自动成为已接受的保证。
8. **路径**（实施细节）：工作目录是 `W/<workdir>`，按平台转换分隔符；命令文本原样传入，Specmetry 不做路径转换；Git Bash 对它启动的程序做的 MSYS 路径转换属于所选 shell 的语义。路径含空格和中文时正常（实测，Windows）。

**备选**（针对默认与解释器缺失）：

- 保留 TD-06 现在的建议（`sh` 找不到时回退到 `cmd /C`）：静默回退，同一配置执行不同的程序；实测 `cmd` 对多行命令只执行第一行。不推荐。
- Windows 默认 `cmd`，其他平台默认 `sh`：同一配置在不同平台上是不同的语言。
- Windows 上必须显式指定 `shell`：改变已登记数据的含义，对使用者负担大。

**影响**：

- 用户行为：没有 Git for Windows `sh` 的 Windows 机器，省略 `shell` 的检查返回退出码 6；`cmd` 检查不能写多行命令；命令不存在时显示为普通失败（方案 A）。
- 现有数据：没有检查执行记录；M1 中已确认、省略 `shell` 的检查，含义统一为 `sh`。不需要迁移。
- Schema：取值不变；方案 A 只改描述；V-P04 的扩展是校验规则的变化（data-model §8.3）。
- 测试：每种 shell 在每个平台上都要有适配器测试；CI 必须明确准备并验证所需的解释器，缺失时测试失败，不能静默跳过。
- 后续模块：M4 的 Skill 需要说明如何选择 shell。

**建议的验收标准**（草案，可作为 EV-14、EV-15，并改写 EV-04）：

1. 每个平台上，每种可用的 shell 用同一组测试字符串（含空格、引号、反斜杠、通配符、花括号、中文、`$`、`%`）经 `printf` 或等价命令回显，结果与输入完全一致；Windows PowerShell 有自己的完整字符串集。
2. 省略 `shell` 的检查在三个平台上都由 `sh` 执行；Windows 上 PATH 中只有 WSL 的 `bash.exe` 时不使用它；位于 worktree 之内的解释器（包括经 PATH 的绝对路径、符号链接或联接到达的）不被执行。
3. 解释器不可用（包括 Unix 上的 `cmd`）→ 退出码 6，`error.details` 中有 `shell_unavailable`，`check_runs` 不增加任何行，没有执行任何检查。
4. 工作目录不存在 → `error` / `spawn_error`。
5. 改写后的 EV-04（方案 A）：命令不存在 → 结果不是 `pass`，`failure_kind` 不是 `not_found`，记录实际退出码；`exit 127` 等主动退出得到同样的分类。
6. `shell = cmd` 的多行命令在提案和审核中被拒绝（退出码 2）；已保存的此类检查在执行前被拒绝，不写记录。
7. 超时后整个进程树都被终止（EV-03），包括 Git Bash 启动的后代；挂起创建与加入 Job 的顺序有测试。

### 5.2 M2-Q2：TD-23 `check.inputs`（草案）

**当前约束**：

- 既有批准决定：`inputs_json` 是开始时 `inputs` 中每个路径在 HEAD 上的 git 对象 ID；路径不存在时结果为 `error` / `input_missing`，计为失败（data-model §4.11、§7.4 第 2 步、§6.9）。沿用要求 `S` 上这些路径的对象 ID 等于 `D.inputs_json`（§6.2）；MVP 没有沿用，但第 7 条规则的原因码 `inputs_changed` 照常推导（CX-19）。
- 既有批准决定：对象读取一律经过 `internal/gitx` 的统一入口；git 不具备安全读取能力时返回退出码 6，不把环境失败转换为正常结论（PD-26）。只支持 SHA-1（TD-26）。
- M1 的实现（已核对代码）：`inputs` 按提交的原样保存；V-P04 把 `\` 换成 `/`、用 `path.Clean` 规范化之后判断是否越出仓库，但不改写保存的值；`check_config_hash` 由保存的值（排序后）计算。所以 `src/a.go`、`./src/a.go`、`src\a.go`、`src/dir/` 都可能已经保存在 M1 的数据中。

**实测要点**（git 2.56，Windows）：

- 作者：`ls-tree -z --full-tree <提交> -- <路径>` 给出 mode、类型与对象 ID：普通文件 `100644 blob`，目录 `040000 tree`，子模块 `160000 commit`，符号链接 `120000 blob`。子模块内部的路径、不存在的路径、未跟踪的空目录、大小写不同的路径都没有输出。一次调用中给出互为前缀的两个路径时，只列出较深的那个。`ls-tree` 的路径按字面匹配。子模块检出的提交与记录的不同时，`git status --porcelain` 报告 ` M sub`。
- 审查 040 独立复验、作者第 2 轮重复：
  - **树条目能列出，不等于叶对象可以读取**：在没有远端、禁止所有传输的临时仓库中，树条目引用一个不存在的 blob，`ls-tree` 返回 0 并列出该条目，`cat-file -e` 对同一对象 ID 返回 1。
  - **同一对象 ID 可以对应不同的 mode**：同一个 blob 同时作为 `100644` 与 `120000` 条目出现。

**对象读取的层次**（按审查 040 N2 区分；PD-26 的衔接写在每一层）：

| 层次 | 例子 | 推荐的处理 |
|---|---|---|
| L1 提交或路径上的树对象无法读取 | 部分克隆缺少树对象；对象损坏；git 不具备安全读取能力 | 环境失败：退出码 6，不执行、不写执行记录（PD-26 的 M2 原则）。能力不具备时，在运行任何读取对象的命令之前就拒绝 |
| L2 提交树中没有这个路径 | 路径不存在、未跟踪、只有被忽略的文件、空目录、大小写不同、子模块内部的路径 | `error` / `input_missing`（data-model §7.4 第 2 步），不再执行命令 |
| L3 条目存在，但叶对象不在本地 | 部分克隆中缺少该文件的 blob，或目录自身的树对象 | **推荐只要求路径元数据**：照常记录 mode、类型与对象 ID，不读取叶对象。理由：`inputs` 只用于比较两个快照上的身份，元数据已经足够；检查读取的是 worktree，不是对象库 |
| L4 子模块的 gitlink | 指向子模块的提交，它本来就不在上级仓库的对象库中 | 只记录元数据，从不要求它可读，不能当作缺失对象拒绝 |

- 备选（对 L3）：同时要求叶对象可读，经 PD-26 的入口用 `cat-file -e` 检查，缺失时退出码 6；每个输入多一次对象读取，并且必须对 gitlink 豁免。
- 所以第 1 版中"对象缺失一律退出码 6"收窄为：**只有读取路径所需的对象（L1）失败时退出码 6**。
- 未验证：中间某级树对象缺失时 `ls-tree` 的具体行为（推断为失败，按 L1 处理）；真实的部分克隆仓库。

**比较语义**（需冻结；完整 WP2.1 开工前，见第 8 节）：

1. **记录**：每个输入一项 `{path, mode, type, oid}`，`path` 是**保存的原值**，按 `path` 排序，例如 `[{"path":"src/a.go","mode":"100644","type":"blob","oid":"…"}]`。
2. **查找路径**：与 V-P04 相同的规范化（`\` 换成 `/`，再 `path.Clean`）。所以 `./src/a.go`、`src/dir/` 与 M1 的校验含义一致：末尾的 `/` 不改变含义，`.` 表示仓库根的树。这样不改变已保存配置的含义，也不改变 `check_config_hash`。
3. **相等**：两份记录的 `{path, mode, type, oid}` 集合完全相同才相等。只比较对象 ID 时，符号链接与内容相同的普通文件无法区分（实测）；可执行位的变化也看不到。
4. **缺失与未知**：`input_missing` 的执行是 `error`，不会成为 `V = pass`，所以比较只发生在通过的执行之间。任何一方没有记录（例如旧数据、非 git 项目）都视为不相等（保守）。
5. **使用位置**：`D.inputs_json` 取自所依据的合格执行（data-model §4.13）；第 7 条规则的 `inputs_changed` 与 §6.2 的沿用条件都用这一相等关系。
6. **读取**（WP2.3 的实施细节）：在固定 `head_start` 之后、执行之前，对每个输入在 `head_start`（完整的提交 ID）上查找路径完全相同的条目，不把互为前缀的路径放进同一次调用；不运行 LFS、子模块或任何过滤器。
7. 各类路径：普通文件为 blob，可执行位变化也算变化；目录为 tree；符号链接只反映链接文本，链接指向的文件变化不会被发现，需要时另行声明该文件；子模块为 commit，检出的提交不一致时工作区不是 `clean`（实测），执行不合格；LFS 管理的文件是指针文件的 blob，指针含有内容的 sha256 与大小（LFS 的规范，未在安装了 git-lfs 的环境中实验）。
8. **行为确认**：`head_start` 为 NULL（分支还没有提交）而声明了 `inputs` 时，记为 `input_missing`；非 git 项目不记录 `inputs_json`，执行本来就不合格（INIT-09）。

**备选**：

- 只记录对象 ID（`git rev-parse <提交>:<路径>`）：实现简单，但无法区分 mode。
- 末尾带 `/` 时要求必须是目录（第 1 版的提议）：比 V-P04 更严格，会改变已保存配置的含义，不再推荐。
- 对象读取失败记为 `input_missing`：把环境失败写成检查结果，违反 PD-26 的 M2 原则。

**影响**：

- 推导：`inputs_changed` 与沿用的相等关系（WP2.1）；复核器的通用合法事实域（WP2.2，第 8.5 节）。
- 用户行为：声明了子模块内部路径或大小写不符的路径时，执行结果是 `input_missing`，需要改写检查配置（审核后生效）。
- 现有数据：没有执行记录，不需要迁移；已保存的 `inputs` 与哈希不变。
- Schema：不变（`inputs_json` 是数据库内部的列，`check-run.v1`、`decision.v1`、`status.v1` 都不包含它）。
- 规范：data-model §4.11、§4.13（记录的内容）、§6.2 与 §6.3（相等关系）、§7.4（读取的层次）同步修改，不只修改存储说明。
- 后续模块：M7 的隔离执行器沿用同一份记录。

**建议的验收标准**（草案，扩展 MVP-EV-10）：上表与各类路径各一个用例；`./a`、`a/`、`a\b` 形式的已保存输入按 V-P04 的方式查找；A、B 两个提交上 mode 不同、对象 ID 相同 → `inputs_changed`（CX-19 的变体）；叶 blob 缺失但条目存在 → 照常记录；提交或树对象无法读取、git 不具备安全读取能力 → 退出码 6，`check_runs` 不增加任何行，没有运行检查命令。

#### 5.3.1 候选流程（草案）

| 阶段 | 内容 |
|---|---|
| P0 通道 | 命令最先调用 `RequireHuman`。`agent_cli` 返回退出码 3，不读取任何文件，不创建数据目录或锁文件 |
| P1 检查与副本准备（Specmetry 不打开原数据库） | 1. 按 §11.1 检查数据目录（不存在时说明没有数据库，退出码 0）。2. 取得 `.migrate.lock`，持有到命令结束。3. 用与只读检查相同的分类判定文件状态；不属于适用状态时说明无需恢复，退出码 0，此时还没有清理任何遗留。4. 判定为适用状态之后，才删除崩溃遗留（E1，第 5.3.3 节）。5. 外部活动检测：不写文件的锁探测（实测只在 Windows 上可行）；记录原数据库各文件的存在情况、大小、修改时间与 sha256。6. 用既有的私有文件与目录机制新建工作目录 `recover-<ULID>/`，写入标记文件，把数据库文件和存在的辅助文件复制进去；复制之后重新记录原文件的状态，与第 5 步不同则停止。7. 以读写方式打开副本，由 SQLite 在副本上回放日志或重建 WAL 索引；`integrity_check`、`foreign_key_check`；用 `guardVersion` 判断版本；校验 `tombstones.json`。8. 在副本上执行墓碑并整理（读取 checkpoint 的结果，依赖 N1 的修复），再做一次完整性检查。9. 判定历史完整性的类别（第 5.3.4 节） |
| P2 确认 | `channel.Guard`，不另设确认机制。摘要包括：状态与涉及的文件名；副本上的检查结果；**历史完整性的类别**（不只是 schema 与 `integrity_check` 的结果）；墓碑将删除的行数；将生成的备份；外部程序的要求（取决于 U1 的选择）；恢复将由 SQLite 以读写方式打开原数据库。确认内容建议为 `recover` |
| P3 备份生成与发布（Specmetry 仍不打开原数据库） | 先重新比较原文件的状态与 P1 第 5 步，不一致则停止（退出码 5，确认期间状态已变化）。然后对 P1 第 8 步之后的副本执行 `VACUUM INTO`，写入 `backups/` 中的临时名称，校验后改名为正式名称。临时名称不符合备份的命名规则（`specmetry-*.db`），所以轮换与备份列表从不把它当作备份。轮换推迟到恢复完成之后 |
| P4 最终复核与接管 | 紧接在打开原数据库之前，重新比较原文件的状态与 P1 第 5 步，并再做一次锁探测；不一致则停止。然后用读写连接打开原数据库，由 SQLite 回放日志或重建索引；在这个连接上重新做版本检查、完整性检查，执行墓碑（同普通打开），切换为 Specmetry 的持久 WAL 状态后关闭。**"数据库恢复已完成"的判定**：这个连接上的版本检查与完整性检查通过，墓碑的删除已经提交，连接已经正常关闭。墓碑之后的整理（checkpoint 与 `VACUUM`）没有完成时，按 N1 修复后的规则保留 `.compaction-pending`，归入 P5 的"收尾未完成"，由下一次打开完成 |
| P5 收尾 | 依次：删除本次的工作目录并确认；执行备份轮换（从不删除本次的新备份）；报告。每一步的失败都单独报告（第 5.3.3 节），不中止已经完成的恢复。全部成功之后，普通打开与 `doctor` 照常工作 |

与第 1 版相比，备份的生成与发布移到了最终复核之前，使最终复核与打开原数据库之间只剩最少的工作。**这只缩小窗口，不消除窗口**（第 5.3.2 节）。

`db recover` 不迁移：数据库版本比程序旧时，恢复之后由下一次普通打开迁移，并生成迁移前备份。

#### 5.3.2 U1：持续排除外部活动（未解决的技术问题）

**问题**：既有契约要求不兼容的数据库在任何修改之前被拒绝（MVP-STO-02 的原则，PD-23 第 4 条"不得绕过版本兼容限制"）。在候选流程中，版本是在副本上检查的（P1），它在原数据库被 Specmetry 修改之前完成；但这只有在**原数据库从复制开始到 SQLite 接管为止都没有变化**时才成立。

- 复制前后的指纹相同，只证明两次观测的值一致，不证明复制期间持续静止，也不等于取得了 SQLite 的一致性快照。SQLite 的说明是：复制原始文件只有在复制期间没有事务、并正确保留相关日志时才安全。
- P4 的最终复核之后、SQLite 取得锁之前仍有窗口。SQLite 打开原数据库时，可能在读取任何内容之前就回放热日志；Specmetry 普通打开的 DSN 还会切换 `journal_mode`。所以在 P4 的连接上"再检查一次版本"发生在这些修改之后，不能证明不兼容的数据库没有被修改，也不能消除"检查之后、使用之前"的竞态。
- 推断：`schema_version`、`min_binary_version` 只由 Specmetry 的迁移写入，而迁移在 `.migrate.lock` 之内进行（architecture §11.2），所以恢复期间另一个 Specmetry 进程不能升级数据库。但外部的非 Specmetry SQLite 程序不认识这把锁，可以写入任何内容（包括这些值），也可以改变日志的状态，使已确认的摘要与已生成的备份不再对应原数据库。
- `.migrate.lock` 只协调 Specmetry 进程；一次锁探测不能阻止之后的新活动，也不能普遍证明所有 SQLite 连接都已关闭；提示用户关闭其他程序不是排他机制。

**结论**：在 U1 解决之前，"不兼容的数据库在原数据库被修改之前被拒绝"**没有被证明**；第 1 版中"检测而不阻止已经足够"的暗示已删除。

**选项**：

- **U1-a 跨平台协调设计**：从复制之前到 SQLite 接管之后，一直持有与 SQLite 兼容的锁，使外部 SQLite 程序在这期间得到 `SQLITE_BUSY`。例如由一个辅助进程持有原数据库的 PENDING、RESERVED 与 SHARED 字节锁（避免 POSIX 锁在本进程关闭任一描述符时被释放），再设计向恢复连接交接、不留空隙的协议。Windows 的锁按句柄计，会挡住本进程自己的连接，需要不同的交接方式。
  - POSIX 与 Windows 的这些性质是设计约束，**不证明协调方案不可行**（第 1 版把它们写成了不可行的理由，已更正）。
  - 需要在三个平台上验证：外部 SQLite 程序确实被挡住；交接没有空隙；进程崩溃时锁被释放。目前只是候选，未验证。
- **U1-b 离线前提**：只在"恢复期间没有其他程序使用这个数据库"的前提下给出保证。Specmetry 在 P1 与 P4 检测它能检测的活动，但不排除；确认摘要要求人确认这一前提；契约与验收写明降低后的保证。这是**新增产品取舍**（降低既有保证），不是默认接受的风险。
- **U1-c 缩小窗口**：备份移到最终复核之前；最终复核紧接在打开之前；P4 再做一次锁探测；打开原数据库的第一个连接不先切换 `journal_mode`。总是适用，但**单独不足以**满足契约，只能与 U1-a 或 U1-b 组合。
- 推荐：以 U1-c 为基础，在 WP2.10 的设计中先尝试 U1-a 并做三平台实验；如果在 M4 自测期限之前无法验证，由负责人明确选择 U1-b。**WP2.10 在 U1 有结论之前不开工。**

#### 5.3.3 各阶段的保证（按审查 040 B3、审查 041 B3-R 重写）

第 1 版中"任何拒绝都不改变文件和目录项"的统一承诺与流程本身矛盾（清理遗留与轮换备份都会改变目录项），已删除，改为下表。下文区分四类内容：

结果的两种说法不能混用：

**清理失败**：

**遗留的识别**：只有名称为 `recover-<ULID>`、并含有 Specmetry 用私有文件机制写入的标记文件的目录，以及名称符合本次临时备份规则的文件，才视为遗留并删除；其他条目保持原样，由 `doctor` 报告。

**`db recover` 的例外**（待负责人逐项批准；只适用于 `db recover` 命令本身，不放宽普通打开与 `doctor` 的保证，即 MVP-STO-02、STO-07）：

| 编号 | 例外 |
|---|---|
| E1 | 判定为适用状态之后（P1 第 4 步），可以删除先前崩溃留下的恢复遗留，即使本次随后被拒绝；目录项因此改变。不适用的状态下不清理。理由：这些遗留可能含已删除项目的数据 |
| E2 | 命令运行期间出现本次的临时内容；数据目录的修改时间可能改变 |
| E3 | 恢复生成新的备份；恢复已完成之后按保留 3 份轮换，可能删除最旧的备份；从不删除本次的新备份；轮换只完成一部分时如实报告 |
| E5 | P4 中 SQLite 修改原数据库。这是 PD-23 批准的恢复本身，由人确认后发生；之后的失败按阶段表报告 |

**E4：普通打开的扩展**（待负责人单独批准；它**不是** `db recover` 的例外，而是改变所有打开数据库的命令的行为）：

- **触发条件**：普通打开（`sqlite.Open`；所有读写数据库的命令都经过它，包括 Agent 通道的命令）已经完成全部步骤，并且数据目录中存在被识别为遗留的条目。全部步骤是指：数据目录与路径检查、打开锁、版本检查、墓碑文件校验、墓碑执行与整理、迁移前备份与迁移。
- **顺序**：清理是打开成功之后、释放打开锁之前的**最后一步**。
  - 在它之前的任何拒绝或失败（版本不兼容或无法确认、墓碑文件无效、墓碑执行失败、备份或迁移失败），都按原来的方式返回错误，不清理遗留。
  - 所以普通打开的拒绝路径与失败路径都不因 E4 改变。"版本检查通过"不足以说明打开已经成功：其后的墓碑、备份与迁移都可能失败（审查 041 B3-R）。
- **影响的文件**：只有数据目录根下被识别为遗留的条目；不涉及数据库文件、正式备份、`.migrate.lock` 或其他条目。
- **失败时**：清理失败不改变打开的结果，因为打开已经成功，命令照常执行。未删除的遗留留在原处；程序日志只记录错误码与遗留的 ULID，不记录内容；`doctor` 报告；下一次打开再试。
- **不变的保证**：
  - 普通打开的拒绝保证（MVP-STO-02，包括两项已批准的文件副作用例外）；
  - `doctor` 的只读契约（MVP-STO-07）：`doctor` 从不清理，只报告；
  - 不兼容或无法确认版本的数据库，打开被拒绝时不清理任何遗留。
- **备选**：不采用 E4，遗留只由在适用状态下运行的 `db recover` 与 `purge` 删除。代价：含已删除项目数据的遗留可能长期留在数据目录中，直到用户运行这两个命令；`doctor` 报告它们。
- **推荐**：采用 E4，理由是遗留可能含已删除项目的数据，尽早删除更符合 §11.4 的意图。这是改变普通打开行为的新增产品取舍，需要负责人单独决定；本 PR 不实施。

#### 5.3.4 U2：历史完整性（未解决的技术问题，按审查 040 B4 重写）

"数据库可以打开""结构一致（`integrity_check`、`foreign_key_check` 通过）""历史上已提交的内容都还在"是三个不同的结论。前两个可以检查，第三个在某些状态下无法证明。

| 状态 | 能得出的结论 | 建议 |
|---|---|---|
| 只有 `-wal`（含帧） | 可以打开；SQLite 恢复 WAL 中校验通过的已提交帧（作者实测：5 行未合并的已提交数据被恢复） | **可恢复**。摘要说明恢复的是 WAL 中能够校验的已提交内容 |
| 非空 `-journal`（回滚日志模式） | 回滚到最后一次提交的状态（作者实测：2000 行全部回滚为原值） | **可恢复** |
| 缺少 `-wal` 与 `-shm` | 可以打开。如果是另一个程序正常关闭（SQLite 在最后一个连接关闭时先合并再删除 WAL），内容完整；如果是有人删除了含未合并帧的 `-wal`，这些已提交的内容已经丢失。Specmetry 无法区分这两种情况 | **完整性未知**：需负责人决定 |
| 只有 `-shm` | `-wal` 已经丢失。若丢失前它含有未合并的已提交帧，这些内容无法恢复，也无法察觉（作者实测：只剩已合并的 3 行）。Specmetry 自己关闭的数据库保留 0 字节的 `-wal`，所以不会进入这一状态 | **完整性未知**：需负责人决定。候选证据：`-shm` 的 WAL 索引头记录了帧数，读取它不修改文件；能否据此判断丢失，未验证 |
| 副本检查失败、版本不兼容、无法识别的文件组合 | 无法安全继续 | 拒绝 |

对"完整性未知"的两种状态，选项：

- (i) 拒绝，要求使用其他备份；
- (ii) 允许恢复"当前可以访问的状态"：确认摘要、成功说明与验收都明确写出"不能证明历史上已提交的内容都被保留"，从不声称数据完整。
- 推荐 (ii)：PD-23 的起因正是"用其他 SQLite 程序打开再退出"，即"缺少两者"；拒绝会让这一命令失去主要用途，而数据如果已经丢失，拒绝也不能找回它。"只有 `-shm`"的说明措辞更强。这是**新增产品取舍**，也不是已接受的风险。

#### 5.3.5 §8.1 第 1 ~ 4 项

**第 1 项：恢复前的检查与一致性备份**

- 当前约束：architecture §11.3"只使用一致性备份机制（`VACUUM INTO`），不直接复制正在使用的数据库文件"。在适用状态下，对原文件执行 `VACUUM INTO` 必须先用 SQLite 打开它，而打开本身就会修改文件。
- 推荐调整（§11.3 增加有限的例外）：
  - 只有 `db recover` 可以复制数据库文件，前提是持有打开锁，并满足 U1 选定方案的条件；
  - 副本只放在数据目录内的私有工作目录中，只用于在副本上恢复和检查，不是备份；
  - 保留的备份仍然只由 `VACUUM INTO` 生成；
  - "一致性检查"指 `integrity_check` 加 `foreign_key_check`，版本检查使用同一个 `guardVersion`；它们证明副本的状态，不证明原数据库在之后被打开时仍是同一状态（U1）。
- 备选：用 `immutable=1` 只读打开原文件（不读 WAL、不回放日志，读到的不是已提交的状态）；自行实现带写时复制的 VFS 或解析 WAL（审查 005 已证明自行解析会读到未提交的数据）。都不推荐。

**第 2 项：墓碑与可保留备份的顺序**

- 当前约束：墓碑在任何备份之前执行，新生成的备份中不含已删除项目的数据（architecture §11.2、§11.4，CX-11，MVP-PRV-03）。
- 推荐调整：保留的备份只由执行过墓碑与整理的副本生成。`VACUUM INTO` 写出一个新的紧凑文件，只含现存的行。含原始数据的中间副本只在私有工作目录中，按第 5.3.3 节清理；崩溃遗留由在适用状态下运行的 `db recover`（E1）、`purge` 与 E4（若批准）删除，删除失败时如实报告。
- 备选：同时保留原始文件的副本作为"恢复之前的原样"：可能含已删除项目的数据，与 CX-11 冲突。

**第 3 项：拒绝路径的临时文件与清理**

- 当前约束：MVP-STO-02 的严格标准与两项已批准的例外。
- 推荐调整：按第 5.3.3 节的阶段表与清理失败表写入新的验收项。E1 ~ E3、E5 是 `db recover` 的例外；E4 是普通打开的扩展，只在打开成功的最后一步执行，不改变普通打开的拒绝与失败路径。它们分别由负责人批准；不修改 MVP-STO-02，不改变 `doctor` 的只读契约。
- 备选：工作目录放在系统临时目录（可能授予其他账户权限，development.md §6；也违背"数据只在受保护的数据目录中"），不推荐。

**第 4 项：范围、需求、CLI、人类专属权限与验收项**

  | STO-13 | 各阶段的失败与崩溃：P3 中失败 → 没有带正式名称的备份，临时文件已删除；P4 打开之后、"恢复已完成"的判定成立之前失败 → 报告"恢复未完成，原数据库的状态未确认"，Specmetry 没有删除任何 `-wal`、`-journal`，备份保留，没有轮换；轮换从不在恢复完成之前删除旧备份，也从不删除本次的新备份；崩溃遗留按 STO-11 清理 |
  | STO-13b | P5 的收尾失败（测试钩子）：工作目录删除失败；轮换在删除一份旧备份之后失败；整理未完成 → 都是退出码 6（草案），报告"数据库恢复已完成，收尾未完成"及具体情况（未删除的目录、删除与保留的备份、`.compaction-pending`）；之后普通打开成功，数据完整性检查通过；从不报告"状态未确认"，也不报告全部成功 |
  | STO-14 | **E4（只在负责人批准时加入）**：数据目录中有遗留时普通打开成功 → 遗留被删除；打开在任何一步被拒绝或失败（版本不兼容、无法确认版本、`tombstones.json` 无效、迁移失败）→ 遗留不变；清理失败 → 打开仍然成功，遗留保留，程序日志与 `doctor` 报告；`doctor` 从不删除遗留；名称相同但没有标记文件的条目不被删除 |

**影响**：

- 用户行为：新增一个人类专属命令；需要额外的磁盘空间（约两倍于数据库），大数据库需要等待复制；"完整性未知"的状态有明确的警告（U2）；U1-b 时需要关闭其他程序并确认。
- 现有数据：不需要迁移。
- Schema：不变（只输出文本与 `error.v1`）。
- 测试：需要真实的外部 SQLite 进程与崩溃辅助进程（存储包已有同类基础）；U1-a 需要三平台的锁实验。
- 后续模块：M3 的拦截规则与 `doctor`（报告遗留）；M4 的 Skill 禁止事项；`backup restore`（P1）复用同一套检查与墓碑顺序，也受 U1 的同类约束。

### 5.4 M2-Q4：`status.v1` 中旧项目名称的兼容（草案）

**当前约束**：

- 方案 1（既有批准决定，review-resolution §48）**只针对 `init`**：已登记的名称含代码围栏时，`init` 返回退出码 2，不改名、不改写事实；不提供改名命令（第 6 条）。方案 1 没有批准把同样的策略或其他处理扩展到 `status` 等读取接口（m1-exit-evidence 第 11 节）。
- architecture §10.2：所有自由文本（包括项目名称、交付目标名称）都不能包含代码围栏，由 schema 强制。`init.v1` 与 `target-scope.v1` 已禁止；`status.v1` 的 `project.name` 和 `target.name` 只有长度限制。
- 交付目标名称不存在旧数据的问题：WP1.8 之前目标只能由 `init` 以 `default` 创建；合并进 master 的 `target set`（PR #14）始终拒绝代码围栏。
- `status --json` 是 Skill 的 `init`、`status`、`sync` 每一步都要读取的接口。
- TD-20：首次发布之前可以完善 v1，但必须同步示例、反例、消费者与测试。

**推荐方案（B，新增产品取舍）**：`status` 照常推导，但不输出旧名称。

1. **`null` 的精确条件**：登记的名称**不能通过当前的项目名称校验**时（与 `init` 使用同一个校验：非空、单行、不含控制字符与代码围栏、不超过 200 个字符），`project.name` 为 `null`；否则输出原名称。按代码历史，其他规则自 WP1.1 起就已存在，实际只有含代码围栏的旧名称会命中（推断）。
2. `status.v1` 的 `project.name` 改为"不含代码围栏的名称，或 `null`"；`target.name` 同时加上代码围栏的禁止。
3. 名称不是推导的输入：推导结果、差距与其他字段与名称合法时完全相同。
4. **消费者**：
   - 人类可读输出显示项目 ID，并说明登记的名称不再被接受、因此不显示；
   - M4 的 Skill 遇到 `null` 时使用项目 ID；
   - 旧名称从不出现在任何输出、错误或日志中。
5. `init` 的行为不变（方案 1）。

**单独决定的相关取舍**（方案 1 没有批准这些扩展）：

- `purge` 要求输入项目名确认。对这类项目改为输入项目 ID，是**独立的确认行为取舍**，在 WP2.8 开工前决定。
- M3 的 `doctor --json`、M5 的项目列表采用什么策略，在各自的阶段分别记录、分别决定，本轮不决定。

**备选**：

- A：`status`、`gaps` 像 `init` 一样拒绝（退出码 2）。这类项目的交付推导完全不可用，又没有改名命令，唯一的出路是 `purge` 后重新初始化，丢失全部基准与事实。不推荐。
- C：新增人类专属的改名命令，`status` 在改名之前拒绝。它同时解除方案 1 的局部限制，但违背方案 1 的第 6 条，需要负责人另行决定；还要修改 marker"只创建、不替换"的规则（architecture §10.6）。
- D：原样输出旧名称。违反 §10.2，不推荐。

**影响**：只影响早期开发版本登记的、名称含三个连续反引号的项目；不改写数据，不迁移；`status.v1` 的两个字段与示例、SCH 反例；测试按 M1 的旧名称测试方式（用 SQL 写入）构造。

**建议的验收标准**（草案）：

1. 名称含代码围栏的旧项目 → `status --json` 退出码 0，输出通过 `status.v1` 校验，`project.name = null`，其余字段与名称合法的同一数据库完全相同；文本与 JSON 模式的 stdout、stderr 中都找不到这个名称（canary）。
2. 名称合法的项目 → `project.name` 原样输出。
3. `gaps --json` 不受影响；`init` 仍按方案 1 返回退出码 2；整个过程不写入业务事实。
4. `status.v1` 拒绝含代码围栏的 `project.name` 与 `target.name`（新的 SCH 反例），接受 `project.name = null`。

### 5.7 M2-Q7：TD-17 提交关联规则

- 当前约束：建议默认是"trailer 优先；正文中的编号也匹配，**可以关闭**"。只保存 SHA、提交时间和关联关系，正文在内存中处理（architecture §6.7、§10.2 第 6 条，FR-EV-06，EV-11）；按 ref 维护游标，历史被改写时重新扫描该 ref、按 SHA 去重（WT-04）；`settings_json` 预留了 `commit_ref_mode`。提交关联只影响进度。

  1. trailer 的键为 `Specmetry-Ref`（不区分大小写），值是逗号或空格分隔的编号，用 git 的 `%(trailers:key=…,valueonly)` 读取（git 2.56 上实测可用）。

### 5.8 M2-Q8：条目级标记的表达（契约补充，草案）

- 当前约束：
  - MVP-SRC-04（M2 部分）要求引用"以 `source_removed` 的形式出现在状态与差距中"，FR-SRC-04、data-model §4.3 也这样写；但 data-model §6.6、§6.10、`status.v1` 与 `common.v1` 中都没有 `source_removed`。
  - MVP-BL-05（M2 部分）要求 `status --json` 带 `inferred` 标记；反推的条目也可以是需求，而 `status.v1` 的需求没有 `flags`；`ref_not_found` 也只能标在 AC 上。
  - 既有的阻塞规则：未移除的来源内容变化 → 阻塞的 `SOURCE_CHANGED`；移除来源会改变来源集合哈希 → 已有的范围确认 `SCOPE_STALE`（阻塞），直到重新确认（data-model §4.3、§6.10）。
- 推荐：
  1. **不改变任何阻塞规则**：`SOURCE_CHANGED` 与 `SCOPE_STALE` 照旧产生和消除；新增的标记与警告不能替代、消除或推迟它们。
  2. `status.v1` 的需求增加 `flags`（取值 `inferred`、`ref_not_found`、`source_removed`）；AC 的 `flags` 增加 `source_removed`。
  3. data-model §6.6 增加 `source_removed`："当前修订的来源引用中，有指向已移除来源的"。
  4. 差距增加不阻塞的标记类警告 `SOURCE_REMOVED`，`target_key` 为目标、需求或 AC 的编号，与 `CONFLICT` 等警告并列。
  5. **范围筛选**沿用 data-model §6.10 的既有规则：有范围确认时，只为 `RS`、`AS` 中的条目产生；没有范围确认时，为全部 `active` 条目产生（都不阻塞）。目标的警告：有范围确认时，只为至少含有一个 `RS` 需求的目标产生；没有范围确认时，为全部 `active` 目标产生。
  6. 典型过程：移除来源 → `SCOPE_STALE`（阻塞）→ 人重新确认范围 → `SCOPE_STALE` 消除，引用了已移除来源的条目只剩不阻塞的 `SOURCE_REMOVED`。
- 备选：只加标记、不加差距类型，同时把 SRC-04 的文字改为"出现在状态中"；只加差距警告、不给需求加 `flags`（BL-05 对需求的标记仍无处表达）。
- 影响：
  - 推导：WP2.1 增加一条标记规则和一类警告（输出语义），截止为**完整 WP2.1 开工前**；
  - 复核器：推荐方案不改变阻塞语义，所以 `ready` 谓词不变；如果负责人选择改变阻塞语义，复核器随之修改；
  - Schema：`status.v1` 的需求结构、`common.v1` 的 `gapType`，补充示例与反例；
  - 后续模块：M5 的标识（FR-UI-11、UI-12）；没有数据影响。
- 验收：SRC-04、BL-05 的 M2 部分分别覆盖需求、AC 与目标；移除来源之后先出现 `SCOPE_STALE`，重新确认之后只剩警告；警告永不阻塞、不改变交付状态（ST-13 的性质测试覆盖）；范围外的条目不产生警告。

### 5.9 M2-Q9：`claim --json` 的输出契约（契约补充，草案）

- 当前约束：prd §6 与 architecture §9.1 列出的面向 Agent 的输出中没有 `claim`；AGENTS.md 要求面向 Agent 的输出都通过 `schemas/` 校验；V-C06 的存在性校验"照常写入并标记"，MVP-INV-02 期望标记为 `missing` 或 `unknown_commit`，但 Agent 目前看不到这些标记。

  - 不回显任何摘要、正文、命令、输出或环境变量的值；存在性只说明引用的位置存在，不表示验收通过。
  - 在 WP2.4 中按"输出契约的语义约束"补充条件约束与反例。

- 验收：CLM-01 ~ 05、INV-01、02 的成功输出按 `claim-receipt.v1` 校验；标记与数据库中的 `refs_check_json` 一致；canary 摘要不出现在输出中。

### 8.5 复核器的规格（草案；完整为 F5，受限为 F5-a）

**独立性**：

1. 复核器放在单独的测试专用包中，不导入 `internal/domain/derive`，也不导入 `scope`、`baseline` 等生产包的计算函数。核对逻辑只用标准库；E2E 阶段读取数据库的前端只额外使用 SQLite 驱动。由测试检查导入关系，两个方向都检查。
2. 只检查导入图不能排除两个包共享同一个错误假设。为此：
   - 谓词按 prd §3.2 的 `ready` 定义、acceptance-criteria §3 不变量 #2 与 data-model §6.8 的文字逐条写出（下文），实现之前交给独立审查；
   - 反例从 data-model §6.3 的规则推出，而不是从推导引擎的代码推出。
3. 不通过放宽 `ready` 的条件来消除两个实现之间的差异。

**完整的 `ready` 谓词**（复核器按以下条件独立判断，全部成立才是 `ready`）：

| # | 条件 |
|---|---|
| R1 | 存在基准版本 |
| R2 | 存在 `active` 的交付目标，并且 `S` 不为 NULL |
| R3 | 该目标存在范围确认（`seq` 最大的一条），并且没有过期：它的基准版本等于当前版本，它的来源集合哈希等于由未移除的来源独立重算的哈希 |
| R4 | `RS`（范围中仍为 `active` 的需求）不为空 |
| R5 | `RS` 中每个需求至少有一个 `active` AC |
| R6 | 对 `AS`（`RS` 下的 `active` AC）中的每个 AC：(a) 父需求适用性没有失效（`requirement_revision` 等于父需求的修订）；(b) 当前决定 `D`（当前修订下 `seq` 最大的决定）存在；(c) `D` 是豁免，或者是适用于 `S` 的接受：手动 AC 的 `manual` 接受且 `D.snapshot = S`；自动化 AC 的 `exception` 接受且 `D.snapshot = S`、`V` 不是失败；自动化 AC 的 `normal` 接受且 `V = pass`，并且 `D.snapshot = S`（直接）或满足沿用条件（只在通用合法事实域中出现） |
| R7 | `AS` 不是全部豁免 |
| R8 | 没有阻塞问题：关联到 `RS` 中需求、`AS` 中 AC 的，或没有关联任何条目的 `open` 且 `blocking` 的问题都不存在；关联条目已被拒绝的问题不计入 |
| R9 | 没有未确认的来源变化：每个未移除的来源，观测哈希都等于 `acked_sha256`（文件缺失也是变化） |
| R10 | 独立重算的 `evidence_grade` 与输出一致：取 `AS` 中 `normal` 接受所依据的执行的最弱等级（直接：`D.evidence_id` 对应的执行；沿用：`S` 上的隔离级执行）；没有 `normal` 接受时为 `none`。这是输出一致性断言：只篡改输出的等级应让复核器失败，但不表示原始事实的交付状态改变 |

**事实输入域**（按审查 041 B5-R 重写）：

1. **合法事实历史**：生产写入能够产生的事实集合。它满足两类条件。
   - 写入前置条件：data-model §7.1 的读取版本、§7.3 的验收前置条件与 §8.3 的校验规则。例如：
     - `normal` 接受时，`evidence_id` 是该 AC 当前修订、当前检查配置下 `runs(S)` 中最新的合格执行，结果为 `pass`；执行与决定是不同的逻辑写入，所以执行的 `seq` 严格小于决定的 `seq`；
     - `exception` 接受时 `V = none`；`manual` 接受只针对手动 AC；
     - 拒收、豁免与例外都有理由；`seen_decision_id` 等于写入时的前一条决定。
   - 事实不变量：
     - `seq` 由全库唯一的计数器在写事务中分配，分配值单调递增、从不重复分配（data-model §1）。它表示写入的先后，**不是每条事实行的唯一标识**：同一次逻辑写入的关联事实可以共享它分到的 `seq`，不同的逻辑写入从不共享同一个 `seq`（见下文"共享 `seq`"）；
     - 事实只追加；
     - 每条事实属于一个项目，引用只指向同一项目的行（data-model §1.1）；
     - 检查执行绑定开始时的修订与配置（§7.4）；Claim 与决定绑定提交时的修订；
     - 基准实体的修订只随基准版本变化（§7.2）；
     - 范围确认的 `seen_scope_confirmation_id` 链与豁免集合满足 V-T01、V-T02。
   - **合法但不能 `ready` 的历史必须保留在生成器中**，不能为了双向一致而预先排除，例如：当前决定是拒收；在同一 `S` 上接受之后又有合格的失败；父需求已被实质修订而 AC 没有后续处理；范围过期；来源变化；阻塞问题。
   - **共享 `seq` 的写入是合法历史的正例**（审查 042），生成器必须产生它们，并让它们参与双向对照，至少包括"审核接受多个条目并附带范围"。依据既有契约与现有的写入调用链：

     | 逻辑写入 | 共享同一个 `seq` 的事实 | 依据 |
     |---|---|---|
     | 审核（`review`），可附带范围 | `baseline_versions` 一行；`baseline_changes` 一行或多行（版本内的顺序由 `change_index` 给出）；这次写入的 `source_refs`、`code_refs`；被审核条目的 `reviewed_seq`；被修改实体的 `revision_seq`、`updated_seq`；附带范围时的 `scope_confirmations` 一行 | data-model §1、§4.7、§5.5；architecture §6.1.5（"以一个 `seq` 完成以下工作"）、§6.1.7（"范围确认与基准版本使用同一个 `seq`"）；`internal/cli/review.go` 只调用一次 `NextSeq`，`baseline.Apply`（`internal/baseline/apply.go`）与 `review.ConfirmScope` → `scope.Write` 使用同一个值 |
     | 人工编辑（`propose --apply`） | 提案、它的全部条目，以及应用产生的基准版本、变更与引用 | architecture §6.1.5（"提案与版本使用同一个 `seq`"）；`internal/cli/apply.go` 用提案回执的 `seq` 作为应用的 `seq` |
     | 提交提案（`propose`） | 提案、全部条目、问题（`created_seq`）与问题的来源引用 | architecture §6.1.4（"分配一个 `seq`，写入提案、全部条目……问题和问题的来源引用"）；`internal/proposal/store.go` |
     | 设置交付目标（`target set`） | 旧目标的 `archived_seq` 与新目标的 `created_seq` | architecture §6.1.7 第 8 步；`internal/scope/target.go` |

     - **范围限定**：
       - `proposals`、`baseline_versions`、`scope_confirmations`、`source_acks` 的 `seq`，以及 `worktrees.registered_seq`、`delivery_targets.created_seq`、`sources.registered_seq` 与 `removed_seq`，在各自的表内唯一（迁移中的 `UNIQUE` 约束）：一次写入在这些表中至多写一行。
       - `baseline_changes`、`source_refs`、`code_refs` 等表中，同一个 `seq` 可以有多行。
       - 共享只发生在同一次逻辑写入之内，不能扩大为任意独立的记录都可以复用 `seq`。
     - **反方向**：一个写事务也可以分配多个 `seq`。例如 `init` 为每个新登记的 worktree 与默认目标各取一个；从新的 worktree 提交提案时，登记 worktree 与保存提案各取一个（m1-exit-evidence 第 6 节）。
     - **M2 的新事实表**（`claim_batches` 与 `claims`、`check_runs`、`decisions`、`commits` 与 `commit_links`）的 `seq` 分配，按 data-model §4 与对应工作包的设计。data-model §4.10 没有写明批次中的 Claim 是否与批次共享 `seq`；冻结 F4 时按 WP2.4 的设计写明，这里不自行假定。
2. **MVP 合法事实域**：合法事实历史中只含观测级执行，因而没有沿用。集成测试的生成器、CX 集成测试与 E2E 使用它。在这一输入域中，没有新的人工决定时，任何 AC 都不会依据观测级证据变为 `accepted`。
3. **通用合法事实域**：另含合成的隔离级执行，它们同样满足上述写入条件与不变量（例如 `head_start = head_end = S`）。只用于单元测试，验证将来适用的沿用规则（ACC-09 的单元部分），需要 F1。合成用例通过不表示 MVP 具有隔离执行或自动沿用的能力。
4. **畸形组合**：违反上述写入前置条件或事实不变量、生产写入无法产生的组合，例如：
   - `S` 上没有任何合格执行的 `normal` 接受；
   - `evidence_id` 指向另一个 AC、另一个快照，或 `seq` 不小于决定的执行；
   - 跨项目的引用；
   - 不同的逻辑写入共用同一个 `seq`，例如在 `seq` 表内唯一的表中出现两行同一 `seq` 的记录（两个基准版本、两条范围确认、两条来源确认）；事实的 `seq` 大于计数器已分配的最大值。

   **不能仅因 `seq` 相同就判为畸形**：同一次逻辑写入共享 `seq` 是合法的（上文）。是否畸形，按具体的写入前置条件或事实不变量判断。

   畸形组合**不参与** `ready` 的双向等价对照，另行测试：
   - 两个实现都不崩溃，结果确定；
   - 复核器按它自己的谓词给出结论；
   - 推导引擎的期望取决于下文"最小澄清建议"的选择。在作出选择之前，畸形组合上的差异如实记录，不判为推导的缺陷，也不判为规格冲突。

**两套转换器保留的内容**：两套转换器各自独立实现，只做原始事实的映射。

- 每条事实的 `seq`，**包括共享同一个 `seq` 的全部关联事实**。生成器与转换器不按 `seq` 去重、合并或丢弃记录，不把 `seq` 当作事实行的唯一键；事实行由各自的 ID 标识。
- `as_of_seq` 作为参数分别交给两个实现，由它们各自过滤：保留 `seq ≤ as_of_seq` 的全部事实，同一个 `seq` 的关联事实一起保留或一起排除。转换器不预先过滤。
- 同一个 `seq` 之内需要的结构顺序，沿用既有规则：版本内的变更按 `change_index`，提案内的条目按 `item_index`，一次审核的应用顺序按 data-model §5.5。不用 ULID、输入数组的顺序或新造的全局排序代替业务先后。
- 不同写入之间的时序比较，各自依据现有契约，不统一改为非严格比较：例如 `V` 取 `runs(S)` 中 `seq` 最大的一条（data-model §6.1）；拒收的解除要求通过的 `seq` 大于拒收的 `seq`（§6.3 第 5 条）；`normal` 接受所依据的执行早于决定（上文）。检查执行与决定的 `seq` 分配，在 WP2.5、WP2.6 中按 data-model §4.11、§4.13 写明。
- 项目与实体的归属：项目 ID、实体 ID、需求与 AC 的父子关系、目标 ID。
- 修订：实体的当前修订与 `revision_seq`、AC 的 `requirement_revision`、Claim、执行与决定所绑定的修订与配置哈希。
- 证据引用与时序：
  - 决定的 `evidence_id`、`snapshot`、`mode`、`seen_decision_id` 与 `seq`；
  - 执行的 `head_start`、`head_end`、`tree_state_start`、`tree_state_end`、`result`、`failure_kind`、`evidence_grade` 与 `seq`。
- 全部决定与执行，包括失败的、被取代的记录。
- 转换器**不能**提前选出当前决定、计算适用性或合格性、丢弃失败或被取代的记录，也不能合并同一 AC 的多条记录。

**R6 与 data-model §6.3 第 6 条的关系**（重写；第 2 版"这类不一致作为规格问题报告"的说法过宽，已更正）：

- 写入不变量：`normal` 接受写入时，`S` 上有当前修订与配置下的合格通过，而且它是 `runs(S)` 中最新的一条（§7.3）。
- 推导规则：第 4 条（自动化 AC 且 `V = fail` → `failing`）先于第 6 条（接受且在 `S` 上适用 → `accepted`）。
- 在合法事实历史中，直接适用的 `normal` 接受意味着 `runs(S)` 不为空。检查配置的变化是强制的 `material` 修订，修订变化之后这条决定就不再是当前决定，所以那次通过一直属于 `runs(S)`。因此 `V` 只能是 `pass` 或失败，失败由第 4 条先处理。
- 所以"第 4 条加第 6 条"与 R6 中"`V = pass` 且 `D.snapshot = S`"**在合法事实域上等价**：R6 与冻结的决策表相容，不是规格冲突。
- 差别只可能出现在畸形组合中（例如没有任何合格执行的 `normal` 接受），它们不在双向对照的输入域内。不能为了消除这类差别而放宽复核器，也不能据此修改决策表。

**最小澄清建议**（草案，不改变规范；批准后写入 data-model §6 的开头或配套规格）：

1. 写明推导的输入域：§6 的规则假定输入是合法事实历史，列出它所依赖的写入前置条件与事实不变量（见上，包括 `seq` 的分配、同一次逻辑写入共享 `seq` 的规则与 `as_of_seq` 的含义）；acceptance-criteria §3 的不变量在这一输入域上成立。这一条只是依据既有规范写出技术规格，不改变规则，也不改变既有的 `seq` 契约。
2. 畸形输入的处理，两个选项：
   - (a) 不作额外规定：推导只对合法事实历史作保证；畸形输入只测试不崩溃、结果确定。
   - (b) 推导在开始前校验 `ready` 所依赖的那部分不变量（例如每条 `normal` 接受的 `evidence_id` 指向同一 AC、同一快照、`seq` 更小、结果为 `pass` 的合格执行），不满足时按 §6.9 最后一行拒绝推导并报错。代价：多一次校验；数据库被篡改或损坏时报错，而不是给出结论。它为畸形输入新增了用户可见的行为，需要负责人决定。
   - 推荐 (a)：不新增语义。数据库的写入由应用逻辑与触发器保护；同一用户直接写数据库属于已声明的信任边界之外（architecture §5），(b) 也不能防御构造得自洽的伪造记录。(b) 可以留作之后的选择。

**必须有的反例**（在合法事实历史中构造；每条以一个条件为目标，复核器必须在结果中指出该条件）：

- 条件之间有结构依赖时，例如没有基准版本就不可能有有效的范围确认，反例只需违反目标条件及其必然的连带条件，复核器的结果包含目标条件即可。不为了"只违反一条"而构造违反写入约束的历史（审查 041 N1）。
- 反例清单：
  - 当前决定是拒收（即使更早有过接受）；
  - 在同一个 `S` 上接受之后，又有一次合格的失败；
  - 父需求已被实质修订，而 AC 没有后续处理（`parent_revised`）；
  - 范围按版本过期；按来源集合过期；范围中的需求都已退役；需求没有 AC；`AS` 全部豁免；
  - 三类阻塞问题各一个，以及关联条目已拒绝、因而不阻塞的对照；
  - 来源内容变化；来源文件缺失；
  - `S` 为 NULL；决定针对另一个快照（手动、例外、没有沿用的 `normal` 各一个）；只有旧修订的决定。
- 输出一致性：篡改输出的证据等级，R10 失败（不是事实的反例）。

**必须有的正例**：

- 依据观测级执行的 `normal` 接受 → `ready`，证据等级 `observed`；
- 手动接受、例外接受与豁免的组合 → `ready`，证据等级 `none`。复核器不能要求所有 AC 都有自动化的通过；
- （通用合法事实域）依据合成的隔离级执行沿用 → `ready`，证据等级 `snapshot_isolated`。

**双向对照**：只在合法事实域上进行（受限首批：MVP 合法事实域；完整首批：MVP 与通用合法事实域）。

- 推导为 `ready` ⇒ 复核器通过；复核器认为全部条件成立 ⇒ 推导为 `ready`。
- 样本中要有足够数量的 `ready` 结果，也要有足够的合法但不能 `ready` 的历史，以免对照空转。
- 任何不一致都必须查明是哪一方或哪条规则的问题，不能为了一致而改动任意一方。真正的规格歧义按最小澄清的方式报告，不自行改变规范。

**推断**（没有实验，依据已知语义或规范）：

- Linux、macOS 上 argv 直接传给 `execve`，不存在 Windows 的命令行转义问题；
