# Specmetry 愿景

> 状态：Draft v0.2 · 2026-10-13（依据 [codex-review-001](reviews/codex-review-001.md) 修订）
> 本文描述长期方向与原则。第一阶段范围以 [mvp.md](mvp.md) 为准，需求细节见 [prd.md](prd.md)。

## 1. 一句话定位

Specmetry 是一个 **local-first 的 AI Coding Agent 项目进度与交付监督平台**：以经人确认的项目基准（Project Baseline）为尺子，持续、可追溯地回答三个问题：

1. 哪些需求已经**真正**完成？
2. 哪些需求还没有完成，卡在哪里？
3. 距离项目交付还差什么？

## 2. 要解决的问题

开发者手里有客户需求、开发文档和代码，却无法持续、可靠地判断项目进度：

- **三者之间没有持续的对照关系。** 需求写在文档里，实现落在代码里，二者的对应关系只存在于某次对话或某个人的脑子里。
- **Agent 自述不可靠。** Agent 经常在测试没跑、功能没做完时报告"已完成"。会话结束后上下文丢失，下一次会话无从核实。
- **进度判断依赖人工复盘。** 每次都要重读代码和对话，成本随项目规模增长，而且结论无法复现。
- **需求漂移不可见。** 客户改需求、Agent 擅自扩大或缩小范围，都没有留下记录。
- **中途接手没有起点。** 多数工具假设项目从零开始规划，而真实项目往往"代码写了一半、文档也只有一半"。

## 3. 核心洞察：把"完成"拆成三层事实

| 层级 | 由谁产生 | 回答什么 | 可信度 |
|---|---|---|---|
| **Agent 自述**（Claim） | Agent | Agent 认为自己做了什么 | 低：只作为线索 |
| **执行证据**（Evidence） | Specmetry 在某个代码上下文中执行 | 客观上发生了什么：经人确认的检查，在哪个提交、哪个 worktree、是否干净的状态下通过或失败 | 中到高，并且只对执行时的那个提交有意义 |
| **正式验收**（Acceptance） | 人 | 在这个代码快照上，是否满足基准中的验收标准 | 最高：判定"已完成"的唯一来源 |

三层事实都对照同一把尺子：**Project Baseline**，即目标、需求和验收标准。它经人确认，并且有版本。

交付判定还要回答"**哪份代码**"：它只针对人确认的交付目标在当前指向的那个确定提交，以及人确认的交付范围。旧代码上的验收、其他分支上的通过，都不能证明当前的代码可以交付。

因此进度不是谁填写的数字，而是由"基准 × 交付快照 × 三层事实"确定性推导出来的结果：可以复现，也能逐条追溯。

## 4. 产品原则

### 4.1 既定原则

1. **不接管 Agent。** Specmetry 不启动、不调度、不控制 Agent，也不要求从 Specmetry 内启动 Agent。
2. **基准优先，事实分层。** 用 Project Baseline 保存目标、需求和验收标准，并严格区分 Agent 自述、执行证据和正式验收。
3. **从任何阶段接入。** 支持仅有文档、开发中、文档不完整的项目。
4. **Skill 负责理解，Hook 与 Collector 负责记录。** Agent Skill 提供 `init`、`status`、`sync`、`goals`、`audit` 等命令；Hook 与本地 Collector 负责可靠地采集事件。
5. **Local Free 免费，无需账号。** 未来的 Hosted Personal / Hosted Team 提供身份认证、远程同步和团队协作。
6. **数据默认留在本地。** 不主动上传客户代码、密钥、完整对话等敏感信息。

### 4.2 本轮设计派生的原则（待确认）

7. **状态只能推导，不能手填。** 不存在"把某需求设为已完成"的操作。人和 Agent 只能产生事实（提案、自述、证据、验收），状态由事实推导而来。
8. **Agent 只能提议和自述，不能确认和验收。** 基准变更与验收都必须由人完成。
9. **核心不调用 LLM。** 需要理解语义的工作，比如从文档提取需求、对照代码盘点，由用户自己的 Agent 通过 Skill 完成。Specmetry 本体只做确定性的存储、校验、执行和推导，因此不需要 API Key，也不需要联网。
10. **不打扰。** Hook 出错永远不影响 Agent 工作。Specmetry 从不修改用户代码，修改 Agent 配置前必须得到显式确认。
11. **可追溯。** 任何状态都能回溯到来源文档原文、Agent 自述、执行证据和验收记录。
12. **交付判定只针对确定的代码快照。** 无法判断时，给出更保守的结论；绝不会因为信息不全而给出"可以交付"。
13. **先后由数据库序号决定，写入携带读取时的版本。** 任何基于过期信息的判断，都不会被记录成新的事实。

## 5. Specmetry 是什么 / 不是什么

**是：**

- 一份轻量、有版本的需求基准（目标 → 需求 → 验收标准）
- 一个记录进度事实（自述、证据、验收）的本地账本
- 一个确定性的状态推导和差距分析引擎
- 一个本地 Web Dashboard

**不是：**

- Agent 编排器、启动器或调度器
- 通用项目管理工具：不做任务分派、排期和工时，不替代 Jira 或 Linear
- CI 系统或测试框架：它调用你已有的测试，而不是替代它们
- 代码审查工具或代码托管平台

## 6. 目标用户

| 用户 | 场景 | 阶段 |
|---|---|---|
| **独立开发者 / 外包开发者 / 小型工作室**（主要用户） | 用 Claude Code 等 Agent 交付客户项目，需要知道还差什么，并向客户说明进度 | MVP |
| 个人项目或开源项目维护者 | 让 Agent 持续推进项目，需要防止"以为做完了" | MVP（次要） |
| 小团队技术负责人 | 多人加多个 Agent 并行开发，需要统一的交付视图和多人验收 | 远期（Hosted Team） |

## 7. 产品形态演进

| 形态 | 内容 | 状态 |
|---|---|---|
| **Local Free** | 单一二进制：CLI + Agent Skill + Hooks + 本地 Collector + SQLite + 本地 Dashboard。无账号，无网络依赖。 | 第一阶段 MVP |
| Hosted Personal | 身份认证、跨设备同步、远程查看 | 远期，本轮不设计 |
| Hosted Team | 团队协作、多成员验收、角色权限、面向客户的只读视图 | 远期，本轮不设计 |

Local 与 Hosted 之间的功能边界尚未确定，见 [prd.md](prd.md) 的 PD-11。

## 8. 成功的样子

- 开发者接手一个开发中的项目后，能在较短的时间内得到一份经确认的基准、交付范围和差距清单。目标耗时用夹具评测和真实项目试用来衡量，不作为承诺。
- 任一需求的状态都能点开追溯：来源文档原文 → 验收标准 → Agent 自述 → 交付快照上的执行证据 → 验收记录。
- "Agent 说完成了，但在交付快照上没有有效证据"成为一个被显式统计、可以追问的数字。
- 交付前，开发者能明确说出"在提交 X 上，还差这 N 项"，并且每一项都有依据。
- Specmetry 宁可说"无法判断"，也不会给出错误的"可以交付"。

## 9. 长期路线（方向性，非承诺）

1. **Local MVP**（当前）：初始化、基准提取与确认、现状盘点、差距分析、持续进度更新、本地 Dashboard。
2. **Local 深化**：适配更多 Agent，导入 CI 证据，交付报告，评估是否需要对有未提交修改的工作区做正式判定（工作区指纹）。
3. **Hosted Personal**：身份认证、可选择性的同步、跨设备查看。
4. **Hosted Team**：多人协作与验收、客户只读视图。
