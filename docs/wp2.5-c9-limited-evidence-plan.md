本轮新做的三项只读核对（都不是运行证据）：

1. **dirhash 的实现来源**（供 G4-Q6）：
   - 固定 Go 中 `src/cmd/vendor/golang.org/x/mod/sumdb/dirhash/hash.go` 共 135 行，SHA-256 `24de6a735c1605e39b6381e6962787faa5c59adab896fb66dbc1ac8b6afcb297`。`cmd/vendor/modules.txt:31` 记录它来自 `golang.org/x/mod` `v0.36.1-0.20260813213634-8569e2639ca1`。

   - 对本机的这个模块目录按 Hash1 的定义只读重算（137 个文件），得到 `h1:ICeL3t2L30ljSPHHxDnR4fqVcBt/zR2zJAb9juavmQg=`，与 `go.sum` 第 42 行相同。这是本机缓存的事实，不是 CI 的事实。

2. **T2 在 Windows 上作为一个参数的传递**（供 LQ-7 与 §4.2）：
   - `os/exec` 在 Windows 上把参数拼成一条命令行（`os/exec/exec.go:408` ~ `414` 的说明）。没有设置 `SysProcAttr.CmdLine` 时，命令行由 `makeCmdLine` 生成（`syscall/exec_windows.go:346` ~ `351`、`:106` ~ `116`）。
   - `appendEscapeArg`（`:48` ~ `102`）：参数中有空格而没有 `"` 与 `\` 时，只在两端加上 `"`，内容原样。T2 有空格，没有 `"`、`\`、TAB 或换行，所以它成为 `"` 加上 T2 原样的字节再加 `"`。
   - 接收方是 Go 程序时，`os` 包在初始化时以 `commandLineToArgv` 拆分命令行（`os/exec_windows.go:94` ~ `101`、`:155` 起）；`readNextArg`（`:114` 起）在引号之内把除 `"` 与 `\` 之外的字节原样加入，遇到配对的 `"` 结束引号。所以 T2 原样成为一个参数。T2 只含 ASCII，UTF-16 的往返不改变它。
   - 前提：被执行的是经 E-10 核对的 `go.exe`（Go 程序），没有包装器，工具不设置 `SysProcAttr.CmdLine`。Unix 上参数以数组传给 `execve`，本轮没有逐行核对那条路径，留到实现的审查时补核。
   - 这只是固定源码的推演。实际的传递只能运行取得（方法记录 §8.2）；输出的校验也不认证 cmd/go 收到的就是原模板（方法记录 §3.3.1）。
3. **既有 workflow 的触发方式**（供 §9）：
   - `ci.yml` 只在推送 master 与 pull request 时运行，以根模块的 `./...` 运行 `go test`、`go vet` 与 golangci-lint。
   - `wp25-prototype.yml` 只在推送它列出的分支、而且改动落在 `prototype/wp25/**` 或它自己时运行，没有手动触发。
   - `prototype/wp25` 有自己的 `go.mod`，根模块的 `./...` 不包含它（`prototype/wp25/go.mod` 第 1 ~ 3 行的说明）。

### 1.3 不做的事

- 不实现工具，不创建或修改 workflow，不运行任何调用、扫描或对照。
- 不把生产 c9lint（`internal/testutil/c9lint`）或 G-6（判定的实现与 A-1 ~ A-10）纳入第一次取证。
- 不做产物证明，不涉及 H-1 或链接方法（原链接方法继续停止）。
- 不覆盖原始入口、汇编与其他未覆盖的路径（U-1 ~ U-4、U-7），不分析发送信号的路径。
- 不改冻结正文、验收项、实现、测试、原型、依赖、Schema、迁移、workflow 或预算的配置。

### 2.5 特别说明

#### 2.5.1 G4-Q1：规则标识与实现摘要

- **两种方式的差别**：
  - (i) 只用规则标识（v1 的 H 行 `rules`），加上审查规则：改动判定的代码或规则的文本时，必须同时改标识。治理可以要求，机器不能发现“改了实现而没有改标识”。
  - (ii) 另外绑定规则实现文件的摘要。机器可以发现文件的改变，代价是任何改动（包括注释）都使清单失效、须重新批准。
- **时间的约束**：决策稿 §6.3 的阶段 3（完整清单的批准）早于阶段 4（G-6 的实现）。批准清单时，判定规则只以文档的形式存在（§12.9、决策稿 §3.2），还没有可以取摘要的实现文件。
- **推荐**：
  - 阶段 3 采用 (i)：`rules` 的值指向经审查的规则文本的版本，治理要求写进清单批准的那一节。
  - 实现摘要作为规范表示 **v2** 的变更提案，在生产实施（N4）时决定。提案只写必要的部分：H 行增加一个键 `rules-impl`，值为规则实现文件清单（按路径排序的相对路径与各自的 SHA-256，不含测试文件）的 SHA-256；文件集合与表示须另行写定；v2 的清单须重新生成与批准。本轮不改 v1。
- **声明的上限**：在 (ii) 生效之前，不能宣称规则实现的改变会被机器发现（方法记录 §4.2、§8.5）。

#### 2.5.4 G4-Q6：Hash1 的实现来源

- **推荐**：工具导入 `golang.org/x/mod/sumdb/dirhash` v0.42.0，只使用 `Hash1`。
  - 依据（§1.2 第 1 项）：它的 `hash.go` 与固定 Go 1.27.3 中 cmd/go 自己使用的副本逐字节相同；本机缓存中这一模块目录的 h1 与 go.sum 相同。实现时仍须在 CI 中由 I-4 核对 x/mod 的模块内容（x/mod 在生产闭包中：`internal/store/sqlite` 导入 `golang.org/x/mod/semver`）。
  - 用法：受控读取先对每个文件打开一次、读到 EOF、关闭，保存字节、SHA-256 与真实的 `Close` 结果；然后以带前缀的名字列表调用 `Hash1`，打开函数只交出内存中的字节。`Hash1` 不检查 `Close` 的返回值，这时也不会掩盖任何真实的结果。
  - 不使用 `HashDir` 与 `DirFiles`（固定源码 `hash.go:67` ~ `109`）。`DirFiles` 以 `filepath.Walk` 枚举：`Walk` 以 `Lstat` 取得根与每一项的信息（`path/filepath/path.go:424`、`:364`），所以**不递归进入**目录的符号链接；但链接不论指向文件还是目录，`IsDir` 都为假，`DirFiles` 把它作为非目录的名字列出（`hash.go:91` ~ `102`；`path.go:345` ~ `346`）。之后 `HashDir` 以 `os.Open` 打开这些名字（`hash.go:75` ~ `77`），`os.Open` **跟随**被打开的链接。I-4 的类型规则要求 `Lstat` 得到的不是普通文件即 J-2（方法记录 §2.2 第 6 条），所以它们不能直接替代 I-4。所选的方案、类型约束与关闭责任不变。
- **不采用时**：工具自己实现 Hash1（约二十行），须与上面的固定源码逐字对照，并以已知的 h1 作正对照（LC-1）。
- 真实的 `Close` 结果无论选哪一种都必须由工具自己保存并消费（方法记录 §2.5）。

## 5. 对照 LC-1 ~ LC-10 与证据的域

### 5.1 原则

- **命中**：每项对照都须证明两件事：进入了目标检查（工具为每项检查写一条“进入”记录，带检查的编号与输入的 SHA-256），而且结果等于写定的完整预期（§5.5）。只有最终失败而没有进入记录的，不算命中。
- **证据的类别**，分开记录：
  - 真实：真实的输入与真实的调用（仓库本身、CI 的模块缓存）；
  - 夹具：真实的工具代码作用于临时目录中的夹具；
  - 接缝：假的调用者、接缝的时钟或注入的结果。
- **进程**：真实的 `go` 调用只在真实采集中（两个配置的六次，§4.2）。对照都不另外调用 `go`：需要调用输出的对照由假的调用者给出字节；只有 LC-9 启动伪工具（测试二进制的再执行，实施计划 §12.12）。之后若要加入在夹具上真实调用 `go` 的变体，须另写依据与预期，计入同一个 120 秒，并以 E-10 (ii) 已经确认为前提（§10.2）。
- **次数与计数**：每个作业把每组对照执行一次。“LC-1 ~ LC-10 各一次”是对照组的口径，组内有多个字节变体、错误分支与夹具；结果中不把十组写成十次原生的观察。真实采集（两个配置）、夹具、接缝与交叉配置的静态分析分开计数。
- **平台的适用**：只在某个平台有意义的对照或变体（例如 pidfd 只在 Linux，符号链接的创建），在实现中写定适用表与理由，并经实现的审查；表中写“不适用”的平台记为“不适用”。表中写“适用”而在运行中无法构造、被跳过、因为没有获准真实调用而没有覆盖，或测试失败的，都是“不命中”，不临时改写为“不适用”。
- **失败出口**：每个变体由外层判定为命中、不命中、未决或不适用（§5.5）；它们怎样进入作业的结论见 §7.1。采集的结果照样保留，但不作为证据。
- 本文中写下的预期只是文档，不计作运行。

### 5.3 LC-5 的 A/B 投影

方法记录 §7 的 V-19b、V-20、V-24、V-40、V-42 是完整方法的预期，含 B′ 与 LP。本工具不实现 B′、规范表示、批准登记与 C 的匹配（§4.3），所以 LC-5 不与这些行“完全相同”地比较，而与它们在本工具检查上的**投影**比较。原方法的 V 不变；本工具也不为通过 LC-5 而实现 B′。

**投影的规则**：

1. **本工具的检查集合 E**：A1-a、A1-b、A1-c、A2、A3、A4、A5；B1（六个键：`GOOS`、`GOARCH`、`CGO_ENABLED`、`GOFLAGS`、`GOWORK`、`GOTOOLCHAIN`，方法记录 §3.2）、B2（方法记录 §3.3.3 的各字段）、B3（逐记录）、B4（逐模块）、B5（受控读取、条件差异检查、I-5 ~ I-7、依赖模块与标准库的装载与类型检查）；S（第三方的对象扫描）；K（与候选的对照，§4.4）。每个用例中，E 的每一项都有且只有一个结果：成立、失败（带 J 与项）或未评估。

| O 外层对照与收尾 | 外层为对照准备夹具（建立临时目录与文件）、消费被测实例、清理（关闭外层自己的句柄、删除临时目录、确认被测实例的任务与资源都已结束）；记录链与诊断（§6.4） | 包级的外层登记表。外部操作按 §12.14 的同一模式进行：先登记，由任务或工作 goroutine 在锁外执行，发起者（测试 goroutine 或父端）只查询已发布的状态；等待都受 `W`、`D` 约束，不另取预算 | 准备失败使该变体不命中（§5.5，无效）；清理的失败或未知使该变体未决；记录链与诊断的失败或缺失使结论不能是 3 或 4（§7.1、§6.4） |

- **身份**（§6.3 的提交与树、T2 的绑定 LC-10）不属于三个域；任何不符直接是 §7.1 的第 1 级“无效”。工具链的守卫（E-10 (i)）不符是 R 的 J-1（A1-a、A1-c），属于第 2 级。
- **与 `TestMain` 及既有登记表的接线**：
  - R 登记表就是 §12.14 第 3 条的包级登记表，§12.14 第 3 ~ 13 条对它照常适用。被测实例的登记表与外层登记表是另外的实例，同一协议、同一个 `D`。
  - 测试函数不经 `testing.T` 报告这些域的结果：结论只由三个域与身份的已发布状态推出（§7.1）。`m.Run` 的结果非零，表示某个测试在这些登记之外失败（例如工具自己的不变量被违反），记为工具的缺陷（无效）。测试函数 panic 时进程由测试框架结束，没有收尾，按 §7.1 的“收尾缺失”读。
  - §12.14 第 13 条的退出状态函数扩展为：接收 `D`、R 登记表、对照表、外层登记表与诊断的输出端，最迟在 `D` 返回结论与退出状态（§7.1）；`TestMain` 只以它的返回值调用 `os.Exit`。

### 5.5 外层接受负向结果的规则

对每个对照的每个变体，外层在实现中写定一份**完整预期**（在固定实现的审查中固定）：

1. 被测实例中每项检查的结果（成立、失败、未评估），以及每条失败的：
   - **站点**：检查的编号与具体的操作（例如“LC-3 第 4 项：受控读取对夹具文件 f 的 `Close`”）；
   - **类型**：J 类与错误的种类（例如“关闭错误”“预算不足”）；
   - **来源**：注入（由接缝登记的标识识别，例如每次注入的序号）、真实，或预算判定；
   - **次数**。
2. 被测实例中控制协议每条登记的终态（§12.14 第 11 条的各项，回收、关闭与请求的结果），以及预期的晚到结果。
3. 外层自己的准备与清理都成功；被测实例的全部任务与资源在包的 `W` 之前进入终态。

外层的判定（每个变体）：

| 判定 | 条件 | 对作业结论的影响（§7.1） |
|---|---|---|
| 命中 | 有进入记录；被测实例已进入终态；它的全部结果与完整预期逐项相同（不多、不少，来源与次数相同）；外层的准备与清理都已成功 | 不妨碍 3、4 |
| 不命中 | 没有进入记录；结果与完整预期有任何不同，包括：多出的真实错误（即使与预期的注入在同一站点、属于同一 J 类）、缺少预期的失败、来源或次数不同；外层的准备失败；适用表中写“适用”而没有执行 | 第 1 级：无效 |
| 未决 | 到快照点（§6.4）被测实例仍有任务或资源没有进入终态；或外层的清理失败、出错或结果未知 | 第 2 级：未完成（另有第 1 级的条件时为无效） |
| 不适用 | 适用表中预先写定的不适用平台 | 无 |

- 外层**不**按 J 类别、错误的文字或问题的个数整体豁免：只接受逐项等于完整预期的负向结果。
- 接受负向结果不删除它：被测实例的全部记录都由持续的持有者保存在内存中，并经记录链写入对照的记录（§6.4）；快照点之后才到达的结果不保证写入文件（§7.1 的“记录的保留”）。
- 外层只在被测实例进入终态之后判定，所以“命中”之后没有晚到的结果；没有进入终态就是“未决”。快照点之后才到达的结果由持续的持有者保存，不使已定的结论变好。
- “命中”不覆盖外层自己的失败：被测结果符合预期，而外层删除临时目录出错，这一变体是“未决”，不是“命中”。

### 5.6 文档推演

只按 §5.3 ~ §5.5、§6.4 与 §7.1 的规则推演，不写或运行测试。

1. **健康的负向命中**（LC-3 第 4 项）：夹具文件 f 的真实 `Close` 返回 nil；接缝随后追加注入的错误 E（标识 #1）。被测实例记：受控读取的进入记录；真实的关闭结果 nil；注入的 E 另行保存；检查记 J-1（来源：注入 #1）。实例进入终态，外层的准备与清理都成功。完整预期是“恰好一条 J-1，站点为 f 的 `Close`，来源为注入 #1，次数 1；真实结果 nil；没有其他失败”，逐项相同 → 命中。R 登记表中没有这条 J-1，它不使作业未完成；它的记录保留在对照的记录中。
2. **真实的关闭错误**（第三稿按 N-144-1 改写）：
   - (a) 同一变体，但 f 的真实 `Close` 返回 EIO。接缝只能在真实结果为成功之后追加注入（实施计划 §12.14 第 12 条；V-29），所以这次**不**进行注入。被测实例记一条来源为“真实”的 J-1（站点为 f 的 `Close`），预期的注入 #1 没有发生。完整预期是“真实结果 nil，加上注入 #1”，两项都不符 → 不命中 → 作业无效。真实错误保留；不因为它与预期的注入同属 J-1、在同一站点而被豁免。f 的释放未知另记在外层，但第 1 级优先。
   - (b) 若要演示“注入之后另有真实错误”：f 的真实 `Close` 为 nil、注入 #1 已经追加之后，同一被测实例中**另一项**必要操作（例如这一变体另一个夹具文件 g 的受控读取）的真实 `Close` 返回错误。被测实例中多出一条来源为“真实”的 J-1（站点为 g 的 `Close`）→ 不命中 → 作业无效；两条记录都保留。注入的前提没有放宽，也不新增原生的故障实验（这一变体只是推演；是否在实现中加入，按 §8.1 在固定实现的审查中决定）。
3. **晚到的真实错误**：
   - (a) R：一个配置的扫描与候选对照都已完成、全部一致；第 3 种调用的一个读端的 `Close` 直到 `W` 之后才返回，返回真实错误。到 `W` 这次调用不满足 §12.14 第 11 条，快照中 R 有失败；之后到达的错误作为晚到的结果写入 R 登记表 → 第 2 级“未完成”。扫描的结果作为诊断保留（V-30），不以“已判一致”保留结论 4。
   - (b) F：LC-9 的一个变体，被测结果在时刻 t 已经与预期相符，但实例的一个关闭还没有返回，外层不判定；之后关闭返回真实错误，实例进入终态，多出一条真实的 J-1 → 不命中 → 无效。若到快照点它仍未返回 → 未决 → 未完成；之后才到的错误由持续的持有者保存，不进入日志，结论也不因此变好。
4. **缺少指定的命中**：Windows 作业中，LC-2 的符号链接变体在适用表中写的是“适用”，运行时因为权限不能创建链接。这一变体没有进入记录 → 不命中 → 作业无效。即使 R 全部成立、发现与候选一致，结论也是无效；不改写为“不适用”，也不记为跳过。

### 6.3 提交与树的身份

- 运行的授权（§8 第 4 步）写定两个值：固定的受审提交 **C**（完整的提交 SHA），与固定实现审查时记录的它的树 **T**（完整的树 SHA）。
- 未来的 push 取证须满足两条关系：
  1. **提交**：C = 实际检出的提交（workflow 中 `git rev-parse HEAD`）= 本次 push 的 `GITHUB_SHA`（workflow 打印；工具从环境变量读出并写入原始记录）。
  2. **树**：tree(C) = 实际检出的树（workflow 中 `git rev-parse HEAD^{tree}`）= T。
  - 提交与树是两类对象：C 与 T 不相等，也不要求相等。第一稿写的“三者必须相同”混合了这两类，本稿撤回（B-143-3）。
- **机械的核对**：workflow 在运行工具之前核对 HEAD 与 `GITHUB_SHA` 相同、工作区干净（`git status --porcelain` 为空），不成立即失败，不运行工具；打印 HEAD、HEAD 的树与 `go version`。工具只记录它读到的 `GITHUB_SHA`，不调用 `git`（工具除三种调用与 LC-9 的伪工具之外不启动进程）。
- **与授权的核对**：审查时，把日志与原始记录中的值与授权写定的 C、T 比较。两条关系都成立才有效；任一不成立即“无效”（§7.1 第 1 级）。
- **由 C 绑定的对象**：工具的源码（`prototype/c9evidence/` 之下）、workflow 文件与 LE-4 的模块准备都取自 C 的树；运行记录与派生记录经原始记录中的 `GITHUB_SHA` 与日志中的 HEAD、树关联到 C 与 T。这次运行实际使用的是哪一份 workflow 文件，在固定实现的审查中按 GitHub 的说明写定核对的方式（例如同时记录 `GITHUB_WORKFLOW_REF` 与 `GITHUB_WORKFLOW_SHA`）。
- **常规 CI 另列**：实现 PR 上的 pull_request 常规 CI 检出的是合并快照（例如本 PR 的 run 43225398424 检出 `adba69f`：它的树与 HEAD 相同，提交不同）。合并快照不能代入取证的 C；常规 CI 只是根模块的回归，不运行工具。
- **工具链**：取证的 workflow 固定 `go-version: 1.27.3`、`GOTOOLCHAIN=local`；工具按 E-10 (i) 核对，不符即 J-1。常规 CI 由 `go.mod` 的 `go 1.27` 解析补丁版本（本 PR 的 run 43225398424 中，显示版本的七个作业都是 go1.27.4），那不是取证的工具链，也不是固定 go1.27.3 的候选方法的执行证据。
- **模块**：LE-4 的下载步骤之后，日志写下 `go.mod` 与 `go.sum` 的 Git blob 与工作区是否干净；工具记录读到的字节的 SHA-256。两者须对应。

### 6.4 记录链：任务、关闭与发布

第一稿只写了记录“在 `D` 之前逐条写出并落盘”，没有写谁执行、谁关闭、失败怎样进入结论（B-143-2）。本节按实施计划 §12.14 的已审模式写定：先登记，外部调用由唯一的任务在锁外执行，父端只查询已发布的状态；全部等待使用原来的 `W`、`D`，不另取预算。§12.14 的协议本身不变，pidfd 与工具子进程的协议不重写。

**对象**：

- 记录目录：检出之外的一个新目录（位置在固定实现的审查中写定），运行之前不存在。
- 记录文件：固定的几个文件（例如原始记录、派生记录、对照记录与收尾记录；名字、版本号与格式在固定实现的审查中写定），UTF-8、LF。
- manifest：一个文件，逐行写出每个记录文件的名字、字节数与 SHA-256。
- 记录项：工具在内存中产生的、只追加的记录。产生者（R、F、O 中的任务、测试 goroutine 与父端）只在锁下把它们追加到内存中的日志，**不做任何文件操作**。所以 §12.14 中被放弃的工作 goroutine 仍然不持有记录文件。

**责任**：

| 操作 | 执行者 | 时机与规则 | 发布的结果 |
|---|---|---|---|
| 登记 | 父端（`TestMain`） | 取得 `D` 之后、`m.Run` 之前，在外层登记表的锁下建立写者的记录，再启动写者任务；父端自己不做文件操作 | 写者的状态：已登记 |
| 建立目录；以独占的方式建立每个记录文件 | 写者任务（唯一） | 在锁外依次进行；每一步的结果在锁下发布 | 每个文件：未建立、已打开或建立失败（带错误） |
| 写入 | 写者任务（唯一） | 在锁下取出尚未写入的记录项的副本，在锁外写入对应的文件，再在锁下发布；每个文件的 SHA-256 在内存中按实际写入成功的字节累计 | 已写的字节数、SHA-256 的累计值、写入的错误 |
| 关闭每个记录文件 | 写者任务（唯一；每个文件一次） | 收到收尾信号之后，写完剩余的记录项，再逐个关闭；关闭在锁外 | 真实的 `Close` 结果；为 nil 才确认释放 |
| 建立、写入与关闭 manifest | 写者任务（唯一） | 只在全部记录文件的写入与关闭都成功之后进行；以独占的方式建立，写完关闭一次；它的 SHA-256 在内存中按写入的字节计算 | 字节数、SHA-256、写入与关闭的结果 |
| 打印结论行、哈希与终结行 | 唯一的诊断任务（即 §12.14 第 13 条的诊断任务，增加本工具的内容） | 见下面的收尾顺序 | 每一次写入标准错误的结果 |
| 最后的判定与退出 | 父端 | 只消费已发布的状态与已经确定的截止资格（见下），按 §7.1 确定结论与退出状态，然后 `os.Exit`；此后不打印、不刷新、不关闭、不查询，也不等待 | 退出状态 |

- **“落盘”的含义**：一个记录项“已落盘”，指写者对它的写入已经返回且没有错误：数据已交给操作系统，本进程之后被终止（例如 OOM，或到 `D` 的退出），之后的 artifact 上传步骤仍可读到它。**不包括 Sync**：本工具不宣称记录在操作系统或 runner 崩溃时仍然保留（那时上传也不会进行）。这依据操作系统的通常语义，三个 runner 上没有取证。若负责人要求 Sync（LE-6），它也由写者任务在锁外执行，错误同样持续保存并进入判定。
- **截止复核**（第三稿，B-143-2-R；第四稿按 B-143-2-R/P 限定适用范围）：每一个要开始新动作的决策点，都在外层登记表的锁下重新读时钟，并检查到期锁存（见下）；已到 `D` 或锁存已置，就走统一的到期出口。新动作的决策点是：
  1. 写者：每一次建立、写入或关闭之前；
  2. 父端：`m.Run` 返回时；等待快照点结束、准备取快照、发出收尾信号与登记诊断任务之前；
  3. 诊断任务：每一次写到标准错误之前，包括第一次写入、等待写者的终态结束之后的那一次，以及每次写入返回之后的下一次。

  此前通过的准入、等待的返回（例如任务的 `Done` 或记录的变化）、外部调用开始时尚未到期，都不能代替当前决策点的复核。本工具不要求调度在 `D` 精确唤醒，也不中断已经开始的系统调用；复核只决定是否开始新的动作。`[W, D)` 中写入收尾与报告的记录，属于 §12.14 允许的收尾与报告，不是新的工作。
- **新动作的准入与最终消费是两种行为**（第四稿，B-143-2-R/P）：
  - **新动作的准入**：发出收尾信号、登记或启动诊断任务、开始任何外部的建立、写入或关闭，都要经过上面的截止复核，受原来的 `D` 守卫。
  - **最终消费**：父端等待诊断任务期间的每次唤醒，只读取已经发布的终态与已经确定的截止资格，**不取得任何新动作的权限**。它不是上面所列的新动作决策点，不适用“已到 `D` 即走到期出口”的一般规则，而按收尾顺序第 5 步写定的唯一顺序处理：先看诊断任务是否已有终态，再看是否已到期。
- **到期锁存与截止资格**（第三稿，B-143-2-R）：
  - **到期锁存**：外层登记表有一个到期锁存。任何持有外层登记表的锁的一方（写者、诊断任务、父端）在锁下读到的时刻已到 `D`，就置上它；它只置不清。
  - **截止资格**：写者与诊断任务每发布一个结果（每次建立、写入、关闭的结果，写者的终态，诊断任务每次写入的结果与它的终态），都在**发布的同一次锁下**确定这个结果的资格：锁存未置，且这次锁下读到的时刻早于 `D` → “及时”；否则 → “晚到”，并置锁存。资格由发布者随结果一起保存在外层登记表的记录中，只追加，之后不改。到期出口发布的“到期停止”“到期未完成”也带资格（晚到）。
  - **资格只看发布**：外部调用在 `D` 之前开始，而结果在 `D` 之后才返回或发布 → 晚到；输出的字节在 `D` 之前写完，而完成状态在 `D` 之后才发布 → 晚到。外部调用的开始时刻、字节是否已出现在日志中，都不决定资格。
  - **竞争的唯一解释**（第四稿按 Review 145 §4.2 精确措辞，规则不变）：在外层登记表的锁串行化下，由**逻辑判定点**（发布者在锁内读时钟并检查锁存的那一点）读到的时刻与到期锁存共同确定资格。判定点上锁存未置、读到的时刻早于 `D`，这次发布是及时的；锁存置上之后发布的一律晚到。先取得锁本身不等于及时：发布者先取得锁，而在判定点读到的时刻已等于或超过 `D`，仍是晚到；判定点恰好等于 `D` 也是晚到。资格按这个逻辑判定点确定，不要求字段实际可见、解锁或其他任务观察到结果与墙上时钟具有硬实时的原子性。晚到的成功不清除已经成立的未完成，也不使锁存复位。
  - **及时完成的保持**：父端消费的是已经确定的资格，不重新判断时刻。及时发布的完成，即使父端在 `D` 之后才获调度、才去读取，仍然是及时的；反过来，父端也不把读取时看到的“当前成功”追认为及时。
- **统一的到期出口**（失败出口）：
  - **父端**：只在两种情形进入：在新动作的决策点（`m.Run` 返回时、等待快照点结束时）已到 `D` 或锁存已置；或在最终消费中诊断任务**尚无终态**而已到 `D` 或锁存已置（第 5 步的分支 (b)）。进入时，置锁存；不取新的快照，不发收尾信号，不登记或启动诊断任务，不打印、刷新、关闭或等待；在这一次锁下只消费已发布的状态，确定最终结论，以非零的退出状态 `os.Exit`。进入这一出口的状态不会得到 3 或 4：要么没有暂定结论，要么暂定为 1 或 2，要么暂定为 3 或 4 而必要的终态没有完整、及时地发布（§7.1）。
  - **置锁存不等于进入失败出口**：父端在最终消费中读到已到 `D` 时也置锁存，但诊断任务已经发布终态时，它先按 §7.1 消费那个终态与已经确定的资格（第 5 步的分支 (a)）。置锁存只影响之后的发布，不撤销历史上已经确定的及时资格；必要结果全部及时成功、只是父端晚醒的情形，不进入这一出口（§6.6 的情形 3）。
  - **诊断任务**：不开始下一次写入；在锁下发布“到期停止”，然后结束。
  - **写者**：不开始新的建立、写入或关闭；在锁下发布“到期未完成”，然后结束；未关闭的句柄、尚未写入的记录项与哈希的累计值留在外层登记表的写者记录中。
  - 已经开始的外部调用由原来的任务继续持有；它们之后的结果照样发布（资格为晚到），不改变已定的结论。
- **半构造与失败出口**（写者是每个记录文件与 manifest 唯一的关闭者；父端与诊断任务都不碰这些文件）：
  - 建立目录失败：没有打开任何文件，没有要关闭的；记录链失败。
  - 第 k 个文件建立失败：写者把已打开的前 k−1 个文件各关闭一次，发布结果；不写入；记录链失败。
  - 任何写入失败：写者不再开始任何写入（剩余的记录项留在内存中），把已打开的文件各关闭一次，发布结果；不建立 manifest；记录链失败。
  - 任何记录文件的 `Close` 出错：释放未知，记为失败，不重试；写者继续关闭其余的文件；不建立 manifest。
  - manifest 的建立、写入或关闭出错：同样记为失败；它已打开时由写者关闭一次。
- **错误持续保存**：每一个真实的建立、写入与关闭的错误都在锁下发布，只追加，不被之后的成功清除，并进入 §7.1 的判定。
- **持续的持有者**：写者停在外部调用中时，它继续持有句柄、尚未写入的记录项与哈希的累计值；外层登记表持有写者与诊断任务的记录；诊断任务持有它的快照与对输出的使用；都直到测试进程结束。进程退出时由操作系统释放句柄，这**不是**已确认的关闭。
- **收尾的顺序**（`m.Run` 返回之后；第三稿在每个决策点加上复核）：
  1. **`m.Run` 返回**：父端在外层登记表的锁下复核；已到 `D` → 到期出口。已落盘的记录照样留在目录中。
  2. **快照点**：父端等待 R、F、O 中除写者与诊断任务之外的全部记录都进入终态，或到 `W`，取两者中较早的（`m.Run` 在 `W` 之后才返回时不再等待）。等待结束时，父端先取得 R 登记表与对照表的快照副本（内存中的读取），再在外层登记表的锁下**复核**：已到 `D` → 到期出口（即使 `m.Run` 返回时还没有到期）。没有到期 → 在**同一次锁下**：取得外层登记表的快照副本；按 §7.1 算出**暂定结论**；把它与快照的摘要作为收尾的记录项追加；向写者发布收尾信号；登记诊断任务。释放锁之后启动诊断任务。这些都是内存中的操作。
  3. **写者的收尾**：收到收尾信号之后，在每一个决策点复核，依次写完剩余的记录项、逐个关闭记录文件，再建立、写入与关闭 manifest。全部成功时在锁下发布终态“成功”，否则发布“失败”（带全部错误）；到期时按到期出口发布“到期未完成”。每个结果都带截止资格。
  4. **诊断任务**：每次写入之前复核。依次写：① 暂定结论行；② 快照中的失败与未决项；然后等待写者发布终态（等待的是记录的变化，不是外部调用），等待结束之后复核；③ 写者的终态为“成功”时，写出每个记录文件的名字、字节数与 SHA-256，manifest 的 SHA-256，最后写**终结行**（含 manifest 的 SHA-256 与暂定结论）；写者的终态为“失败”时，写出它已发布的错误，不写终结行（终态为“到期未完成”时锁存已置，等待结束之后的复核即走到期出口）。每次写入返回之后，在同一次锁下发布这次的结果与资格，并复核是否开始下一次。任一写入出错即停止写入，发布终态“写入失败”。全部写完之后，在锁下发布终态“完成，有终结行”或“完成，没有终结行”，同样带资格。
  5. **父端的最后消费**（第四稿写定为唯一的顺序，B-143-2-R/P）：父端在外层登记表的变化与原来 `D` 的计时器上等待。每次被唤醒，都在锁下读时钟（读到已到 `D` 即置锁存；这只是记录到期，不是进入失败出口），然后**只按下面的顺序**判断：
     - (a) 诊断任务已经发布终态 → 按 §7.1 消费真实结果与已经确定的截止资格，得到最终结论：暂定 3 或 4 而必要结果全部成功、全部及时时保持 3 或 4，否则为 2；暂定 1 或 2 时不变。
     - (b) 否则，已到 `D` 或锁存已置 → 进入未完成的到期出口（暂定 3 或 4 时为 2；暂定 1 或 2 时不变），非零退出。
     - (c) 否则，继续等待原来的 `D`；这次唤醒没有出口。

     这一入口只读取已经发布的终态与资格，不取得任何新动作的权限。确定之后 `os.Exit`。父端最后消费的只是：暂定结论、写者与诊断任务的终态及其截止资格、到期锁存；不为收尾重新取得预算。
- **晚到的结果**：快照点之后才到达的结果（例如写者或诊断任务在 `D` 之后才返回，R 或被测实例中晚到的关闭）由持续的持有者保存在内存的记录中，不保证写入记录文件或进入日志，也不使结论变好。暂定结论为 3 或 4 时，快照点上全部非收尾的记录都已进入终态，此后只有写者与诊断任务还在工作（§7.1）。
- 范围只限本工具新增的记录链与诊断；测试函数经 `testing.T` 输出的内容由测试框架处理，不在范围内（与 §12.14 第 13 条的范围相同）。

### 6.5 保存与核对

- **保存**：记录目录以 workflow 的 artifact 上传（`if: always()`，保存 90 天）。上传的是进程结束之后目录中实际存在的字节：可能有部分写入的文件，也可能没有 manifest。
- **完整的条件**（审查时逐项核对，全部成立才算记录完整；它们成立也不使非零退出的作业变成 3 或 4，§7.1）：
  - 日志中有终结行；
  - artifact 中 manifest 的 SHA-256 等于终结行中的值；
  - manifest 列出的每个文件都在 artifact 中，字节数与 SHA-256 相同；目录中除这些文件与 manifest 之外没有其他文件；
  - 原始记录中的 `GITHUB_SHA` 与日志中的检出值满足 §6.3 的两条关系。
- **不完整时**：部分写入的文件、没有 manifest、manifest 与文件不符、日志中没有终结行，或日志被截断，都使记录不完整，结论不能是 3 或 4（§7.1）。artifact 的上传成功不使缺失或部分的记录变成完整，也不证明资源已经释放。只有日志而没有完整的记录时，日志的内容只作诊断。
- **内容的范围**（LE-6）：记录不含第三方源码的字节，只有名字、字节数、SHA-256、位置与对象名；工具的输出（`go env`、`go list`）原样保存，其中有 runner 上的路径。这些是开发阶段的取证记录，不是 Specmetry 产品的数据；不记录继承的环境变量。

## 7. 结论

### 7.1 每个作业的四种结论（唯一，按优先级）

工具在快照点按已发布的状态判定（§6.4）；“域”见 §5.4；截止复核、到期锁存与截止资格见 §6.4。

| 优先级 | 结论 | 条件 |
|---|---|---|
| 1 | **无效** | 任何对照的变体“不命中”（§5.5）；工具的记录中出现 LC-5 不覆盖集合 N 的结果（§5.3）；T2 的绑定不符（LC-10）；`m.Run` 的结果非零，或工具自身的缺陷使结果不能解释 |
| 2 | **未完成** | R 中：预算不足、超过截止；模块缓存的内容不符（J-4）或类型不符（J-2）；输出缺失；清理未知（例如 darwin 上到期）；其他 J-1 ~ J-3（包括工具链守卫的不符）；任何调用不满足 §12.14 第 11 条。任何对照的变体“未决”（§5.5）。O 中：外层的清理失败或未知；记录链或诊断已发布的失败（§6.4） |
| 3 | **与候选不一致** | 前两项都不成立；R 的采集完整，**R 中** A、B 的全部检查成立，但发现与静态候选不同，或 LQ-6 发现新的包 |
| 4 | **与候选一致** | 前三项都不成立，发现与候选逐项相同 |

- OOM、`go test` 的包期限或作业的外层期限终止进程时，工具来不及判定，日志中通常没有暂定结论行，按下面“读法”的第三种情形报告。
- **域的使用**：第 3、4 级的“A、B 的全部检查成立”只指 R。F 中被测的检查按 §5.5 的完整预期判定：负向对照中被测的失败是“命中”所要求的，不是第 3、4 级的障碍，也不要求被测实例“健康通过”；它们的记录都保留（保留的范围见本节末）。反过来，F 的命中也不能抵消 R 或 O 中的任何失败。
- **暂定结论与最终结论**（第三稿按 B-143-2-R 修订；第四稿按 B-143-2-R/P 写定最终消费的顺序）：
  - 父端在快照点（§6.4 第 2 步，复核没有到期时）按上表算出暂定结论。父端在快照点之前就走了到期出口时，没有暂定结论：它在那一次锁下由已发布的状态算出最终结论，有第 1 级的条件为 1，否则为 2。
  - 暂定结论为 1 或 2：最终结论等于暂定结论。之后的任何成功（及时或晚到）都不使它变好，收尾晚到或到期也不使它再细分。
  - 暂定结论为 3 或 4：这时快照点上 R、F、O 中全部非收尾的记录都已进入终态，而且没有使结论成为 1 或 2 的失败（F 中预期的被测失败不在其内）。最终结论等于暂定结论，**当且仅当**下面各项都已发布、都成功，而且截止资格都是“及时”：
    - 写者：全部记录项的写入、每个记录文件的关闭、manifest 的建立、写入与关闭，以及终态“成功”；
    - 诊断任务：每一次写入（暂定结论行、失败与未决项、各文件与 manifest 的哈希、终结行），以及终态“完成，有终结行”。

    锁存只置不清，资格在锁串行化下按逻辑判定点确定（§6.4），所以诊断任务的终态是及时的，就意味着它之前发布的写者终态也是及时的；两项仍分别列出。任一项失败、晚到，或父端最后消费时诊断任务仍没有终态而已经到期（第 5 步分支 (b)，到期出口），最终结论都为 2（未完成：记录或日志没有及时完成）。晚到的成功不恢复结论。
  - **父端最后消费的**只是：暂定结论；写者与诊断任务的终态及其截止资格；到期锁存。它按 §6.4 第 5 步的唯一顺序判断（第四稿，B-143-2-R/P）：(a) 诊断任务已有终态，先按本节消费；(b) 否则已到 `D` 或锁存已置，进入到期出口；(c) 否则继续等待原来的 `D`。这是最终消费，不是新动作的准入，不取得任何新动作的权限。它不重新判断时刻：必要结果全部及时成功、只是父端晚醒时，读到已到 `D` 而置锁存不撤销已经确定的及时资格，结论保持 3 或 4（§6.6 的情形 3）；读取时看到的成功若不是及时发布的，不被追认。
- **退出状态**（LE-10，仍是未采纳的提案）：最终结论为 3 或 4 时为 0，否则非零。作业的成功**不**表示“与候选一致”；结论以日志中的结论行为准。
- **读法**：
  - 退出状态 0：日志中必有暂定结论行（3 或 4）与终结行，而且它们都已及时发布；结论就是行中所写。
  - 退出状态非零，日志中有暂定结论行：行中写 1 或 2 → 就是它；行中写 3 或 4 → 未完成（收尾没有取得及时的完成资格）。日志中即使已经有终结行，也可能只是字节在 `D` 之前写完、完成状态在 `D` 之后才发布，或父端已经走了到期出口；终结行不使结论变成 3 或 4（§6.6 的情形 4）。
  - 退出状态非零，日志中没有暂定结论行（`m.Run` 返回或等待快照点结束时已经到期、诊断任务的第一次写入没有完成，或作业被外层的期限终止）：只能确定结论不是 3 或 4；报告写“无效或未完成，不能区分（收尾缺失）”，不作为证据，按 §7.2 停止。
- **审查时的核对**：审查另核对 §6.3 的两条关系与 §6.5 的完整条件。前者不成立 → 无效；后者不成立 → 未完成（例如退出状态 0 而日志被截断，按未完成报告，并登记这一不一致）。审查的核对只能使结论降低，不能使它提高。
- 三个作业各自给出结论；六个配置的取证完成，须三个作业都是“与候选一致”或“与候选不一致”。
- **记录的保留**（第三稿按 Review 144 精化）：任一结论都不删除记录。已经取得的结果由持续的持有者保存在内存的记录中，直到测试进程结束；只有在进程结束之前已经落盘的部分才在记录目录与 artifact 中（§6.4、§6.5）。快照点之后才到达的结果不保证写入文件，所以不承诺失败运行的 artifact 包含全部最终的错误；这既不删除任何真实结果，也不使结论变好。
- 不自动重跑、清理缓存、下载、换版本、缩小范围或增加预算（§9.5）。

### 7.2 停止

- 结论为 1 ~ 3 的作业，以及只能确定“无效或未完成，不能区分”的作业（§7.1 的读法），停下报告，交负责人决定。结论 3 是取证的正常可能结果，它的作业以退出状态 0 结束，同样停下报告：它是新的事实，按决策稿 §6.3 的阶段 3 停止报告，不自动批准新增的例外。
- 结论 4 也不自动进入下一阶段：结果须经独立审查，再由负责人决定是否作为状态 1 的发现使用。

### 7.3 结论的上限

即使三个作业都是“与候选一致”，也只能说：在固定的代码点、工具链与 CI 输入下，得到了这些发现，它们带有可以核对的内容身份（限于 §2.5.3 的声明）。它**不**说明：

- 运行时信任成立（T-2 未决定），或原始路径、发送信号的风险已被接受；
- 任何例外条目或清单已经批准或生效；G-4 之外的任何 G 项已经满足；
- G-6 已经完成，或第三批可以开工；
- 产物中链接了或没有链接这些代码，或这些能力在运行时可达或不可达；
- LP-8 已经完整核对（G4-Q4），规则实现的改变会被发现（G4-Q1），或标准库的字节经过认证（G4-Q3）；
- 交叉配置在相应的架构上原生执行过；
- 发现是最终的违规判定（它们是对象引用，§4.4），或 T-4 已经决定；
- 仓库自身的 C-9 规则都已验证、生产 lint 已经完成或 G-6 成立（主模块不做完整的类型检查与规则扫描，§4.3）；
- 负向对照的命中证明了实际调用的接线（例如 N-143-1 的同一个 `Context`），或 B′ 的部分已经验证（LC-5 只比较投影，§5.3）。

## 9. 执行场所与资源（提案，本轮不创建或修改 workflow）

### 9.1 runner 与 workflow

- **runner**：与常规 CI 相同的三个 GitHub 托管 runner：ubuntu-latest、macos-latest、windows-latest（§3.3）。不需要 arm64 的 Linux 或 Windows runner，也不需要 macOS Intel：分析不执行目标代码。
- **workflow**（建议名为 `c9-evidence.yml`，随实现一起审查）：
  - 触发：`push`，`branches` 只有一个运行分支（例如 `evidence/c9-run-1`）；不设 `paths` 过滤，所以建立这个分支的那一次推送就触发；没有 `pull_request`、`workflow_dispatch` 或 `schedule`。
  - `permissions: contents: read`；`concurrency` 以分支分组，`cancel-in-progress: false`。
  - 矩阵为三个 runner，`fail-fast: false`；作业的 `timeout-minutes` 作为外层的兜底（建议 20，与原型的 workflow 相同；只是兜底，不是预算）。
  - 步骤：检出（与 `ci.yml` 相同的固定版本）；setup-go 固定 `go-version: 1.27.3`、关闭缓存，`GOTOOLCHAIN=local`；核对 HEAD 与 `GITHUB_SHA` 相同、工作区干净，打印检出的提交、树与 `go version`（§6.3）；LE-4 的模块准备与工作区核对；在工具模块的目录运行测试（`-count=1 -v`），并显式地把 R 传给工具（§4.2）；上传记录目录（`if: always()`）。
- **一次运行一个分支**：之后若负责人授权再运行，使用新的分支名（例如 `evidence/c9-run-2`），在同一个审查过的 workflow 中加入，或另作修订并审查。

### 9.2 执行授权之前不会触发的保证

- 运行分支只在运行的授权之后建立，建立在经审查的固定代码点上。
- 实现 PR 所在的分支不在触发列表中；新的 workflow 没有 `pull_request` 触发，所以实现 PR 的推送不会运行工具。
- 常规 CI（`ci.yml`）只测试根模块：根模块的 `go test ./...`、`go vet ./...` 与 golangci-lint 不包含另一个模块（与 `prototype/wp25` 相同，§1.2 第 3 项）。所以实现 PR 的常规 CI 不会运行工具。
- 推送 master 不匹配运行分支；若实现之后合并，master 上也不会触发。
- 没有手动触发，所以不能在授权之外盲目运行。GitHub 界面中的“重新运行”只在负责人授权时使用。
- 残余的风险：任何有推送权限的人建立这个分支，都会触发运行。这由流程约束，不由技术保证；如有需要，可以另加分支保护规则（属于仓库设置，须负责人决定）。

### 9.3 预算

- 沿用实施计划 §12.14：每个作业中，工具测试进程的全部工作（对照与两个配置的采集、全部工具子进程与伪工具、记录链、诊断与收尾）共享一个 **120 秒**的总预算；`TestMain` 开始时取 `D`，`W = D − 10 s`，准入按 §12.14。测试二进制的编译、setup-go 与 LE-4 的模块准备不在其中。
- 不按配置、对照或步骤分别取预算，不滚动延长。

### 9.4 与既有 CI 的隔离

- 新的 workflow 在独立的 runner 上运行，与 `ci.yml` 的作业不共用机器，不争用 `internal/cli` 的测试资源。

### 9.5 失败的处置
