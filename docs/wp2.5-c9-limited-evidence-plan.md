本轮新做的三项只读核对（都不是运行证据）：

1. **dirhash 的实现来源**（供 G4-Q6）：
   - 固定 Go 中 `src/cmd/vendor/golang.org/x/mod/sumdb/dirhash/hash.go` 共 135 行，SHA-256 `24de6a735c1605e39b6381e6962787faa5c59adab896fb66dbc1ac8b6afcb297`。`cmd/vendor/modules.txt:31` 记录它来自 `golang.org/x/mod` `v0.36.1-0.20260813213634-8569e2639ca1`。
   - 本机模块缓存中 `golang.org/x/mod@v0.42.0/sumdb/dirhash/hash.go` 与它逐字节相同（SHA-256 相同）。
   - 对本机的这个模块目录按 Hash1 的定义只读重算（137 个文件），得到 `h1:ICeL3t2L30ljSPHHxDnR4fqVcBt/zR2zJAb9juavmQg=`，与 `go.sum` 第 42 行相同。这是本机缓存的事实，不是 CI 的事实。
   - `Hash1`（`hash.go:44` ~ `65`）以调用者给出的名字列表与打开函数计算，读完即调用 `r.Close()` 而不检查返回值（`:58`）。
2. **T2 在 Windows 上作为一个参数的传递**（供 LQ-7 与 §4.2）：
   - `os/exec` 在 Windows 上把参数拼成一条命令行（`os/exec/exec.go:408` ~ `414` 的说明）。没有设置 `SysProcAttr.CmdLine` 时，命令行由 `makeCmdLine` 生成（`syscall/exec_windows.go:346` ~ `351`、`:106` ~ `116`）。
   - `appendEscapeArg`（`:48` ~ `102`）：参数中有空格而没有 `"` 与 `\` 时，只在两端加上 `"`，内容原样。T2 有空格，没有 `"`、`\`、TAB 或换行，所以它成为 `"` 加上 T2 原样的字节再加 `"`。
   - 接收方是 Go 程序时，`os` 包在初始化时以 `commandLineToArgv` 拆分命令行（`os/exec_windows.go:94` ~ `101`、`:155` 起）；`readNextArg`（`:114` 起）在引号之内把除 `"` 与 `\` 之外的字节原样加入，遇到配对的 `"` 结束引号。所以 T2 原样成为一个参数。T2 只含 ASCII，UTF-16 的往返不改变它。
   - 前提：被执行的是经 E-10 核对的 `go.exe`（Go 程序），没有包装器，工具不设置 `SysProcAttr.CmdLine`。Unix 上参数以数组传给 `execve`，本轮没有逐行核对那条路径，留到实现的审查时补核。
   - 这只是固定源码的推演。实际的传递只能运行取得（方法记录 §8.2）；输出的校验也不认证 cmd/go 收到的就是原模板（方法记录 §3.3.1）。
3. **既有 workflow 的触发方式**（供 §9）：
   - `ci.yml` 只在推送 master 与 pull request 时运行，以根模块的 `./...` 运行 `go test`、`go vet` 与 golangci-lint。
   - `wp25-prototype.yml` 只在推送它列出的分支、而且改动落在 `prototype/wp25/**` 或它自己时运行，没有手动触发。
   - `prototype/wp25` 有自己的 `go.mod`，根模块的 `./...` 不包含它（`prototype/wp25/go.mod` 第 1 ~ 3 行的说明）。

### 2.5 特别说明

#### 2.5.1 G4-Q1：规则标识与实现摘要

- **两种方式的差别**：
  - (i) 只用规则标识（v1 的 H 行 `rules`），加上审查规则：改动判定的代码或规则的文本时，必须同时改标识。治理可以要求，机器不能发现“改了实现而没有改标识”。
  - (ii) 另外绑定规则实现文件的摘要。机器可以发现文件的改变，代价是任何改动（包括注释）都使清单失效、须重新批准。
- **时间的约束**：决策稿 §6.3 的阶段 3（完整清单的批准）早于阶段 4（G-6 的实现）。批准清单时，判定规则只以文档的形式存在（§12.9、决策稿 §3.2），还没有可以取摘要的实现文件。
- **推荐**：
  - 阶段 3 采用 (i)：`rules` 的值指向经审查的规则文本的版本，治理要求写进清单批准的那一节。
  - 实现摘要作为规范表示 **v2** 的变更提案，在生产实施（N4）时决定。提案只写必要的部分：H 行增加一个键 `rules-impl`，值为规则实现文件清单（按路径排序的相对路径与各自的 SHA-256，不含测试文件）的 SHA-256；文件集合与表示须另行写定；v2 的清单须重新生成与批准。本轮不改 v1。
- **声明的上限**：在 (ii) 生效之前，不能宣称规则实现的改变会被机器发现（方法记录 §4.2、§8.5）。

#### 2.5.4 G4-Q6：Hash1 的实现来源

- **推荐**：工具导入 `golang.org/x/mod/sumdb/dirhash` v0.42.0，只使用 `Hash1`。
  - 依据（§1.2 第 1 项）：它的 `hash.go` 与固定 Go 1.27.3 中 cmd/go 自己使用的副本逐字节相同；本机缓存中这一模块目录的 h1 与 go.sum 相同。实现时仍须在 CI 中由 I-4 核对 x/mod 的模块内容（x/mod 在生产闭包中：`internal/store/sqlite` 导入 `golang.org/x/mod/semver`）。
  - 用法：受控读取先对每个文件打开一次、读到 EOF、关闭，保存字节、SHA-256 与真实的 `Close` 结果；然后以带前缀的名字列表调用 `Hash1`，打开函数只交出内存中的字节。`Hash1` 不检查 `Close` 的返回值，这时也不会掩盖任何真实的结果。
  - 不使用 `HashDir` 与 `DirFiles`：它们以 `filepath.Walk` 与 `os.Open` 读取，会跟随符号链接（方法记录 §2.2 第 6 条），不符合 I-4 的类型规则。
- **不采用时**：工具自己实现 Hash1（约二十行），须与上面的固定源码逐字对照，并以已知的 h1 作正对照（LC-1）。
- 真实的 `Close` 结果无论选哪一种都必须由工具自己保存并消费（方法记录 §2.5）。

- **错误的传播**：按方法记录 §6.1 ~ §6.3：调用或解码的失败使依赖它的检查未评估；语义的失败照常记录，其余可得的检查照常评估。由对照 LC-5 检验。

## 5. 对照 LC-1 ~ LC-10

### 5.1 原则

- **命中**：每项对照都须证明两件事：进入了目标检查（工具为每项检查写一条“进入”记录，带检查的编号与输入的 SHA-256），而且结果等于固定的预期。只有最终失败而没有进入记录的，不算命中。
- **证据的类别**，分开记录：
  - 真实：真实的输入与真实的调用（仓库本身、CI 的模块缓存）；
  - 夹具：真实的工具代码作用于临时目录中的夹具（夹具模块上的真实调用须 LE-5 允许）；
  - 接缝：假的调用者或注入的结果。
- **次数**：每个作业各执行一次。只在某个平台有意义的对照（例如 pidfd 只在 Linux），在实现中写明适用的平台与理由，并经实现的审查；不适用的平台记为“不适用”。实现中没有写明而在运行中跳过的，算作没有命中。
- **失败出口**：任何对照没有命中，或结果与预期不同 → 这个作业的结论为“无效”（§7.1）。采集的结果照样保留，但不作为证据。
- 本文中写下的预期只是文档，不计作运行。

## 6. 记录、身份与保存

### 6.1 原始记录

- 每次调用：参数数组的原样字节（含 T2）；工具设定的环境变量的名字与值（G4-P1 一行）；工作目录；标准输出与标准错误的字节及 SHA-256；退出状态；开始与结束的时刻；控制协议的登记记录（§12.14 第 3 条）。
- `R/go.sum`、`R/go.mod` 的字节数与 SHA-256。
- 每个模块的 M（相对名字 → 字节数与 SHA-256）、每个文件真实的 `Close` 结果，以及计算出的 h1。
- 工具链：分析者的 `runtime.Version()`、`<GOROOT>/VERSION` 的第一行、go 可执行文件的绝对路径与 SHA-256（E-10）。

### 6.2 派生记录

- 解码结果；A、B 各项检查的结果（成立、失败、未评估）与它的进入记录；受控读取的消费记录（名字、组 C 或 P、用途、SHA-256）。
- 每个配置的闭包、条件差异检查各步的结果、交给 `MatchFile` 的 `build.Context`。
- 发现（模块、版本、h1、包、文件、文件的 SHA-256、约束行、调用方、对象、次数、每处的行与列）、LQ-5 的诊断、与静态候选的对照结果。
- LP-3 ~ LP-7 的当前值。
- 每条派生记录写明它的父记录（名称与 SHA-256）与产生它的步骤；只追加，不改写（方法记录 §3.6）。

### 6.3 身份与保存

- **固定代码点**：实现审查所针对的完整提交 SHA。运行时，workflow 在日志中打印检出的提交与树，工具把 `GITHUB_SHA` 写入原始记录；三者必须相同，否则“无效”。
- **工具链**：workflow 固定 `go-version: 1.27.3`、`GOTOOLCHAIN=local`；工具按 E-10 核对，不符即 J-1。
- **模块**：LE-4 的下载步骤之后，日志写下 `go.mod` 与 `go.sum` 的 Git blob 与工作区是否干净；工具记录读到的字节的 SHA-256。两者须对应。
- **格式**：记录为 UTF-8、LF 的文本文件，每个文件有版本号；确切的格式在实现的审查中固定。记录在 `D` 之前逐条写出并落盘，使中途终止时已写出的部分保留。
- **清单**：所有记录文件的名字、字节数与 SHA-256 写成一份清单；工具在日志中打印清单的 SHA-256 与每个文件的哈希。
- **保存**：记录目录以 workflow 的 artifact 上传（`if: always()`，保存 90 天）。审查时以日志中的哈希核对 artifact。
- **内容的范围**（LE-6）：记录不含第三方源码的字节，只有名字、字节数、SHA-256、位置与对象名；工具的输出（`go env`、`go list`）原样保存，其中有 runner 上的路径。这些是开发阶段的取证记录，不是 Specmetry 产品的数据；不记录继承的环境变量。

## 7. 结论

### 7.1 每个作业的四种结论（唯一，按优先级）

| 优先级 | 结论 | 条件 |
|---|---|---|
| 1 | **无效** | 任何对照没有命中或结果不符（§5）；T2 的绑定不符；固定代码点或身份不符；工具自身的缺陷使结果不能解释 |
| 2 | **未完成** | 预算不足、超过截止、超时、OOM；模块缓存的内容不符（J-4）或类型不符（J-2）；输出缺失；清理未知（例如 darwin 上到期）；其他 J-1 ~ J-3 |
| 3 | **与候选不一致** | 前两项都不成立，采集完整，A、B 的全部检查成立，但发现与静态候选不同，或 LQ-6 发现新的包 |
| 4 | **与候选一致** | 前三项都不成立，发现与候选逐项相同 |

- 三个作业各自给出结论；六个配置的取证完成，须三个作业都是“与候选一致”或“与候选不一致”。
- 任一结论都保留全部记录。不自动重跑、清理缓存、下载、换版本、缩小范围或增加预算（§9.5）。

### 7.2 停止

- 结论为 1 ~ 3 的作业，停下报告，交负责人决定。结论 3 是取证的正常可能结果：它是新的事实，按决策稿 §6.3 的阶段 3 停止报告，不自动批准新增的例外。
- 结论 4 也不自动进入下一阶段：结果须经独立审查，再由负责人决定是否作为状态 1 的发现使用。

### 7.3 结论的上限

即使三个作业都是“与候选一致”，也只能说：在固定的代码点、工具链与 CI 输入下，得到了这些发现，它们带有可以核对的内容身份（限于 §2.5.3 的声明）。它**不**说明：

- 运行时信任成立（T-2 未决定），或原始路径、发送信号的风险已被接受；
- 任何例外条目或清单已经批准或生效；G-4 之外的任何 G 项已经满足；
- G-6 已经完成，或第三批可以开工；
- 产物中链接了或没有链接这些代码，或这些能力在运行时可达或不可达；
- LP-8 已经完整核对（G4-Q4），规则实现的改变会被发现（G4-Q1），或标准库的字节经过认证（G4-Q3）；
- 交叉配置在相应的架构上原生执行过。

## 9. 执行场所与资源（提案，本轮不创建或修改 workflow）

### 9.1 runner 与 workflow

- **runner**：与常规 CI 相同的三个 GitHub 托管 runner：ubuntu-latest、macos-latest、windows-latest（§3.3）。不需要 arm64 的 Linux 或 Windows runner，也不需要 macOS Intel：分析不执行目标代码。
- **workflow**（建议名为 `c9-evidence.yml`，随实现一起审查）：
  - 触发：`push`，`branches` 只有一个运行分支（例如 `evidence/c9-run-1`）；不设 `paths` 过滤，所以建立这个分支的那一次推送就触发；没有 `pull_request`、`workflow_dispatch` 或 `schedule`。
  - `permissions: contents: read`；`concurrency` 以分支分组，`cancel-in-progress: false`。
  - 矩阵为三个 runner，`fail-fast: false`；作业的 `timeout-minutes` 作为外层的兜底（建议 20，与原型的 workflow 相同；只是兜底，不是预算）。
  - 步骤：检出（与 `ci.yml` 相同的固定版本）；setup-go 固定 `go-version: 1.27.3`、关闭缓存，`GOTOOLCHAIN=local`；打印检出的提交、树与 `go version`；LE-4 的模块准备与工作区核对；在工具模块的目录运行测试（`-count=1 -v`）；上传记录目录（`if: always()`）。
- **一次运行一个分支**：之后若负责人授权再运行，使用新的分支名（例如 `evidence/c9-run-2`），在同一个审查过的 workflow 中加入，或另作修订并审查。

### 9.2 执行授权之前不会触发的保证

- 运行分支只在运行的授权之后建立，建立在经审查的固定代码点上。
- 实现 PR 所在的分支不在触发列表中；新的 workflow 没有 `pull_request` 触发，所以实现 PR 的推送不会运行工具。
- 常规 CI（`ci.yml`）只测试根模块：根模块的 `go test ./...`、`go vet ./...` 与 golangci-lint 不包含另一个模块（与 `prototype/wp25` 相同，§1.2 第 3 项）。所以实现 PR 的常规 CI 不会运行工具。
- 推送 master 不匹配运行分支；若实现之后合并，master 上也不会触发。
- 没有手动触发，所以不能在授权之外盲目运行。GitHub 界面中的“重新运行”只在负责人授权时使用。
- 残余的风险：任何有推送权限的人建立这个分支，都会触发运行。这由流程约束，不由技术保证；如有需要，可以另加分支保护规则（属于仓库设置，须负责人决定）。

### 9.3 预算

- 沿用实施计划 §12.14：每个作业中，工具测试进程的全部工作（对照与两个配置的采集、全部工具子进程与收尾）共享一个 **120 秒**的总预算；`TestMain` 开始时取 `D`，`W = D − 10 s`，准入按 §12.14。测试二进制的编译、setup-go 与 LE-4 的模块准备不在其中。
- 不按配置、对照或步骤分别取预算，不滚动延长。
- 读取量的参考（方法记录 §8.3 的本机统计，不是测量）：libc 约 86.7 MB / 4199 个文件，SQLite 约 150.4 MB / 1899 个文件，x/sys 约 9.7 MB / 555 个文件；libc 在预筛中命中，须完整检查。能否在 120 秒内完成没有依据。
- 超出预算即“未完成”，停下报告。拆分作业、单独的预算或更长的期限都是资源的变更，须负责人另行决定，不自动采用。

### 9.4 与既有 CI 的隔离

- 新的 workflow 在独立的 runner 上运行，与 `ci.yml` 的作业不共用机器，不争用 `internal/cli` 的测试资源。
- 不改 `ci.yml`，不改 Windows 上 `internal/cli` 的单独期限；不顺带处理 M-16。

### 9.5 失败的处置

超时、OOM、缓存内容不符、输出缺失、清理未知或对照没有命中时：

- 保留日志、artifact 与已写出的记录；
- 按 §7.1 给出结论，停下报告；
- 不自动重跑，不清理缓存，不下载，不换版本，不缩小范围，不增加预算；
- 是否修复、重跑或改变资源，由负责人决定。
