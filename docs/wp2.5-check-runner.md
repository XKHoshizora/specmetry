## 1. 范围

**在范围内**：

- 命令：`specmetry check run [AC...] [--all] [--isolation off|required] [--json]`（prd §6）。
- 选择：显式给出的 AC，或 `--all`（全部 `active`、自动化、有检查的 AC）。
- 执行前的检查：参数、隔离模式、选择、静态规则、解释器、PD-26、私有临时区、worktree 路径的密钥扫描。
- 观测级执行：开始与结束时的代码上下文、`inputs` 的输入记录（TD-23，已冻结）、在 `W/<workdir>` 中执行、环境、进程树、超时、取消、收尾、输出转发。
- 结果分类、合格判定、`check_runs` 的写入（迁移 0009）、`seq`、worktree 的首次登记。
- 输出：`check-run.v1`（带 `--json`）或文本；错误为 `error.v1`；退出码 0 / 10 等。
- `--isolation required`：按冻结的规则一律退出码 6，不执行、不记录（不实现隔离执行器）。

## 3. 命令与选择

- 语法：`specmetry check run [AC...] [--all] [--isolation off|required] [--json]`。
  - 不接受临时命令或命令片段（FR-EV-03，MVP-EV-06）：执行的只能是基准中已确认的检查配置。
  - `--isolation` 省略时为 `off`。`auto` 不是 MVP 的取值（prd §6 的语法只有 `off|required`），按命令行错误处理（退出码 2，§17.1 D16）。
  - 同时给出 AC 与 `--all`，或两者都没有 → 退出码 2。
- Agent 与人的 CLI 都可以执行（prd §3 的权限表：“触发检查”对两者都是 ✓，Dashboard 为 ✗；prd §6 的命令表为“任意”）。它不是人类专属操作，不调用 `RequireHuman`；通道识别的结果只作为 `triggered_channel` 记录。
- **显式的 AC**：每个编号必须是当前 `active`、`verification = automated` 且有检查的 AC。不存在、已退役、只在待审提案中、手动 AC、没有检查 → 退出码 2，`details` 逐项指出参数的位置；整批都不执行（MVP-EV-06）。重复的编号：退出码 2，指向后出现的位置（§17.1 D15）。
- **`--all`**：全部 `active`、自动化、有检查的 AC，**与交付范围无关**（准备报告 §5.11；FR-INV-04、MVP-INV-03）。没有符合条件的 AC 时，不执行任何检查，退出码 0，`runs` 为空数组（`worktree_id` 见 §17.1 E3 与 §17.3 D18）。
- **顺序**：按 AC 编号的数值顺序（需求号，再按 AC 序号）串行执行；显式给出时同样按编号排序，不按参数顺序（§17.1 E1）。
- **配置的固定时刻**：见 §17.3 D13。

## 4. 处理顺序

拒绝为退出码 2，未初始化为 4，环境为 6，内部错误为 1。**“不执行、不记录”与“执行之后不合格”严格区分**（§7.5 的总表）。“不执行、不写记录、不分配 `seq`”只针对本次的业务事实，不扩大为“数据目录逐字节不变”：正常打开数据库与私有临时区按各自的既有契约（与 WP2.4 §5 相同）。

### 4.1 执行任何检查之前（失败时不执行、不写记录、不分配 `seq`）

1. **解析命令行**（architecture §9.1 的统一处理）。
2. **`--isolation required`**：立即退出码 6（`environment`，`details` 中有 `isolation_unavailable`），**不打开数据库，不运行 git，不启动任何进程**（data-model §7.4，MVP-EV-13，CX-28(a)）。
3. **确定项目与 `W`，打开数据库**（architecture §6.1.2）：`W` 是 `gitx.Locate` 给出的 worktree 根，非 git 项目为项目根；没有数据库或项目未登记 → 退出码 4；版本、墓碑与只读拒绝按既有顺序先行。第 7 步的 worktree 排除用到 `W` 与本项目已登记的全部 worktree。
4. **worktree 路径的密钥扫描**：`W` 尚未登记时，要登记的路径与 git 目录先做密钥扫描（与 `claim` 相同）；命中 → 退出码 2，不启动任何检查（Review 071 N3）。
5. **读取选择**（一个读事务）：所选 AC 的 `r`、`ar`、`h` 与检查配置（§17.3 D13）；不符合 §3 的条件 → 退出码 2。
6. **静态规则**：`shell = cmd` 的命令含 CR 或 LF（§17.3 D3）、`sh` / `bash` 的命令含 CR（§17.3 D4）→ 退出码 2，在获批之前不实施。
7. **解释器**（§5.3）：对所选 AC 用到的每一种 `shell` 查找解释器。任何一个不可用 → 退出码 6，`details` 给出 `shell_unavailable` 与受影响的 AC 编号，不回显路径（§17.3 D1）。
8. **git 项目**：
   - PD-26：git 不具备安全读取对象的能力 → 退出码 6，在运行任何读取对象的命令之前拒绝（与 `claim`、`propose` 相同的入口）；
   - 准备私有临时区（`gitx.NewScratch`，WP2.3 §14.3）；
   - 解析交付目标的快照 `S`（一次，只用于 §11.2 的批次汇总）：没有 `active` 目标或 ref 无法解析 → `S` 为 NULL，不是错误；读取失败（对象损坏、PD-26）→ 退出码 6。
9. **输出句柄**（§9.1）：取得用于检查转发的底层输出对象；决定每个流走继承路径还是管道路径。目的端不属于 §9.1 支持的类型 → `internal` / 退出码 1，不启动任何检查（候选，D20）。
10. **worktree 的登记**：`W` 尚未登记时，在第一次写入的事务中登记（§10.3）。

### 4.2 每一次执行（按 §3 的顺序串行）

对第 k 个 AC：

1. **开始上下文**（§7.1）：`head_start`、`tree_state_start`。读取失败（环境错误）→ 退出码 6，**第 k 个不执行、不记录**，之前已写入的执行保留，之后的不再执行（§11.4）。
2. **输入记录**（§7.3）：声明了 `inputs` 时，在 `head_start` 上逐个读取：
   - 读取路径所需的对象失败（L1）→ 同第 1 步：退出码 6，第 k 个不执行、不记录；
   - 任一路径不存在（L2，含 `head_start` 为 NULL）→ 结果为 `error` / `input_missing`，**不启动进程**，转第 4 步（仍读取结束上下文并记录）。
3. **启动、等待与收尾**：按 §8.5 的收尾协议执行，直到协议给出“树已确认结束”或某个失败出口。启动、主进程退出、超时、取消、终止、确认、排空的顺序与时限都在那里定义。
4. **结束上下文**（§7.1）：**只在 §8.5 确认进程树已经结束之后**读取 `head_end`、`tree_state_end`。没有确认时，不读取，按 §8.5 的失败出口处理（§17.3 D19）。读取失败见 §17.3 D6。
   - **例外：不启动进程的情形**（Review 073 B3-R3-S）。`input_missing`（第 2 步）与 `spawn_error`（第 3 步中操作系统拒绝创建进程）没有本次的消费者，所以不经过 §8.5 的 S2 ~ S6 的进程与输出步骤，直接读取结束上下文。“没有本次的消费者”就是读取的依据。
   - `spawn_error` 时，Specmetry 关闭自己持有的写端，复制读到 EOF（O1，空）。
5. **分类**（§6.2）：`result`、`failure_kind`、`exit_code`、`duration_ms`。
6. **写事务**（`BEGIN IMMEDIATE`，§10）：必要时首次登记 worktree（另取一个 `seq`）；分配一个 `seq`，写入这一条 `check_runs`；用写入的行构造输出中的这一项，并在**提交之前**按 `check-run.v1` 中执行项的定义校验（§11.3）；提交。失败时按 §8.6 的 B 表叠加：提交之前的失败为“确认未提交”，提交阶段的错误为“结果不确定”；都不重新执行；用户代码是否运行过等之前的状态保持不变（§11.4）。
7. 下一个 AC。

### 4.3 全部执行之后

1. 用写入的行构造 `check-run.v1`，校验，编码。
2. 输出（§11）。任一执行不是 `pass` → 退出码 10；否则 0（MVP-EV-02、MVP-INV-03）。
3. 提交之后的输出失败见 §11.4。

**不自动重试**：重试会再次执行检查命令。收到退出码 6 时，调用方先读取状态（WP2.7），再由人或 Agent 决定是否重新执行。**没有执行记录不能证明检查从未执行**（它可能已执行而写入失败）；提交返回不确定时，读不到记录也不能证明没有提交（Review 071 N3）。不暗示任何“安全的自动重试”。

## 5. 解释器（TD-06 / M2-Q1，待决）

### 5.1 已有的约束（不变）

- `shell` 的取值与可省略（`common.v1`）；`check_config_hash` 包含 `shell`（省略时为 null），`shell` 是强制 `material` 的字段（data-model §4.4、§7.2）。所以同一个配置哈希必须对应同一种解释器的选择规则，不能因机器而变。
- 检查继承用户的环境，注入 `SPECMETRY_CHECK=1`（architecture §6.4）。
- TD-06 的建议默认与准备报告 §5.1 的推荐都**没有获批**（§2）。

### 5.2 默认解释器（§17.3 D1）

**推荐**：省略 `shell` 时，**所有平台都用 `sh`**，**不回退到 `cmd`**。解释器不可用时整批不执行（§4.1 第 7 步）。

- 统一的是**解释器的种类与语言约定**（POSIX shell），不是同一个二进制或相同的执行环境：Linux 的 `/bin/sh` 常是 dash（实验环境即是）；Git for Windows 的 `sh.exe` 是 bash 的 POSIX 模式；macOS 的 `/bin/sh` 是什么、行为如何，本轮**没有验证**。
- 理由：同一个已确认的配置（同一个 `check_config_hash`）不应在有、没有 Git Bash 的 Windows 机器上执行语法不同的程序；实验表明 `cmd` 对多行命令只执行第一行且不报错（§5.6），静默回退会把一个多行 `sh` 检查变成“只执行第一行、然后通过”。
- 代价：没有 Git for Windows `sh` 的 Windows 机器上，省略 `shell` 的检查返回退出码 6、不产生检查失败的事实；需要安装 Git for Windows 的完整安装，或在审核中把配置改为 `pwsh` / `cmd`。

### 5.3 解释器的查找（§17.3 D1、D2；技术门槛 T5）

共同规则（准备报告 §5.1 第 3 条与审查 040 N1，按实验与 Review 071 N1 细化）：

- 只使用**绝对路径**。Specmetry 自己的查找器**显式忽略** PATH 中的相对路径项与空项；Go 1.27 的 `exec.LookPath` 对当前目录候选返回 `ErrDot` 的防护不等于这一规则，不能代替它，必须单独实施并测试（Review 071 N1）。
- 候选路径先**规范化**（解析符号链接与联接；Windows 上统一短文件名与大小写，取最终路径），再判断实际位置：位于本项目**任何已登记 worktree** 之内，或当前 worktree 之内的，一律不用。理由：PATH 可能含有某个 worktree 中 `bin` 目录的绝对路径。
- 查找在 §4.1 第 7 步对所有用到的 `shell` 一次完成，之后启动时使用同一个路径；启动时它已不存在 → `spawn_error`（§6.1 第 ② 层）。
- 不使用 `ComSpec`、`SystemRoot` 等环境变量决定解释器的位置；系统目录由 `GetSystemDirectory` 取得（实验：`C:\WINDOWS\system32`）。

| `shell` | Linux / macOS | Windows |
|---|---|---|
| 省略、`sh` | `/bin/sh`。这是**本产品的支持策略**（Linux / macOS 上固定使用 `/bin/sh`，不经 PATH），**不是** POSIX 的规定：POSIX 明确说明应用不能假定 `sh` 位于 `/bin/sh`（Review 071 N1）。不提供 `/bin/sh` 的系统不在支持范围内（退出码 6） | Git for Windows 的 `sh`：由 `internal/gitx` 所用的 git 推出安装根（§5.4） |
| `bash` | PATH 上第一个合格的绝对路径 | Git for Windows 的 `bash`（同上） |
| `cmd` | 不可用（退出码 6） | `<系统目录>\cmd.exe` |
| `pwsh` | PATH 上第一个合格的绝对路径 | PATH 上第一个合格的绝对路径（实验：`C:\Program Files\PowerShell\7\pwsh.exe`） |
| `powershell` | 不可用（退出码 6） | `<系统目录>\WindowsPowerShell\v1.0\powershell.exe` |

- Windows 上的 `sh`、`bash` **只取 Git for Windows**，不回退到 PATH 上的其他 `sh`（例如 WSL 的 `WindowsApps\bash.exe` 启动器、Cygwin、独立的 MSYS2、busybox）：它们各有不同的命令行解析规则（§5.5），本轮只验证了 Git for Windows 的 MSYS 运行时。这比准备报告“其次是 PATH 上的绝对路径项”更窄（§17.3 D2）。
- `git --exec-path` 在 `gitx` 的受控环境中运行，不继承 `GIT_EXEC_PATH` 等变量（审查 040 N1）。实验中它给出 `C:/Program Files/Git/ucrt64/libexec/git-core`：安装根是 `git-core` 往上第三级的目录（`git-core` → `libexec` → `ucrt64` → 安装根；`mingw64`、`clang64` 等与 `ucrt64` 在同一层）。推不出、或推出的根中没有 `usr\bin\sh.exe` → `sh` 不可用。其他安装布局与版本是技术门槛 T5 的一部分。

### 5.4 Windows 的 `sh` 入口与 PATH（§17.3 D2）

**实验**（§16 X6）：PATH 只含系统目录时：

| 入口 | 检查中能找到的工具 | 检查看到的 PATH | 其他变化 |
|---|---|---|---|
| `<Git>\usr\bin\sh.exe` | `test`（内建）；`sleep`、`grep`、`sed`、`git` 都找不到 | 与调用者相同 | — |
| `<Git>\bin\sh.exe`（包装程序） | 全部找到 | 前面加上 `/ucrt64/bin`、`/usr/bin`、`~/bin` | 另设 `HOME`、`EXEPATH`、`PLINK_PROTOCOL=ssh`、`TERM=xterm-256color` |

在普通的 PowerShell 会话中，Git for Windows 的默认安装只把 `Git\cmd` 放进 PATH（准备报告 §5.1 的实测：PATH 上没有 `sh`）。所以直接使用 `usr\bin\sh.exe` 时，`go test ./... | grep -q ok` 这类检查会因 `grep` 不存在而失败，并且这种失败与真正的检查失败无法区分（§6）。

| 方案 | 做法 | 代价 |
|---|---|---|
| **W2（推荐）** | 使用 `<Git>\usr\bin\sh.exe` / `bash.exe`，Specmetry 只在检查的 PATH **前面**加上 `<Git>\usr\bin`，其他变量不动。它**不等价于**完整的 Git Bash 会话：不加 `/ucrt64/bin`、`~/bin`，不设 `HOME`、`TERM` 等 | 偏离“只继承用户环境、只注入 `SPECMETRY_CHECK=1`”（architecture §6.4），需要批准并写明；工具的解析顺序改变：`<Git>\usr\bin` 中的 `find`、`sort` 等在 `sh` 中优先于 Windows 自带的同名程序 |
| W1 | 使用包装程序 `<Git>\bin\sh.exe` / `bash.exe` | 与用户打开 Git Bash 时的环境最接近；但 PATH 之外还改了 `HOME`、`TERM` 等，改动由 Git for Windows 决定、随版本变化；多一层进程（实验：退出码、参数与进程树都正常） |
| W3 | 使用 `usr\bin\sh.exe`，不改环境 | 检查能用哪些工具取决于调用者的 PATH，同一配置在不同会话中结果不同 |

无论哪种方案，实验只覆盖 Git for Windows 2.56（UCRT64）的一个安装；安装布局、路径规范化与版本适配是工程测试（T5），其他版本与安装方式（精简安装、便携版、Scoop 等）未验证。

### 5.5 命令行与参数（实施细节，按实验修订；技术门槛 T5）

- **Linux / macOS**：直接以 argv 传给 `execve`：`[解释器, -c, 命令]`，或 PowerShell 的 `[pwsh, -NoLogo, -NoProfile, -NonInteractive, -Command, 命令]`。实验（WSL，dash 与 bash）：23/23 个测试字符串原样到达。macOS 未验证。
- **Windows**：一律自行构造完整的命令行（`SysProcAttr.CmdLine`），不使用 Go 的默认转义。**每种解释器的规则不同**：

| 解释器 | 命令行 | 实验（23 个测试字符串，§16 X5） |
|---|---|---|
| Git for Windows `sh`、`bash` | `"<解释器>" -c "<命令>"`，命令按 **MSYS 规则**加引号：每个 `\` 写成 `\\`，每个 `"` 写成 `\"` | 23/23 原样到达；按 MSVCRT 规则（只在引号前加倍反斜杠）时 21/23，`two\\`、`\\server\share\` 中的 `\\` 变成 `\`；Go 的默认转义同样 21/23。Review 071 用选定的字符串独立复验了这一机制 |
| `pwsh`、`powershell` | `"<解释器>" -NoLogo -NoProfile -NonInteractive -Command "<命令>"`，按 **MSVCRT 规则**总是加引号 | 23/23（逐字节，经 UTF-8 十六进制比较） |
| `cmd` | `"<系统目录>\cmd.exe" /d /s /c "<命令>"`，命令**原样**放在引号之间 | `cmd` 自己解析引号与 `&`、`\|`、`^`、`%` 等元字符，这是所选 shell 的语义；Specmetry 不转义 |

- 测试字符串含：空格、单双引号、`\`（单个、末尾、成对、UNC 前缀）、`\"`、`*`、`{a,b}`、`[ab]`、`~`、`$HOME`、`%PATH%`、`!`、`^`、`&|<>`、制表符与中文。23 个字符串是作者的选择，**不是穷尽的证明**（Review 071 N4）。
- `/d` 关闭 `cmd` 的 AutoRun，`-NoProfile` 不加载 PowerShell 的配置文件：它们不属于经人确认的检查配置。
- **启动文件**（Review 071 N1）：Specmetry 不承诺“不读取任何启动文件”。`sh -c`、`bash -c` 是非交互启动：非交互的 bash 会读取 `BASH_ENV` 指向的文件；以 `sh` 的名字启动的 bash 与 dash 对 `ENV` 的处理与交互模式不同（各解释器自己的规则）。Specmetry 不清除这些变量：它们属于“继承用户环境”的边界，如实说明，由各解释器的适配器测试分别覆盖。
- 不使用 `-EncodedCommand`（准备报告：输出被重定向时会混入 CLIXML）。
- 每种解释器各有自己的适配器与测试，不以一种解释器的实验推论其他解释器（审查 040 N1）。

### 5.6 `cmd` 与多行命令（§17.3 D3）

- **实验**（§16 X4；Review 071 独立复验）：`cmd /d /s /c "echo one<CRLF>echo two"` 与 `<LF>` 两种写法都只输出 `one`，退出码 0，没有任何提示。`sh` 与 `powershell` 正常执行多行。
- **推荐**：`shell = cmd` 时命令不得含 CR 或 LF，拒绝而不静默截断。
  - 覆盖所有写入路径：`propose`、`review`（含 `accepted_with_edits`）与人工编辑（扩展 V-P04 与共用的校验，退出码 2）；
  - 已保存的此类检查：`check run` 在执行前拒绝（退出码 2，§4.1 第 6 步），不写记录；M1 中已保存的配置不能直接执行，须按现有的人工 `material` 更新路径修订。
  - 批准之前，不改变已保存配置的含义。
- 代价：多行的 Windows 批处理需要写成单行（`&` 连接）或改用 `pwsh`。

### 5.7 `sh` / `bash` 命令中的 CR（§17.3 D4）

- **实验**（§16 X4）：命令 `echo one\necho two\r\necho three`：Linux 的 dash 输出 `two\r`（CR 是 `echo` 参数的一部分）；Git for Windows 的 `sh` 输出 `two`（CR 被忽略）。这只是作者在两个平台上的观察，不能外推到全部 bash 版本。
- 影响：在 Windows 编辑器中写成 CRLF 的命令，同一个配置哈希在 Linux 上可能失败（例如 `test -f a.txt\r` 查找名为 `a.txt\r` 的文件）。
- **推荐**：`sh`、`bash` 的命令不得含 CR（LF 可以），**包括引号之内的 CR**；拒绝而不静默规范化（规范化会改变保存的值与哈希）。与 D3 同样处理（V-P04 的扩展，覆盖同样的写入路径；已保存的在执行前拒绝）。备选：不限制，在文档中说明 CR 的平台差异。

## 6. 结果分类与 EV-04（§17.3 D5）

### 6.1 层次

**分类只依据 Specmetry 实际观察到的结果**：进程能否创建、解释器（主进程）的最终状态、Specmetry 自己的计时与取消，以及开始与结束时的上下文。不用任何普通退出码反向证明“命令不存在”，不依赖 stderr 文本，也不解析命令串（审查 040 B1、Review 071 B4）。

| 层次 | 例子 | Specmetry 得到的证据（实验） | 推荐的处理 |
|---|---|---|---|
| ① 解释器不可用 | 找不到解释器；平台上不存在的取值（Unix 的 `cmd`、`powershell`）；Windows 上没有 Git for Windows 的 `sh` | §4.1 第 7 步查找失败，进程没有创建 | 整批不执行、不记录，退出码 6，`shell_unavailable` |
| ② 进程无法创建 | 工作目录不存在或不是目录；查找之后解释器被删除；不是可执行文件；没有执行权限 | 创建进程时操作系统返回的错误，进程不存在。实验：Windows 为 errno 267（目录）、2（不存在）、216（不是程序）；Linux 为 ENOENT、ENOTDIR、ENOEXEC、EACCES | `error` / `spawn_error`，`exit_code` 为 NULL；只输出受控的类别，不捕获操作系统的错误文本、命令或路径（§17.1 E6） |
| ③ 解释器已运行，最终以非零状态结束 | 测试失败；`exit 1`；命令串最后一条命令不存在 | 解释器的最终退出码。实验：单独一条不存在的命令，dash、bash 为 127（= `exit 127`），`cmd` 为 1（= `exit /b 1`），`pwsh`、`powershell` 为 1（= `exit 1`） | `fail` / `nonzero_exit`，记录**解释器的最终退出码**；不区分原因 |
| ④ 解释器已运行，最终以 0 结束 | 测试通过；命令串中某条命令不存在或失败，但被后面的命令覆盖 | 退出码 0。实验（§16 X10；Review 071 复验）：`missing; :`、`missing \|\| true`、`false \| true`（sh），`missing & exit /b 0`（cmd），`missing; exit 0`（powershell）都以 0 结束 | 上下文、超时、取消等优先规则都不命中时为 `pass`（§6.2）：Specmetry 不发现命令串内部的失败 |
| ⑤ 解释器启动之后自身失败 | MSYS 初始化失败（审查 040 的 `0xC0000022`）；崩溃 | 只有退出码，一般无法与 ③ 区分 | 按 ③。不增加“空命令预检”（§17.1 E7） |
| ⑥ 被信号终止（Unix） | 检查被外部 `kill -9`、OOM | 没有退出状态，只有信号（实验：Go 的 `ExitCode()` 为 −1） | `fail` / `nonzero_exit`，`exit_code` 为 NULL（§17.1 D12）；不把 −1 当作用户的退出码 |
| ⑦ 超时 | 长时间运行 | Specmetry 自己的计时 | `error` / `timeout`，`exit_code` 为 NULL；终止与收尾按 §8.5 |
| ⑧ 取消 | Ctrl+C、SIGTERM、控制台事件 | Specmetry 收到的信号或控制台事件 | §17.3 D8 |

- Windows 上被他人终止的进程，退出码是终止者给出的任意值（例如 `TerminateProcess(h, 1)`），与 ③ 无法区分，按 ③ 处理。
- 实验中，Git for Windows 的 `sh` 被 `kill -9 $$` 终止时，Windows 退出码为 2304。这是所测 MSYS 运行时的行为，按 ③ 记录实际的 Windows 退出码，不从它推断信号（§17.1 D17）。

### 6.2 分类规则（按优先级，命中第一条即停止）

| # | 条件 | `result` | `failure_kind` | `exit_code` |
|---|---|---|---|---|
| 0 | 取消（D8）、进程树没有确认结束（D19）及它们与输出、上下文、持久化失败的组合 | 见 §8.6 的决策表与 §17.3 D8、D19 | | |
| 1 | 上下文变化（§7.2）；结束上下文无法读取（D6，推荐） | `error` | `context_changed` | 主进程正常退出时为它的退出码，否则 NULL |
| 2 | 输入路径不存在（§7.3 L2） | `error` | `input_missing` | NULL |
| 3 | 进程无法创建（§6.1 ②） | `error` | `spawn_error` | NULL |
| 4 | 超时 | `error` | `timeout` | NULL |
| 5 | 解释器最终退出码 0 | `pass` | NULL | 0 |
| 6 | 其他（最终退出码非零；Unix 上被信号终止） | `fail` | `nonzero_exit` | 最终退出码；信号为 NULL（D12） |

- 第 1 条优先：data-model §7.4 第 4 步无条件地把上下文变化记为 `error` / `context_changed`，它也使这次执行不合格。所以**退出码 0 不推出 `pass`**。
- `not_found` 在 MVP 中**不产生**（推荐的方案 A，§6.3）。
- 一致性（迁移兜底，§10；`check-run.v1` 的约束见 §17.1 D14）：`pass` ⇔ `failure_kind` 为 NULL，`pass` 时 `exit_code = 0`；`fail` ⇔ `nonzero_exit`，`exit_code` 为非零值或 NULL（信号）；`error` ⇔ `timeout`、`spawn_error`、`input_missing`、`context_changed` 之一。`context_changed` 可以与退出码 0 同时出现。

### 6.3 EV-04 的契约冲突（§17.3 D5）

- **现有契约**：MVP-EV-04“检查命令不存在 → `error` / `not_found`”。
- **冲突**：检查命令都经由 shell 执行。“命令不存在”发生在解释器内部，Specmetry 看到的只有解释器的最终状态：
  - 它可能是非零（单独一条不存在的命令），而同一个数值也可以由主动退出产生；
  - 它也可能是 0（命令串处理了这次失败）。

  能可靠识别的“不存在”只有第 ① 层（解释器本身），而第 ① 层推荐为退出码 6、不写记录。所以经 shell 执行的检查不会产生 `not_found`，EV-04 无法满足。

| 方案 | 内容 | 代价 | 验收的变化 |
|---|---|---|---|
| **A（推荐，按 Review 071 B4 修订）** | **按解释器的最终状态分类**：在 §6.2 的优先规则都不命中时，最终 0 → `pass`，最终非零 → `fail` / `nonzero_exit` 并记录最终退出码。**不保证**发现命令串内部的命令查找失败，也不保证发现被命令串掩盖的失败；相同的最终非零码不区分原因。人类可读输出说明 Specmetry 不判断失败的原因。`not_found` 保留在枚举中（不改 `check-run.v1`、`status.v1` 的取值），留给将来可能由 Specmetry 直接启动程序的执行方式，保留不表示本实现会产生它 | 被命令串掩盖的失败不会被额外识别，检查照常通过；“命令不存在”与“测试失败”在记录中看起来一样；人需要看转发的输出 | 改写 MVP-EV-04（§14 的草案）；data-model §4.11 的 `failure_kind` 说明；`check-run.v1`、`status.v1` 的描述；交付状态的推导不变 |
| A' | A 的变体：第 ① 层记为 `error` / `not_found`，不再是退出码 6 | 把环境问题写成检查结果：一次解释器缺失就会让已验收的 AC 变为 `failing`（`regressed`） | 改写 EV-04 为“解释器不存在” |
| B | 在能识别的 shell 上注入前置代码报告“未找到”：bash 的 `command_not_found_handle`、PowerShell 的 `CommandNotFoundAction` | 实验：dash（Linux 常见的 `/bin/sh`）没有等价机制，定义了处理函数仍返回 127；bash 有效；PowerShell 的机制未验证。`cmd` 没有已知机制。注入的代码改变了经人确认的检查的执行环境；被命令串掩盖的失败仍然发现不了 | EV-04 只对部分 shell 成立，同样要改写 |
| C | 增加不经 shell 的执行形式（例如 `argv` 数组），操作系统能可靠报告程序不存在 | 修改 `checkSpec`、审核、人工编辑与 Skill 指南；较大的契约变化 | EV-04 只对 argv 形式成立 |

- **已被审查否定**：第 1 版方案 A 与 §14 中“命令不存在 → 结果不是 `pass`，为 `fail` / `nonzero_exit`”的普遍断言（Review 071 B4）。命令串可以消化这次失败并以 0 结束，这一断言不成立，**不能作为可以批准的推荐**。
- 不采用：按退出码 127 或 9009 推断（`exit 127` 同样得到 127；`cmd` 的“未找到”是 1，`exit /b 9009` 才是 9009）；按 stderr 文本推断；解析命令串。

### 7.1 代码上下文

## 8. 进程树、超时、取消与收尾

### 8.1 共同规则

- 每次执行一个独立的进程组（Unix）或 Job（Windows），只包含这一次检查的进程。
- 终止的时机：超时、取消，以及主进程退出之后仍有剩余进程（§17.3 D11 推荐终止）。终止之后按 §8.5 确认结束，再读取结束上下文。
- 标准输入为空设备（`/dev/null`、`NUL`）：检查是非交互的，等待标准输入的检查读到 EOF（§17.1 E8）。直接打开终端（`/dev/tty`、`CONIN$`）的检查，行为取决于平台与条件：Unix 上检查处在后台进程组时，读取终端通常收到 `SIGTTIN` 而停止，但没有控制终端、信号被忽略或阻塞、孤儿进程组等情况各不相同；本轮**没有验证**这些情况，不作一般性承诺（Review 071 N1）。被停止的检查最终由超时与 §8.5 收尾。

### 8.2 机制与实验

**Unix**（Linux 有实验，macOS 未验证）：

- `Setpgid`：Go 在 fork 之后、exec 之前于子进程中调用 `setpgid`，所以检查的任何代码都在新的进程组中运行，没有“启动之后、加入之前”的窗口。
- 终止：`kill(-pgid, SIGKILL)`。实验（§16 X1）：后台、双重 fork（`(sleep &)`）与嵌套 `sh` 的 6 个成员全部终止。
- **边界**（实验，§16 X2）：
  1. `setsid`（或 `setpgid`）主动离开进程组的后代，不受 `kill(-pgid)` 影响：实验中它在组被终止之后仍存活。
  2. 创建进程组的进程（Specmetry）被 SIGKILL 时，组内进程全部存活；`Pdeathsig` 只让直接子进程收到信号，孙进程仍存活。
- **进程组的身份**（Review 072 B3-R2b；技术门槛 T1、T2、T3）：
  - **事实**：组 ID 就是主进程（组长）的 PID。组长在被回收之前（不论仍在运行还是已成僵尸），它的 PID 不会被复用，所以这个组 ID 仍然指向本次检查的组。组长被回收、组中又没有其他成员时，组就消失了，这个数字可以被同一用户的另一个进程或进程组再次使用（kill(2)、waitpid(2) 的语义）。“组中还有成员时 ID 不复用”只覆盖组未变空的情形，**不能**作为向 `-pgid` 发信号的一般保证（第 2 版的这一推理已被 Review 072 否定）。
  - **规则（候选，T1）**：Specmetry 观察主进程退出时**不回收它**：Linux 用 `waitid(P_PID, pid, WEXITED | WNOWAIT)`；macOS 的同一调用是否可用、行为是否一致，**未验证**。从第一次 `kill(-pgid, SIGKILL)` 到确认组中没有存活的成员，组长都保持未回收；确认之后才由 `exec.Cmd.Wait` 回收组长，**此后不再向 `-pgid` 发送任何信号**。
  - **实验 X12**（Linux）：组长退出而未回收时，它保持僵尸状态，`pgrp` 仍是原值，`kill(-pgid, 0)` 成功；有残留后代时，`kill(-pgid, SIGKILL)` 终止了它们；回收组长之后，`kill(-pgid, 0)` 返回 ESRCH。这只证明这个窗口确实可以保持，**没有**做强制复用 PID 的实验；macOS 没有证据。
  - **无法保持时**：不回收的等待不可用，或组长在收尾完成之前已被回收（按设计不应发生）→ 不再按数字向组发信号，进入 F1（§8.5、§8.6），不宣称整棵树已经结束。
- **Linux 的候选加强：收养与清扫**（技术门槛 T2，§17.3 D7）：Specmetry 把自己设为 child subreaper，脱离进程组的后代在其父进程死亡时回到 Specmetry 名下，由 §8.5 的清扫收回。下面把两个问题分开（Review 072 B3-R2a）；X2、X9、X13 都只是局部的正例或反例，**不是完整的保证**：
  - **归属：这个进程是否属于本次检查**。
    - 一个进程成为 Specmetry 的子进程，只有两条途径：Specmetry 启动了它；或者它的父进程死亡时，Specmetry 是它最近的 subreaper 祖先。所以归属只能从“这段时间里 Specmetry 子树中都有谁”推出，不能从“开始之后才出现”或一次直接子进程的快照推出。
    - **第 2 版的推理不成立**（Review 072 的反例，作者的 X13 复现）：设置之前已有的子进程，可以在基线之后产生新的后代；后代被 Specmetry 收养，不在基线中，期间也没有启动任何检查。只排除基线中的 PID，会把这样的进程当作检查的后代清扫掉。
    - **候选规则：排他的检查区间**：
      1. 只在检查进程启动之前的一刻设置 subreaper，收尾完成之后清除（`PR_SET_CHILD_SUBREAPER` 可以设回 0）。
      2. 设置的那一刻，Specmetry 进程**没有任何子进程**，僵尸也算在内；基线必须为空，不是“记录并排除”。基线不为空或无法读取 → 不启用收养清扫，**不启动这次检查**（退出码 6，不记录；是否改为“不清扫而照常执行”属于 D7 的范围选择）。
      3. 在整个区间内，Specmetry 进程中没有其他代码启动子进程。这需要进程级的互斥：生产 CLI 中一个进程只执行一条命令，开始上下文的 git 在设置之前结束并被回收，结束上下文的 git 在清除之后才运行；进程内测试中并发的 `Execute`、并发的 `gitx` 调用都会破坏这一条，必须由测试基座串行化。如何在代码中强制这种互斥，属于 T2。
    - 在 1 ~ 3 都成立时，区间内 Specmetry 的子树只有检查的主进程及其后代，所以每个被收养的进程都属于本次检查。这是推理；X9（基线为空的正例）与 X13（反例与拒绝规则）支持它的两个方向，完整的证明与强制机制仍是 T2 的门槛。
  - **身份：当前的操作是否仍指向已确认的那个进程**。
    - 每个候选先用 `pidfd_open` 绑定，打开之后**再次**核对它的父进程仍是 Specmetry、启动时间与打开之前读到的一致；不一致即放弃这个候选（PID 已被复用）。
    - 信号经 `pidfd_send_signal` 发送，回收经 `waitid(P_PIDFD)`。
    - pidfd 只证明身份，**不证明归属**：它会准确地绑定一个归属被错误推断的进程。归属只能来自上面的排他区间。
    - 需要 Linux 5.3（`pidfd_open`）与 5.4（`P_PIDFD`）。内核不支持时，这一机制不可用，按 F1 处理，不回退到按 PID 的猜测。
  - **重复收养与回收**：终止一个被收养的进程之后，它的子进程又会回到 Specmetry 名下，所以清扫按轮次进行，直到没有候选；每个进程只经它自己的 pidfd 回收一次。进程组中被杀死的成员若其父进程已死，也会以僵尸回到 Specmetry 名下，同样经 pidfd 回收。
  - **与 Go `Wait` 的协作**：
    - Specmetry 从不调用 `wait(-1)` / `waitpid(-1)`。
    - 主进程只由 `exec.Cmd.Wait` 回收，并且只在收尾完成之后（上面的组身份规则）。
    - 清扫按 PID 排除主进程：主进程此时尚未被回收，它的 PID 不可能已被复用，所以这一比较是安全的。
  - **无法确认时**：基线不为空、内核不支持、身份不符、清扫在 `T_kill` 内没有收敛，或无法确认互斥成立 → 停止。不终止、不回收任何归属或身份没有确立的进程，不宣称整棵树已经结束，进入 F1。
  - **不覆盖**：
    - 不是 Specmetry 后代的进程（由 systemd、`at`、D-Bus 等启动的）；
    - 处于不可中断睡眠、无法及时结束的进程（按 F1）；
    - Specmetry 本身被 SIGKILL。
- **macOS**：没有 subreaper，脱离进程组的后代无法被发现，边界 1、2 都保留。进程组的终止、不回收的等待与组身份规则，本轮都**没有任何实验**（技术门槛 T3，§17.3 D7）；其他平台的实验不能外推为 macOS 的证据。

**Windows**（实验，§16 X1、X2、X8）：

- Job Object，设 `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE`，**不**设 `BREAKAWAY_OK` 或 `SILENT_BREAKAWAY_OK`。
- 顺序：以 `CREATE_SUSPENDED` 创建 → `AssignProcessToJobObject` → 用 `IsProcessInJob` 确认 → 恢复主线程。Go 的 `syscall.StartProcess` 会关闭主线程的句柄，所以经线程快照（`CreateToolhelp32Snapshot`）找到并恢复它（`golang.org/x/sys/windows`，已有依赖）。检查的任何代码都在加入 Job 之后才运行。任何一步失败的回收见 §8.5 S1（技术门槛 T4）。
- 终止：`TerminateJobObject`。它只是终止**请求**，进程真正结束是异步的（Review 071 B3）：结束的确认看 Job 的 `JobObjectBasicAccountingInformation.ActiveProcesses` 是否为 0（实验 X8 中，请求之后第一次查询即为 0；这不说明一般情况）。
- 身份：Job 与主进程都经 Specmetry 持有的句柄操作，句柄存在期间对象不会被替换，不存在按数字复用的问题。主进程的退出由它的句柄变为已发出信号观察，与 Unix 的“不回收的等待”对应。
- 实验：Git for Windows `sh` 的后台、双重 fork 与嵌套成员（6 个；经包装程序 `bin\sh.exe` 时 7 个）全部终止。持有 Job 的进程直接退出（不做清理）时，`KILL_ON_JOB_CLOSE` 终止了全部后代。Job 中的进程以 `CREATE_BREAKAWAY_FROM_JOB` 创建子进程 → 拒绝（errno 5）；普通创建的子进程在 Job 中。
- **边界**：不是由检查的进程树创建的进程不在 Job 中，例如经服务、计划任务、WMI 或 COM 的进程外服务器启动的进程，以及检查连接到的已在运行的守护进程（§17.3 D7）。

### 8.3 超时与计时

- `timeout_sec` 是**主进程**的时间预算：从进程开始运行（Windows 恢复主线程之后、Unix 启动之后）到主进程退出。超过 → 按 §8.5 终止与收尾，`error` / `timeout`，`exit_code` 为 NULL（MVP-EV-03）。
- 收尾另有独立的预算（§8.5）：
  - `T_kill`：终止到确认结束，提议 10 s；
  - `T_drain`：管道路径的正常排空，提议 5 s；
  - `T_join`：管道路径停止读取之后等复制返回，提议 2 s。

  它们是工程参数，不随 `timeout_sec` 变化；一次执行最长约为 `timeout_sec + T_kill + T_drain + T_join`，另加上下文的读取。
- `duration_ms` 用单调时钟，只计主进程的运行时间；没有启动进程（`input_missing`、`spawn_error`）时为 0。它不包含收尾时间，也不能用来掩盖收尾中的等待（§17.1 E9）。

### 8.4 取消（§17.3 D8）

- **Unix**：终端的 Ctrl+C 把 SIGINT 发给前台进程组，即 Specmetry 所在的组；检查在自己的组中，不直接收到。Specmetry 捕获 SIGINT、SIGTERM（也包括上层工具超时发出的 SIGTERM），按 §8.5 终止与收尾。SIGKILL 无法捕获，见 §8.2 的边界 2。
- **Windows**：控制台的 Ctrl+C 发给附着在同一控制台上的所有进程，检查也会收到，可能自行退出；Specmetry 捕获控制台事件，按 §8.5 终止 Job。Specmetry 被强制结束时，`KILL_ON_JOB_CLOSE` 终止检查。真实控制台中的这些事件本轮**没有验证**。
- 截止点与竞争：在写事务开始之前收到取消，这一次不记录；写事务已经开始的，按事务完成或回滚的实际结果，已提交的不撤回。检查在取消的同一时刻自行退出时，Specmetry 可能先看到它的退出状态：主进程退出之后、写事务之前再检查一次取消标记。信号到达 Go 程序的通道有延迟，不能完全排除“取消之前已经写入”的情况，此时记录的是检查自己的退出状态（如实说明）。退出码 3 不能反推检查没有运行。取消与 F1、F2、上下文失败、持久化失败同时出现时，按 §8.6 的决策表处理（依赖 D8、D19、D20 的选择）。

### 8.5 收尾协议（Review 071 B3，按 Review 072 B3-R1、R2 修订；技术门槛 T1）

**要区分的事件**：

| 事件 | 含义 | 由什么观察到 | 不依赖 |
|---|---|---|---|
| E-main | 主进程（解释器）退出，**尚未回收** | Unix：主进程退出而不回收（§8.2 的组身份规则）。观察用**有时限**的等待，不留下阻塞的等待任务：Linux 对主进程的 pidfd 做有时限的 `poll`，再以 `waitid(P_PID, pid, WEXITED \| WNOWAIT)` 取得状态而不回收；macOS 的对应机制未验证（T3）。Windows：对主进程句柄做有时限的等待。检查的 stdout、stderr 都是 `*os.File`（§9.1），所以这一观察不依赖任何复制 | 管道的 EOF；`exec.Cmd.Wait`（它会回收，只在收尾完成之后调用） |
| E-tree | 这一次检查的进程树已确认结束 | Unix：进程组中除未回收的组长之外没有存活的成员；Linux 另加 §8.2 的清扫没有剩余的被收养进程（只在排他区间成立时）；Windows：`ActiveProcesses = 0` | 终止调用的成功、PID 列表暂时为空、主进程已退出 |
| E-copy-end | 管道路径中复制任务已经返回 | 复制 goroutine 返回（不论原因）并被 Specmetry 等到 | — |
| E-drain | 管道路径中输出完整地转发了 | E-copy-end，且复制以 EOF 结束、全部字节都写入了目的端。复制因读错误、写错误或停止读取而返回，**不是** E-drain（Review 072 B3-R1） | — |
| E-final | 可以读取结束上下文 | E-tree 已确认 | E-drain |

Review 071 的复验与作者的 X7 都表明：输出走 `exec.Cmd` 自己的管道时，主进程已经被回收、`Cmd.Wait` 却仍在等复制完成。所以**禁止把非 `*os.File` 的 Writer 交给子进程**；管道路径只使用 Specmetry 自己建立的 `os.Pipe`，并且只用于 §9.1 支持的目的端。

**顺序**（所有分支都走完同一个顺序；任何一步都不先等复制结束再终止进程树）：

- **S0（准备）**：
  - 管道路径时，先确认目的端属于 §9.1 支持的类型（否则在启动之前拒绝，§9.1），再建立每个流的 `os.Pipe`，把写端（`*os.File`）交给检查。
  - Linux 上检查排他区间的条件（§8.2：没有任何子进程，区间内没有其他子进程来源），满足才设置 subreaper；不满足 → 不启动，退出码 6，不记录（候选，D7）。
- **S1（启动）**：
  - 创建进程失败（操作系统拒绝）→ 没有进程。Specmetry 关闭自己的写端，写端再无持有者，复制读到 EOF → E-drain。按 `spawn_error` 记录（§6.2）。
  - Windows：已挂起创建，但加入 Job、确认或恢复线程失败 → 绝不恢复这个进程。`TerminateProcess` 之后，等它的句柄在 `T_kill` 内变为已终止。挂起的进程持有写端，所以：
    - 确认终止 → 写端再无持有者，复制读到 EOF；退出码 6，这一次不记录（§17.1 E5）；
    - 没有确认 → 按 S6 停止读取并等复制返回；退出码 6，并在 stderr 说明“一个挂起的进程可能仍然存在”（不回显路径）。
  - 成功 → Specmetry **立即关闭自己持有的写端副本**，此后写端只被检查的进程持有。启动复制 goroutine，开始主进程的计时。
- **S2（等待）**：同时等待三者，先到者为准：
  - E-main；
  - `timeout_sec` 到期 → 标记超时；
  - 取消 → 标记取消。
- **S3（终止）**：无论哪种原因（包括正常退出，D11），对整个进程组或 Job 发出终止：
  - Unix 为 `kill(-pgid, SIGKILL)`，这时组长还没有被回收（仍在运行，或已是僵尸），组 ID 仍指向本次检查的组（§8.2）；
  - Windows 为对持有的 Job 句柄调用 `TerminateJobObject`。
- **S4（主进程）**：超时、取消时主进程可能还没有退出：等待 E-main，与 S5 共用 `T_kill`（从 S3 算起）。
- **S5（确认结束）**：在 `T_kill` 内确认 E-tree：
  - Unix 在组长保持未回收的前提下，反复终止并查询组成员，直到除组长之外没有存活者；
  - Linux 再按 §8.2 清扫被收养的后代，只在排他区间成立时进行；
  - Windows 轮询 `ActiveProcesses`。

  确认之后：先由 `exec.Cmd.Wait` 回收组长（此后不再向 `-pgid` 发信号）；Linux 再清除 subreaper 设置。
- **S6（输出，只用于管道路径；按 Review 073 B3-R1-S 修订）**：时间线如下。预算的候选安排是 `T_drain` 与 `T_join` 两段，彼此独立、各自有界；`T_join` 不是 `T_drain` 的剩余部分。
  1. **D 阶段（正常排空）**：从 S5 确认 E-tree 起，最多 `T_drain`。写端已没有持有者，读端会读到 EOF；等待 E-copy-end。
  2. **停止读取**：Specmetry 关闭读端，复制任务阻塞中的 Read 返回错误（X11：Windows 与 Linux 上立即返回；macOS 与其他 Windows 版本未验证）。管道中尚未读出的数据丢弃；仍存活的写端持有者之后的写入得到断开的管道错误。触发条件：
     - D 阶段到期仍没有 E-copy-end；
     - 或者进入不允许排空的分支：F1、S1 的终止没有确认。这些分支**跳过 D 阶段**，因为仍可能有写端持有者，排空可能永远等不到 EOF。
  3. **J 阶段（等复制返回）**：从停止读取起，最多 `T_join`，等待 E-copy-end。
  4. **封闭复制入口**：不论前面的结果如何，在继续之前，封闭这一次的全部复制入口（§9.1 的受控目的端）。
     - 封闭之后，这些复制任务的任何写入都被目的端拒绝。
     - 封闭只是在受控目的端的锁下设置标记；目的端的 Write 是不阻塞的内存追加，所以封闭本身有界（X15）。
     - 继承路径没有复制任务，不需要这一步。
  - **结果分三种**，只有第一种是 E-drain：

    | 结果 | 含义 | 转发 |
    |---|---|---|
    | O1 | 复制以 EOF 结束，并且全部写完 | 完整（E-drain） |
    | O2 | 复制已返回，但因读错误、写错误（包括目的端的容量上限）或停止读取而不完整 | 不完整（F2） |
    | O3 | J 阶段到期，仍没有确认复制返回 | 不完整（F2），并且**复制任务尚未确认结束** |

  - **O3 时还能保证什么**（X15 A：一个忽略关闭、永不结束的复制任务）：
    - **能保证**：入口已封闭，这些任务之后的写入都被拒绝。所以以下三者都不会收到这一次的迟到输出：
      - 最后的文档：经 Specmetry 自己的入口，在封闭之后写出；
      - 之后的错误呈现：只使用 Specmetry 自己的入口或真实的 stdout / stderr，从不经过已封闭的复制入口；
      - 同一目的端的后续调用。

      X15 A 中，封闭之后目的端只多出 Specmetry 写入的文档，复制任务在下一次写入时被拒绝而返回。
    - **不能保证**：返回时这个任务已经结束。
      - 它仍持有读端对象与入口的引用，但不能再写出；在 Read 返回之后的第一次写入时结束。
      - 如果 Read 在关闭之后仍不返回（两个平台的实验中都没有出现），它会一直留着，直到读端对象被释放。
      - 这是**不能写出的残留任务**，不是已经结束。它对同一进程中后续调用的影响（例如是否允许继续执行下一项、是否允许新的调用）是冻结之前要定的规格（T1、T6），本文不把它写成已接受的风险。
  - **撤回**：第 3 版把“没有确认复制结束”判为目的端违约（`internal` / 1），同时又保证“只有确认之后才返回”，这两者冲突（Review 073 B3-R1-S），连同“在支持的目的端上复制任务也在时限内确认结束”一并撤回。O3 按 F2 处理（D20），说明中写明复制任务尚未确认结束。
  - 转发的结果是一个独立的维度，与执行的结果、上下文分开（§8.6）。
- **S7（结束上下文）**：只有 S5 确认了 E-tree，才读取结束上下文（§7.1），再分类与写入（§4.2 第 5、6 步）。不启动进程的情形（`input_missing`、`spawn_error`）没有本次的消费者，不经过 S2 ~ S6，直接读取（§4.2）。

**失败出口**（不得悄悄按正常完成处理；组合与持久化的叠加见 §8.6）：

- **F1（`T_kill` 内没有确认结束）**：
  - 典型情形：
    - 进程组仍有成员；
    - 组身份无法保持（§8.2）；
    - Linux 的清扫仍有剩余、无法绑定身份、排他区间无法确认，或内核不支持 pidfd；
    - Windows 的 `ActiveProcesses > 0` 或查询失败；
    - E-main 没有出现（例如进程处于不可中断睡眠）。
  - 要求：
    - **不读取结束上下文，不走正常的合格记录路径**；
    - 不再向归属或身份未确立的进程发信号；
    - 不执行之后的检查（残留的进程可能影响它们）；之前已提交的事实保留；不重新执行这一次；
    - 管道路径跳过 D 阶段，按 S6 停止读取、等待 J 阶段、封闭入口；继承路径中，残留的进程仍可能向调用者的 stdout / stderr 写出迟到的输出（§9.1）；
    - 等待本身都有时限，不留下等待任务：主进程仍未退出时不调用 `Cmd.Wait`（它会一直阻塞）；
    - Windows 关闭 Job 句柄（`KILL_ON_JOB_CLOSE` 会再次请求终止），不能因此宣称已经结束。
  - **宿主资源的归属**（Review 073 N1；冻结之前的规格，T1、T2）：
    - **主进程**：已退出但未回收，或仍在运行。
    - **其他资源**：`exec.Cmd` 与进程句柄、pidfd、已收养的僵尸、subreaper 属性与进程级互斥。
    - **候选规则**（未定稿，只是方向）：
      - 关闭本次自己打开的 pidfd 与句柄（Windows 的 Job 句柄见上）；
      - 清除 subreaper 属性，以后的孤儿不再回到 Specmetry；
      - 已收养的进程仍是 Specmetry 的子进程，所以同一进程中下一次检查的基线不为空，按 §8.2 拒绝启动。这就是“残留时不复用”的机制。
    - **不能宣称的**：Specmetry 进程结束时，系统收养并最终回收残留的进程，但这**不保证**仍在运行的检查立即被终止。`Execute` 返回也不等于宿主进程已经退出。进程内的 F1 用测试接缝模拟时，只能验证分支的结果，不能证明真实进程、句柄与属性的生存期。
  - 这一次是否尝试记录、记为什么，是新增的语义，见 §17.3 D19。
- **F2（输出转发不完整，只在管道路径）**：S6 的 O2 或 O3。输出不是证据，这次执行的结果与上下文不因此改变；如何呈现见 §17.3 D20 与 §8.6。
- **S1 的 Windows 失败**：如上，退出码 6，不记录。

**时限**（候选安排；具体取值是工程细化）：

- `T_kill`：从 S3 起算，覆盖 S4、S5 与组长的回收。提议 10 s。
- `T_drain`：D 阶段，从 S5 确认起算；F1 与 S1 的终止未确认时跳过。提议 5 s。
- `T_join`：J 阶段，从停止读取起算。提议 2 s。
- 封闭入口：受控目的端锁下的一次设置，没有外部 I/O。
- 一次执行的最长时间约为 `timeout_sec + T_kill + T_drain + T_join`，另加上下文的读取（§8.3）。

这些时限只限制 Specmetry 自己的等待，不保证复制任务在时限内结束；保证“不再写出”的是封闭入口（O3）。Specmetry 写自己的最后文档、文本到真实的 stdout / stderr 时，与其他命令一样没有超时：调用者一直不读取时，进程会阻塞。这不属于检查收尾的协议。

### 8.6 组合失败的决策表（Review 072 B3-R3；按 Review 073 B3-R3-S 修订；草案）

**状态维度**：只用于文档分析，不新增数据库列或输出字段。每一个后来发生的情况**只更新它影响的维度**，不覆盖之前已经确定的状态；最后的报告带着全部维度（Review 073 B3-R3-S）。

| 维度 | 取值 |
|---|---|
| U 用户代码 | 未运行（S0 拒绝、开始上下文或 L1 读取失败、`input_missing`、`spawn_error`、Windows S1 管理失败）/ 已运行 |
| T 进程树 | 没有本次的进程 / 已确认结束 / **未确认**（可能残留）/ 挂起的进程未确认终止（S1） |
| C 结束上下文 | 未读 / 读取失败 / 已取得 |
| O 输出 | 继承路径：没有复制任务（T 未确认时可能有迟到输出）；管道路径：O1 完整 / O2 复制已结束但不完整 / O3 复制未确认结束（入口已封闭） |
| K 取消 | 没有 / 有 |
| P 持久化 | 未尝试 / **确认未提交**（提交之前失败：BEGIN、写锁下的检查、写入、执行项校验）/ **已提交** / **结果不确定**（提交阶段返回错误，或提交的结果没有被观察到） |

**判断规则**（都是候选；依赖 D6、D8、D19、D20 的部分标为“若采用”，补表不使它们成为正式规则）：

1. **是否尝试写当前项**：由 U、T、C、O、K 按优先级决定。顺序为：不启动的拒绝与 S1 管理失败 > T 未确认（D19）> 取消（D8）> C 读取失败（D6）> O2 / O3（D20）> 正常。
2. **P 叠加在上面**：持久化的结果只改变 P，从不改变 U、T、C、O、K。
   - 例如 F1 之后尝试写入又失败，仍可能有残留进程，结束上下文仍然未读；
   - `input_missing` 之后写入失败，用户代码仍然没有运行；
   - F2 之后写入失败，输出仍然不完整。
3. **P 的含义**：
   - 确认未提交 → “这一次没有记录”；
   - 已提交 → 记录保留；
   - 结果不确定 → “这一次**可能已经记录，也可能没有**”。读不到记录不能证明没有提交，也不能作为重新执行的依据。
   - 区分的方法：Runner 记下写事务的函数体是否已经成功返回。`withTx` 先运行函数体，再提交：函数体返回错误时回滚；函数体成功之后的错误只能来自提交（`internal/store/sqlite/store.go` 的 `withTx`）。不改变存储层、重试或错误映射。
4. **后续项**：任一情况成立都停止，不执行之后的项：
   - T 未确认；
   - 取消；
   - 尝试了写入而 P 不是“已提交”；
   - O2 / O3（若采用 D20(a)）；
   - C 读取失败（若采用 D6(b)）；
   - 任何环境错误。
5. **退出码**：只有一个，按 `internal` 1 > `environment` 6 > 取消 3 > 10 > 0，在**全部**维度的情况中取最高者。退出码不抹掉其他维度：`message` 与受控的 `details` 逐项写明残留进程的可能、结束上下文未读、转发不完整、这一次的记录状态（没有 / 已有 / 不确定）以及之前已提交的执行（§11.4、D10 的字段与数量限制）。
6. **不回滚、不暗示重跑**：之前已提交的事实一律保留。没有记录、没有观察到记录，都不是安全重新执行的依据。

## 9. 输出与隐私

### 9.1 检查输出的转发

- **底层输出对象**（Review 071 B3）：CLI 的 Cobra 输出被包装为 `termtext.Writer`（`internal/cli/root.go`），它会转义文本，也不是 `*os.File`。检查转发**不得**使用这些包装后的 Writer。`cli.Execute` 收到的原始 stdout / stderr 必须显式传给检查执行：
  - Specmetry 自己的文本仍经安全的 `termtext` Writer；
  - JSON 文档仍只写到 stdout；
  - 检查的输出只经下面两条路径之一。
- **继承路径**（推荐，§17.1 E2）：原始对象是 `*os.File`（正常的 CLI 进程中是 `os.Stdout`、`os.Stderr`）时，检查**直接继承**这些句柄。Specmetry 不建立管道、不复制、不读取检查的输出：
  - 不带 `--json`：检查的 stdout、stderr 分别是 Specmetry 的 stdout、stderr；
  - 带 `--json`：检查的 stdout 与 stderr **都是** Specmetry 的 stderr；Specmetry 的 stdout 只写最后的一份 `check-run.v1`（FR-EV-01，MVP-EV-12）。
  - 可继承的句柄只限于这些与空设备的 stdin。Windows 上由 Go 的句柄列表属性限制；Unix 上其他描述符默认 close-on-exec。实现时测试。
- **管道路径**：原始对象不是 `*os.File` 时，按 §8.5 使用 Specmetry 自己的 `os.Pipe`：
  - 写端交给检查；
  - 每个流一个复制 goroutine，把读端原样复制到目的端，不经 `termtext`；
  - 数据只在复制时经过内存，不保留、不检查内容；
  - 收尾、时限与失败出口完全按 §8.5。
- **目的端的支持契约**（Review 072 B3-R1；候选，D20 与技术门槛 T1、T6）：关闭读端只能停止读取，不能打断一个已经进入目的端 `Write` 的调用（Go 的 `os/exec` 文档；自行复制也不会给任意 `io.Writer` 增加取消能力）。所以对任意不可中断的 Writer，**不能同时**承诺有界返回、复制已结束与返回之后不再写出。候选方案分三类：

  | 目的端 | 处理 | 能给出的保证 |
  |---|---|---|
  | `*os.File`（生产 CLI 的 `os.Stdout`、`os.Stderr`；测试中的临时文件） | 继承路径：检查直接持有句柄，没有复制任务 | Specmetry 从不阻塞在检查的输出上；E-tree 确认之后，检查的进程树不再写出。F1 时残留的进程仍可能写出迟到的输出：文本模式在 stdout / stderr，JSON 模式只在 stderr（检查从未拿到 Specmetry 的 stdout），所以最后的 JSON 文档不受影响 |
  | Specmetry 控制的内存目的端（进程内测试使用；类型由 Specmetry 定义并识别，按类型识别本身不是证明，规则见下） | 管道路径：每次执行的每个流一个**复制入口**；Specmetry 自己的文本与最后的文档经独立的**所有者入口**写入 | 见下面的规则。概括：封闭之后复制任务不能再写出；所有者写入成功时，最后的文档字节不被复制输出插入，并在这一次的复制输出之后；复制任务**不保证**在返回时已经结束（O3），但已无法写出 |
  | 其他 `io.Writer`（无法取消、也无法隔离） | **在启动任何检查之前拒绝**：`internal` / 退出码 1，“the output cannot carry check output”；不执行，不记录 | 不提供上述保证。要支持这类 Writer（例如将来的嵌入式调用），尚**没有可依赖的方案**，是未解决的技术门槛，不能用“放弃复制 goroutine、留到进程结束”代替生命周期的说明 |

  - `cli.Execute` 是内部接口，生产中只以 `os.Stdout`、`os.Stderr` 调用，进程内的调用方只有测试。拒绝其他 Writer 不缩小产品对外的使用保证。但它确实限制了进程内调用可以使用的输出对象，这一点列入 D20，由负责人确认。
  - **受控目的端的规则**（Review 073 B3-R1-S 与第六节；候选，T6）：
    - **同步**：目的端内部以一个锁串行化全部写入，包括两个流的复制入口、所有者入口，以及别名到同一对象的入口。
    - **不阻塞**：每次写入都是锁下的内存追加，没有用户回调或外部 I/O。
    - **容量**：可以设上限，超出时复制入口的写入返回错误，复制以写错误结束（O2）。
    - **封闭**：每次执行在 S6 第 4 步封闭本次的复制入口，之后来自这些入口的写入都被拒绝。
    - **最后的文档**：在封闭之后经所有者入口**一次加锁地整体写入**，所以所有者写入成功时，即使 stdout 与 stderr 是同一个对象，文档字节也不会被检查的输出插入，并且在这一次的复制输出之后。加锁不保证写入成功：所有者写入失败或短写按 §8.6 C2 与 §11.4 处理。这也不表示别名到同一对象的整个流只有一份 JSON：调用者合流的既有例外不变。
    - **别名与并发调用**：
      - 两个流别名到同一对象时，检查的两路输出可能交错，与调用者主动 `2>&1` 相同，这一既有例外不扩大；
      - 两个调用共用同一个目的端时，各自的入口互不影响，各自的文档都是整体写入，但两个调用的输出之间可能交错；
      - 进程内并发执行检查本身受 §8.2 排他区间的限制。
    - **复用**：同一目的端被后续调用复用时，之前的入口都已封闭，后续调用收不到旧输出。之前调用中尚未结束的复制任务（O3）可能仍然存在，但已无法写出。
    - **撤回**：第 3 版的“停止读取之后复制在时限内返回；确认 E-copy-end 之后才写最后的文档、才返回，重复调用不会累积 goroutine”（Review 073 B3-R1-S）。现在“不再写出”由封闭入口保证；复制任务是否已经结束只作为状态报告（O1 ~ O3），不作为保证。
  - **JSON 模式**：检查输出的目的端是 stderr 对象，与 JSON 文档所在的 stdout 对象不同。不能把 stderr 上的迟到输出说成 stdout 被污染；如果两者是同一个对象，就按上面的封闭与整体写入处理。
  - **实验**：
    - X11（Windows 与 Linux）：
      - 旧设计（第 2 版：放弃阻塞在 Write 中的复制任务）复现了 Review 072 的反例：后一次写出的 JSON 之后又出现了旧的检查输出；
      - 不阻塞的目的端上，停止读取之后复制立即返回，仍存活的持有者 1 s 之后的输出没有进入目的端，JSON 是最后一项。这是正常的正例。
    - X15（Windows 与 Linux）：针对异常出口。
      - 一个忽略关闭、永不结束的复制任务在 D、J 两个阶段都没有返回；封闭立即完成，之后目的端只多出所有者写入的文档，复制任务在下一次写入时被拒绝而返回；
      - F1 情形下 stdout 与 stderr 别名到同一个目的端：J 阶段两个复制任务返回，封闭之后写入的 JSON 是最后一项，持有者的迟到输出没有进入。
    - 这些都只是局部证据：一个阻塞在 Read 中、永不返回的复制任务没有被模拟（它无法写出，但会一直留着）；macOS 与其他 Windows 版本没有实验。
- 理由（实验 X7、X8、X11；Review 071、072 的复验）：
  - 输出交给 `exec.Cmd` 自己的管道时，退出的检查留下的后台进程持有管道，`Wait` 一直阻塞，`WaitDelay` 也不能打断阻塞中的目的端 `Write`；
  - 直接继承句柄，或使用自己的 `os.Pipe` 并把 `*os.File` 交给子进程时，主进程的退出不依赖复制即可观察到（§8.5 E-main）；
  - 继承路径中 Specmetry 从不读取输出，也就不可能保存它（隐私契约，architecture §10）。
- 句柄继承让检查看到的终端属性与调用者相同（例如 stdout 是终端时，测试工具的彩色输出照常）。
- **显示的信任边界**：检查的输出原样出现在终端中（data-model §7.4“原样转发”），可以含有控制字符，能改变终端或模仿 Specmetry 的文本行。Specmetry 自己的文本仍经 `termtext` 转义（architecture §9.1），但文本输出不是可信的通道；以 `--json` 的结果与数据库为准。
- 调用者把 stderr 合并到 stdout（`2>&1`）时，`--json` 的 stdout 不再只有 JSON；这是调用者的选择，文档说明。

### 9.2 环境

- 继承调用者的环境，加上 `SPECMETRY_CHECK=1`（已有同名变量时覆盖）；Windows 的 `sh` / `bash` 另见 §5.4（D2）。
- **读取与记录要区分**（Review 071 N2）：
  - Specmetry 会**读取**环境：用来把它传给检查、查找解释器，以及 D2 获批时构造 PATH。
  - Specmetry **不把**任何环境变量的值写入执行记录、错误、日志或输出（architecture §10）。D2 的 PATH 前置不记录原来的 PATH。
- `internal/gitx` 的受控环境（清除 `GIT_DIR` 等）只用于 Specmetry 自己运行的 git，**不**施加给检查：检查继承用户的环境，包括其中的 `GIT_*` 变量（如实说明）。

### 9.3 隐私

- **不保存**：
  - 命令文本（`check_runs` 没有命令列，运行时也不在日志、错误中捕获命令）；
  - 检查输出及其尾部与哈希；
  - 环境变量的值；
  - 启动错误的文本与路径。
- 已确认的检查配置按既有的基准契约保存在基准中（由 `check_config_hash` 找到），这与“运行时不捕获原始命令”不是一回事。
- **保存**：data-model §4.11 的字段；`workdir` 来自已确认并经过密钥扫描的检查配置；首次登记的 worktree 路径在任何检查启动之前做密钥扫描（§4.1 第 4 步）。
- **日志**：不记录 C0 / C1 内容。
- **对仓库的写入**：Specmetry 不写入（architecture §10.6）；检查自己对 worktree 的写入属于检查的行为，按 §7.2 判定。

### 10.3 `seq` 与事务

- 写入**没有版本前置条件**：执行绑定开始时读取的修订与配置（CX-15），之后的基准变化不拒绝这次写入。
- 写事务沿用 `DB.WriteTx`（`BEGIN IMMEDIATE`，`busy_timeout`）。M-15（`SQLITE_BUSY`）是未解决的维护事项；本工作包不改变既有的重试与错误映射。

### 11.2 `is_target_snapshot` 是批次汇总，不决定逐条执行的效力（Review 071 B2；§17.3 D9）

- **逐条效力**（已冻结，不变）：一条执行能否影响交付状态，只由 data-model §6.1 的逐条规则决定。它要属于该 AC 的 `runs(S)`：合格、`head = S`、修订与配置为当前值。然后它参与 `V`。推导从不读取 `is_target_snapshot`（`derive/criterion.go` 逐条筛选，`CheckRun` 模型不含批次字段）。
- **批次汇总**：`is_target_snapshot` 只是给调用方的一个布尔汇总，**不进入** `runs(S)`、`V` 或任何推导。它为 false，**不表示**批次中没有能影响交付的执行。
- **混合 `head_start` 的例子**（合法历史，不涉及执行期间的变化）：
  - 目标 `S = A`。AC-001-1 在 A 上开始和结束，干净，通过。
  - 两次执行之间，用户把 worktree 切换到 B。AC-001-2 在 B 上开始和结束，干净，通过。
  - 按 D9 的选项 (b)，汇总为 false。但 AC-001-1 的那一条仍属于 AC-001-1 的 `runs(A)`，参与 `V`，可以把它推到 `ready_for_review`。AC-001-2 的那一条不属于目标快照。
  - 调用方应按每一条的 `head_start` 与 `qualifying` 判断，不能用汇总代替。
- **汇总含义的选项**（D9，需负责人确认；无论选哪个，上一条都不变）：
  - (a) 命令开始时的 HEAD 等于 `S`（现有描述的字面含义）；
  - (b) 每一次执行的 `head_start` 都等于 `S`；没有执行时，比较命令开始时的 HEAD；
  - (c) 不再输出这个字段的“交付效力”说法，只澄清描述。

  `check-run.v1` 中这个字段的描述“only then can observed qualifying runs affect delivery status”与逐条规则冲突，无论哪个选项都需要澄清，不改结构。
- **已被审查否定**：第 1 版中“只有这时，这些执行中的合格执行才能影响交付状态”（Review 071 B2）。它与冻结的逐条规则冲突，不能作为推荐。

| 字段齐全、没有多余字段（因而不会出现输出或命令）；枚举；格式 | schema（已有；反例 SCH-49、SCH-59） |
| `result`、`failure_kind`、`exit_code` 一致（§6.2） | 现在只有业务测试；§17.1 D14 提议在 `check-run.v1` 中加入 `if/then` 约束（须允许 `context_changed` 与退出码 0、信号的 `fail` 与 NULL） |

**提交之前校验**：

- 每次执行的那一项，在写事务中用刚写入的行构造，并在提交之前按 `check-run.v1` 中执行项的定义校验。失败 → 回滚（包括这个事务中首次的 worktree 登记），退出码 1，这一次确认未提交。然后停止，不执行之后的，不重新执行。用户代码是否运行过沿用 U 的状态（`input_missing`、`spawn_error` 时没有运行）；F1 时的可能残留、未读的结束上下文与 O 的状态同样沿用（§8.6）。
- 全部执行之后，再校验并编码整份文档。它由已校验的各项构成，失败只可能是内部错误：退出码 1。**之前的执行已经提交，不能回滚**。
- 这比 `propose` 的现有顺序更严格，与 WP2.4 §9.3 的做法相同。

**缺口**（不在本工作包中改变，§17.1 D14）：`check-run.v1` 没有 `head_end`、`tree_state_end`、`requirement_revision`、`check_config_hash`、`workdir`；调用方只能从 `failure_kind`、`tree_state_start` 与 `qualifying` 看出不合格的原因。推荐保持现状，需要时另行提出。

### 11.4 失败的呈现

| 阶段 | 已经写入的 | 呈现 |
|---|---|---|
| 执行任何检查之前（§4.1） | 无 | 带 `--json` 时 stdout 一份 `error.v1`，stderr 为空；不带时为文本 |
| 第 k 次之前的环境错误（开始上下文、L1、建立 Job 失败） | 第 1 ~ k−1 次 | 停止；§17.1 D10 |
| 第 k 次决定写入之后，提交之前失败（BEGIN、写锁下的检查、写入） | 第 1 ~ k−1 次；第 k 次**确认没有记录** | 停止，不执行后面的；退出码 6；§17.1 D10。说明按 §8.6 保留之前的状态：用户代码已运行时写“已执行而没有记录”；`input_missing`、`spawn_error` 时写“检查没有运行”；可能残留的进程、未读的结束上下文、不完整的转发照常写明。**不重新执行第 k 次** |
| 第 k 次提交阶段返回错误，或提交的结果没有被观察到 | 第 1 ~ k−1 次；第 k 次**不确定** | 停止；退出码 6；说明“这一次可能已经记录，也可能没有”，不写“没有记录”；读不到记录也不能作为重新执行的依据 |
| 第 k 次的执行项校验失败 | 第 1 ~ k−1 次；第 k 次确认未提交（已回滚） | 退出码 **1**（`internal`，不被 D10 的 environment 文案覆盖）；停止。用户代码是否运行过沿用 U（`input_missing`、`spawn_error` 时没有运行），F1 的可能残留、未读的结束上下文与 O 的状态也沿用（§8.6） |
| 第 k 次的进程树没有确认结束（F1）、输出转发不完整（F2），以及它们与取消、上下文、持久化失败的组合 | 按 §8.6 | §8.6 的决策表；§17.3 D8、D19、D20 |
| 第 k 次被取消 | 第 1 ~ k−1 次 | §17.3 D8 |
| 全部提交之后，整份文档的校验或编码失败 | 全部 | 退出码 1；不回滚 |
| 全部提交之后，写出失败或短写 | 全部 | 退出码 6；不回滚；stdout 可能被截断，不再追加第二份 JSON；尽力在 stderr 说明“执行已经记录，不要盲目重试”（与 WP2.4 §9.3 第 4 步相同） |

各阶段的故障注入在实现测试中分别进行，文本与 JSON 两种模式都覆盖（Review 071 N3）。

### 11.5 文本输出（§17.1 E4）

- 每次执行之前，一行 `checking AC-001-1 (sh, timeout 300 s)`；之后一行结果：`AC-001-1 pass (8.4 s)`、`AC-001-2 fail (exit 1)`、`AC-003-1 error: timeout`，以及不合格的原因（`not qualifying: the worktree was dirty at the start` 等）。都写到 stdout，经 `termtext` 转义；带 `--json` 时不输出这些行。
- 最后一行汇总：通过、失败、错误的数目，证据等级 `observed`，以及“observed: only the start and the end were checked”（不称为“快照已验证”，CX-26）。
- `fail` / `nonzero_exit` 的说明写明：Specmetry 只看解释器的最终状态，不判断失败的原因，也不发现被命令串掩盖的失败（方案 A）。

## 12. 与推导的关系（不改变）

- 推导读取 §10.2 的逐条字段；`runs(S)`、`V`、`inconsistent`、`HIST` 的定义不变（data-model §6.1）。批次级的 `is_target_snapshot` 不是推导输入（§11.2）。

- 推导引擎与复核器不改；MVP 合法事实域只含观测级执行（data-model §6.14）。

**建议新增的验收项**（草案，编号待定，获批后写入 acceptance-criteria）：

1. **解释器与参数**（D1、D2）：每个平台上每种可用的解释器，用 §5.5 的字符串集回显，结果与输入完全一致；Windows 上 PATH 中只有 WSL 的 `bash.exe` 时不使用它；位于 worktree 之内的解释器（经 PATH 的绝对路径、相对路径项、符号链接或联接到达的）不被执行。
2. **解释器不可用**：退出码 6，`shell_unavailable`，没有新行，没有启动任何进程；Unix 上的 `cmd`、`powershell` 同样。
3. **进程无法创建**：工作目录不存在 → `error` / `spawn_error`。
4. **`cmd` 多行与 CR**（D3、D4）：提案、审核、人工编辑中拒绝；已保存的在执行前拒绝，没有新行。
5. **进程树与收尾**（T1 ~ T4、D7、D11、D19、D20）：

   - Job 不允许 breakaway；持有 Job 的进程意外退出时后代被终止；

   - 进程树没有在 `T_kill` 内确认结束时，不读取结束上下文、不记录为合格；
   - Unix 的组长在收尾完成之前不被回收，回收之后不再向 `-pgid` 发信号；
   - Linux：基线不为空时不启用清扫、不启动检查；被收养后代的清扫按 pidfd 身份进行，与 `Wait` 协作；既有子进程的后代不会被当作检查的后代（Review 072 的反例）。
6. **输出的生命周期**（D20、T1、T6）：
   - 不受支持的目的端在启动之前被拒绝；
   - 管道路径的 D、J 两个阶段与封闭入口按 §8.5 S6 的时间线进行；
   - 封闭之后复制入口不再写入，包括复制任务尚未结束的 O3；
   - 仍存活的持有者的迟到输出不进入目的端；同一目的端的后续调用收不到旧输出；
   - 最后的 JSON 文档整体写入、不与检查输出交错，stdout 与 stderr 别名时同样；
   - O1、O2、O3 分别报告，只有 O1 算作完整转发。
7. **组合失败**（§8.6）：
   - A、B、C 三张表的每一行都有用例；
   - 持久化的结果叠加在收尾状态之上，不覆盖它：F1 之后的写入失败仍报告可能残留，`input_missing` 之后的写入失败报告检查没有运行；
   - 提交之前的失败与提交阶段的错误分别注入，后者报告“记录不确定”；
   - 退出码按候选的优先级，`internal` / 1 不被 environment 覆盖。
8. **取消**（D8）、**结束上下文读取失败**（D6）、**写入失败不重新执行**（D10）、**剩余后代被终止之后才读取结束上下文**（D11）。
9. **批次汇总**（D9）：混合 `head_start` 的批次中，汇总的取值按 D9 的决定；位于 `S` 的那一条照常参与推导。

## 14. EV-04 改写的草案（方案 A，待 D5；按 Review 071 B4 修订）

> MVP-EV-04（改写草案）：检查按**解释器的最终状态**分类，Specmetry 不解析命令串，也不判断失败的原因。
>
> - 命令串最终以非零状态结束（例如单独一条不存在的命令：sh、bash 为 127，`cmd`、`pwsh`、`powershell` 为 1）→ `fail` / `nonzero_exit`，`exit_code` 为解释器的最终退出码，`failure_kind` 不是 `not_found`；主动以同一数值退出的命令（`exit 127`、`exit /b 1`、`exit 1`）得到相同的记录。
> - 命令串中有不存在或失败的命令，但最终以 0 结束（`missing; :`、`missing || true`、`false | true`、`cmd` 的 `missing & exit /b 0`、`powershell` 的 `missing; exit 0`）→ 上下文一致时为 `pass`：这是方案 A 已披露的能力边界。
> - 优先规则不变：上下文变化、输入缺失、进程无法创建、超时与取消先于最终状态（§6.2），所以最终退出码 0 不一定是 `pass`。
> - 解释器本身不可用时，见“解释器不可用”（退出码 6，不记录）。
