## 2. 现有日志不能确认的环节

测试工具在看到提示文本之后写入回车，但**不检查写入的返回值**，也没有记录匹配与写入的时间。因此对原始失败，以下各项现有日志都不足以确认：

- 提示是否被匹配到；
- 是否尝试了写入回车；
- 写入的返回字节数与错误；
- 子进程是否收到了输入；
- 超时那一刻，读取任务、`Wait` 与 PTY 关闭各自处在什么状态。

## 3. 调用链（静态阅读）

```
子进程：channel.Guard 写出提示 → bufio.Reader.ReadString('\n')（控制台的行输入）
  ↓ ConPTY 渲染输出
测试工具的读取任务：outPipe.Read → 追加到缓冲 → bytes.Index(提示) 命中
  → Before 回调（本测试没有）→ p.Write("\r")（返回值被忽略）
  ↓ ConPTY 的输入管道 → 控制台输入缓冲
子进程：读到一行（空）→ 取消，退出码 3
测试工具：cmd.Wait 返回 → 最多再等 500 ms 读取 → p.Close（ClosePseudoConsole 与两条管道）→ 最多再等 2 s 读取结束
```

- 依赖：`github.com/aymanbagabas/go-pty` v0.2.3。
  - `conPty.Write` 直接调用输入管道的 `os.File.Write`；
  - `Cmd.Wait` 调用 `os.Process.Wait`，收尾向一个容量为 1 的通道发送，不会阻塞。
- **静态推断**（没有动态证据）：
  - 失败输出中，提示文本是连续的；而匹配是在累积的缓冲上进行的，所以提示**大概率**被匹配到，写入也**大概率**被尝试了。
  - 健康运行中，回车被处理之后，会有回显与“was not confirmed”的消息输出。失败输出中两者都没有，这与“回车没有进入子进程的行输入”一致。但仅凭这一点，不能区分是写入失败、短写，还是写入了而 ConPTY 或控制台没有处理。

## 4. 有界实验（作者本机，仓库外）

**做法**：

- 用 `git archive` 导出 `cc4514a` 到仓库外。
- 只把副本中的 `internal/testutil/pty.go` 换成带观测点的版本，会话逻辑不变。观测点是 `PTYTRACE=1` 时记录的事件：启动与 PID、每次读取的字节数与错误、步骤匹配的偏移、Before 的开始与结束、写入的开始与返回值、`Wait` 的返回、超时时各状态、Kill 与 Close 的结果。只记录时间、字节数、索引与错误，不记录输入或输出的文本。
- 另有两项受控故障：
  - `PTYCHUNK=n`：每次读取最多 n 字节，使提示跨读取分块；
  - `PTYWRITEFAULT=error|short`：回答不写入，分别返回错误，或返回 0 字节而不报错。后者是观测包装层的受控故障：Go 的 `os.File.Write` 在 n 不等于输入长度时会返回错误，所以这不表示原生写入会这样返回；不论哪种，测试工具都忽略返回值。
- **平台**：Windows 11（10.0.26300）、Go 1.27.1、本地工具链、`GOPROXY=off`。只操作本轮自己的测试进程；每次调用都有硬期限；结束后没有残留。
- **计划**：实验前写明数量与总时限，跑完即停，不运行到出现失败为止。

| # | 实验 | 性质 | 次数 | 结果 |
|---|---|---|---:|---|
| X1 | `TestSourceRemoveInTerminal`（空输入取消 + 正确文本确认） | 原生 | 40 | 40/40 通过，没有超时。两种回答各 40 次：匹配之后写入都在 1 ms 之内返回（1 字节、21 字节，没有错误）；写入到 `Wait` 返回 2.6 ~ 43.9 ms（中位数 5.4 ms） |
| X2 | `TestSourceAckRefusesSecretRationale`（无需提示，直接退出） | 原生 | 20 | 20/20 通过 |
| X3 | X1，读取限制为 7 字节（提示跨读取分块） | 受控注入 | 10 | 10/10 通过；提示在 20 次中都被匹配到；写入到 `Wait` 返回最长 64.3 ms。只说明在相同的输入字节下不因读取边界而漏匹配，不是对任意终端布局的保证 |
| X4a | X1，回答的写入返回错误、不写入 | 受控注入 | 1 | 60 s 超时失败 |
| X4b | X1，回答的写入返回 0 字节、不报错（短写） | 受控注入 | 1 | 60 s 超时失败 |

- **X4 的现象与原始失败相似**：超时的错误签名相同，提示的末尾与其后的控制序列（`\x1b[1C`、窗口标题序列、`\x1b[?25h`）类似，之后没有任何输出。这不是整份输出的逐字节相等（项目 ID 与临时路径本来就不同），只说明这一签名不具排他性，不能证明原始失败属于注入的原因。
- **观测记录能区分它们**：匹配已发生、写入已开始也已返回（返回值见上），读取任务仍在、`Wait` 没有返回；Kill 之后 `Wait` 返回，读取以“file already closed”结束，Close 没有错误。

## 5. 结论与未知项

- **没有复现**：原失败测试 40 次（X1）与另一个无需提示的测试 20 次（X2），都没有出现原始失败。这不是原失败路径重复 60 次，只说明在这台机器、这些次数下没有出现，**不能凭此关闭事项**。
- **已确定**（受控注入）：
  - 测试工具忽略写入的返回值。所以“回答没有写入”（写入失败或短写）产生的超时签名，与原始失败的签名**无法区分**。
  - 当前的累积缓冲算法，在相同的输入字节、读取与调度都有效的前提下，不会仅因读取边界的拆分而漏匹配；本机 7 字节分块的 10 次实验没有复现。这不是对所有 ConPTY 渲染、窗口宽度、控制序列或终端布局的保证（N-088-1）。
- **静态推断**：原始失败中，提示大概率被匹配到，写入大概率被尝试了。“大概率”只是源码阅读的判断，没有动态证据，也没有统计依据。
- **未知**：原始失败究竟是哪种情形，现有证据不能确定，可能是以下之一：
  - 写入失败或短写；
  - 写入了，但 ConPTY 或控制台没有把它交给子进程的行输入；
  - 子进程收到了输入，却没有退出或没有被观察到退出。

  不预设根因是 ConPTY、提示匹配或生产 CLI。
- **与其他维护事项分开**：
  - 不是 M-15（`SQLITE_BUSY`）的签名；
  - 不是 M-16（包超过超时）的签名：这次包耗时 475 s，在预算之内。

**没有得到明确的修复方案**，本轮也不实施任何修复。下一步可考虑的方向如下，都需要另行授权与审查：

- **只记录**：让测试工具记录匹配、写入的返回值（n、err）与时间，并在超时时报告匹配、写入与 `Wait` 的状态。这只增加观测，不改变失败路径、预算或断言；
- **按错误提前失败**：写入出错或短写时立即判失败。这会改变测试工具的失败路径、时间与收尾行为，与“只记录”分开，须另行授权与审查（N-088-2）；
- 在 Windows CI 上以同样的观测重复运行有界次数，取得失败时的状态。
