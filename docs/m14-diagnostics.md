# M-14 诊断工具与运行说明

> 状态：**M-14 未解决**（维护事项，[m1-exit-evidence.md §9](m1-exit-evidence.md)）。本工具只用于诊断：它不修改 `Open`、只读保护、错误分类或重试行为，也不决定任何修复。没有复现不等于已经解决。
>
> 工具版本：审查 051（NO-GO，§7）指出最初版本（`1d8b73c`）的有效性缺陷：辅助进程崩溃、结果损坏或缺失、零工作量时，测试仍可能通过。本版修复了有效性门禁（§3），**待复审**：审查 051 B1 没有由审查方关闭。§5.1 的结果来自最初版本，按其说明使用；§5.2 是本版的运行。

## 1. 要区分的四件事

| # | 内容 | 性质 |
|---|---|---|
| 1 | **原始 CI 失败** | 事实（GitHub CI 日志） |
| 2 | **辅助只读探测出现同一错误码** | 事实，但只针对辅助探测 |
| 3 | **真实的 `Open` 路径尚未复现** | 事实，限于已运行的次数 |
| 4 | **SQLite 内部机制** | **尚未确认** |

**1. 原始 CI 失败**

- 位置：PR #23 的 [run 39110669282](https://github.com/XKHoshizora/specmetry/actions/runs/39110669282) attempt 1，Go tests (macos-latest)，检出 `4f2393d`。
- 测试：`internal/store/sqlite` 的 `TestSeqIsUniqueAcrossProcesses`。
- 现象：一个辅助进程在 `Open` 中报告 `cannot read the database version: cannot read the database: attempt to write a readonly database (264)`。
- 后续：attempt 2 只重新执行了这个作业，通过。

**2. 辅助只读探测出现同一错误码**

- 做法：在 `Open` 之外、不持有打开锁，循环调用 `Open` 使用的只读版本探测 `readMetaReadOnly`，同时有其他进程在提交。
- 结果（最初版本的工具，§5）：Windows 本机与 macOS CI 都出现了 264，错误文字与原始失败相同；macOS CI 还出现了 1288（`SQLITE_READONLY_CANTINIT`）。没有提交的对照组为 0。
- 限制：
  - 这只说明探测函数本身在这种并发下会遇到这些错误码，**不等于 `Open` 会遇到**。`Open` 在打开锁之下调用它，而且只调用一次。
  - 辅助探测省略了真实 `Open` 的数据目录检查与打开锁，所以也不能据此说已经复现了相同的内部竞争机制。

**3. 真实的 `Open` 路径尚未复现**

- 做法：按真实的锁与顺序运行 `Open`，即原测试的模式。
- 结果（最初版本的工具，§5）：在 Windows 本机、Windows CI、macOS CI 上，打开阶段的失败都是 0。
- 原始失败只出现过一次。

**4. SQLite 内部机制尚未确认**

- 读 modernc 转写的 SQLite 代码得到的假设：只读的 `-shm` 连接在无锁读取 WAL 索引头时，与另一进程的提交重叠，读到不一致的头，于是返回 `SQLITE_READONLY_RECOVERY`。
- 没有对 SQLite 插桩确认是哪一种坏头。macOS 上的 1288 也还没有解释。

## 2. 能确认的保证（限定范围）

只陈述有实际证据的部分：

- **只读探测失败的这一次 `Open` 没有执行的步骤**（代码路径，只读审查）：
  - 探测在 `store.go:117` 调用，失败时在 `:118 ~ 124` 返回。
  - 这时还没有执行：墓碑的读取与应用（`:136`、`:172`）、创建数据库文件（`:140`）、打开读写连接（`:143 ~ 147`）、迁移，以及任何用户写事务。所以可以说"这次 `Open` 没有执行这些 SQL 或业务写入"。
  - 探测连接是 `mode=ro&readonly_shm=1`（`readonly.go:173`），在只读事务中执行（`:179`）。
  - 错误归类为 environment（退出码 6）。
- **这不等于"数据目录没有任何变化"**（审查 051 N4）：
  - 探测之前已经执行了数据目录的准备（`store.go:99`）与打开锁（`:105`），协调文件 `.migrate.lock` 可能在这时首次创建。
  - MVP-STO-02、STO-07 另有一个狭窄的、已批准的例外：另一个 SQLite 程序在检查期间关闭数据库时，原生只读连接可能创建空的 `-wal`、`-shm`。
- **本工具运行过的场景中，所测数据库的检查都通过**：
  - 结构检查 `PRAGMA integrity_check` 为 `ok`；
  - 合成 facts 的行数等于各辅助进程报告已提交的数；
  - `seq` 唯一、恰好是 1 到 n，`seq_counter` 等于 n。最初版本没有检查下界（审查 051 N1），本版补上了。
- 这些检查的含义有限：
  - 它们只说明在这些运行中，失败的探测与写入阶段的 `SQLITE_BUSY` 没有留下多出来的行；
  - 不核对每条 payload 的身份与内容；
  - 这些运行中真实的 `Open` 没有出现过打开失败，所以 `Open` 的失败分支没有经过动态验证；
  - 数据库检查不能代替实验有效性的检查（§3）。

**不在保证之内**：

- 这些运行之外的场景，例如崩溃、断电或其他程序。
- 用户体验：命令会以退出码 6 误报环境错误。
- SQLite 的内部状态，以及任何关于"无害"的一般结论。
- 任意状态下不丢数据、不损坏数据库。

## 3. 工具

| 文件 | 内容 |
|---|---|
| `internal/store/sqlite/m14_diag_test.go` | 两个诊断测试与两个辅助进程 |
| `internal/store/sqlite/m14_validity_test.go` | 有效性回归，属于常规测试（见本节最后） |
| `internal/store/sqlite/store_test.go` | `TestMain` 登记这两个辅助进程（`m14open`、`m14probe`） |
| `.github/workflows/m14-diagnostics.yml` | 在 macOS 与 Windows 上运行这两个诊断。不属于 `ci.yml`，后者只把它们作为跳过的测试，有效性回归则照常运行 |

**`TestM14ReadOnlyProbe`**（辅助只读探测）：

- 测试进程打开数据库并一直保持打开，与原测试相同。
- 探测进程在循环中调用 `readMetaReadOnly`，即 `Open` 使用的探测，但没有数据目录检查，也没有打开锁。至少探测一次。
- 遇到 SQLite 错误后立即再探测一次。
- 两个变体：
  - "control, no commits"：没有写入进程；
  - "during commits"：写入进程各自 `Open` 之后在循环中提交，至少尝试一次。

**`TestM14OpenPath`**（真实的 `Open` 路径）：

- 每一轮一个新的数据库，由测试进程打开并保持。
- 同时启动 `M14_PROCS` 个辅助进程，每个都按真实的方式 `Open`（数据目录检查、打开锁、只读探测、读写连接），再写入 `M14_FACTS` 条事实。
- 默认是原测试的规模（3 个进程，各 100 条），重复 `M14_ROUNDS` 轮。
- 失败按阶段与错误码归类：
  - 只读版本探测的查询（错误含 `cannot read the database version: cannot read the database:`，只来自 `readonly.go:161`）；
  - 无法检查；
  - 版本读取，步骤未知：其余的 `cannot read the database version` 可能来自探测的文件检查，也可能来自读写连接，这时不能定位（审查 051 N3）；
  - 其他打开步骤；
  - 写入。

**实验的有效性**（审查 051 B1）：

- **两类结果分开**：
  - **观测**：被诊断的调用（`Open`、探测、写入）返回的错误。SQLite 错误按阶段与错误码计数，不使测试失败。一轮中所有真实的 `Open` 都以已识别的错误返回，仍是有效的结果。
  - **实验无效**：辅助进程没有启动、异常退出或被杀；结果缺失或损坏（必须恰好是一行、字段都已知的 JSON）；在自己的准备阶段失败（`setup`、`resolve`、`migrations`），也就是还没有调用 `Open`；到达期限；报告前后矛盾（例如没有调用 `Open` 却报告了打开之后的阶段，或 `done` 时的提交数不对）。
  - 实验无效时测试失败，结果行记录 `valid: false` 与原因（`invalid`，最多 20 条，另有 `invalid_count`）。
- **工作量**：
  - 参数有下限与上限（下表），越界时在任何工作之前就失败，不再按上限截断。
  - 每个探测进程至少要探测一次。
  - "during commits" 必须有实际的提交（`writer_commits` > 0），还要有探测与提交重叠的依据：`overlap_ms` > 0。`overlap_ms` 是至少一个写入进程处在它第一次与最后一次提交之间、同时至少一个探测进程处在它第一次与最后一次探测之间的毫秒数。它只说明各进程首末事件的区间相交：不证明某一次探测与某一次提交的临界区实际重叠，也不证明整个期间所有写入进程都在并发。
  - 对照组没有写入进程，`writer_commits` 为 0，仍然合法。
  - 各进程的起止时间也写进结果行（`writer_spans_ms`、`prober_spans_ms`，相对于变体开始的毫秒）。
- **计数**：
  - 两个测试都记录计划启动的辅助进程数（`planned_helpers`）与实际启动的数（`started_helpers`）。
  - `Open` 路径另外记录：实际调用了 `Open` 的辅助进程数（`open_calls`）、`Open` 成功的数（`opens_succeeded`）与实际提交的事实数（`facts_committed`）。
  - `probes` 是首轮探测的次数，`retries` 是立即重试的次数，`probe_calls` 是两者之和（审查 051 N3）。
- **期限与回收**（审查 051 N2）：
  - 每个辅助进程都有期限（`M14_DEADLINE`），并用它作为自己的 context：只读探测为循环秒数加 60 秒（写入进程的 `Open` 最多等 30 秒打开锁），`Open` 路径为每轮 `M14_ROUND_TIMEOUT` 秒。
  - 期限过后 3 秒仍在运行的辅助进程会被杀掉，属于实验无效。测试等待每个进程结束；进程结束后，等待它的输出最多再给 3 秒（`WaitDelay`）。
  - 结果行把循环秒数（`loop_seconds`）与硬期限（`deadline_seconds`、`round_timeout_seconds`）分开记录。
  - 工作流另有 25 分钟的测试超时与 30 分钟的作业超时。

**开启与上下限**：

- 不设置 `SPECMETRY_M14=1` 时，两个诊断都跳过，所以常规测试与 CI 不运行它们。

| 变量 | 默认 | 范围 | 用于 |
|---|---|---|---|
| `M14_SECONDS` | 20 | 1 ~ 300 | 只读探测每个变体的循环秒数 |
| `M14_WRITERS` | 3 | 1 ~ 16 | 只读探测的写入进程数（对照组固定为 0） |
| `M14_PROBERS` | 3 | 1 ~ 16 | 只读探测的探测进程数 |
| `M14_ROUNDS` | 30 | 1 ~ 1000 | `Open` 路径的轮数 |
| `M14_PROCS` | 3 | 1 ~ 16 | `Open` 路径每轮的辅助进程数 |
| `M14_FACTS` | 100 | 1 ~ 1000 | `Open` 路径每个辅助进程写入的事实数 |
| `M14_ROUND_TIMEOUT` | 120 | 1 ~ 600 | `Open` 路径每轮辅助进程的期限（秒） |
| `M14_SHA` | — | — | 被测提交，写进结果行 |

- `M14_FAULT`、`M14_INJECT` 只给有效性回归使用（故障注入与真实的 SQLite 拒绝），诊断工作流从不设置；设置了它们的运行，结果行会记录它们（`m14_fault`、`m14_inject`）。

**结果行**：每个变体一行 `M14-RESULT {...}`（JSON）。内容包括：

- 平台：`GOOS`、`GOARCH`、Go 版本、SQLite 版本（`sqlite_version()`）、驱动版本、`M14_SHA`，在 GitHub 上还有运行器镜像；
- 上下限与期限；
- 有效性：`valid`、`invalid`、`invalid_count`；
- 实际工作量（见上）；
- 各结果的计数，零也记录；
- 失败的阶段、错误码与分类；
- 出错的时刻（相对于变体开始的毫秒）与立即重试的结果；
- 数据库检查发现的问题。

**有效性回归**（`m14_validity_test.go`，属于常规测试，每个平台的 CI 都运行）：

- 每种情形用小参数在子测试进程中运行一个诊断（几秒，不是工作流的压力规模），检查两件事：判定（`verdict`），以及结果行记录的内容（`records`）。子进程有 3 分钟的期限，并被等待回收。
- 必须判为失败的情形：
  - 写入进程或辅助进程崩溃（退出 42）、打印损坏的结果、不打印结果；
  - 辅助进程在准备阶段失败；
  - 辅助进程挂起：每轮期限 2 秒，必须在 15 秒内以失败结束；
  - 零秒数、零探测进程、零写入进程、零轮数、零辅助进程、零事实，以及超过上限的辅助进程数。
- 必须判为通过的情形：
  - 正常的只读探测（对照组与有提交的变体，记录实际探测、实际提交与 `overlap_ms`）；
  - 正常的 `Open` 路径（记录计划、启动、调用 `Open`、成功打开与提交的数）；
  - 每个辅助进程的 `Open` 都成功、但每次写入都被真实的 SQLite 错误拒绝（触发器，`SQLITE_CONSTRAINT_TRIGGER`，1811）：结果有效，失败按写入阶段与错误码计数。
- 另有三个单元测试：`seq` 的下界缺口（0 与 2）、阶段标签、重叠的计算。
- **修复之前的结果**：先只提交回归与故障注入点（提交 `2347678`），在最初版本的判定上运行（Windows 本机，go1.27.1）：
  - 15 个必须失败的情形全部被判为通过；其中挂起的情形 21 秒后才以通过结束；
  - 3 个必须通过的情形判定通过，但结果行没有记录实际的工作量；
  - `seq` 缺口没有被发现；含糊的版本读取被标为读写连接。
- **修复之后**：全部通过（Windows 本机；以及 `e52d6f5` 的常规 CI 中的三个平台，§5.2）。

## 4. 运行说明

**本机**（macOS、Linux 或 Windows 的 Git Bash，在仓库根目录中执行）：

```bash
SPECMETRY_M14=1 M14_SHA=$(git rev-parse HEAD) M14_SECONDS=60 M14_ROUNDS=200 \
  go test -tags nowebui -count=1 -v -timeout 25m -run '^TestM14' ./internal/store/sqlite | tee m14.log
grep M14-RESULT m14.log
```

Windows PowerShell：

```powershell
$env:SPECMETRY_M14 = "1"; $env:M14_SHA = git rev-parse HEAD; $env:M14_SECONDS = "60"; $env:M14_ROUNDS = "200"
go test -tags nowebui -count=1 -v -timeout 25m -run '^TestM14' ./internal/store/sqlite | Tee-Object m14.log
Select-String M14-RESULT m14.log
```

- 一次运行大约 4 ~ 5 分钟：两个探测变体各 60 秒，加上 200 轮 `Open` 路径。
- 测试只在实验无效或数据库检查发现问题时失败（§3）。出现 264 不会让测试失败，它被计入结果。
- 只运行有效性回归：`go test -tags nowebui -count=1 -run '^TestValidityOfM14' ./internal/store/sqlite`。

**GitHub**：

- 工作流 "M-14 diagnostics" 在两种情况下运行：
  - 推送到 `test/m14-diagnostics` 分支、并且改动了被诊断的代码（`internal/store/sqlite/**`、`internal/datadir/**`、`go.mod`、`go.sum`）或工作流本身。只改文档的推送不触发。
  - 手动触发（`workflow_dispatch`，可以给出秒数与轮数）。GitHub 只对默认分支上已有的工作流提供手动触发，所以本 PR 合并之前只能用推送触发。
- 在同一提交上重跑：`gh run rerun <run-id>`。重跑沿用原来的提交与输入。
- 不要无限重跑；每次运行的结果都按原样记录。

## 5. 实际结果

### 5.1 最初版本的工具（`1d8b73c`）

**这一版有审查 051 B1 的有效性缺陷**：辅助进程崩溃、结果损坏或缺失、零工作量时，测试仍可能通过。所以它的绿色结果**不能证明工具有效**。

下表的具体观测仍然保留：

- 审查方核对了 run 39118832445 的日志：两个平台都实际运行了探测与提交；没有工具崩溃或初始化失败；`Open` 路径的 600 个辅助结果都是 `done` 或写入失败，支持它们确实进入了 `Open`。
- 所以这些观测在其提交、参数与检查范围内可信（审查 051 §五、N3）。它们不是 M-14 根因的证明，也不是一般安全性的证明。
- Windows 本机一行是作者的本地记录，审查方没有重新取得原始日志，不能当作独立复现。

被测提交 `1d8b73c9e637e339f2e1ebac4c81b5bd029480de`。两处都用 `M14_SECONDS=60`、`M14_ROUNDS=200`，其余参数为默认值（3 个写入进程、3 个探测进程、每轮 3 个进程各 100 条）。

| 平台 | 环境 | 只读探测：对照（无提交） | 只读探测：有提交 | `Open` 路径（200 轮，600 个辅助进程） | 数据库检查 |
|---|---|---|---|---|---|
| Windows，本机 | windows/amd64，go1.27.1，SQLite 3.53.4，modernc.org/sqlite v1.60.1 | 24,010 次，全部成功 | 23,609 次：**3 次 264**，在 18,431、27,107、56,110 ms；3 次立即重试都成功。写入进程：39,395 次提交，2 个进程以 `SQLITE_BUSY`（5）停止 | 打开失败 0；写入失败 0 | 无问题 |
| macOS，CI [run 39118832445](https://github.com/XKHoshizora/specmetry/actions/runs/39118832445) | darwin/arm64，go1.27.2，SQLite 3.53.4，modernc.org/sqlite v1.60.1，运行器 macos26 20261013.0424.1 | 689,388 次，全部成功 | 466,837 次：**8 次 264，4 次 1288**（`SQLITE_READONLY_CANTINIT`）；12 次立即重试中 11 次成功、1 次失败。写入进程：288,420 次提交，2 个进程以 `SQLITE_BUSY` 停止 | 打开失败 0；写入失败 0 | 无问题 |
| Windows，CI（同一运行） | windows/amd64，go1.27.2，SQLite 3.53.4，modernc.org/sqlite v1.60.1，运行器 win25-vs2026 20261007.264.1 | 73,932 次，全部成功 | 23,901 次，全部成功。写入进程：15,622 次提交，2 个进程以 `SQLITE_BUSY` 停止 | 打开失败 0；**写入失败 3 次，在 2 轮中**：`database is locked (5) (SQLITE_BUSY)`，分类为 internal | 无问题 |

- 表中的探测次数是首轮探测；macOS 的 466,837 次首轮探测加上 12 次立即重试，是 466,849 次实际的探测调用（审查 051 N3）。
- 没有逐次的时间线，所以不能据总数声称整个 60 秒都维持着所有写入进程的并发；两个平台都有写入进程因 `SQLITE_BUSY` 提前停止。

**结论**：

- **原始失败**（`Open` 中的 264）在三处的 600 次真实打开中都没有复现。
- **辅助探测**：

## 6. 剩余边界与下一步

- M-14 保持未解决：没有确认的根因，也没有修复。原始失败没有在真实的 `Open` 路径中复现。
- M-15（写入阶段的 `SQLITE_BUSY`）同样未解决，与 M-14、M-1 分开，没有证据表明它们同根因。
- 尚未解释：macOS 上的 1288（`SQLITE_READONLY_CANTINIT`），以及 Windows CI 上辅助探测的 264 至今为 0（`1d8b73c`、`dce8b67`、`e52d6f5` 三次运行；Windows 本机在最初版本的工具下出现过）。
- 本工具不批准生产重试、错误映射或 SQLite 插桩。
- 下一步建议（都需要负责人另行授权）：
  1. 在隔离环境中插桩：记录数据目录检查、打开锁、只读连接与事务、读写连接、`BEGIN` / `COMMIT` 的实际阶段与 SQLite 扩展错误码，不只按包装文字归因；

  3. 对 Windows 的 code 5，确认发生在开始事务、语句还是提交；
  4. 如果将来提出有界的重试，单独验证版本保护、拒绝之后的副作用、错误类别与 MVP-STO-02、STO-07；"12 次重试中 11 次成功"不足以批准它。
