### 2.3 名字规则

- **成员的名字**：设 `n = "modernc.org/libc." + h`（h 为 H(F) 的成员）。A 的 ELF 符号表中一个条目的名字等于 `n`，或以 `n` 开头、紧接 `.` 或 `-`，就属于 h（证明准备 §2.4）。分隔符的要求排除 `Xwait` 与 `Xwait3` 之类的字面前缀。
- **已知的派生形式**（链接方法审计 §3.1、§3.2）：`.abi0`、`.func<N>`（可以嵌套为 `.func<N>.<M>`）、`.gowrap<N>`、`.deferwrap<N>`、`-range<N>` 及其组合。名字属于某个成员、但余下部分不符合这一语法 → **T(mapping)**（未知的派生形式），不忽略，也不按出现计。
- **原始条目的身份与多重性**：只读 `STT_FUNC` 条目；每个条目记录名字、`st_value`、`st_size`、绑定与节索引。同名的条目可以有多个（内容寻址的闭包写为 `STB_LOCAL`，可以同名；ABI0 与 ABIInternal 的同名对写为 `F` 与 `F.abi0`），全部记录，不去重，不假设名字与符号一一对应（审计 §6、§7）。
- **汇编包装**：`Y*` 是 ABI0 的汇编块。没有同名的 ABIInternal 符号时，它的 ELF 名字没有 `.abi0`（审计 §3.2）；两种形式都由前缀规则覆盖。
- 名字按字节比较，除上面的规则之外不做其他规范化。

### 2.4 停止使用该证明的条件

执行之前，对每个目标逐项检查；任一命中，该目标的状态改为“证明不足”（未成立），不能得到 absent：

1. **方法**：H(F) 中有方法。方法包装（提升方法、指针接收者包装、`-fm` 方法值）以接收者类型命名，名字关系没有写定（证明准备 §5.1）。
2. **泛型**：H(F) 中有泛型函数，或经过泛型的实例化。实例的名字语法没有审计。
3. **`init`**：任一引用位于 `func init()` 中。编译器把它改名为 `<包>.init.<N>`（`cmd/compile/internal/noder/noder.go:450` ~ `460`）；`init` 不能被引用，所以不必向外扩展，但它自己可以内联 F（Review 133 §4.2）。证明准备 §3.1 的“`init` 不加入”只是不向外扩展的理由，不能当作排除宿主的通用规则。在 init 宿主的名字规则另经审查之前，命中即停止。
4. **包级声明**：任一引用位于包级的变量或常量声明中（会进入包的初始化函数或静态初始化生成的闭包）。同名的**类型**声明（例如 darwin 子包中的 `X__sigaction` 类型）须逐处确认不是对函数的引用、且不在 K 中，否则停止。
5. **内容合并**：任一引用位于函数字面量之中，或承载 F 的函数体的代码可能是内容寻址的符号（固定编译器把闭包的文本符号标为内容寻址，`ir/func.go:539` ~ `542`）。合并之后只显示代表对象的名字，不能证明目标的来源已被排除（L6，Review 133 N-133-2）。
6. **词法的歧义**：以 `//` 判注释、以行首定位顶层声明，不是 Go 词法分析的一般替代：字符串中的 `//` 不一定是注释，原始字符串中行首的 `func` 不一定是声明（Review 133 §4.2）。执行之前，以 Go 的词法（`go/scanner` 或同等的、经审查的分词器）对两个模块的全部非测试文件重算引用，与 §2.2 逐项比较；多出或缺少任何一处，该目标停止，直到重新审查。这一步要运行 Go 程序，须在执行授权之内进行。
7. **引用的其他来源**：重新核对 L5 的前提（固定提交上没有指向 `modernc.org/libc` 的 `//go:linkname`，其他模块的汇编不引用 libc 的符号，导入 libc 的只有 sqlite 与 libc 自身）。任一不成立，涉及的目标停止。
8. **平台**：丙组依赖 K 的文件与包选择（R4）；R4 不成立时，丙组的宿主集合回到全集，实际上不能得到 absent，按停止处理。

目前的静态结果（词法的限制见第 6 条）：

- 第 1 ~ 4 条：本轮复核证明准备的检索数据，前 20 个目标在各自范围内的命中，所在的声明只有普通函数与汇编块；没有方法、泛型、`init` 或包级的变量与常量；唯一的同名类型声明是 darwin 子包中的 `X__sigaction`，不在 K 中。
- 第 5 条：§2.2 的每处引用都逐行重读，是顶层函数体中的直接调用；宿主中的函数字面量只有两种清理用的闭包（证明准备附录 A）。
- 第 7 条：证明准备 §2.5 的检索，本轮没有重做。
- 第 8 条只涉及 #8、#19、#20。
- `Xsignal` 命中第 1 条（方法），且宿主中有通用入口。

## 3. 唯一的分类与总结论

### 3.1 整体（先判；按顺序，先命中者为准）

| # | 类别 | 条件 |
|---|---|---|
| 1 | **T(tool)** | 任一工具非零退出、被终止或超过截止；输出缺失；写入、读取或关闭出错；预算不足而没有开始；清理未知（链接验证计划 §8.3、§8.4，不变） |
| 2 | **T(identity)** | 工具链、模块或产物的身份核对不符（§4 的 R2、R3、R6）；`GOCACHE` 开始时不为空；`-x` 中没有 A 的链接命令，或出现重放的 `cat … # internal`（M-5 的规则） |
| 3 | **T(premise)** | R1、R4、R5 的前提不成立或缺少实际证据 |
| 4 | **T(read)** | ELF 的读取或自检失败（§4 的 R5） |
| 5 | **T(mapping)** | 未知的派生形式（§2.3）；H(F) 的某个成员在编入的归档中找不到（§6.2） |
| 6 | **T(control)** | 任一对照与预期不同，或应当命中而未命中（§5） |

- T 优先于全部按目标的类别。工具或前提的失效（T）与证明不足（§3.2）分开记录：前者是这次运行不可信，后者是方法对这个目标本来就给不出 absent。

|---|---|---|---|
| 1 | **present** | A 的符号表中有 F 自己的名字或派生名字（§2.3） | F 的代码在 A 中（本方法、配置 K） |
| 2 | **证明不足** | 目标在执行之前被标为证明不足（`Xsignal`，或命中 §2.4） | 没有 absent 的论证；不是 absent，也不是 present |
| 3 | **未得到 absent** | F 自己的名字与派生名字都不在，但 H(F) 中其他成员的名字在 | F 的代码可能以内联的形式在宿主中，也可能不在；方法不能区分。不是 absent，也不是 present |
| 4 | **absent** | H(F) 中所有成员的名字与派生名字都不在 | “F 的代码不在产物 A 中（本方法、配置 K）”；强命题，没有收窄 |

- 宿主的出现不能反推 present：宿主的代码可以不含 F 的任何残留。present 只来自 F 自己的表示。
- `Y*` 包装的出现而 F 自己的名字不在，按第 3 类处理。
- absent 只由第 4 类得出。“搜不到名字”本身不是 absent：它须以整体没有 T、R1 ~ R6 都有实际证据、目标没有命中 §2.4 为前提。

### 3.3 总结论（替代链接验证计划 §1 的三种）

| # | 总结论 | 条件 | 对原 (a) |
|---|---|---|---|
| 1 | **不可判定** | 任一 T | 未兑现 |
| 2 | **有目标 present** | 没有 T；至少一个目标 present | 对该目标不成立 |
| 3 | **未全部 absent** | 没有 T；没有 present；至少一个目标为“证明不足”或“未得到 absent” | 未兑现 |
| 4 | **目标都 absent** | 没有 T；全部目标 absent | 对固定的清单、配置 K 与产物 A 成立 |

- 只有第 4 种兑现原 (a) 的“目标代码不在产物中”。第 3 种**不能**算作兑现，也不能写成“基本 absent”。
- 以当前的清单，`Xsignal` 证明不足，第 4 种不可能出现。
- 报告可以按组列出事实（例如“17 个启动与回收目标中 k 个 absent”），但这只是陈述，不改变总结论，也不是范围的改变。

### 6.2 归档见证的规则（保留项须补齐的部分）

- **定位**：每个必需的包（libc、sqlite 及其子包、对照程序的包）由 `-x` 中的 `-p <导入路径>`、`-o $WORK/b<NNN>/_pkg_.a` 与之后的 `cp $WORK/b<NNN>/_pkg_.a <GOCACHE>/<xx>/<hex>-d # internal` 三者关联（审计 §5.3）。缺少 `cp` 行 → T(identity)。
- **身份**：对缓存文件重算 SHA-256，须等于文件名中的十六进制串；记录路径与哈希。这支持关联与追溯，不认证来源。
- **缓存**：`GOCACHE` 在构建之前新建且为空（链接验证计划 §2）；读取的是这份缓存中的文件，不读 `$WORK`（命令返回之后可能已删除）。
- **读取**：以已核对的 Go 可执行文件运行 `go tool nm <归档>`，作为驱动程序的一个受控步骤（计划 §8.3 已列出这类调用）。输出的每一行按“地址、类型、名字”解析；不能解析的行 → T(read)。
- **多重性**：同一个名字可以出现多次（不同的目标文件、内容寻址的闭包），全部记录，不去重。
- **要求**：H(F) 的每个 Go 成员在其包的归档中至少有一个文本类型（`T` 或 `t`）的条目；每个 `Y*` 在同一归档的汇编目标中有条目。缺少 → T(mapping)。这同时是 R4 的实际证据之一。
- **不能证明的**：归档中有名字只说明它被编译，不说明它在 A 中；归档的见证不代替 A 的符号表。

### 6.3 已关闭的协议

驱动程序的拓扑与身份、前置条件、步骤的状态与责任、pidfd 的状态机、各活动的截止与守卫、报告的规则、文件与描述符的责任（计划 §8.3），以及单一的时间线（§8.4），都直接引用，不重新设计。删除构建 B 只是少一个步骤，不改变这些协议；时间线的数值与资源维持“未获授权”。

### 7.2 推荐（不是批准）

1. **不推荐 A**：当前没有技术基础；按 §3.3，以当前清单不能兑现。
2. **推荐 C（(b) 精确例外）**，条件是：清单精确到对象与平台、钉定版本与哈希、写清升级失效的条件、登记为新的 L、同步规范与验收，并由负责人明确批准这一风险。理由：
   - B 的额外保证很窄：只有一个配置、一个产物、具名的函数，而且不解决 F-5；代价却很高：驱动程序、场所、CI 资源、多轮方法审查，每次升级还要重做。
   - 冻结的第三方扫描对任何依赖都不覆盖原始入口与汇编（U-4）。C 把 ① 类写成明确的例外，没有把未覆盖的部分说成已经覆盖。
   - 已有的运行时检查在排他区间开始时对意外的子进程失败关闭，并在区间中清扫；这是缓解，不是证明。
   - 这改变了实施计划 §12.11 中“(b) 本设计不推荐”的推荐。那是在证明准备与 Review 133 的发现之前作出的：`Xsignal` 没有 absent 的论证，T0 不完整，通用入口使有限的 absent 不能代表能力。
3. 负责人若仍希望有产物证据，B 可以作为 C 之后的、可选的加强，而不是 C 的前提。
4. D、E 现在不推荐（范围与维护的代价），保留为 C 的风险不可接受时的后备。

本文不执行任何方案，不替负责人批准风险，也不改变冻结的规则。

### 7.3 有限 T0 的 absent 不解决 F-5

- 通用入口 `X__syscall0` ~ `X__syscall6`、`___syscall_cp` 与 `Xsyscall` 以参数接收系统调用号（`syscall_musl.go:14` ~ `170`）。有限 T0 的 absent 不排除别处把 `execve`、`fork`、`wait4`、`waitid`、`kill`、`rt_sigaction` 的调用号交给它们。
- T0 之外的直接位置（证明准备 §6.2）：`Xabort`（`___libc_sigaction`、`unix.Tgkill`、`unix.Kill`、`resetSigDfl`）、`resetSigDfl`（原始的 `rt_sigaction` 与 `rt_sigprocmask`）、`(*TLS).raiseSignal` 与 `(*TLS).killSignal`（`unix.Kill`）。按 Review 133 §6，须按操作的类型（改变处置、发送信号、运行模拟的处理函数、通用入口）、信号值与调用位置分别评价，不能一律等同于破坏 C-10，也不能因为只向自身发送 `SIGABRT` 就说它与 C-9 和例外的范围无关。
- 经函数指针表、`unsafe`、反射或字符串构造的到达方式，文本检索看不到。
- 所以：17 个启动与回收目标即使全部 absent，也**不能**推出启动与回收能力在产物中整体不可达，也不能推出依赖例外可以批准。
