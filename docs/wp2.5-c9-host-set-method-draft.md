## 2. 目标、证明方式与宿主集合

### 2.1 统一的目标描述（生产目标与对照共用）

每个目标或对照对象由一条描述 D 给出，执行之前写定，不从被测的 `nm` 或 ELF 输出反算：

| 字段 | 含义 |
|---|---|
| 包 P | 完整的导入路径；`package main` 记为 `main` |
| 名字 S | 顶层函数为函数名；方法为 `(*Recv).M`（指针接收者）或 `Recv.M`（值接收者） |
| 种类 | 函数或方法。方法只作正面检查，不定义 H，不能得到 absent |
| 证明状态 | 不可内联与宿主集合、宿主集合、证明不足；对照对象为“由构造固定” |
| 检索集合 H_search | 名字的描述列表（同样是 D）；只对函数定义 |
| 预期 | 生产目标没有预期；对照对象写明预期的类别与命中谓词（§5） |

- **链接名的基名**：`base(D) = PathToPrefix(P) + "." + S`；P 为 `main` 时为 `"main." + S`。`PathToPrefix` 只转义最后一个 `/` 之后的 `.`、控制字符、空格、`%`、`"` 与非 ASCII（`cmd/internal/objabi/path.go:18` 起）；本文用到的包路径（`modernc.org/libc`、`modernc.org/sqlite`、`specmetry.test/c9ctl/hc`）都不需要转义，基名就是路径加 `.`。
- 编译器与汇编器用同一个前缀：汇编的 `·name` 先被替换为 `.name`（`cmd/asm/internal/lex/lex.go:109`），再加上包的前缀（`cmd/asm/internal/asm/parse.go:880` ~ `888`）。所以 `TEXT ·Yexecve(SB)` 的名字是 `modernc.org/libc.Yexecve`。
- 归档层与 ELF 层的名字规则不同，分开写在 §2.5，不做混合的全局规范化。

### 2.5 名字规则：ELF 层与归档层分开

**ELF 层**（A 的 `.symtab`，判定 present / absent 用）：

- 名字属于描述 D，当且仅当它等于 `base(D)`，或以 `base(D)` 开头、紧接 `.` 或 `-`，且余下部分符合已知的派生语法。分隔符的要求排除 `Xwait` 与 `Xwait3` 之类的字面前缀。
- **已知的派生语法**（链接方法审计 §3.1、§3.2）：`.abi0`、`.func<N>`（可以嵌套为 `.func<N>.<M>`）、`.gowrap<N>`、`.deferwrap<N>`、`-range<N>` 及其组合。以 `base(D)` 加 `.` 或 `-` 开头、但余下部分不符合这一语法 → **T(mapping)**（`M.unknown`），不忽略，也不按出现计。
- 只读 `STT_FUNC` 条目；每个条目记录索引、原始的名字偏移、名字、`st_value`、`st_size`、绑定与节索引。同名的条目可以有多个（内容寻址的闭包写为 `STB_LOCAL`；ABI0 与 ABIInternal 的同名对写为 `S` 与 `S.abi0`），全部记录，不去重，不假设名字与符号一一对应（审计 §6、§7）。
- `Y*` 是 ABI0 的汇编块。没有同名的 ABIInternal 符号时，它的 ELF 名字没有 `.abi0`（审计 §3.2）；两种形式都由上面的规则覆盖。

**归档层**（`go tool nm` 的输出，作编译见证用；语法见 §6.2）：

- 名字是对象文件中的名字：**没有** `.abi0`。同名的 ABI0 与 ABIInternal 定义各输出一行 `T`，名字相同（`cmd/internal/objfile/goobj.go:154` ~ `186`，版本只区分静态）。
- 静态符号的名字加 `<1>` 后缀，类型字母为小写（`goobj.go:77` ~ `82`、`177` ~ `179`）。
- 见证只认名字与 `base(D)` **逐字节相等**的 `T` 行；不去掉 `<1>`，不加 `.abi0`，不按 ELF 层的派生语法匹配。

名字都按字节比较，除上面的规则之外不做其他规范化。

### 2.6 停止使用该证明的条件

执行之前，对每个目标逐项检查；任一命中，该目标的状态改为“证明不足”（未成立），不能得到 absent：

1. **方法**：H_search 中有方法。方法包装（提升方法、指针接收者包装、`-fm` 方法值）以接收者类型命名，名字关系没有写定（证明准备 §5.1）。
2. **泛型**：H_search 中有泛型函数，或经过泛型的实例化。实例的名字语法没有审计。
3. **`init`**：任一引用位于 `func init()` 中。编译器把它改名为 `<包>.init.<N>`（`cmd/compile/internal/noder/noder.go:450` ~ `460`）；`init` 不能被引用，所以不必向外扩展，但它自己可以内联 F（Review 133 §4.2）。证明准备 §3.1 的“`init` 不加入”只是不向外扩展的理由，不能当作排除宿主的通用规则。在 init 宿主的名字规则另经审查之前，命中即停止。
4. **包级声明**：任一引用位于包级的变量或常量声明中（会进入包的初始化函数或静态初始化生成的闭包）。同名的**类型**声明（例如 darwin 子包中的 `X__sigaction` 类型）须逐处确认不是对函数的引用、且不在 K 中，否则停止。
5. **内容合并**：任一引用位于函数字面量之中，或承载 F 的函数体的代码可能是内容寻址的符号（固定编译器把闭包的文本符号标为内容寻址，`ir/func.go:539` ~ `542`）。合并之后只显示代表对象的名字，不能证明目标的来源已被排除（L6，Review 133 N-133-2）。
6. **词法的歧义**：以 `//` 判注释、以行首定位顶层声明，不是 Go 词法分析的一般替代：字符串中的 `//` 不一定是注释，原始字符串中行首的 `func` 不一定是声明（Review 133 §4.2）。执行之前，以 Go 的词法（`go/scanner` 或同等的、经审查的分词器）对两个模块的全部非测试文件重算引用，与 §2.4 逐项比较；多出或缺少任何一处，该目标停止，直到重新审查。这一步要运行 Go 程序，须在执行授权之内进行。
7. **引用的其他来源**：重新核对 L5 的前提（固定提交上没有指向 `modernc.org/libc` 的 `//go:linkname`，其他模块的汇编不引用 libc 的符号，导入 libc 的只有 sqlite 与 libc 自身）。任一不成立，涉及的目标停止。
8. **平台**：丙组依赖 K 的文件与包选择（R4）；R4 不成立时，丙组的宿主集合回到全集，实际上不能得到 absent，按停止处理。

## 3. 唯一的分类与总结论

### 3.1 T 的来源域与唯一的主分类

每一项检查有一个编号，并且**只属于一个域**。域按下表的优先级排列：

| 优先级 | 类别 | 来源域 | 检查（编号前缀） |
|---|---|---|---|
| 1 | **T(tool)** | 工具的执行与采集的 I/O | `X.*`：工具的启动、退出状态（非零或被信号结束）、截止、预算不足而没有开始、清理未知（链接验证计划 §8.3、§8.4，不变）；采集文件的写入、关闭与读回（读到的字节数等于文件大小）；把 A 与归档的字节**完整读入内存**时的 I/O 错误 |
| 2 | **T(identity)** | 身份与关联 | `I.*`：工具链（R2）、模块（R3）、产物关联（R6 的 ①、②）、归档的定位与哈希（§6.2） |
| 3 | **T(premise)** | 事实前提 | `P.*`：R1（构建形态与 PGO）、R4（文件与包的选择、排除证据）、R5a（产物的形态） |
| 4 | **T(read)** | 读取与结构自检 | `D.*`：从内存中的字节解析 ELF 与 R5b 的自检；`nm` 输出的语法（§6.2） |
| 5 | **T(mapping)** | 映射 | `M.*`：未知的派生形式（`M.unknown`）、缺少归档见证（`M.witness`）、排除的成员出现（`M.excluded`） |
| 6 | **T(control)** | 对照 | `C.*`：任一对照与预期不同、应当命中而未命中，或对照无效（§5） |

- **字节读取与格式分开**：A 与每个归档先由驱动程序完整读入内存（I/O 错误属 `X.*`），之后的解析（`debug/elf.NewFile` 以内存中的字节为输入）、结构自检与 `nm` 输出的语法都属 `D.*`。所以格式错误不会被 T(tool) 吞掉。
- **依赖与“未评估”**：一项检查若依赖的上游检查失败，它记为“未评估”，不记为失败。依赖关系固定为：工具与采集 → 身份 → 解析（`D.R5b.parse`）→ R5a 的形态检查 → R5b 的其余自检 → 映射与分类；R1、R4 只依赖它们所读的记录已完整采集。例如 ELF 的头部不能解析时，`D.R5b.parse` 失败，R5a“未评估”，主分类为 T(read)，不是 T(premise)。
- **主分类**：失败（不含“未评估”）的检查中，优先级最高的域给出唯一的主分类。
- **全部原因都保存**：每项失败与“未评估”的检查、它的原始错误文本与相关字节位置都写入记录，不因主分类而丢弃。
- T 优先于全部按目标的类别。工具或前提的失效（T）与证明不足（§3.2）分开记录：前者是这次运行不可信，后者是方法对这个目标本来就给不出 absent。证明不足不会变成 T，也不能把 T 改记为证明不足来豁免工具错误。

### 3.2 每个目标（整体没有 T 时；按顺序）

| # | 类别 | 条件 | 含义 |
|---|---|---|---|
| 1 | **present** | A 的符号表中有属于 F 自己的描述的名字（§2.5 的 ELF 层） | F 的代码在 A 中（本方法、配置 K） |
| 2 | **证明不足** | 目标在执行之前被标为证明不足（`Xsignal`，或命中 §2.6） | 没有 absent 的论证；不是 absent，也不是 present |
| 3 | **未得到 absent** | F 自己的名字与派生名字都不在，但 H_search 中其他成员的名字在 | F 的代码可能以内联的形式在宿主中，也可能不在；方法不能区分。不是 absent，也不是 present |
| 4 | **absent** | H_search 的所有成员的名字与派生名字都不在 | “F 的代码不在产物 A 中（本方法、配置 K）”；强命题，没有收窄 |

- 宿主的出现不能反推 present：宿主的代码可以不含 F 的任何残留。present 只来自 F 自己的表示。
- `Y*` 包装出现而 F 自己的名字不在，按第 3 类处理。
- absent 只由第 4 类得出。“搜不到名字”本身不是 absent：它须以整体没有 T、R1 ~ R6 都有实际证据、目标没有命中 §2.6 为前提。

### 3.3 总结论（替代链接验证计划 §1 的三种）

| # | 总结论 | 条件 | 对原 (a) |
|---|---|---|---|
| 1 | **不可判定** | 任一 T | 未兑现 |
| 2 | **有目标 present** | 没有 T；至少一个目标 present | 对该目标不成立 |
| 3 | **未全部 absent** | 没有 T；没有 present；至少一个目标为“证明不足”或“未得到 absent” | 未兑现 |
| 4 | **目标都 absent** | 没有 T；21 个目标全部 absent | 对固定的清单、配置 K 与产物 A 成立 |

- 只有第 4 种兑现原 (a) 的“目标代码不在产物中”。第 3 种**不能**算作兑现，也不能写成“基本 absent”。
- 以当前的清单，`Xsignal` 证明不足，第 4 种不可能出现。
- 报告可以按组列出事实（例如“17 个启动与回收目标中 k 个 absent”），但这只是陈述，不改变总结论，也不是范围的改变。

### 6.2 归档见证：`go tool nm` 的受限语法

依据固定的 Go 1.27.3：`cmd/nm/nm.go:69` ~ `171`、`cmd/internal/objfile/goobj.go:29` ~ `222`、`cmd/internal/archive/archive.go:289` ~ `405`、`cmd/go/internal/work/gc.go:461` ~ `536`、`cmd/compile/internal/gc/obj.go:53` ~ `79`。

**定位与身份**：

- 每个必需的包（libc、sqlite 及其子包、主包、`hc`）由 `-x` 中的 `-p <导入路径>`、`-o $WORK/b<NNN>/_pkg_.a` 与之后的 `cp $WORK/b<NNN>/_pkg_.a <GOCACHE>/<xx>/<hex>-d # internal` 三者关联（审计 §5.3）。缺少 `cp` 行 → T(identity)（`I.archive`）。
- 对缓存文件重算 SHA-256，须等于文件名中的十六进制串；记录路径与哈希。这支持关联与追溯，不认证来源。`GOCACHE` 在构建之前新建且为空；读取的是这份缓存中的文件，不读 `$WORK`。
- 归档的字节先由驱动程序完整读入并记录哈希（I/O 属 `X.*`）；`nm` 读取的是同一路径。

**命令**：以已核对的 Go 可执行文件运行 `[<go>, "tool", "nm", <归档的绝对路径>]`，不带任何选项，作为驱动程序的一个受控步骤（计划 §8.3 已列出这类调用）。所以：按名字排序（`-sort name`，`nm.go:38`），不打印大小与 Go 类型（`-size`、`-type` 关闭），只有一个文件参数（`filePrefix` 为假，`nm.go:86`）。

**预期的成员**（由固定源码推演，执行时与 `-x` 的 `pack` 命令核对）：

- 编译器写出的归档只有 `__.PKGDEF` 与 `_go_.o` 两个成员（`gc/obj.go:63` ~ `72`）；`objfile` 跳过 `__.PKGDEF`（`goobj.go:38` ~ `39`）。
- 包有汇编文件时，cmd/go 以 `go tool pack r <归档> <对象…> # internal` 把汇编对象追加进同一个归档（`work/gc.go:461` ~ `486`），成员名是对象文件名的前 16 个字节（`gc.go:511` ~ `516`），解析时去掉右侧的空格（`archive.go:285`、`319`）。
- 所以预期的成员集合 = {`_go_.o`} ∪ {对 `pack` 命令中每个对象的文件名取前 16 个字节、去掉右侧空格}。在 K 上：libc 为 `_go_.o`、`abi0_linux_amd64`（由 18 个字节的 `abi0_linux_amd64.o` 截断）、`tls_linux_amd64.`（由 17 个字节的 `tls_linux_amd64.o` 截断）；`hc` 为 `_go_.o`、`hc_amd64.o`；sqlite 及其子包、主包只有 `_go_.o`。
- 两个对象截断之后同名 → 成员的身份不唯一，T(read)（`D.nm.member`）。

**行的语法**（`nm.go:139` ~ `162`）：

- 归档有多于一个成员时（`len(entries) > 1`），每行以 `<归档路径>(<成员>):\t` 开头；只有一个成员时没有这个前缀。前缀的有无由预期的成员数决定，与之不符 → `D.nm.line`。
- 之后是 8 个字节的地址栏：类型为 `U` 时是 8 个空格（`nm.go:150` ~ `151`）；否则是 `%8x`，即右对齐的小写十六进制、左侧补空格，恰好 8 个字节（地址是 `uint32` 的数据偏移，`goobj.go:183`）。
- 之后是一个空格、类型字母、一个空格、名字，再是换行。类型字母只能是 `T`、`R`、`D`、`B`、`?`（`goobj.go:165` ~ `176`），静态符号为小写（`t`、`r`、`d`、`b`、`_`，`goobj.go:177` ~ `179`），或 `U`（引用，`goobj.go:208` ~ `219`）。
- 名字是该行余下的全部字节（可以含空格，例如类型描述符的名字），非空；静态符号的名字带 `<1>`。
- 受限的正则形式（`A` 为归档路径的字面值，`M` 为预期成员之一）：多成员 `^A\((M)\):\t(ADDR) ([TRDB?trdb_U]) (.+)$`；单成员 `^(ADDR) ([TRDB?trdb_U]) (.+)$`；其中 `ADDR` 在类型为 `U` 时必须是 8 个空格，否则必须匹配 ` *[0-9a-f]+` 且长度恰好为 8。

**保存的字段**：归档路径与 SHA-256；`nm` 的参数、退出状态、标准错误的全部字节；标准输出文件的大小与 SHA-256；每行的行号、原始字节、成员、地址栏的原文、类型字母与名字；每个（成员，类型，名字）的出现次数。

**见证的谓词**：H_K 的成员（或对照、正对照的描述）d 有归档见证，当且仅当在 d 所在包的归档中，存在一行：成员等于预期的成员（Go 函数为 `_go_.o`，`Y*` 为 `abi0_linux_amd64`，`hc.W` 为 `hc_amd64.o`；单成员的归档为唯一的成员），类型字母为 `T`，名字与 `base(d)` 逐字节相等。`U` 行、`R` / `D` / `B` / `?` 行、小写的静态行与其他成员中的行都**不能**作为见证。

**退出状态与采集**：

- 退出状态独立消费：非零（`nm` 对任一成员的读取错误都会置 1 并继续输出其他成员，`nm.go:119` ~ `123`；没有任何符号也置 1，`166` ~ `168`）→ T(tool)（`X.exit`），即使标准输出非空、甚至含有所需的行。标准错误非空 → 同样 T(tool)（`nm.go` 以 `log.Printf` 报告错误）。
- `nm` 不检查 `File.Close` 与缓冲区 `Flush` 的结果（`nm.go:111`、`170`），退出状态为 0 **不证明**它的全部 I/O 成功。所以外层仍按已关闭的协议核对：采集文件的写入、关闭与读回（读到的字节数等于文件大小）；标准输出以换行结尾（最后一行不完整 → `D.nm.trunc`）；每行都符合语法；全部必需的见证都在。
- 能够发现的：中途截断造成的不完整行，以及缺少的必需见证。不能发现的：恰好在行边界截断而丢掉的、与见证无关的行；它们不能制造见证，只会使需要的见证缺失（T(mapping)）。

**正常与异常行的模型与独立预期**（文档推演，不运行 `nm`；`A` 为归档路径，`⟶` 为制表符）：

### 7.2 推荐（不是批准）

1. **不推荐 A**：以当前方法与清单没有兑现的条件。这不证明原 (a) 在技术上永远不可能，也不把“没有证明 `Xsignal` absent”当作它 present 的反证。
2. **推荐 C（(b) 精确例外）**，附第 3 项的条件与负责人对风险的明确批准。这是对维护成本与证据收益的工程判断，**不是已测量的工时或资源结论，也不是由当前证据推出的技术必选项**。理由：
   - B 的额外保证很窄：只有一个配置、一个产物、具名的函数，而且不解决 F-5；代价却高：驱动程序、场所、CI 资源、多轮方法审查，每次升级还要重做。
   - 冻结的第三方扫描对任何依赖都不覆盖原始入口与汇编（U-4）。C 把 ① 类写成明确的例外，没有把未覆盖的部分说成已经覆盖。
   - 这改变了实施计划 §12.11 中“(b) 本设计不推荐”的推荐。那是在证明准备与 Review 133 的发现之前作出的：`Xsignal` 没有 absent 的论证，T0 不完整，通用入口使有限的 absent 不能代表能力。§12.11 的表与冻结的规则没有修改。
3. **选择 C 之前须写定的决定内容**（Review 134 §6.2）：
   1. **精确清单**：模块的版本与内容身份、包、调用方的函数、被引用的对象或方法、平台 / 架构 / 构建条件、允许的用途。举例不是清单；不能以整个 libc 包作为任意能力的豁免。
   2. **失效与陈旧项**：升级、源码或哈希的漂移、`replace` / vendor / 来源或相关工具链的变化如何重新审核；例外未命中、出现额外的对象或扫描不完整，都失败关闭。版本与哈希的限定不能省略平台与调用位置。
   3. **未覆盖的原始入口**：② 类只表示已登记的未覆盖，不表示负责人已经接受风险或原始入口不在实际产物中；Q / X / E / U 仍待决，不自动归入 L。
   4. **运行时前提的信任边界**：例外允许源码中保有能力，与允许它在检查期间并发启动、回收或改变信号处置，是不同的风险范围；须说明对协议前提的信任边界，不能以“已有缓解”一句代替（见第 4 项）。
   5. **硬规则保留**：已观察到的错误、归属未知、清理未确认、提交不确定与宿主禁用，仍按现冻结规则处理。例外不能解释为这些状态可以 PASS、可以向未知 PID 动作或可以宣称已清理。
4. **运行时检查的作用与局限**（N-134-2；冻结规范 §19.4、C-10，链接验证计划 §8.3 只是类比，不是生产协议）：
   - **子进程基线**：在取得排他租约之后、启动检查之前，对本进程的子进程做一次完整扫描（§19.4 第 2、3 步）；非空或未知时不启动。它是一个时点的检查，不能证明扫描之后没有依赖并发的启动或回收，也不能阻止其发生。
   - **subreaper**：只在排他区间中设置（§19.4 第 5 步），改变孤儿的领养关系，配合协议规定阶段的清扫。它不阻止进程的创建，不自动证明归属，不保护本次子进程的状态不被其他回收者先取走，也不代替确认的收尾。
   - **C-10**：在取得排他租约时检查当时的 `SIGCHLD` 处置（是否被忽略）；不是区间之内永不改变的保证。
   - **条件性风险**：基线与 C-10 都通过之后，依赖若经保留的能力改变 `SIGCHLD` 的处置，或在闸门之外回收本次的子进程，会破坏“唯一的回收者、未回收的身份”这一前提。固定的 libc 的 `Xsignal` 确实可以按参数调用 `signal.Ignore`、`Reset`、`Notify`；这说明能力存在，**不是**证明 SQLite 会走到这个分支。一次检查通过，不能排除随后在闸门之外的启动、回收或信号处置的变化。这是能力与信任边界的问题。
5. 负责人若仍希望有产物证据，B 可以作为 C 之后的、可选的加强，而不是 C 的前提。
6. D、E 现在不推荐（范围与维护的代价），保留为 C 的风险不可接受时的后备。

本文不执行任何方案，不替负责人批准风险，也不改变冻结的规则。

### 7.3 有限 T0 的 absent 不解决 F-5

- 通用入口 `X__syscall0` ~ `X__syscall6`、`___syscall_cp` 与 `Xsyscall` 以参数接收系统调用号（`syscall_musl.go:14` ~ `170`）。有限 T0 的 absent 不排除别处把 `execve`、`fork`、`wait4`、`waitid`、`kill`、`rt_sigaction` 的调用号交给它们。
- T0 之外的直接位置（证明准备 §6.2）：`Xabort`（`___libc_sigaction`、`unix.Tgkill`、`unix.Kill`、`resetSigDfl`）、`resetSigDfl`（原始的 `rt_sigaction` 与 `rt_sigprocmask`）、`(*TLS).raiseSignal` 与 `(*TLS).killSignal`（`unix.Kill`）。按 Review 133 §6，须按操作的类型（改变处置、发送信号、运行模拟的处理函数、通用入口）、信号值与调用位置分别评价，不能一律等同于破坏 C-10，也不能因为只向自身发送 `SIGABRT` 就说它与 C-9 和例外的范围无关。
- 经函数指针表、`unsafe`、反射或字符串构造的到达方式，文本检索看不到。
- 所以：17 个启动与回收目标即使全部 absent，也**不能**推出启动与回收能力在产物中整体不可达，也不能推出依赖例外可以批准。
